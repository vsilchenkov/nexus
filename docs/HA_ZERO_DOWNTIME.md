# Развёртывание без простоя: две реплики Receiver / Web / Sender

Аналитическая записка. Отвечает на три вопроса: **сколько это стоит в железе, в эксплуатации
и в доработках**. Рамки, заданные до написания: дублируются все три сервиса приложения, сервер
один, балансировщик — nginx-контейнер внутри стека плюс скрипт последовательного выката.

Записка ничего не меняет в коде. Реализация — отдельным решением, план блоков в §7.

---

## 1. Почему вообще этот разговор

ТЗ [§9.1](../specs/sections/09-resilience.md) уже обещает:

> **Целевой даунтайм** при штатном обновлении — 0 (rolling deploy, graceful shutdown).
> **Горизонтальное масштабирование** — оба сервиса stateless по отношению к запросу, можно
> запускать N инстансов за load balancer.

В развёртывании этого нет. Каждый сервис — ровно один контейнер, обновление идёт
`docker compose up -d --build`, то есть через пересоздание контейнера: процесс останавливается,
поднимается новый. На время остановки и старта запросы не обслуживаются — единицы-десятки секунд
на сервис, и столько же ещё до подтверждения `healthcheck`. Падение процесса даёт тот же простой,
только незапланированный и без оператора рядом.

Обещание §9.1 сегодня не выполнено. Эта записка — про то, чтобы либо закрыть его, либо осознанно
переписать.

## 2. Что именно является единой точкой отказа

Деталь, которая меняет постановку задачи: **Web — не только панель**. Он реверс-прокси боевого
трафика ([receiver_proxy.go](../internal/web/adapter/in/http/receiver_proxy.go)): всё, что приходит
на `/api/v1/*`, уходит в Receiver. В боевом профиле
([docker-compose.standalone.override.yml](../deploy/docker-compose.standalone.override.yml))
наружу опубликован только Web, Receiver слушает loopback.

Путь одного синхронного запроса:

```
клиент → nginx на хосте (TLS) → web:8000 → receiver:8080 → sender:9190 (gRPC) → внешний узел
                                    ▲            ▲              ▲
                                    └─── три единые точки отказа подряд ───┘
```

Асинхронный путь начинается так же: `web → receiver → Kafka`, дальше `sender`-consumer забирает
из топика.

Отсюда вывод: **дублировать только Receiver и Web недостаточно**. Пока Sender один, его обновление
рвёт синхронный трафик целиком — Receiver получит `Unavailable` по gRPC и вернёт клиенту 503.
Поэтому реплицируются все три.

## 3. Целевая схема

```
                          :443 TLS (nginx на хосте — как сейчас)
                                        │
                            ┌───────────▼────────────┐
                            │  nginx (контейнер)     │   новый сервис в стеке
                            │  /api/v1/*  → receiver │   ← боевой трафик МИМО Web
                            │  всё прочее → web      │   ← панель и REST админки
                            └──┬──────────────────┬──┘
                  upstream web │                  │ upstream receiver
                    (2 сервера,│                  │ (2 сервера, max_fails)
                     /health)  │                  │
              ┌───────────┬────▼─────┐      ┌─────▼─────┬───────────┐
              │  web-1    │  web-2   │      │receiver-1 │receiver-2 │
              └─────┬─────┴────┬─────┘      └─────┬─────┴─────┬─────┘
                    │ replay,  │                  │ gRPC dns:///sender:9190
                    │ dry-run  │                  │ + round_robin + health
                    └──────────┴──────────┐  ┌────▼──────┬────────────┐
                                          │  │ sender-1  │  sender-2  │
                                          │  └─────┬─────┴──────┬─────┘
                                          │        │ Kafka consumer group
                                          │        │ (8 партиций делятся)
        ┌─────────────────────────────────▼────────▼──────────────────────┐
        │  PostgreSQL · Redis · Kafka · ClickHouse — ПО ОДНОМУ ЭКЗЕМПЛЯРУ  │
        │  (их обновление или падение по-прежнему = простой)               │
        └──────────────────────────────────────────────────────────────────┘
```

Ключевое решение схемы: **`/api/v1/*` балансируется сразу в Receiver, минуя Web**. Что это даёт:

- падение или выкат Web больше не влияет на приём боевых запросов — сейчас влияет;
- с горячего пути уходит лишний сетевой хоп и лишний буфер тела (при телах до 124 МиБ это заметно);
- две реплики Web становятся «панельными», их обновление можно делать без оглядки на трафик.

Прокси в Web при этом остаётся: он нужен для replay §85 и dry-run §55, где Web сам инициирует
запрос через реальный pipeline. Но это уже не горячий путь.

## 4. Что в коде уже готово к репликам

Главная причина, по которой работа стоит дёшево. Состояние давно вынесено из процессов:

| Механизм | Где | Состояние |
|---|---|---|
| Rate limit по узлу | [platform/ratelimit/redis.go](../internal/platform/ratelimit/redis.go) | Redis; в godoc прямо написано «согласованность между всеми инстансами Receiver» |
| Circuit breaker | [platform/circuitbreaker/redis.go](../internal/platform/circuitbreaker/redis.go) | Redis; «согласованное поведение между несколькими Sender'ами» (§9.5) |
| Сессии, статусы узлов, отмена очереди, кеш Kafka | [web/adapter/out/redis/](../internal/web/adapter/out/redis/) | Redis → sticky-сессии на балансировщике **не нужны** |
| Инвалидация кеша узлов | [platform/nodeevents](../internal/platform/nodeevents/nodeevents.go) | Redis pub/sub → L1-кеши всех реплик выселяются разом |
| Hot-reload настроек (§8.4) | [platform/reloader](../internal/platform/reloader/reloader.go) | Redis pub/sub → доезжает до всех реплик |
| Планировщик уведомлений | [redis/notif_lock.go](../internal/web/adapter/out/redis/notif_lock.go) | Лок **уже написан под несколько реплик Web** — готовый образец |
| async-consumer, DLQ-reprocessor, paused-sweeper | [sender/adapter/in/kafka/](../internal/sender/adapter/in/kafka/) | consumer-группы Kafka → партиции делятся между репликами сами |
| Логи при недоступном CH | [chlog/writer.go](../internal/sender/adapter/out/chlog/writer.go) | NDJSON-fallback заменён Kafka retry-топиком (§38) → **локальный диск состояния не держит** |
| Метрики панели | [prometheus/client.go](../internal/web/adapter/out/prometheus/client.go) | все PromQL уже `sum(...)` / `sum by (node)` → по репликам суммируются корректно |
| Алерты | [prometheus.alerts.yml](../deploy/prometheus.alerts.yml) | `max by (...)` → устойчивы к нескольким сериям на одну сущность |
| Миграции | [platform/pg/migrate.go](../internal/platform/pg/migrate.go) | advisory-lock; состояние `Ahead` — не ошибка старта → выкат со смешанными версиями легален |
| gRPC health на Sender | [sender/app.go](../internal/sender/app.go) | `grpc_health_v1` уже зарегистрирован → клиентская балансировка включается почти даром |
| Graceful shutdown | `Stop()` всех трёх приложений | есть, с ожиданием фоновых горутин |

Единственное «липкое» состояние в Web — TTL-кеши на 15–30 с
([metrics_totals.go](../internal/web/usecase/metrics_totals.go), автоокно логов в
[logs.go](../internal/web/usecase/logs.go)). Следствие: цифры шапки на двух репликах могут
отличаться в пределах TTL. Для панели несущественно.

## 5. Что мешает прямо сейчас

Список закрытый — это всё, что нашлось при разборе.

1. **Порты.** `ports: "8080:8080"` у app-сервисов делает вторую реплику невозможной физически:
   конфликт публикации. Публиковать должен только nginx.
2. **Prometheus скрейпит `static_configs`** ([prometheus.yml](../deploy/prometheus.yml)).
   Это не украшение, а дефект: с одним статическим таргетом `receiver:8080` Docker DNS будет
   отдавать то одну реплику, то другую, счётчики начнут прыгать между рядами, и `increase()`
   выдаст мусор в панель §21. Нужен `dns_sd_configs`, который обнаружит обе.
3. **gRPC Receiver → Sender без балансировки.**
   [grpcsender/client.go](../internal/platform/grpcsender/client.go) держит пул из 8 соединений
   к одному адресу `sender:9190`, без health-check. При падении реплики часть соединений будет
   упорно ходить в мёртвую.
4. **Пул PostgreSQL.** `postgres.max_open_conns: 25` × 6 процессов = 150 против дефолтных
   `max_connections = 100`. В [override](../deploy/docker-compose.override.yml) это даже записано:
   «max_connections НЕ трогаем: дефолтные 100 должны покрывать 25 × 3 = 75». С шестью процессами
   расчёт ломается — сервисы начнут получать «too many connections».
5. **Kafka-консьюмеры.** `kafka.consumer.instances: 8` при `partitions: 8` — при двух Sender'ах
   получится 16 читателей на 8 партиций, половина простаивает вхолостую (обратный случай той же
   ошибки уже был в бою 2026-08-07, см. комментарий в `config.yml`).
6. **Нет дренажа перед остановкой.** `/ready`
   ([platform/healthcheck](../internal/platform/healthcheck/healthcheck.go)) отражает только
   состояние зависимостей; режима «выводи меня из ротации, я останавливаюсь» нет. Плюс таймаут
   shutdown зашит константой 30 с, а синхронный запрос живёт по таймауту узла — до 600 с.
   Без дренажа выкат будет рвать долгие запросы.
7. **Логи реплик неразличимы.** Консоль §51 читает Redis-кольцо `nexus:logs:<service>`
   ([logsink/entry.go](../internal/platform/logsink/entry.go)); поле `instance` там есть, но это
   идентификатор **ноды** §70, а не реплики. Записи двух реплик перемешаются без пометки.
   То же в Sentry: `ServerName` = имя сервиса.
8. **Периодические задачи, не идемпотентные вдвоём:**
   [`ch_housekeeping`](../internal/sender/usecase/ch_housekeeping.go) — двойной `DROP PARTITION`
   на общем ClickHouse, и [`Housekeeping`](../internal/web/usecase/housekeeping.go) аудита.
   Обе переживут дубль, но дадут лишнюю нагрузку и шум в логах.
9. **RabbitMQ-pullers §27.** [PullerManager](../internal/receiver/usecase/puller_manager.go)
   поднимает воркер на каждый узел RabbitMQAsync и тянет через `basic.get` с дефолтами
   `pull_interval_sec 5`, `pull_batch_size 100`. Дублей при двух Receiver'ах **не будет** — брокер
   отдаёт сообщение одному потребителю, — но темп вычитки удвоится (до 200 сообщений за 5 с),
   а порядок доставки во внешний узел перемешается сильнее. Решение — в §7, блок B.5.

Побочная находка при сверке цифр: таблица «содержимое профиля под 2 ГБ» в
[DEPLOYMENT §5.4](../DEPLOYMENT.md) отстала от самого файла
[deploy/docker-compose.override.yml](../deploy/docker-compose.override.yml) — в тексте
`receiver mem_limit 192m` / `sender 256m`, в файле `1g` / `1792m` (подняты после перехода на тела
124 МиБ). Правится вместе с остальным DEPLOYMENT.

## 6. Оценка 1 — ресурсы сервера

Замеры взяты из [DEPLOYMENT §5.4](../DEPLOYMENT.md) (таблица снята на боевом профиле), а не
оценены на глаз.

### 6.1. В простое

| Компонент | `docker stats` | RSS |
|---|---|---|
| +receiver (вторая копия) | +8 МиБ | +30 МБ |
| +sender | +13 МиБ | +36 МБ |
| +web | +19 МиБ | +53 МБ |
| +nginx:alpine | ~5 МиБ | ~10 МБ |
| **Итого** | **≈ +45 МиБ** | **≈ +130 МБ** |

На фоне стека в ~1 ГБ это **+5…13 %**. CPU в простое не меняется: все три Go-сервиса дают ~0,
nginx в простое тоже. Prometheus получает 6 таргетов вместо 3 — серий примерно вдвое больше,
TSDB на 15 днях хранения вырастет с ~0.07 до ~0.13 ГБ. Диск: +образ nginx (~50 МБ) и вдвое больше
docker-логов приложения.

### 6.2. Под нагрузкой решают потолки, а не простой

Текущие `mem_limit` ([override](../deploy/docker-compose.override.yml)) рассчитаны на тела до
124 МиБ: receiver 1 ГБ, sender 1792 МБ, web 192 МБ — **3.0 ГБ на приложение** плюс 1.3 ГБ на
инфраструктуру. Каждая реплика обязана держать тот же одиночный предельный запрос, поэтому
потолки удваиваются вместе с репликами.

| Профиль трафика | Сегодня | С двумя репликами | Вывод |
|---|---|---|---|
| Обычные тела (≤ 1 МиБ) | 2 ГБ хватает | 2 ГБ хватает, комфортно 4 | железо не трогаем |
| Крупные тела (до 124 МиБ) | 3.0 ГБ потолков приложения | 6.0 ГБ потолков приложения | **нужно 8 ГБ**, либо урезать лимиты на реплику и ограничить число одновременных крупных запросов |

Второй путь (остаться на 4 ГБ) выглядит так: receiver 640 МБ / `GOMEMLIMIT` 500 МиБ, sender
1 ГБ / `GOMEMLIMIT` 800 МиБ на реплику — и жёсткое ограничение одновременных предельных запросов
через `receiver.rate_limit_per_node`. Риск честный: два 124-МиБ запроса, попавшие на одну реплику,
дадут OOM-kill контейнера. С двумя репликами это уже не катастрофа (второй продолжает работать),
но запросы на убитой реплике теряются.

### 6.3. Параметры, которые надо поднять до выката

Не «желательно», а иначе шесть процессов упрутся в потолки, которых сегодня хватает трём:

| Параметр | Сейчас | С двумя репликами | Почему |
|---|---|---|---|
| `postgres.max_open_conns` | 25 (×3 = 75) | 12–15, либо `max_connections` PG до 150 | 25 × 6 = 150 > дефолтных 100 |
| `kafka.consumer.instances` | 8 | 4 на реплику | 16 читателей на 8 партиций = половина вхолостую |
| `sender.workers` | 50 | 25 на реплику либо осознанно 100 суммарно | давление на внешние узлы удваивается |
| `redis.pool_size` | 50 (×6 = 300) | можно не трогать | Redis держит такое число соединений спокойно |

### 6.4. Итог по железу

**При обычном трафике — +130 МБ RAM и ~0 CPU, текущего сервера достаточно.** При работе с
крупными телами — рекомендуется 8 ГБ вместо нынешних 4, либо сознательный размен на урезанные
потолки. Отдельного железа под балансировщик не нужно.

## 7. Оценка 3 — доработки

Разбито на блоки-коммиты по правилу «Процесс работы» из [CLAUDE.md](../CLAUDE.md).

### Блок A — развёртывание, без Go-кода (~1 день)

- **A.1 nginx-контейнер.** `deploy/docker/nginx.conf` + сервис в compose. Upstream'ы `web` и
  `receiver` (по 2 сервера, `max_fails` / `fail_timeout`), маршрут `/api/v1/*` → receiver.
  Обязательные детали, которые легко забыть: `proxy_read_timeout 600s` (синхронный вызов живёт по
  таймауту узла, дефолтные 60 с его оборвут), `client_max_body_size 140m` (≥ `max_body_bytes`
  124 МиБ + запас), `proxy_buffering off` для SSE-стрима логов §77, `X-Forwarded-For` /
  `X-Forwarded-Proto` — иначе `client_host` §67 и rate-limit по IP увидят адрес прокси, а не
  клиента.
- **A.2 compose.** Реплики (`deploy.replicas: 2`), публикация портов уезжает с app-сервисов на
  nginx, отдельный профиль-оверлей — одиночный режим должен остаться рабочим для стенда и dev.
- **A.3 `scripts/deploy/rolling.sh`.** Выкат по одной реплике: вывести из ротации → дренаж →
  пересобрать → дождаться `healthy` → вернуть → следующая. Перед началом вызывает
  `images.sh tag` (сохранение образов для отката, §74.5), **после успешного завершения чистит
  мусор сборки**:

  ```bash
  docker builder prune -f --filter until=72h   # кэш слоёв прошлых сборок
  docker image prune -f                        # только dangling (<none>) образы
  ```

  > **Грабли, которые надо закрепить в скрипте комментарием:** `docker image prune -a` использовать
  > **нельзя** — он снесёт версионные образы `nexus-*:1.29.0`, сохранённые `images.sh tag`, и
  > быстрый откат (§10.1, секунды) превратится в пересборку трёх образов под нагрузкой. Чистится
  > только build cache и dangling-слои. Фильтр `until` оставляет кэш последней сборки — следующий
  > выкат не начинается с нуля.

- **A.4 Prometheus.** `static_configs` → `dns_sd_configs` (см. §5, пункт 2) плюс алерт
  «живых реплик сервиса меньше двух» — без него «тихая половина» не видна вообще.
- **A.5 Параметры.** Пулы PG, `consumer.instances`, `sender.workers`, `mem_limit` / `GOMEMLIMIT`
  из §6.3 — в конфиг и override-профиль.

### Блок B — Go-доработки (~1–1.5 дня)

- **B.1 Балансировка gRPC Receiver → Sender.** В
  [grpcsender/client.go](../internal/platform/grpcsender/client.go): `dns:///sender:9190` +
  `round_robin` + healthCheckConfig. Серверная половина (`grpc_health_v1`) уже есть, правка мелкая.
  Обе половины keepalive-контракта живут в этом же пакете намеренно (§82.1) — балансировку туда же.
- **B.2 Дренаж перед остановкой.** По SIGTERM `/ready` начинает отвечать 503 («draining»),
  балансировщик выводит реплику из ротации, выдерживается пауза `shutdown_drain_sec`, затем
  graceful stop с **конфигурируемым** `shutdown_timeout_sec` вместо зашитых 30 с. Без этого выкат
  рвёт длинные синхронные запросы на 30-й секунде.
- **B.3 Различение реплик в наблюдаемости.** Поле `replica` (hostname контейнера) в
  `logsink.Entry` + показ и фильтр в консоли логов §51; `ServerName` в Sentry. Без этого
  диагностика «почему один запрос прошёл, а соседний нет» становится гаданием.
- **B.4 Локи периодических задач** по образцу
  [`NotifLockRedis`](../internal/web/adapter/out/redis/notif_lock.go): `ch_housekeeping` в Sender
  и `Housekeeping` аудита в Web.
- **B.5 RabbitMQ-pullers §27 — лидер-лок на узел.** Redis-лок по образцу того же `NotifLockRedis`:
  `SETNX` с TTL ≈ 2 × `pull_interval_sec`, продлевается на каждом цикле; воркер узла работает
  только у владельца лока. Поведение остаётся ровно сегодняшним (темп и порядок вычитки не
  меняются), а при падении лидера вторая реплика подхватывает узел за время TTL.
  **Альтернатива «делить `pull_batch_size` пополам» отвергнута:** она уполовинивает пропускную
  способность, когда одна реплика лежит, и не чинит перемешивание порядка.

## 8. Оценка 2 — эксплуатация

### Что становится дороже

1. **Процедура выката.** Была одна команда и ~30 с простоя. Станет `rolling.sh` — тоже одна
   команда, но внутри шесть шагов с ожиданиями; время растёт с ~2 до ~5–8 мин. Взамен — ноль
   простоя.
2. **Диагностика раздваивается.** «Почему один запрос прошёл, а соседний нет» теперь может
   означать «реплики разошлись». Блок B.3 закрывает это в логах и Sentry, но привычку смотреть
   на реплику придётся выработать.
3. **Новый класс отказа — «тихая половина».** Одна реплика в crash-loop выглядит снаружи как
   «всё работает, но иногда 502». Алерт из A.4 обязателен, без него деградация невидима.
4. **Контракт схемы §74.2 из рекомендации становится жёстким требованием.** В момент выката две
   версии кода работают на одной схеме. Неаддитивная миграция теперь ломает не откат, а сам выкат.
5. **Связанные настройки.** `consumer.instances` делится между репликами, `sender.workers`
   суммируется, пулы PG умножаются на число процессов. Описывается один раз в DEPLOYMENT — иначе
   следующий оператор наступит.

### Что становится дешевле

Падение процесса перестаёт быть инцидентом «сервис лёг ночью»: трафик переживает его на второй
реплике, разбор переносится на утро. Плановое обновление перестаёт требовать окна.

### Итог по эксплуатации

**+1 скрипт, +1 алерт, +2 переписанные процедуры, +1 сценарий на стенде.** Регулярная нагрузка
почти не растёт; растёт разовая цена освоения. При первом же ночном падении процесса это
окупается.

## 9. Что этим НЕ закрывается

Формулировку «простоев не должно быть» после этой работы можно давать **только про обновления и
падения приложения**. Остаётся:

- **PostgreSQL, Redis, Kafka, ClickHouse** — по одному экземпляру. Их обновление или падение =
  простой, полный либо частичный (без Redis Web отвечает 503 на авторизованные эндпоинты, §9.4;
  без Kafka `requestAsync` отдаёт 503, а sync продолжает работать).
- **Сам сервер, ядро, Docker daemon, диск.** Один хост — это один хост. Реальная
  отказоустойчивость требует второго; на одном достигается «обновление без простоя» и
  «переживание падения процесса», не более.
- **nginx-контейнер** — сам единая точка. Смягчено тем, что смена конфига идёт `nginx -s reload`
  без разрыва соединений, а падение самого nginx — редкий класс отказа. Второй nginx с keepalived
  на одном хосте от падения хоста не спасает и в план не входит.
- **Долгие синхронные запросы** (до 600 с) на выводимой реплике: даже с дренажем выкат либо ждёт
  их, либо рвёт. `shutdown_drain_sec` / `shutdown_timeout_sec` делают выбор управляемым, но не
  бесплатным.
- **Неаддитивные миграции** — во время выката несовместимы в принципе (§74.2).
