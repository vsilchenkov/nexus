## [Unreleased]

## [1.15.2] - 2026-07-19

### Fixed

- **Узлы на внутренних доменах перестали падать с ошибкой TLS.** Запросы к адресам вида
  `*.vz78.vozovoz.ru` завершались с `x509: certificate signed by unknown authority` — в образе
  Sender'а не было корпоративного центра сертификации. Теперь в него встроен **промежуточный**
  «Vozovoz Issuing CA». Важная деталь: добавить **корневой** «Vozovoz Root CA» недостаточно — у него
  отсутствует расширение `basicConstraints` (`CA:TRUE`), поэтому по RFC 5280 он не вправе подписывать
  сертификаты и Go отвергает его независимо от наличия в хранилище. Подробности, порядок обновления
  сертификата и сверка отпечатка — в [deploy/certs/README.md](deploy/certs/README.md).
  **Требует пересборки образа Sender'а** (`docker compose up -d --build sender`).

### Changed

- **CI больше не запускает дублирующий пайплайн на `master`.** Раннер один и обрабатывает задачи
  последовательно, а релиз пушит `master` и тег на один и тот же коммит — из-за чего пайплайн ветки
  занимал раннер, а релизный пайплайн тега простаивал в очереди по 30–90 минут. Теперь push-пайплайн
  `master` не создаётся: выпускается всегда коммит с тегом, и его пайплайн проверяет тот же код
  плюс security-сканеры и loadtest. Ручной запуск через «Run pipeline» на `master` сохранён.
- **Шапка этого файла больше не ссылается на несуществующий job `release`** — он был удалён ещё
  в 1.0.3 вместе со стадией `release`; описание приведено в соответствие с фактическим поведением.
- **DEPLOYMENT.md §13** пополнен двумя типовыми симптомами: ошибка TLS на внутренних доменах и
  `real call is not available: web.sender_grpc.addr is not configured` у тестового запроса.

## [1.15.1] - 2026-07-19

### Fixed

- **Срок хранения ClickHouse (native-TTL) больше не «сбрасывается» по кругу (§56).** Интроспекция
  существующей таблицы распознавала только форму `INTERVAL N DAY`, тогда как ClickHouse хранит TTL
  как `toIntervalDay(N)`. Из-за этого план синхронизации схемы **каждый раз** предлагал `MODIFY TTL`,
  будто retention не применён, хотя он уже стоял. Теперь обе формы распознаются — повторный план по
  неизменной таблице пуст.
- **Клик по команде в «Избранном» всегда открывает её «Узлы» (§49.2).** Находясь на разделе, отличном
  от «Узлы» (Аудит/Kafka/Логи/Настройки), клик по избранной команде выглядел «не реагирующим»: он
  менял контекст команды, но не переходил к её узлам, а по уже текущей команде не делал ничего. Теперь
  клик по избранному всегда ведёт на страницу «Узлы» выбранной команды (и переключает команду, если
  она отличается).
- **Предупреждение о смене схемы CH ссылается на нужную кнопку (§56).** Текст предупреждения C.1 в
  форме узла теперь прямо отсылает к кнопке **«Синхронизировать схему»**, а не к абстрактному
  «ручному ALTER».

### Changed

- **«Синхронизировать схему» предлагает сохранить несохранённые CH-правки (§56).** Синхронизация
  строила план по **сохранённому** конфигу узла, поэтому только что изменённые в форме поля CH
  (шаблон/кодеки/индексы/TTL) в план не попадали. Теперь при наличии несохранённых CH-правок кнопка
  сначала предлагает их сохранить — план строится по актуальному состоянию.

## [1.15.0] - 2026-07-18

### Added

- **«Поделиться узлом» — прямая ссылка с авто-переключением команды (§58).** На странице просмотра
  узла и в форме правки появилась кнопка **«Поделиться»**: она даёт прямую ссылку вида `/nodes/:id`,
  которую можно отправить коллеге. При открытии такой ссылки, если узел принадлежит другой команде,
  интерфейс **сам переключает команду** на нужную (а не показывает пустой список) — за это отвечает
  новый резолвер `GET /nodes/:id/team`. Если узел недоступен (удалён или нет прав), вместо пустого
  экрана показывается понятное **«Узел не доступен»**.
- **Синхронизация схемы ClickHouse у существующей таблицы (§56).** Раньше смена ClickHouse-шаблона,
  кодеков, data-skipping индексов или native-TTL у уже созданного узла **не доезжала до таблицы** —
  она создаётся один раз (`CREATE TABLE IF NOT EXISTS`), и ALTER'ов не было. Теперь в настройках узла
  есть кнопка **«Синхронизировать схему»**: система читает текущую структуру таблицы (`SHOW CREATE`),
  показывает **план** (какие `ALTER … MODIFY COLUMN` / индексы / `MODIFY TTL` будут выполнены, а что
  требует пересоздания — движок, ORDER BY, PARTITION BY), и по подтверждению применяет его. Появились
  эндпоинты `POST /api/nodes/{id}/ch-schema/plan` (только чтение) и `/apply`.
- **Перевыпуск (rotate) значения API-токена (§7.14).** В списке токенов появилась операция
  **перевыпуска**: она генерирует новое значение токена, **сохраняя его настройки** (команда, срок,
  scope). Прежнее значение немедленно перестаёт работать — удобно при подозрении на утечку, не
  пересоздавая токен с нуля.
- **Мониторинг всех узлов и Kafka в Grafana + алерты по узлам (§7.6).** Добавлены два новых
  дашборда: **«Nexus — Nodes»** (сразу видно проблемные узлы — счётчики DOWN/DEGRADED/OK, таблица
  проблемных, сводка по каждому узлу: отправлено/ошибки/%/p95/статус с подсветкой, история статуса,
  секция RabbitMQ pull-узлов) и **«Nexus — Kafka & Async»** (lag по группам/топикам, конвейер
  produced→delivered→failed, ошибки async по узлам, DLQ, loop-detection). В `deploy/prometheus.alerts.yml`
  добавлена группа `nexus.nodes` (узел down/degraded/высокий error rate, RMQ-разрыв, потеря сообщений
  из DLQ). Дашборды в `deploy/grafana/` импортируются во внешнюю Grafana вручную.
- **Тестовый запрос подставляет входящую авторизацию и метод узла (§55.6).** Диалог диагностики узла
  теперь автоматически заполняет ожидаемое поле входящей авторизации и HTTP-метод из конфигурации
  узла — на один шаг меньше ручного ввода перед запуском.

### Changed

- **Изменения узла применяются к маршрутизации мгновенно (§57).** При правке узла в Web горячий кеш
  Receiver'а раньше мог какое-то время отдавать **устаревшую** конфигурацию (до истечения TTL). Теперь
  Web публикует событие изменения (новый пакет `nodeevents`), Receiver на него подписан и немедленно
  инвалидирует запись в своём кеше узлов — правки (адрес, авторизация, статус) вступают в силу без
  ожидания и без рестарта.
- **Предупреждение о смене схемы ClickHouse (§19).** Если у существующего узла поменять CH-шаблон
  без смены имени таблицы, новые кодеки/индексы/движок к ней сами не приедут (см. §56 выше). Форма
  теперь **честно предупреждает** об этом и подсказывает, что для применения нужно либо новое имя
  таблицы, либо ручная «Синхронизировать схему». Срок хранения (Retention, дни) — исключение:
  он применяется автоматически фоновым housekeeping'ом.

### Fixed

- **Replay доступен только роли «менеджер» и выше (§58, RBAC).** Кнопка повторной отправки запроса
  (Replay) ошибочно показывалась роли «наблюдатель» (viewer); теперь доступ приведён в соответствие
  с матрицей прав. Заодно проведён аудит прав на кнопки в шапке узла.

## [1.14.0] - 2026-07-17

### Added

- **«Тестовый запрос» стал настоящей диагностикой узла (§55).** Раньше тест отвечал на вопрос
  «валиден ли конфиг», но не на вопрос «дойдёт ли запрос до получателя»: при снятой галке mock шаг
  «Ответ» просто сообщал, что реальный режим не поддерживается. Теперь **запрос можно реально
  отправить получателю** — тем же путём, что и боевой трафик, поэтому в отчёте видны настоящие
  статус, длительность, число попыток, редиректы и таймауты (ровно то, ради чего тест и открывают).
  Что важно: **тест не оставляет следов** — он не пишет в логи узла, не влияет на графики и метрики,
  не меняет статус узла на дашборде и не участвует в защите от сбоев (circuit breaker). То есть
  диагностика зависшего узла не может усугубить его состояние. Реальный режим требует адреса Sender
  в настройке `web.sender_grpc` (см. DEPLOYMENT.md); если она не задана, всё работает как прежде,
  а шаг «Ответ» объясняет причину.
- **Диалог теста заполнен целиком.** Появились поля **Заголовки** и **Query-параметры** (пары
  «имя → значение»), **Хвост пути** (для узлов, дописывающих путь к адресу получателя) и переключатель
  **«Использовать mock-сервер»** (включён по умолчанию; при снятии рядом с «Запустить» появляется
  предупреждение с реальным адресом). Для узла с входящей авторизацией диалог **подсказывает, какое
  именно поле он ожидает** (например, `Authorization: Basic base64(логин:пароль)`) и позволяет
  подставить его одним кликом. Раньше подставить заголовок было нечем, и тест такого узла всегда
  обрывался на первом шаге сообщением «authorization header missing».
- **Кнопка «Тестовый запрос» на странице просмотра узла** (рядом с «Обновить»/«Копировать»/
  «Изменить») — проверить сохранённый узел, не заходя в редактирование. Пароли и токены узла при
  этом подставляет сервер: наружу они не отдаются, поэтому без этого тест узла с авторизацией
  всегда получал бы 401. Доступна с ролью «менеджер» и выше.
- **Команда API-токена выбирается при создании и видна в списке.** Токен действует ровно в одной
  команде, но раньше выбора не было: он молча наследовал команду, выбранную в переключателе шапки в
  момент нажатия «Создать», и увидеть её было негде — отсюда сюрприз «токен видит не те узлы».
  Теперь в форме есть поле **Команда** (список — команды, в которых вы состоите), а в таблице
  токенов — колонка **Команда**. Попытка выписать токен в команду без членства отклоняется (403).

### Fixed

- **Срок действия токена больше не игнорируется.** Выбранный в интерфейсе срок (по умолчанию 365
  дней) не доходил до сервера — из-за расхождения имён полей он молча терялся, и **все выданные
  токены были бессрочными**. Теперь срок применяется и считается на сервере (часы браузера на него
  не влияют); пустое поле по-прежнему означает бессрочный токен. **Ранее созданные токены остались
  бессрочными** — если это нежелательно, отзовите их и выпустите заново со сроком.
- **Раздел «Настройки» больше не перезагружается при переключении команды.** Вкладки Общие,
  Пользователи, Команды, API-токены, Разрешённые хосты, Заголовки, ClickHouse, Sentry и Уведомления
  показывают данные, которые от команды не зависят, но при каждом переключении они зря
  перезапрашивались и мигали. Теперь Настройки живут вне скоупа команды: где данные всё же
  принадлежат команде, она задаётся явно внутри формы (как команда токена).
- **Логи узлов не-default команд больше не падают после деплоя (Sentry 158619).** На установке с
  несколькими командами открытие логов узла могло вернуть ошибку
  `Unknown expression identifier 'request_size'`: при старте Web добавлял новые колонки только в
  таблицы команды по умолчанию, а базы остальных команд (`nexus_<команда>.*` — там и живёт весь
  боевой трафик) не трогал вовсе. Схему чинил только рестарт Sender'а, поэтому в промежутке
  «новый Web уже поднят, новый Sender ещё нет» просмотр логов отдавал 500. Теперь Web мигрирует
  таблицы **всех** команд — симметрично Sender'у, порядок деплоя действительно не важен. Дефект
  существовал с 1.12.0 и затрагивал колонки `node_id`, `http_method`, `request_size`/`response_size`.
- **Таблица логов узла вмещается по ширине — горизонтальный скролл убран.** После появления колонки
  «Ответ» (размер тела, 1.12.0) таблица на вкладке «Логи» перестала помещаться в карточку: внизу
  возникала полоса прокрутки, а последние колонки уезжали за край. Причина — ширина таблицы
  подстраивалась под содержимое (колонка URL резервировала фиксированные 448 пикселей). Теперь
  служебные колонки (время, HTTP, статус, мс, ответ, повтор) имеют заданную ширину, а «Метод» и
  «URL» делят остаток и обрезаются многоточием — таблица вмещается на любой ширине экрана.
- **Полный «Метод» и «URL» видны во всплывающей подсказке.** Значения в этих колонках обрезаются,
  и раньше прочитать их целиком было негде — теперь полный адрес показывается при наведении.
- **Переключение команды при открытой странице узла больше не оставляет чужие данные на экране.**
  Узел принадлежит одной команде: после переключения он становится недоступен, но страница
  продолжала показывать его **старые данные** — без ошибки и без перехода, как будто всё в порядке.
  Теперь происходит переход к списку узлов выбранной команды.
- **Кнопка «Обновить» на странице узла больше не висит заблокированной.** Она реагировала на любой
  фоновый запрос во всём интерфейсе (а не только на данные этой страницы), а после смены команды
  недоступный узел ещё и опрашивался по кругу с повторными попытками — в результате кнопка крутилась
  практически постоянно. Теперь она отслеживает и обновляет только данные открытого узла.
- **Несохранённые правки в форме узла больше не пропадают.** Достаточно было переключиться в другое
  окно и вернуться (или сменить команду) — форма молча перезаполнялась данными с сервера, стирая
  введённое. Теперь форма заполняется один раз при открытии. Если узел оказался в другой команде,
  показывается подсказка и сохранение блокируется — введённые данные при этом сохраняются на экране.

## [1.13.0] - 2026-07-17

### Added

- **Сохранение фильтров рабочего стола (§54).** Фильтры на странице узлов (поиск, метод, статус,
  выбранный период) больше не сбрасываются при переходе на страницу узла и возврате — ни по кнопке
  «Назад» в браузере, ни по кнопке «Узлы» в сайдбаре. Раньше фильтр приходилось перенабирать при
  каждом возврате. Фильтры отражаются в адресной строке (`/?q=…&method=…&status=…&range=…`), поэтому
  переживают перезагрузку страницы (F5) и **ссылку с фильтром можно отправить коллеге**; в рамках
  вкладки они дополнительно восстанавливаются из `sessionStorage` (кнопка «Узлы» ведёт на адрес без
  параметров). В адрес попадают только отличия от значений по умолчанию — при дефолтных фильтрах
  адрес остаётся чистым, а сохранённый «по умолчанию» период (звёздочка, §44.B) продолжает
  действовать: новая вкладка стартует с него. Очистка фильтров убирает их окончательно.

### Fixed

- **Календарь произвольного периода показывает выбранный диапазон.** `PeriodPicker` не заполнял поля
  дат из текущего значения: при возврате на страницу с «Произвольным» периодом диапазон был
  применён (метрики и подписи считались по нему), но поля показывали пустое `дд.мм.гггг` — не было
  видно, какой именно период выбран. Затрагивало рабочий стол, мониторинг Kafka и вкладки узла.

## [1.12.0] - 2026-07-16

### Added

- **Копирование узла — кнопка «Скопировать узел» (§53).** `POST /api/nodes/{id}/copy` (manager+):
  серверный клон узла с новым `path` в той же команде. Копируются **все** настройки, включая креды
  (`auth_credentials`/`incoming_auth_credentials`/`rmq_password`) — расшифровка/перешифровка только
  внутри бэкенда, через API секреты не проходят — и привязки каталога разрешённых хостов (§23,
  клонируются в той же транзакции со снимком). Копия **всегда создаётся в статусе `paused`**, чтобы
  копия активного узла не начала молча принимать трафик. UI: кнопка «Копировать» в шапке страницы
  узла (рядом с «Изменить») + диалог с полем нового пути (префилл `<path>-copy`, клиентская
  валидация) → переход на страницу копии. Аудит-действие `node.copy` с провенансом `source_node_id`.
- **Управление логированием сервисов — консоль «Логи» + runtime-уровень (§51).** Новый пункт
  сайдбара **«Логи»** (admin): follow-tail-консоль служебных slog-логов всех трёх сервисов
  (Receiver/Sender/Web) — чипсы сервисов, поиск, режим Live с паузой, скачивание в файл. Доставка
  через Redis-кольцо `nexus:logs:<service>` (неблокирующий шиппер с маскировкой чувствительных
  полей). **Смена уровня логирования в runtime без рестарта**: сегмент уровня в UI пишет
  `app_settings.logging.level`, reload-шина применяет его сразу во всех трёх процессах (`LevelVar` в
  собственной сборке цепочки slog-хендлеров). API `GET /api/logs` + `GET /api/logs/download`
  (admin). Заложено debug-инструментирование ключевых путей (маршрутизация, внешние вызовы, тихие
  fallback'и) — видно без рестарта при переключении уровня.
- **Избранные команды (§49).** Пер-пользовательское избранное команд: звезда «в избранное» в
  переключателе команд, секция **«Избранное»** в сайдбаре (клик переключает команду, drag-and-drop
  меняет порядок). В шапке и списке переключателя показывается отображаемое имя команды без slug.
  Хранение в PostgreSQL (`user_team_favorites` с каскадом на членство — инвариант «избранное ⊆
  членство»); API — `favorites` в `GET /api/me/teams` + `PUT /api/me/favorite-teams` (full-replace).
- **Видимость 3xx-редиректов Sender (§50).** `CheckRedirect` логирует каждый хоп внешнего редиректа
  (Info; Warn при POST→GET с потерей тела) и дописывает сводку в поле `reason` лога — видно в UI
  «Причина»; `redactURL` вырезает query. Следование редиректам сохранено.
- **Трёхсостоянье runtime-статуса узла: OK / Degraded / Down (§52).** Продолжение инцидента
  site/push (§50.4): серия 422 от протухших FCM-токенов красила живой узел в «Down». Теперь бейдж
  узла на Overview различает **Degraded** (жёлтый — узел ответил, но не-2xx и < 500: ошибка
  данных/клиента, узел жив) и **Down** (красный — транспортная ошибка или 5xx; включая
  503 breaker-open и 502 oversize). Граница `< 500` = здоровье breaker'а из §50.4. Новая опция
  «Degraded» в фильтре статусов; сортировка «проблемные первыми»: Down → Degraded → Queue.
  API `GET /api/metrics/nodes`: новое поле `items[].last_outcome` (`ok|degraded|down`),
  `last_error` сохранён (back-compat). Счётчики ошибок (§44) и `nexus_request_incomplete_total`
  не меняются — 4xx остаётся ошибкой доставки.
- **Истинные размеры тел в логах: колонки `request_size`/`response_size` + колонка «Ответ» в UI
  (§42.10).** Лог-таблицы ClickHouse получают размеры тел запроса/ответа в байтах — по ПОЛНОМУ телу,
  до усечения лог-копии по `max_body_size` (не путать с `request_len`/`response_len` — рунами
  сохранённой копии). На старте Web/Sender — авто-`ALTER` (`EnsureBodySizeColumns`) и **разовый
  backfill исторических строк** (`BackfillBodySizes`, `length()` сохранённой копии — нижняя граница
  у усечённых). API логов отдаёт `request_size`/`response_size` всегда (list/stream/detail). UI:
  компактная колонка «Ответ» в таблице логов («12.0 КБ», «—» = тела нет; локализованные единицы) и
  размеры в скобках в заголовках панелей раскрытой записи — «Запрос (12.0 КБ)» / «Ответ (34.5 КБ)».

### Changed

- **Метрика `nexus_node_last_request_error{node}` расширена** (§52): 0=ok, 1=degraded, 2=down
  (было 0/1). Алерты `>= 1` продолжают ловить любую проблему; «только down» — `>= 2`.
  Redis-ключ `nexus:node:last_error:<path>` кодируется как `"0"`=ok/`"1"`=down/`"2"`=degraded
  (legacy `"1"` читается как down; rolling-деплой безопасен, см. DEPLOYMENT.md).

### Fixed

- **Кеш узла: ключ по реальной команде — правки узлов вне команды `default` доходили до Receiver
  только по TTL (§50).** Web писал/инвалидировал ключ `node:default:<path>`, а Receiver читает
  `node:<team_slug>:<path>` — для узла вне команды `default` изменения `target_url`/статуса,
  **удаление** и перенос не доходили до Receiver до истечения Redis-TTL (до 5 мин). Боевой симптом:
  http-target ещё 5 минут ходил на старый https и падал на TLS. Фикс: ключ по реальному slug
  команды (`resolveCacheTeamSlug`); креды в кеше теперь **шифруются** (AES-256-GCM; Receiver делает
  Decrypt) — раньше plaintext давал cache-miss.
- **Circuit breaker не открывается по 4xx (§50.4).** Боевой инцидент `site/push`: серия `422
  NotRegistered` от протухших FCM-токенов открывала breaker → 30 с все пуши узла, включая валидные,
  отбивались `circuit_breaker_open` и терялись. Теперь «здоровье апстрима» = `status < 500` (4xx =
  узел жив, ошибка данных клиента), breaker считает только 5xx/транспорт; лог по-прежнему `done=0`.

### Fixed

- **Скролл таблицы логов «не двигает вниз» на узлах с массой записей (§44, keyset-пагинация).** Курсор
  подгрузки был по `date_request` секундной точности с `<=`; на узле с сотнями записей в одной секунде

- **Зависание скролла таблицы логов на узлах с сотнями тысяч записей (§44).** Бесконечный скролл без
  виртуализации копил DOM без предела — на большом узле прокрутка вниз вешала вкладку. Введён потолок

- **Список логов больше не читает тела `request`/`response` из ClickHouse (§44).** Тела в списке не
  показывались (тянутся лениво при разворачивании строки — §42), но CH-запрос всё равно читал их с

  пагинацию при скролле. Теперь список их не читает (`'' AS request/response`); контентный поиск (q)

- **Прыжки интерфейса из-за переменной высоты верхних KPI-счётчиков (§44).** Строка процента

  ней сдвигался. Теперь строка delta резервируется всегда (nbsp), высота карточки постоянна.
- **Скоупинг команды при входе (§44.H).** Пользователь, чей `default_team_id` указывал на команду,
  в которой он больше не состоит (членство удалили, колонку не переписали), при входе попадал на

## [1.7.2] - 2026-06-24

Исправление семантики лимитов размера тела (§43 из 1.7.0 был выполнен неверно) + видимость причины
ошибки в логах.

### Changed

- **Исправлена семантика лимитов размера тела (§43-rev).** Первая редакция §43 (в 1.7.0) ошибочно сделала
  per-node «Ограничить размер тела» (`max_body_size`) жёстким reject (413/502). Возвращено к §22.2:
  `max_body_size` режет **только** копию тела в ClickHouse-логе (в рунах), а ответ клиенту приходит
  **полностью**, checksum по полному телу. Жёсткие лимиты — транспортные, **из конфига**:
  - тело ЗАПРОСА больше `receiver.max_body_bytes` → **413** (Receiver, sync/async/callback; раньше 400);
  - тело ОТВЕТА апстрима больше `sender.grpc_max_message_bytes` → **502** (Sender; чтение оборвано на
    лимите — memory-safe, тело не затягивается в память; раньше — `ResourceExhausted` в gRPC).
  Связи лимитов задокументированы комментарием в `config.example.yml`/`config.yml`.

### Added

- **Колонка «Причина» (reason) в таблице логов** и показ reason в раскрытой записи — причина не-OK
  (4xx/5xx, circuit breaker, превышение лимита) видна сразу, без раскрытия записи (§43 self-explanatory).

### Fixed

- **Чистый 413 через Web-прокси** при превышении `receiver.max_body_bytes`: ранний отказ по
  `Content-Length` (для клиентов с `Expect: 100-continue`) + дренаж ограниченного остатка тела — раньше
  большое тело через единый вход (Web → Receiver) давало 502 «receiver unavailable» вместо 413
  (Receiver отвечал, не дочитав тело → TCP-reset).

Плюс §43: жёсткий лимит размера тела (reject вместо тихого усечения).

### ⚠️ Изменения при апгрейде

- **§43 — изменена семантика `max_body_size`** (узлы с **включённым** лимитом). Раньше тело > лимита
  тихо усекалось в логе, а клиент получал полный ответ. Теперь тело > лимита **отклоняется**: sync —
  `413` (тело запроса) / `502` (тело ответа), async — не доставляется; во всех случаях запись лога
  `done=0` с `reason`, тело не сохраняется, `checksum` по полному телу. Узлы с **выключенным** лимитом
  (дефолт) — без изменений (большие тела проходят, показываются через §42). Миграций/ENV нет.

- **Новые параметры конфига для размера gRPC-сообщения** (с дефолтами — обратная совместимость, задавать
  не обязательно): `receiver.sender_grpc.max_message_bytes` и `sender.grpc_max_message_bytes`, оба дефолт
  **64 МиБ (67108864)**. Поднимают прежний предел gRPC 4 МиБ, из-за которого большой ответ апстрима
  (десятки МБ) рвался `ResourceExhausted desc = grpc: received message larger than max`. Значения двух
  сервисов **должны совпадать**; держите `≥ receiver.max_body_bytes`. Если в проде ожидаются ответы
  крупнее 64 МиБ — поднимите оба параметра согласованно. Новых миграций/ENV нет.

### Fixed

- **Большой ответ/запрос рвался в gRPC `ResourceExhausted` (лимит 4 МиБ).** Транспорт Receiver↔Sender
  использовал дефолтный лимит gRPC-сообщения 4 МиБ в обе стороны: уже 5-МиБ тело запроса (предел
  `receiver.max_body_bytes`) не доезжало до Sender, а ответ апстрима в десятки МБ — обратно к
  Receiver/клиенту. Лимиты подняты на сервере Sender (`MaxRecvMsgSize`/`MaxSendMsgSize`) и клиенте
  Receiver (`MaxCallRecvMsgSize`/`MaxCallSendMsgSize`) из новых конфиг-параметров (дефолт 64 МиБ).
- **Async (Kafka): большое тело не публиковалось.** Producer `BatchBytes` равнялся `producer.batch_size`
  (64 КиБ в дефолте), и segmentio kafka-go отвергал единичное сообщение крупнее него
  (`MessageTooLargeError`) ещё до брокера — хотя топик допускал `topic.max_message_bytes` (10 МиБ).
  `BatchBytes` теперь = `max(producer.batch_size, topic.max_message_bytes)`.
- **Вкладка «Логи» зависала при разворачивании большого тела.** `Get` тянул всё тело, фронт синхронно
  делал `JSON.parse`+`stringify` и рендерил гигантскую строку в `<pre>` — главный поток вставал.

### Added

- **§42 — динамическая подгрузка тел логов.** `Get` отдаёт превью (первые 64K рун, нарезка `substringUTF8`
  в ClickHouse) + полные длины; остаток — срезами по рунам (`GET …/log/{logId}/body`); очень большое —
  потоковым скачиванием файлом (`…/log/{logId}/body/download`). UI: «показать весь» (с предупреждением
  > 2 МБ), «скачать файлом», «копировать»; pretty-print JSON отключается для тел > 256K (убирает фриз).
- **Уточнена подсказка параметра «Ограничить размер тела»** — лимит режет только тело в логе; ответ
  клиенту приходит полностью, checksum считается по полному телу.

### ⚠️ Изменения при апгрейде

- **Миграция БД `0020_node_method_any`** — пересоздаёт CHECK-констрейнты `incoming_method`/

  добавлять руками не обязательно; образец в [config/config.example.yml](config/config.example.yml).
- **Удалён параметр `clickhouse.fallback_dir`** — локальный NDJSON-fallback заменён durable-retry
  через Kafka. Если он оставался в вашем `config.yml`, его можно убрать (теперь игнорируется).
- Миграций БД в этом релизе нет.

### Added

- **§38 — durable-retry проваленных ClickHouse-батчей через Kafka.** При недоступности ClickHouse
  INSERT лог-батча в Sender падает (отправка данных при этом **не** блокируется, §9.4 — падает только
  логирование). Раньше проваленный батч писался в локальный NDJSON-файл; теперь он продьюсится в топик
  `nexus.logs.retry`, а отдельная consumer-group (`<group>-clog-retry`) дренит его обратно в CH после
  восстановления — retry-in-place с экспоненциальным бэкоффом (1с→15с), без рестарта Sender. Реплицируемо,
  без локальных файлов; Kafka нагружается **только** во время простоя CH (сообщение на батч ~100 строк,
  не на запрос) — в норме прямой INSERT как прежде. Спека: [specs/sections/38-clog-retry-kafka.md](specs/sections/38-clog-retry-kafka.md).
- **Новые метрики:** `nexus_clickhouse_fallback_total{op="queued"|"restored"}`,
  `nexus_clickhouse_errors_total{op="insert"|"retry_produce"}`; lag топика `nexus.logs.retry` —
  в `nexus_kafka_lag`.

### Changed

- **Read-path логов в Web мягко деградирует при недоступности ClickHouse** (List/CountFailed/Get/Stream):

- Формат сообщения retry-буфера — `Envelope{table, logs}` с резкой по `max.message.bytes` (`clogwire`).

### Fixed

- **Ложный суффикс `-dirty` в версии при сборке образов на сервере** (`deploy/docker/*.Dockerfile`).
  Перед `git describe --tags --always --dirty` добавлен `git update-index -q --refresh`: после
  `COPY . .` у файлов в Docker-слое новые `mtime`/`inode`, а `git describe` (в отличие от
  `git status`) сам индекс не освежает — и принимал неизменённое дерево за грязное. Из-за этого
  `/api/version` и футер SPA показывали, например, `v1.2.0-dirty` при **чистом** `git status` на
  сервере. Refresh обновляет stat-кэш индекса по содержимому; реальная грязь (изменённое
  содержимое отслеживаемых файлов) по-прежнему корректно даёт `-dirty`. См. DEPLOYMENT.md §9.4.
- CI loadtest: добавлена колонка `node_id` в ClickHouse-таблицу загрузочного теста (§37).

### Removed

    повторяет неудачную async-доставку;
  - `nodes.dlq_retry_delay_seconds` (`NOT NULL DEFAULT 300` = 5 мин) — минимальная пауза перед повтором.
  - Обе с `NOT NULL DEFAULT` → существующие узлы заполняются дефолтами атомарно (backfill не нужен).
- **Новая колонка ClickHouse-логов `node_id` (§37)** — добавляется **автоматически** на старте Web и
  Sender (`ALTER TABLE … ADD COLUMN IF NOT EXISTS node_id String DEFAULT ''`, идемпотентно; новые
  таблицы — из шаблона). Конфиг менять не нужно. Старые записи получают пустой `node_id` (legacy,
  истекают по TTL); per-node разделение метрик/логов вступает в силу на новом трафике.

### Added

- **§36 — авто-репроцессор DLQ.** Фоновый sweeper в Sender повторно доставляет неудачные async-сообщения
  из `nexus.async.dlq` (отдельная consumer-группа `<group>-dlq-reprocess`) до per-node TTL; при
  восстановлении приёмника сообщения уходят автоматически. Уважает circuit breaker, tombstone'ы (§34.4)
  и статус узла. Метрики `nexus_dlq_reprocess_total{node,result}` и `nexus_dlq_reprocess_duration_seconds`.
- **§36.10 — очистка «Неудачных доставок» узла** (`POST /api/nodes/{id}/async-queue/purge-failed`,
  admin): отменяет авто-повтор (qcancel) и удаляет записи `done=0` из CH-логов узла.
- **§36.11 — «Повторить все сейчас»** (`POST .../async-queue/replay-failed`, admin): массовый форс-повтор
  всех неудачных узла через Receiver с отменой оригиналов в DLQ (без двойной доставки).
- **§37 — идентификатор узла в логах** (`node_id`): per-node атрибуция для узлов, делящих одну
  CH-таблицу (счётчики/графики/очистка/replay фильтруют по узлу; `DeleteFailed` не задевает чужие
  записи). Node id выведен во вкладку «Конфиг» узла.
- **§35 — переработка вкладки «Очередь»**: KPI, секции «Ожидают отправки»/«Неудачные доставки»,
  источник из ClickHouse-логов, RBAC.

### Changed

- **§21 — per-node метрики из ClickHouse вместо Prometheus.** Страница узла («Обзор»/«Метрики») и
  throughput рабочего стола (таблица/карточки) считаются по CH-логам узла — точные мгновенные счётчики
  по уникальным запросам, без неточного `increase()` и без мерцания; цифры стола и страницы узла

- Очистка pending-очереди узла доступна в **любом** статусе (не только на паузе).

### Fixed

- **§36 критбаги:** потеря DLQ-сообщения в sweeper'е (seen-break до commit); Sender не читал
  `dlq_ttl`/`dlq_retry_delay` из БД → репроцессор всё дропал как `ttl_dropped`.
- **§35:** peek живой очереди висел ~9с (короткий `MaxWait` у `kafka.Reader`); нестабильный
