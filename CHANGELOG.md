# Changelog

Все заметные изменения в проекте документируются в этом файле.

Формат основан на [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
проект следует [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

> Версионирование ведётся по git-тегам `v*`: версия вшивается в бинарь при сборке через
> `git describe` (см. DEPLOYMENT.md §9). Тег `v*` прогоняет в CI обычные test/lint/build и
> security-сканеры; job `release` был удалён в 1.0.3, GitLab-релиз создаётся вручную
> из раздела CHANGELOG соответствующей версии.
> Первый релиз — `1.0.0`; его записи сгруппированы по фазам разработки до тега.
>
> **Каждый релиз содержит строку «Откат» (§74.6)** — сколько миграций откатывать при
> возврате на предыдущую версию и что при этом теряется:
> `**Откат:** без отката схемы (миграций нет).` либо
> `**Откат:** 4 миграции (0029–0032); down теряет реестр инстансов §73 и сохранённые периоды §71.`
> Значение готовит `python scripts/release/rollback_info.py <от-тега> <до-тега>`. В аварии
> оператору нужно одно число, и считать его по `git ls-tree` в этот момент уже поздно.

## [Unreleased]

### Fixed

- **nginx: пересоздание `web`/`receiver` больше не роняет шину в 502.** Апстримы
  балансировщика объявлены с `server … resolve` — nginx перерезолвивает их адреса
  в рантайме через `resolver` (valid=10s), а не только при старте/reload. Раньше
  `docker compose up -d --build web receiver sender` давал контейнерам новые IP, а
  не тронутый nginx держал прежние → 502 на весь `/api/v1/*`, пока кто-то не
  сделает `nginx -s reload` вручную (для одиночного nginx-профиля rolling.sh нет —
  делать было некому; инцидент kz 24.08.2026). Затронуты `deploy/docker/nginx-upstreams.sh`,
  `scripts/deploy/rolling.sh`, комментарий в `nginx.conf`. **Активируется после
  пересоздания контейнера nginx** — не исключайте его из выката (DEPLOYMENT §5.4).
- **Sender: маскирование логов (§95) само включается при гонке старта с миграцией.**
  Если Sender стартовал раньше, чем web накатил миграцию 0041, `seedLogMasks` падал
  на 42P01 и маскирование молча оставалось выключенным до ручного reload настроек —
  токены писались в логи узлов открытым текстом (инцидент kz 24.08.2026). Теперь при
  неудаче сида запускается фоновый ретрай с backoff (20×3с) — типовая гонка
  закрывается сама за секунды, старт при этом не блокируется.

## [1.32.0] - 2026-08-24

**Откат:** 1 миграция (0041); `down` удаляет справочник шаблонов маскирования логов §95 (`DROP TABLE
log_mask_patterns`). При повторном накате сиды (Telegram, green-api) восстановятся, пользовательские
шаблоны придётся завести заново. Откат НЕ размаскирует уже записанные логи — маскирование
необратимо и применяется на записи, откат лишь выключает механизм для будущих записей.

### Added

- **§95 — маскирование секретов в логах узлов по regex-шаблонам.** При `path_passthrough` (§39)
  секрет приходит от клиента **в пути** и оседал открытым текстом в логе узла ClickHouse: колонка
  `url` = `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, колонка `method` (§39, RequestPath) =
  `bot<ТОКЕН>/getUpdates` (та же беда у green-api). Существующие механизмы этот сток не закрывали:
  `platform/sensitive` маскирует по **именам полей**, `redactURL` — только **query**, маскирование
  nginx (1.31.6) — только **access-лог балансировщика**. Найдено на бою `nexus-kz` (узлы `telegram`,
  `green-whatsapp`).

  Теперь есть справочник **regex-шаблонов (RE2)** в PostgreSQL (миграция `0041_log_mask_patterns`,
  сиды Telegram + green-api), по которым **Sender маскирует колонки `url`/`method`/`parameters` перед
  записью** в ClickHouse. Замена поддерживает **группы** (`$1..$9`), чтобы не терять смысл лога
  (`(bot[0-9]+):[A-Za-z0-9_-]+` → `$1:***` оставляет `bot123456:***`). Маскирование — в **единой
  точке** `chlog.Writer.Write`, до буфера **и** до retry-топика Kafka `nexus.logs.retry` (§38): иначе
  сырой токен утёк бы через retry-путь. Набор шаблонов держит атомарный провайдер, сидится из
  PostgreSQL на старте и **обновляется без рестарта** через новую секцию reload `masking`.

  Управление — «Настройки → **Маскирование логов**» (admin-only): справочник с тумблером «Вкл» и
  диалог с **живым превью** замены (REST `/api/log-masks/*`). Порядок применения — по полю «Порядок».
  Вкладка логов узла не меняется — там отображается уже замаскированное значение.

  **Границы v1:** маскируются только `url`/`method`/`parameters` — тела `request`/`response` вне
  рамок (план на v2); применяется только к **новым** записям (исторические логи не меняются); RE2
  (Go regexp) без backreferences/lookaround. **Не заменяет** маскирование пути в access-логе nginx
  (1.31.6) — это два разных стока (лог узла в ClickHouse пишет Sender; access-лог nginx —
  балансировщик, до Sender'а), секрет проходит оба, нужны оба.

## [1.31.6] - 2026-08-24

**Откат:** без отката схемы (миграций нет). Возврат на 1.31.5 безопасен, но вернёт утечку токена
в access-лог nginx (см. ниже) — откатывать только вместе с откатом nginx-схемы.

### Security

- **Маскировка пути в access-логе nginx не закрывала токен при короткой форме адреса (§78).** Первая
  версия (1.31.2) резала всё после «команда/узел», но на боевом `nexus-kz` команда опущена, и путь
  `/api/v1/telegram/bot<ТОКЕН>/getUpdates` клал токен в позицию «узла» — он оставался в логе
  (`/api/v1/telegram/bot<ТОКЕН>/***`). Плюс многосегментные пути узлов (`green/whatsapp`) ломали
  подсчёт сегментов. Теперь в лог попадает **только первый сегмент** после `/api/v1` (и
  сегмент-метод §78, если есть), всё дальше — `***`. Первый сегмент — всегда команда или узел, не
  секрет, поэтому «куда шёл трафик» видно, а токен не утекает ни при какой форме. Проверено на
  стенде: короткая форма, форма с командой, verb-форма, многосегментный узел — токенов в access-логе
  ноль.

  **Граница (не меняется):** `error_log` формат в nginx не настраивается, поэтому при ошибке
  апстрима (502/connect failed) полный путь с токеном по-прежнему может попасть в stderr. Кому нужен
  нулевой след — `error_log … crit` в своём конфиге ценой потери диагностики «апстрим недоступен».

## [1.31.5] - 2026-08-23

**Откат:** без отката схемы (миграций нет). Возврат на 1.31.4 безопасен.

Только документация — код, образы и compose-файлы не менялись.

### Fixed

- **DEPLOYMENT §5.4.1: предупреждение про healthcheck внешнего прокси перед nginx.** На бою
  `nexus-kz` домен отдавал 503, хотя Nexus был исправен: HAProxy проверял бэкенд запросом
  `option httpchk GET /` **без заголовка Host**. Пока перед Nexus стоял только `web`, такой запрос
  возвращал 200; с nginx впереди он проксируется в `web` по HTTP/1.1, где Host обязателен, Go
  отвечает `400 missing required Host header`, и внешний балансировщик метит бэкенд недоступным.
  Документация теперь требует нацеливать проверку **внешнего** прокси на `/nginx-health` либо слать
  `GET /` с заголовком Host. Сам фикс — host-конфиг HAProxy, вне этого репозитория.

## [1.31.4] - 2026-08-23

**Откат:** без отката схемы (миграций нет). Возврат на 1.31.3 безопасен.

### Changed

- **Сервис `nginx` переехал в корневой `docker-compose.yml`** под `profiles: ["nginx"]` — раньше он
  жил целиком в оверлее `deploy/docker-compose.nginx.yml`. Теперь балансировщик описан там же, где
  остальные сервисы стека, и по умолчанию просто не поднимается.

  **Включение стало из двух частей, и обе обязательны:** `COMPOSE_PROFILES=nginx` активирует сам
  сервис, а оверлей `deploy/docker-compose.nginx.yml` снимает публикацию портов у `web`/`receiver`.
  Разделение вынужденное: профиль решает, поднимать ли сервис, но не меняет поля соседних сервисов,
  а пока nginx активен, порты 8000 и 8080 должны быть свободны. Активировать профиль и забыть
  оверлей — стек не поднимется с «port is already allocated»; это названо в обоих файлах и в
  DEPLOYMENT §5.4.1.

  Для установок без nginx (сервер 4 ГБ) ничего не меняется: без профиля сервис отсутствует в
  проекте, порты у `web`/`receiver` прежние.

## [1.31.3] - 2026-08-23

**Откат:** без отката схемы (миграций нет). Возврат на 1.31.2 безопасен.

### Fixed

- **В журнал отказов §94 попадали успешно обслуженные запросы.** Узел с `path_passthrough` (§39)
  отдаёт клиенту ровно то, чем ответил внешний API, а правило «любой 4xx без явной причины — отказ»
  записывало такой ответ как отказ шины. На бою это дало группы
  `telegram/bot…/editMessageReplyMarkup` и `green/whatsapp/…/getAvatar` с причиной `bad_request`:
  Telegram штатно отвечает `400 message is not modified`, Green API — `400` на неизвестный
  идентификатор. Шина при этом отработала правильно — запрос дошёл, ответ доставлен и целиком
  записан в лог узла. Теперь обработчик помечает проброшенные ответы, и журнал их пропускает; то же
  сделано для статуса из шаблона ответа приёма (§83), который задаёт настройка узла, а не отказ.
  Настоящие отказы (нет узла, 401, 405, 413, 429, 508) не затронуты — проверено тестом, что явная
  причина от обработчика главнее пометки.

  **Уже накопленные ложные записи останутся** — они удаляются кнопкой в карточке группы либо уйдут
  сами по сроку хранения («Настройки → Общие», по умолчанию 30 дней).

### Changed

- **Вкладка «Отказы» стала первой в разделе «Логи» и открывается по умолчанию — всем, включая
  администратора.** На пункте меню горит счётчик непросмотренных отказов, а клик по нему уводил
  администратора на служебные логи: сигнал звал в одно место, а приводил в другое, и требовался
  второй переход. Служебные логи открывают осознанно, отказы — по сигналу.

## [1.31.2] - 2026-08-23

**Откат:** без отката схемы (миграций нет). Возврат на 1.31.1 безопасен.

Патч по трём находкам с боевого сервера после выката 1.31.1. Код сервисов не менялся —
только контекст сборки, конфигурация nginx и профили compose.

### Fixed

- **Версия показывалась как `1.31.1-dirty` при полностью чистом `git status`.** `config/config.yml`
  начал отслеживаться git в 1.31.0, но в `.dockerignore` остался исключённым — внутри
  builder-стейджа файла нет, и `git describe --dirty` принимает это за грязное дерево.
  `git update-index --refresh` не помогает: файл реально отсутствует. Тот же класс, что уже
  описан там для `.env.example` и `.vscode/*.json`. В финальный образ файл по-прежнему не
  попадает, секретов в нём нет (плейсхолдеры `${PG_PASSWORD}` и т. п.).
- **Токен Telegram-бота светился в access-логе nginx целиком** —
  `POST /api/v1/messengers/telegram/bot<ТОКЕН>/getUpdates`. Секрет лежит в пути, а не в query,
  поэтому путь боевого запроса теперь режется после «команда/узел»:
  `/api/v1/<команда>/<узел>/***`. Диагностика не страдает — видно узел, статус, время и какая
  реплика ответила. **Границы названы в конфиге:** обрезка не действует на `error_log` (там
  формат не настраивается, и при отказе апстрима полный путь попадает в stderr) и не скрывает
  первые два сегмента.
- **Docker печатал `Your kernel does not support swap limit capabilities` на каждую сборку.** На
  ядре без `swapaccount=1` это выдаётся для любого контейнера с `mem_limit`, а им был только
  nginx. Потолок вынесен в `NGINX_MEM_LIMIT` с дефолтом `0` — не задавать; нужен лимит,
  ставится `NGINX_MEM_LIMIT=64m` в `.env`.

## [1.31.1] - 2026-08-23

**Откат:** без отката схемы (миграций нет). Возврат на 1.31.0 безопасен.

Инфраструктурный релиз: ни строчки кода сервисов не изменилось, только профили развёртывания
и документация. Появился **промежуточный шаг к §93** — nginx перед прежним одиночным стеком,
без пар реплик и без роста памяти.

### Added

- **`deploy/docker-compose.nginx.yml` — nginx перед ОДИНОЧНЫМИ `web` и `receiver`.** Схема входа
  становится такой же, как в §93 (боевой `/api/v1/*` идёт сразу в Receiver, минуя Web; заголовки
  с подчёркиванием и крупные JWT не теряются), но реплики по-прежнему по одной, а расход растёт
  на 64 МБ. Обновление — обычное `docker compose up -d --build`, без `rolling.sh`. Когда сервер
  будет готов к двум репликам, меняется только подключаемый файл: `ha.yml` вместо этого.
- **Шаблоны локальных override под полный профиль §93** — `deploy/docker-compose.ha.standalone.override.yml`
  (ClickHouse в стеке, loopback-порты, урезанные под 4 ГБ потолки) и
  `deploy/docker-compose.ha.external-pg.override.yml` (внешний PostgreSQL). Без второго стек с
  внешней базой **не собирается вообще**: `service "sender-2" depends on undefined service "postgres"`.

### Changed

- **Корневой `docker-compose.yml`: привязка портов `web` и `receiver` вынесена в `WEB_BIND` /
  `RECEIVER_BIND`.** Дефолты прежние (`0.0.0.0`), поведение существующих установок не меняется.
- **CI: таймаут `integration` 35 → 50 минут** (`go test` 30m → 45m). На теге 1.31.0 job упал по
  таймауту, но перезапуск того же коммита прошёл за 1157 с против 1453 с на 1.30.1 — то есть дело
  было в выбросе раннера, а не в объёме тестов. Запас нужен, чтобы такой выброс не ронял тег.

### Fixed

- **DEPLOYMENT: локальные `docker-compose.override.yml` при переходе на §93 ломаются молча.**
  Секции для `web`/`receiver`/`sender` применяются к сервисам, отключённым профилем, и лимиты
  памяти, привязки портов и `depends_on` уходят в никуда. Отдельно: при ЯВНЫХ `-f` корневой
  override **не подхватывается вовсе** — из проекта пропадает ClickHouse вместе с loopback-привязками.
  Описано в §5.5.2-a вместе с расчётом памяти перед переходом.

## [1.31.0] - 2026-08-21

**Откат:** 1 миграция (`0040`); down удаляет журнал отказов §94 целиком (группы, клиенты, сэмплы).
Аддитивная — откат кода без отката схемы безопасен. **Но:** если стек уже переведён на две реплики
за nginx (§93), возврат к 1.30.x — это и возврат к одиночному стеку, см. «Откат к одиночному стеку»
в DEPLOYMENT §5.5.2-a.

> ⚠️ **Меняется схема развёртывания.** Появился профиль двух реплик за nginx; переход с одиночного
> стека — разовая процедура с окном недоступности в десятки секунд (DEPLOYMENT §5.5.2-a). Оставаться
> на одиночном стеке можно: оверлей подключается вторым `-f` и по умолчанию не активен.

### Added

- **§93 — развёртывание без простоя: по две реплики Web, Receiver и Sender за nginx.** Обновление
  перестаёт быть простоем: `scripts/deploy/rolling.sh` выводит реплики из ротации по одной.
  Боевой `/api/v1/*` уходит из nginx СРАЗУ в Receiver, минуя Web. Появились: оверлей
  `deploy/docker-compose.ha.yml`, образ nginx, секция `shutdown` (дренаж по SIGTERM), балансировка
  gRPC (round-robin + health), Redis-локи периодических задач, аренда pull-узлов §27, имя реплики в
  консоли логов и теге Sentry, шесть таргетов Prometheus и алерт «живых реплик меньше двух».
  Зависимости (PostgreSQL, Redis, Kafka, ClickHouse) остаются одиночными — что НЕ закрывается,
  перечислено в DEPLOYMENT §5.5.6.
- **§92 — кнопка «По умолчанию» на всех экранах с периодом**: сквозной режим «Все команды», вкладки
  узла «Обзор»/«Очередь», монитор Kafka. Новых таблиц и эндпоинтов нет — хранилище префов §71
  универсальное.

- **§94 — журнал отказов на входе, «Логи → Отказы».** Клиенты, которым шина отказала (нет узла,
  метод не разрешён, авторизация, лимиты, петля), больше не невидимы: группа
  `(команда, путь, причина, метод)` с IP, PTR и User-Agent, последними 20 запросами и подсказкой
  похожего узла. Раньше следов не оставалось вовсе — лог узла живёт в таблице УЗЛА, которого нет,
  а `nexus_requests_total` не знает клиента.
- **Срок хранения отказов** — «Настройки → Общие», 0…365 дней (по умолчанию 30). `0` выключает сбор
  и удаляет накопленное; уменьшение срока применяется сразу, без рестарта.
- **Секция `receiver.reject_log`** (`disabled`, `flush_interval_sec`, `queue_size`) — темп сброса и
  аварийный стоп на уровне процесса. Без секции работают дефолты.
- **Метрики** `nexus_ingress_rejected_total{reason,status}` и
  `nexus_ingress_reject_dropped_total{cause}`.

### Changed

- **`receiver.max_async_body_bytes` возвращён к 10 МиБ** (в 1.30.0 было 32 МиБ). Async-тело едет в
  Kafka в base64-конверте (+33 %), а брокерский потолок боевого стека — 16 МиБ: 32 МиБ туда не
  помещались физически, и запрос отвергался уже ПОСЛЕ приёма. Sync-лимит не менялся — 124 МиБ.
  Полная таблица лимитов — в описании релиза и в шапке `config/config.example.yml`.
- **Метка `node` у `nexus_requests_total` при 404 несуществующего узла — `<unresolved>`** вместо

- **Почта (SMTP) и восстановление пароля** (§88). Пользователь, забывший пароль, задаёт
  новый сам по ссылке из письма — вместо того чтобы идти к администратору.

  Причина: сменить пароль до сих пор можно было только двумя способами, и оба требуют
  того, чего у забывшего человека нет, — админских прав либо знания текущего пароля.
  На боевой установке это десятки человек в двенадцати командах, и каждый случай
  оборачивался ручной выдачей временного пароля в мессенджере. Почтового канала у шины
  при этом не было вовсе: единственным внешним каналом оставался Telegram (§20), а
  колонка `users.email` заполнялась администратором и нигде, кроме поиска, не
  использовалась.

  **Настройки → Почта** (admin): адрес и порт релея, режим шифрования (нет / STARTTLS /
  SSL-TLS), способ аутентификации (нет / PLAIN / LOGIN / CRAM-MD5), учётные данные,
  отправитель, таймаут, имя в HELO/EHLO и кнопка **«Отправить тестовое письмо»**.
  Хранится в БД (`app_settings`), применяется на всех инстансах без перезапуска.

  **Восстановление**: ссылка «Забыли пароль?» на форме входа → диалог с логином или
  email → письмо со ссылкой → страница задания нового пароля. Ссылка живёт заданное
  время (по умолчанию 60 минут) и срабатывает один раз; смена пароля завершает все
  сессии пользователя и аннулирует ранее отправленные ссылки.

  Что важно знать эксплуатации:

  - **Форма отвечает одинаково при любом исходе** — «если такой пользователь есть и у
    него указан email, письмо отправлено». Иначе публичная страница входа стала бы
    справочником существующих логинов и почтовых адресов. Настоящая причина (нет
    пользователя, нет email, учётка отключена, адрес неоднозначен, превышен предел
    активных ссылок) видна администратору в разделе **Аудит**.
  - **Письмо уходит фоном**, поэтому пользователь не узнает о сбое отправки: время
    ответа не должно выдавать существование учётной записи. Сбой виден в аудите
    (`result: send_failed`), в служебном логе уровня `error` (значит и в Sentry) и в
    метриках `nexus_mail_send_total` / `nexus_password_reset_requests_total`. Проверять
    настройки следует кнопкой тестового письма — она отвечает синхронно и внятно.
  - **Требуется публичный адрес приложения** (Настройки → Общие): без него ссылка в
    письме собирается без хоста. В этом случае «Забыли пароль?» на форме входа не
    появляется, а экран почты предупреждает об этом.
  - **Email обязательным не стал.** У кого он не заполнен — восстановление недоступно;
    такие пользователи помечены в списке `Настройки → Пользователи`.
  - Частота запросов ограничена ключом `web.password_reset_rate_limit_per_min`
    (по умолчанию 5). При недоступном Redis ограничение, как и остальные в шине,
    деградирует в пропуск.

- **Роль доступа «Оператор»** (§87). Четвёртая роль UI между «Только просмотр» и «Управление
  узлами» — для дежурного, который разбирает затор, но не должен трогать конфигурацию.

  Причина: разгрести очередь узла, переотправить провалившиеся запросы, притормозить
  захлёбывающийся узел и снять открытый breaker до сих пор требовало роли «Управление узлами»
  (§35.5, §85.9). А эта роль — заодно право переписать адрес доставки, креды и авторизацию
  узла. То есть чтобы дать человеку разгребать очередь, ему выдавали право сломать
  маршрутизацию.

  **Оператор может:** вкладку «Очередь» целиком (просмотр, удаление сообщения, очистка за
  период и полная, очистка неудачных доставок, «Повторить все сейчас»), пауза / отключение /
  включение узла, сброс circuit breaker (§81.4), повтор запроса из логов — одиночный (§7.4.1)
  и за период (§85), — чтение журнала действий.

  **Оператор не может:** создавать, изменять, удалять и копировать узлы, запускать dry-run,
  синхронизировать схему ClickHouse, править каталоги разрешённых хостов и заголовков, а также
  всё, что закрыто от роли «Управление узлами» (пользователи, команды, общие настройки).

  Иерархия прав стала `Только просмотр < Оператор < Управление узлами < Полный доступ`.
  Существующие роли не затронуты: возможности оператора — строгое подмножество менеджерских,
  поэтому проверки доступа остались прежними (`AtLeast`), а живые сессии пережили обновление
  без разлогина. В диалоге пользователя роли теперь показываются сеткой 2×2 (в один ряд
  четыре карточки не помещаются), в таблице у роли янтарный чип.

  **Порядок обновления:** миграция 0035 → Web. Receiver и Sender роль UI не читают и обновления
  не требуют.

- **Фильтр по статусу в режиме «Все команды» переставал работать после смены периода** (§86.4).
  Симптом: выбран статус «OK», оператор переключает период — и список пустеет насовсем
  («Узлов пока нет»), хотя счётчики шапки показывают трафик; помогала только перезагрузка
  страницы со сброшенным фильтром.

  Корень — замкнутый круг, внесённый порционной загрузкой метрик. Статус узла ВЫВОДИТСЯ ИЗ
  МЕТРИК, а метрики в сквозном режиме считаются только для строк, попавших в поле зрения. Смена

  нет → ничего не становится видимым → метрики не запрашиваются. Круг не размыкается сам: нужен
  рендер, чтобы пришли данные, и данные, чтобы случился рендер.

  Починка признаёт природу фильтра: чтобы ответить «какие узлы сейчас OK», надо посчитать ВСЕ
  узлы-кандидаты, а не только видимые. Метрики догружаются целиком, когда выбран статус,
  выводимый из метрик; «Пауза» и «Отключён» берутся из конфигурации узла и догрузки не требуют.
  Порционность при этом сохранена: досыл идёт через тот же механизм, что и прокрутка, пачки
  остаются заморожёнными, уже запрошенное не перезапрашивается.

- **Честное пустое состояние.** Пока метрики отфильтрованных узлов не досчитаны, показывается
  «Загрузка», а не «Узлов пока нет»: прежнее сообщение утверждало, что узлов с таким статусом не
  существует, хотя их просто ещё не посчитали. То же короткое окно есть и в режиме одной команды.

## §86 — сквозной просмотр узлов всех команд

### Added

- **Пункт «Все команды» в переключателе команд** — раздел ТЗ
  [§86](specs/sections/86-all-teams-scope.md). Показывает узлы всех команд пользователя одним
  списком, с метриками каждого узла, в обоих представлениях рабочего стола (таблица и карточки).
  Повод: на боевой установке двенадцать команд, а экран показывал ровно одну — окинуть взглядом
  всё хозяйство было нечем, единственным кросс-командным чтением оставался глобальный поиск §62
  (подстрока, до 50 строк, без метрик).

  **Это РЕЖИМ ПРОСМОТРА, а не команда.** Сессионная `current_team_id` при входе в режим не
  меняется и продолжает обслуживать всё остальное приложение. Причина — цена альтернативы:
  `currentTeamID(c)` читают около девяноста мест, и специальное значение в сессии потребовало бы
  от каждого уметь «команда не выбрана», включая все мутации, которым писать было бы некуда.

  Множество — **членства пользователя**, а не все команды инстанса; роль (`viewer`/`manager`/
  `admin`) видимость не расширяет (no-leak, как §62.3 и §76.5). Членства резолвятся на КАЖДЫЙ
  запрос, то есть строже действующего сессионного скоупа §18.3, который переживает исключение из
  команды до самолечения §18.9.

- **`scope=all` на `/api/nodes`, `/api/metrics/nodes`, `/api/metrics/totals` и `/api/audit`**
  (плюс `/api/audit/export.csv` — выгрузка повторяет скоуп экрана). Только session-cookie:
  API-токен закреплён за одной командой, сквозная выдача ему даёт **403**. Отдельно от
  существующего `?team_id=*` аудита: тот означает «все команды ИНСТАНСА» и доступен только
  `admin`, новый — «все МОИ команды».

- **Избранное для пункта «Все команды»** — звезда в переключателе, первым пунктом в секции
  «Избранное» сайдбара. Хранится в generic-префах §71 (ключ `teams.favorite_all`), а не в
  `user_team_favorites`: у той составной внешний ключ на `user_teams`, и псевдо-идентификатора
  режима туда не вставить. **Миграции не потребовалось.**

- **Команда узла выбирается явно при создании** — поле `team_id` в `POST /api/nodes` и селект на
  форме. До §86 команда наследовалась молча из сессии, а в сквозном режиме такой команды нет
  вовсе. Поле необязательное (пусто → команда сессии), поэтому существующие клиенты и API-токены
  не ломаются; команда вне членств → 403. Префикс БД ClickHouse в поле «Таблица логов» следует за
  выбором: `normalizeCHTable` дописывает БД только к именам без префикса, а явно указанный чужой
  сохраняет — узел одной команды начал бы писать логи в БД другой.

### Fixed

- **Утечка в Prometheus-ветке рабочего стола.** Fallback без ClickHouse строил строки из ответа
  Prometheus, а у его метки команды нет (`node = <path>`) — то есть рабочий стол без ClickHouse
  показывал пути узлов **всех** команд инстанса. Теперь строки строятся по узлам скоупа. Два
  следствия: узел без трафика получает строку с нулями (как в CH-ветке), а «сирота» — трафик по
  пути без узла в конфигурации — остаётся предметом диагностики §44.E.

- **Совпадение путей между командами больше не показывает чужой исход.** Бейдж последнего вызова
  читается из Redis по ключу `nexus:node:last_error:<path>` — без команды, и метка Prometheus
  тоже. Путь уникален лишь внутри команды, поэтому у двух одноимённых узлов значение общее. В
  сквозном режиме такие узлы показываются как «неизвестно» (правило §84.7 «неизвестное не красить
  в ok»). Числа и спарклайн не задеты: они из ClickHouse по `node_id`.

### Performance

- **Метрики грузятся порционно**, только для узлов в поле зрения, пачками; KPI-шапка считается
  отдельным запросом (`/api/metrics/totals`) с кешем и `singleflight`, обновляется в четыре раза
  реже строк. Границы окна в ключе кеша квантуются по TTL — у скользящего окна правая граница это
  «сейчас», и без квантования кеш не срабатывал бы никогда.

- **Порядок строк в сквозном режиме стабильный** (команда, затем путь): сортировка «проблемные
  первыми» опирается на метрики, а они приходят порциями — каждая досчитанная пачка переставляла
  бы строки под курсором. В режиме одной команды порядок прежний.

- **Замер на бою до написания кода** (§86.4.1) отменил два запланированных приёма: батч
  `GROUP BY node_id` бесполезен (34 узла на 33 различные таблицы), а принудительный
  приблизительный подсчёт не нужен — всё хозяйство за период по умолчанию считается около
  секунды. Заодно выяснилось, что стоимость определяется объёмом данных, а не числом узлов.

## §85 — повторная отправка запросов из логов за период

### Added

- **Повторная отправка async-запросов из логов за период** — раздел ТЗ
  [§85](specs/sections/85-replay-from-logs.md), кнопка и диалог на вкладке «Логи» узла.
  Боевой повод: приёмник отвечал `200`, запись получала `done=1`, очередь очищалась — но из-за
  собственного дефекта запросы он не обрабатывал; после починки понадобилось переотправить всё за
  период, **включая успешно доставленное**. Ни один существующий механизм не подходил: все три
  построены вокруг НЕУДАЧИ (одиночный replay §7.4.1 — по одной записи, «Повторить все» §36.11
  берёт нерешённые, авто-репроцессор §36 видит только DLQ).

  Набор задаётся периодом плюс теми же фильтрами журнала (подпуть, полнотекст §48, OK/Ошибки
  §72.1), собранными тем же модулем — свой язык фильтрации развёл бы предпросмотр и отправку.
  Предпросмотр показывает два множества с разбивкой по причинам непригодности
  (`record_not_async`, `body_multipart`, `body_truncated`, `body_missing`, `already_replay`).

  Защита от самоусиления: границы окна фиксируются на предпросмотре (иначе «по сейчас» затягивает
  в набор собственные повторы), записи с `__replay_of` исключаются по умолчанию. `manager+`,
  только session-cookie, аудит `node.replay_period` на КАЖДЫЙ батч — прогон обрывается закрытием
  вкладки, и след обязан остаться от того, что успело уйти.

- **Ключ конфигурации `web.replay_period_rate_limit_per_user_per_min`** (дефолт 60): общий лимит
  одиночного повтора 10/мин остановил бы цикл батчей на десятом.

### Fixed

- **Идентификатор записи после повтора берётся из ответа шины, а не выдумывается.**
  `ReplayResult.NewLogID` заполнялся `uuid.NewString()` — значение выглядело как идентификатор
  новой записи, но не было связано ни с чем: диалог показывал его оператору, а аудит `node.replay`
  ссылался на несуществующую запись. Теперь источников два и порядок между ними значим: заголовок
  `X-Nexus-Id` → тело штатного async-ответа. Тело **sync**-ответа не разбирается никогда — это
  ответ приёмника, и его собственное поле `id` (заказ, документ) уехало бы в аудит как
  идентификатор записи журнала.

## §83 — шаблон ответа приёма

### Added

- **Шаблон ответа приёма (ack) для async-узлов** — раздел ТЗ
  [§83](specs/sections/83-async-ack-template.md). Узел декларативно описывает, чем шина отвечает
  клиенту на успешный приём запроса в очередь, вместо жёсткого `{"result":true,"id":"<uuid>"}`.
  Причина: клиенты с курсором (СКУД `acs_sigur`, callback-провайдеры) двигают свой указатель только
  по эхо-подтверждению из собственного тела — `acs_sigur` ждёт `{"confirmedLogId": <max logId>}` и
  без него шлёт тот же пакет бесконечно. §82.4 вынес это «вне шины» для sync-режима справедливо, но
  в async отвечает сама шина — §83 эту границу пересматривает.

  Спека хранится в новой JSONB-колонке `nodes.async_ack_spec` (`NULL` = «отвечать как раньше», то
  есть существующие узлы не затронуты). Язык подстановок — свой мини-DSL без внешних зависимостей:
  `${ body.logs[*].logId | max }`, источники `body`/`query`/`path`/`nexus`, функции
  `max`/`min`/`first`/`last`/`count`/`default(x)`. Числа возвращаются числами (курсоры журналов
  выходят за 2^53, и `float64` их портит). **Заголовки запроса источником не являются** — там
  `Authorization`; тело и query приходят в шаблон после вырезания кред.

  Применяется к async-приёму (200), к 202 узла на паузе (§3.6) и к callback (§16); к **ошибкам
  приёма — никогда**. При провале подстановки узел либо отвечает как раньше (запрос принят, растёт
  `nexus_async_ack_render_failed_total`), либо возвращает 400 и не принимает запрос — рендер идёт до
  публикации в Kafka, поэтому отказ честен.

- **Предпросмотр ответа и подробная справка в форме узла.** `POST /api/nodes/ack-preview`
  (manager+) прогоняет шаблон на образце запроса и показывает точный ответ ещё до сохранения узла;
  кнопка «Взять последний запрос из логов» подставляет реальное тело. Справка из 12 разделов с
  кликабельными рабочими примерами открывается иконкой «?» в карточке.

### Changed

- **Узел, переведённый обратно в sync, накопленную очередь больше не доставляет** (§83.5). Раньше
  доставлял: `root_method` не проверялся ни consumer'ом, ни репроцессором DLQ, и настройка узла на
  судьбу уже принятых сообщений не влияла. Теперь такие сообщения уходят в DLQ с
  `reason="node_not_async root_method=<текущий>"` и доставляются сами, если узел вернуть в async в
  пределах `dlq_ttl_seconds`. Сообщения, попавшие в очередь по §3.6 (узел был на паузе),
  доставляются как прежде — их различает новое поле конверта `ingress_method`; конверты, принятые до
  этой версии, доставляются без изменений.

### Fixed

- **Вырезание креды из тела больше не искажает остальные значения** (§83.2). У узлов с
  `auth_dynamic_source=body` тело пересобиралось через `float64`, и **получателю** уходило
  испорченное: `9007199254740993` → `9007199254740992`, `<a>&b` → `\u003ca\u003e\u0026b`,
  `1.50` → `1.5`. Дефект действующий, найден при проектировании §83.

### Как перевести боевой узел `acs_sigur` на async

Пошагово, с проверкой на каждом шаге. Порядок важен: сначала ответ, потом режим — иначе между
переключением и настройкой шаблона клиент получит ответ, которого не понимает.

1. **Убедиться, что доставка идёт.** Узел → вкладка «Очередь»: «Неудачные доставки» пусты либо
   разобраны. Включённый шаблон подтверждает клиенту ПРИЁМ, а не доставку, — начинать с непустой
   очереди неудач нельзя.
2. **Настроить ответ, не меняя режим.** Форма узла → карточка «Ответ при постановке в очередь» →
   «Включить». Формат `application/json`, HTTP-код «как сейчас», при ошибке — «ответить как раньше».
   Шаблон:

   ```json
   {"confirmedLogId": "${ body.logs[*].logId | max }"}
   ```

   (его же кладёт кнопка «Использовать» в справке, раздел «Готовые примеры»).
3. **Проверить на реальном теле.** Кнопка «Взять последний запрос из логов» → «Проверить». Ожидаемо:
   `200 · application/json` и `{"confirmedLogId": <число>}`. Число — именно число, без кавычек.
   Сохранить узел. На sync-узле шаблон пока не работает — это нормально.
4. **Переключить режим** на `requestAsync` и сохранить. **Адрес клиента менять не надо**: короткая
   форма `/api/v1/webhook/acs_sigur` (§78.1) разводит вызов по типу узла сама. Клиенты, ходящие на
   длинный `/api/v1/requestAsync/…`, продолжат работать; ходящие на длинный `/api/v1/request/…`
   получат 404 — их адрес нужно заменить на короткую форму.
5. **Убедиться, что указатель поехал.** В течение 1–2 минут: журнал узла — новые записи с растущим
   `logId`, размер пакета падает до единиц записей; со стороны СКУД — очередь выгрузки уменьшается.
   Проверить `nexus_async_ack_render_failed_total{node="acs_sigur"}` — должен остаться нулём.
6. **Если клиент продолжает слать дубли** — вернуть `root_method=request`. Спека при этом
   сохраняется и заработает снова при возврате в async; накопленная очередь доставлена не будет
   (уйдёт в DLQ, откуда вернётся сама при обратном переключении).

## §82 — потолок sync-вызова и гейт async-входа

Раздел ТЗ [§82](specs/sections/82-sync-ceiling-and-async-ingress.md) — продолжение разбора
`acs_sigur` от 06.08.2026. §81 остановился на выводе «соединение рвёт инфраструктура перед шиной»:
вывод верный, но **неполный** — внешний фронт срабатывал первым и прятал собственный потолок Nexus.
Оба дефекта ниже воспроизведены на локальном стенде, где никакой инфраструктуры перед шиной нет.


### Fixed

- **Синхронный запрос больше не обрывается на середине из-за keepalive gRPC** (§82.1). gRPC-сервер
  Sender'а не объявлял enforcement-политику, поэтому действовал дефолт grpc-go: допустимый интервал
  между keepalive-ping'ами клиента — 5 минут, тогда как Receiver и Web пингуют каждые 30 секунд.
  Каждый ping считался нарушением, на третьем сервер закрывал **соединение целиком** вместе с идущим
  по нему вызовом. Потолок = `4 × keepalive_time_sec`, и `timeout_ms` узла на него не влиял: замеры
  на стенде при узле `timeout_ms=600000` и приёмнике, отвечающем за 300 секунд, — обрыв на **121 с**
  напрямую в Receiver и на **91 с** через Web. Потолок плавающий, потому что ping-таймер привязан к
  соединению пула, а не к запросу, поэтому запрос длиннее ~30 секунд мог оборваться в произвольный
  момент. Асинхронная доставка затронута не была — отсюда боевая картина, где async того же узла
  доставлял за 145–155 секунд, а sync не доходил ни разу. Теперь `timeout_ms` узла — единственный
  предел длительности синхронного вызова внутри шины.
- **`client_canceled` в журнале больше не обвиняет клиента** (§82.2). Маркер ставится на любую
  смерть родительского контекста — не только на уход вызывающей стороны, но и на штатную остановку
  сервиса и на обрыв транспорта между Receiver'ом и Sender'ом. Именно эта подмена увела разбор во
  внешнюю инфраструктуру больше чем на сутки. Отдельный маркер не вводится (признак пришлось бы
  тянуть через gRPC-запрос ради случая, который после §82.1 почти не встречается) — вместо него
  контракт сказан честно и назван способ различить исходы на стороне Receiver'а.

### Changed

- **ЛОМАЮЩЕЕ: `/api/v1/requestAsync/<путь>` теперь требует узел с `root_method = requestAsync`**
  (§82.3). Раньше проверки не было вовсе: послабление делалось ради §3.6 (узел на паузе копит
  запросы в очереди), но выдавалось безусловно — то есть наружу, и настройка узла `request` не
  значила ничего. Боевое следствие: узел `acs_sigur` принимал ~11 async-запросов в минуту от
  клиента, застрявшего на одной записи журнала больше суток — тот ждал ответ приёмника, а получал
  мгновенное подтверждение приёма шиной и не сдвигался никогда (~1,5 млн повторных записей в 1С за
  сутки), и отбить его настройкой узла было нечем. Теперь такой запрос получает
  `404 node not found` — существование узла наружу не раскрывается; для диагностики есть warn с
  `root_method` и IP клиента и метрика `nexus_async_ingress_rejected_total{node}`.
  **Перед обновлением** найдите узлы с `root_method = request`, у которых в логах есть записи
  `type = requestAsync`, и переведите их клиентов на синхронный адрес. Не затронуты:
  `/api/v1/callback/…` (§16) и узлы на паузе (§3.6) — sync-запрос к ним по-прежнему отвечает
  `202 queued`. Побочно закрыт приём push-запросов узлом `RabbitMQAsync`, у которого входящего HTTP
  нет вовсе.

### Added

- Секция конфигурации `sender.grpc_keepalive` (`enforcement_min_time_sec`,
  `deny_ping_without_stream`) с проверкой на старте, что политика не строже клиентских
  `keepalive_time_sec` — рассинхронизацию этих значений по симптому не вычислить.
- Метрика `nexus_async_ingress_rejected_total{node}`.

## §81 — circuit breaker

Раздел ТЗ [§81](specs/sections/81-breaker-manual-reset.md) — из боевого инцидента 06.08.2026 на узле
`acs_sigur` (команда `webhook`): шина перестала доставлять к **исправному** приёмнику и не вышла из
этого состояния сама. За окно 09:14–09:53 из 71 синхронного вызова успешных — **ноль**, 65 обрывов
ровно по 50 000 мс; параллельно 313 async-сообщений ушли в DLQ без единого сетевого вызова.

### Fixed

- **Обрыв соединения вызывающей стороной больше не считается отказом приёмника** (§81.2). Приёмник
  отвечал 200 за 145 секунд, соединение рвал элемент инфраструктуры перед шиной на 50-й секунде — а
  учёт здоровья узла засчитывал это отказом приёмника. Пять обрывов подряд открывали защиту, и
  выйти из состояния было нельзя: пробный запрос обрывался ровно так же. Введён трёхзначный вердикт:
  уход вызывающей стороны — **воздержание**, защита не трогается ни в одну сторону. Различает не
  текст ошибки, а живость родительского контекста.
- **Ключ защиты общий для sync и async**, поэтому обрывы синхронного трафика душили асинхронную
  доставку того же узла (313 сообщений в DLQ с `attempts=0`). Следствие исправления выше.
- **Учёт исхода выполнялся на уже отменённом контексте** и молча не доезжал до Redis: клиент
  отбрасывает такую команду ещё в пуле соединений, а ошибка гасилась. Записи учёта и персистентного
  статуса узла отвязаны от контекста запроса.

### Added

- **Карточка «Защита узла» на вкладке «Очередь»** (§81.4): состояние, счётчик отказов, обратный
  отсчёт до пробного запроса и кнопка **«Снять защиту»**. Раньше причину было видно только в тексте
  отдельной записи журнала, а снять блокировку — никак: оставалось ждать, пока протухнет состояние.
  Состояние видят все роли, снимает защиту `manager+`; действие пишется в аудит
  (`node.breaker_reset`). Тем же действием снимается бейдж «Down» узла.
- **Порог отказов и пауза до пробы настраиваются** (§81.3): глобально —
  `sender.circuit_breaker.{threshold,cooldown_sec}`, на узле — поля в блоке «Таймауты и повторы»
  (пусто = «как в конфигурации»). Прежде это были литералы в коде: для медленного, но живого
  приёмника пять таймаутов подряд уводили весь его поток в DLQ.
- `GET /api/nodes/{id}/breaker` и `POST /api/nodes/{id}/breaker/reset`.

### Changed

- **Стабильные маркеры причин в журнале** (§81.2.1): `client_canceled: …` и `upstream_timeout: …`
  вместо сырого текста ошибки. Прежний текст нельзя было отфильтровать и он **содержал полный адрес
  узла** — у узлов с динамическим URL хвост собран из входящего запроса. Историю это не меняет;
  внешние алерты, ищущие `context canceled`, надо перевести на `client_canceled`.
- **«Повторить все сейчас» пропускает записи, отменённые вызывающей стороной** (§81.5): приёмник
  тело принял целиком и, вероятно, обработал — повтор дал бы дубли (в §79 так ушло 15 дублей в 1С).
  Записи остаются видимыми в «Неудачных доставках», число пропущенных показывается отдельно,
  точечный повтор из строки журнала по-прежнему доступен.

### Deployment

- **Порядок выката: Receiver → Sender → Web.** Sender не применяет миграции автоматически при
  старте (это делают `receiver` и `web`), а новый Sender запрашивает колонки 0033 при каждом чтении узла — выкатив его первым,
  вы остановите async-доставку до обновления Receiver'а. Совместимость протокола обратный порядок
  не нарушает: старый Sender новые поля gRPC-запроса игнорирует и работает по глобальной политике.
- Два новых ключа `config.yml` (значения совпадают с прежними захардкоженными — поведение не
  меняется):
  ```yaml
  sender:
    circuit_breaker:
      threshold: 5
      cooldown_sec: 30
  ```
- Узел, чью защиту открывали нетерпеливые клиенты, после обновления начнёт доставлять — убедитесь,
  что приёмник к этому готов.

### Added

- **Короткий адрес узла — без сегмента `request`/`requestAsync`** (§78.1). Узел доступен по

  **Старые адреса (`/api/v1/request/…`, `/api/v1/requestAsync/…`, `/api/v1/callback/…`) работают
  без ограничения срока и с прежней семантикой** — выданные внешним системам URL менять не нужно.
- **Карточка «Конфиг» узла показывает оба адреса** (§78.5): короткий — основным, классический —
  строкой ниже, у каждого своя кнопка копирования.

### Fixed

- **«Показано 17 из 40» в логах узла: счётчик и список считали разные единицы** (§78.6). Строка в
  ClickHouse — это ПРОГОН доставки: повторная доставка (redelivery Kafka, DLQ-репроцессор §36,
  `ttl_expired`, replay, дренаж retry-топика §38) пишет свою строку с тем же `ID`, а внутренние
  ретраи одного прогона схлопнуты в `attempts`. Счётчик считал строки, список — записи, и
  «недостающие» записи было не открыть: скролл честно сообщал, что история кончилась.
  Теперь единица одна во всём чтении логов — **запись**: `Count`/`CountFailed` считают уникальные
  `ID`, страница отдаёт по одной (свежайшей) попытке на запись. Как следствие, KPI «неудачные
  доставки» сошёлся со своим списком и с числом отменяемых сообщений — видимое «очищено N» больше
  не расходится с `cancelled` в аудите. Live-tail и порог Telegram-уведомлений (§20.3) намеренно
  продолжают считать прогоны.

### Changed

- **Маршруты шины объединены в один** (§78.2). Три маршрута Receiver (`request`/`requestAsync`/
  `callback`) заменены одним `/api/v1/*path` с разбором первого сегмента в обработчике: иначе
  короткий адрес не зарегистрировать — gin падает при старте, если catch-all соседствует с занятым
  сегментом. Web проксирует `/api/v1/*` одним маршрутом. Метки Prometheus `method="request"` и
  `"requestAsync"` сохранены (на них стоят дашборд Kafka и алерт латентности); добавились
  `callback` (раньше метился именем маршрута) и `route` (обращения по короткому адресу, для
  которых узел не найден). Ключ rate-limit не зависит от формы адреса — обе формы делят квоту.
- **Не-POST запрос на `/api/v1/callback/…` отвечает `405 Method Not Allowed`** вместо прежнего
  `404 not found`; неизвестный путь под `/api/v1/…` отвечает ответом Receiver
  (`{"error":"node not found"}`), а не SPA-фолбэка Web (`{"error":"not found"}`). Если мониторинг
  различает эти коды или тела — поправьте его.
- **Слоги команд `request`, `requestasync`, `callback` запрещены при создании** (§78.3): они
  сделали бы короткий адрес неоднозначным. Уже существующие команды с такими слогами не ломаются
  (их узлы остаются доступны по классическому адресу), переименование им тоже не запрещено.
  Проверить боевые данные перед выкатом: `SELECT slug FROM teams WHERE lower(slug) IN
  ('request','requestasync','callback');`
- **Защита от зацикливания (§32.2) распознаёт короткий адрес** (§78.4): узел, чей `target_url`
  ведёт на собственный `/api/v1/<команда>/<путь>`, отклоняется при сохранении — иначе проверка
  молча пропускала бы новую форму.
- **Проброс параметров при смене метода зафиксирован контрактом и тестом** (§78.7). Поведение не
  менялось: query входящего запроса всегда переносится в URL исходящего (в том числе при
  `GET`→`POST`), тело исходящего равно телу входящего, конверсии «query → тело» нет. Раньше эта
  связка не была покрыта тестами. Известное ограничение: `Content-Type` берётся из входящего
  запроса, поэтому «голый» GET даёт исходящий POST без `Content-Type`.

больше не закрывается при обновлении, поиск применяется без кнопки, прокрутка перестала зависеть
от объёма таблицы.

### Fixed

- **Раскрытое тело запроса больше не схлопывается при автообновлении списка** (§77.1). Причин было
  две, и обе устранены: обновление раз в 5 с перезапрашивало ВСЕ накопленные страницы и пересоздавало
  список, а возврат к верху дополнительно выбрасывал страницы 2+ вместе с раскрытой строкой. Теперь
  список обновляется инкрементально — подтягиваются только записи новее самой свежей загруженной и
  вставляются сверху, существующие строки не пересоздаются. Обновление при этом продолжает работать:
  новые записи приезжают, счётчик растёт, а открытая запись остаётся открытой.

- **Прокрутка журнала логов на больших таблицах** (§77.2). Каждая порция из 50 записей на боевом
  узле с 11 млн записей стоила 870–980 мс — независимо от глубины прокрутки. Причина: запрос без
  временно́го окна заставляет ClickHouse читать широкие колонки практически по всей таблице. Сервер
  теперь подбирает окно сам (от свежей записи или от курсора, расширяя 1ч → 6ч → 24ч → 7д → 30д →
  90д → без границы) — окно «едет» вслед за прокруткой, поведение интерфейса не меняется.
  Замер на 50 млн записей: **7 мс средняя страница и 27 мс худшая против 1153 мс**; время страницы
  больше не растёт с объёмом таблицы. Проверить у себя — `make test-int-logs-scale
  LOG_SCALE_ROWS=50000000`.

### Changed

- **Кнопка «Применить» в расширенных фильтрах логов убрана** (§77.3). Поиск запускается по
  завершении ввода: Enter или уход фокуса из поля «Поиск» (Esc возвращает применённое значение),
  выбор в списках «Метод»/«Хост клиента», выбор даты, переключение режимов Aa / ab| / .*. Повторный
  запрос с теми же значениями не отправляется.

- **Долгий поиск можно прервать** (§77.3). Запрос дольше ~0.7 с показывает строку «Поиск…» с кнопкой
  «Отменить»; отмена рвёт запрос не только в браузере, но и в самом ClickHouse. Если поиск идёт по
  всей истории (полнотекст без указанных дат) — рядом подсказка об этом. После отмены — кнопка
  «Повторить». Если запрос под текущими фильтрами занял больше 2 с, автообновление для них
  выключается с явной подписью, чтобы тяжёлые запросы не накладывались друг на друга.

- **Фильтр «Все / Завершено / В работе» удалён из шапки логов** (§77.4) — он дублировал
  «Все / OK / Ошибки». Проверено замером на 17 боевых узлах трёх команд: «Ошибки» и «В работе»
  всегда возвращали одно и то же множество, «ОК» и «Завершено» — тоже, а комбинация «В работе» +
  «ОК» была заведомо пустой. Причина в записи логов: `done` выставляется только при успешном
  ответе. Параметр `done` в API сохранён (на нём переход из вкладки «Очередь»), и когда он приходит
  из такого перехода, в шапке показывается снимаемый чип «В работе» — активный фильтр больше не
  бывает невидимым.

  мягкий варианты читают одинаковый объём (1.40 млн строк / 59.72 МиБ, время в пределах шума) —
  `node_id` не входит в ключ сортировки, поэтому гранулы им не отсекаются ни в одном варианте.

- **Владение таблицей (§70.4) больше не влияет на атрибуцию при чтении** — правило и так строгое
  везде, кроме §64. Гейт остался там, где он и нужен: на разрушающих операциях (очистка неудачных

- **Минимальные требования к серверу — в README и DEPLOYMENT §5.4.** В документации была только

### Fixed

- **Таймаут внешнего узла отдавался клиенту как 502 вместо 504.** Ветка, выставлявшая 504,
  проверяла ошибку в точке, где она заведомо `nil` (её вернули строкой выше), поэтому была
  недостижима — вопреки контракту proto («Receiver проксирует это как 502/504»). Для
  вызывающей стороны разница существенна: таймаут имеет смысл повторить, отказ соединения —
  нет. Признак теперь передаётся полем `SendResponse.timeout` (аддитивное: Sender прежней
  версии его не заполняет, и Receiver ведёт себя как раньше); сам таймаут определяется по
  цепочке ошибки, а не разбором её текста. **Деплой:** обновить оба сервиса — иначе Receiver
  новой версии со старым Sender'ом продолжит отдавать 502.
- **Происхождение сообщений RabbitMQAsync терялось при доставке.** Копия конверта на стороне
  Sender'а разошлась с каноном (не было блока `rmq`), а `encoding/json` неизвестные поля

### Changed

- **JMX-агент Kafka берётся из репозитория, а не качается при сборке (§75).** Образ брокера

- **У HTTP-сервера Web появился `web.idle_timeout_sec`** (дефолт 120) — простаивающие

- **Фоновые операции, порождённые запросом** (отметка last_used_at токена, write-back кеша
  узла в Redis), наследуют значения запроса через `context.WithoutCancel` — в их логах снова
  есть request-id, а события доходят до Sentry с нужным hub.

## [1.21.0] - 2026-07-30

### Fixed

- **Фильтр «Ошибки» на вкладке «Логи» показывал лишь часть записей (§72).** При выборе «Ошибки»
  шапка сообщала, например, «Показано 3 из 33», прокрутка дальше не подгружала ничего, и остальные
  ошибки посмотреть было нельзя ни при каком размере страницы; то же — с фильтром «В работе».
  Причина: быстрые фильтры применялись в браузере к уже загруженной странице, а счётчик «из N»
  считался сервером по всей таблице — два числа описывали разные множества. Теперь фильтр уходит на
  сервер: список содержит только подходящие записи, прокрутка догружает их до конца, а «Показано N
  из M» сходится. Заодно исправлена семантика: записи с кодом 3xx (редирект) не попадали НИ В ОДИН
  из фильтров и пропадали из интерфейса, а незавершённые запросы с кодом 2xx числились успешными —
  теперь «ОК» и «Ошибки» вместе покрывают все записи без пересечений, и та же логика применяется к
  подсветке строк. Список «Неудачные доставки» на вкладке «Очередь» тоже листается прокруткой: он
  показывал ровно 50 записей независимо от их числа. Для больших таблиц чтение ClickHouse сокращено
  кратно — окно фильтра теперь отсекает лишние партиции (замер на 200 000 строк: 200 000
  прочитанных строк против 8 192); на таблицах, которыми Nexus не управляет (внешние, §64),
  оптимизация намеренно отключена. Возврат к началу списка больше не заставляет автообновление
  перезапрашивать всю пролистанную историю. Миграций, новых настроек и ключей интерфейса нет.
- **После переноса узла в другую команду он открывался в старой (§58).** Перенёс узел, открываю его
  из списка — сессия уходила в прежнюю команду, team-scoped запрос отдавал 404 и выбрасывал на
  главную; через F5 бага не было, поэтому он «то воспроизводился, то нет». Причина целиком во
  фронте: переключатель команды по ссылке на узел принимал решение по закешированному ответу
  резолвера команды (глобальный `staleTime` 30 с) и после первого срабатывания залипал, так что
  пришедший позже свежий ответ уже ничего не менял. Теперь решение принимается по ответу, полученному
  после открытия страницы, а признак «уже переключились» привязан к паре «узел + команда» — узел,
  переехавший при открытой странице, переключает сессию заново, а ручная смена команды в шапке
  по-прежнему не откатывается. При недоступном резолвере (5xx/сеть) переключение сознательно
  деградирует в кеш — иначе страница висела бы в загрузке; поведение зафиксировано тестом. После
  успешного переноса строка «Команда» на форме и вкладке «Конфиг» обновляется сразу, а не через 30 с.
  Бэкенд правок не потребовал.

### Added

- **Раздел «Инстансы» в Настройках — список соседних развёртываний Nexus (§73).** §70 научил шину
  работать несколькими инстансами на общем ClickHouse, но из интерфейса соседние развёртывания
  видно не было: каждая нода знала только себя, а чтобы узнать версию соседа и жив ли он, адрес
  приходилось помнить наизусть и открывать вручную. Новая вкладка **Настройки → Инстансы**
  (admin-only) показывает подключённые инстансы: название, адрес-гиперссылку (открывается в новой
  вкладке), код инстанса, версию и статус — «Активен», «Деградация», «Нет ответа», «Ошибка» или
  «Не проверялся», а рядом время ответа и момент проверки. Список опрашивается при открытии вкладки
  и по кнопке «Проверить»; отдельная кнопка перепроверяет одну строку. Диалог подключения умеет
  проверить адрес **до** сохранения и подставить название из кода инстанса.
  **Ни на одном из соседних инстансов ничего настраивать не требуется:** версия и активность
  снимаются с уже существующих публичных адресов `GET /api/version` и `GET /ready`, токен не нужен.
  Проверку выполняет сервер, а не браузер, поэтому с хоста Web должен быть доступен адрес соседа
  (сосед за ingress'ом с basic-auth или IP-фильтром покажется как «Ошибка» — нужен whitelist на
  стороне ingress). Свой инстанс в списке не показывается: его версия видна в футере, код — бейджем
  в шапке. Реестр — справочник ссылок: данными инстансы не обмениваются, удаление записи на работу
  соседа не влияет. Новая таблица `peer_instances` (миграция `0032`, PostgreSQL 12-совместимая) и
  два конфиг-ключа `web.instance_probe_timeout_ms` (3000) и `web.instance_probe_rate_limit_per_min`
  (30) — см. DEPLOYMENT.md. Создание, изменение и удаление пишутся в журнал аудита; проверки — нет.
- **Дефолтный период рабочего стола — свой у каждой команды (§71).** Раньше кнопка «По умолчанию»
  сохраняла период в `localStorage` браузера: один на браузерный профиль, без привязки к
  пользователю и команде — у оператора разные команды означают разные горизонты наблюдения,
  настройка не переезжала на другое устройство, а два человека за одной машиной перетирали дефолты
  друг другу. Теперь дефолт хранится в PostgreSQL (новая таблица `user_preferences`, миграция
  `0031`) и применяется по команде: при переключении команды рабочий стол показывает её период —
  даже если до этого период был выбран вручную. Период не переживает и уход со страницы: вернувшись
  на «Узлы», видите период своей команды (поиск и остальные фильтры восстанавливаются как прежде).
  Прямая ссылка `?range=…` при открытии страницы уважается. Прежнее значение из браузера разово переносится в глобальный преф
  пользователя. Таблица generic (`key` + JSONB `value`), поэтому будущие персональные настройки
  интерфейса не потребуют новых миграций. Совместимо с PostgreSQL 12 (минимальная поддерживаемая
  версия); новых ENV и конфиг-ключей нет. Вкладки узла и Kafka-монитор
  по-прежнему стартуют с 24ч. Новые эндпоинты: `GET/PUT /api/me/prefs` (session-only).
- **Несколько нод Nexus на одном ClickHouse (§70).** Нода — самостоятельное развёртывание со своими
  PostgreSQL/Redis/Kafka, пишущее логи в общий с другими нодами ClickHouse. Новая секция конфига
  `instance` (`id` — 1..8 символов, по умолчанию пусто; `adopt_unowned`) разводит имена баз:
  `nexus_<id>_<slug>` вместо `nexus_<slug>`. Одного разведения имён мало — слаг команды допускает
  `_`, поэтому нода без идентификатора с командой `kz_edo` и нода `kz` с командой `edo` дают одно
  имя базы. Владение определяется служебной таблицей-маркером `__nexus_owner` внутри каждой базы
  (движок `TinyLog` — она невидима в разделе «Бесхозные таблицы» и не удаляется кнопкой); захват
  атомарен через `CREATE TABLE` без `IF NOT EXISTS`. Гейт закрывает все разрушающие операции:
  удаление партиций по retention, удаление бесхозных таблиц, `ALTER`'ы синхронизации схемы (§56),
  стартовые `ADD COLUMN` и мутации размеров тел, создание и переименование таблиц и баз, очистку
  неудачных доставок; на чужой таблице также отключается послабление атрибуции записей без
  `node_id` (§61). Узел не может ссылаться на таблицу в чужой базе (400), кроме режима внешней
  таблицы (§64) — там межнодовые чтение и запись разрешены осознанно. Идентификатор фиксируется в
  PostgreSQL ноды (миграция 0029, `instance_identity`) и неизменяем: при расхождении с конфигом
  сервис не стартует. Первый запуск с пустым `instance.id` при уже существующей в ClickHouse
  `nexus_default` прекращает старт с требованием задать идентификатор. Ноды различимы в
  наблюдаемости: тег `instance` в Sentry, постоянная метка `nexus_instance` в метриках (имя не
  `instance` — его занимает scrape Prometheus), атрибут `instance` в служебных логах, подпись
  `Nexus [<id>]` в уведомлениях Telegram, чип с кодом ноды в шапке интерфейса. При пустом
  идентификаторе поведение действующей ноды не меняется: те же имена баз, те же запросы, ни новых
  тегов, ни меток, ни полей в JSON. Развёртывание второй ноды — DEPLOYMENT.md §5А.

  сообщения из RabbitMQ — они остаются в очереди брокера, и очистка их не тронет.

### Changed

- **`target_url` обязан быть абсолютным http(s)-адресом (§69.2).** В режиме «Статичный» (и у
  pull-узлов) адрес без схемы больше не сохраняется: и форма, и API отвечают понятной ошибкой у
  поля. Раньше такой узел сохранялся молча, а падал уже на доставке — `unsupported protocol
  scheme ""` на каждом вызове. Пробелы по краям адреса срезаются автоматически. В режиме «Из
  запроса» поле не используется и не проверяется (требование http(s) к адресу из запроса
  действовало и раньше).
- **Адрес доставки async-сообщений пересобирается по актуальному конфигу узла (§69.3).** Receiver
  фиксирует целевой URL в сообщении в момент приёма, поэтому исправление `target_url` не влияло на
  уже принятые сообщения: они повторялись по старому адресу до истечения DLQ TTL (сутки по
  умолчанию). Теперь для узлов в режиме «Статичный» адрес собирается заново перед каждой
  отправкой — правка узла чинит и застрявшие сообщения, без ручного «Повторить все». Ограничения:
  правка query внутри самого `target_url` на уже принятые сообщения не действует (query берётся из
  сообщения), режим «Из запроса» не пересобирается.

## [1.18.0] - 2026-07-24

### Added

- **Поддержка multipart/form-data (§68).** Шина полноценно проксирует запросы с вложениями
  (`multipart/form-data` и прочие `multipart/*`) во всех видах отправки — sync, async, RabbitMQAsync,
  dry-run: тело с файлами уходит получателю байт-в-байт, `Content-Type` с `boundary` сохраняется.
  Размер сообщения в логах (`request_size`/`response_size`) считается по полному телу — вложения
  учтены. При этом само вложение в ClickHouse **не сохраняется**: вместо тела в колонку пишется
  компактный плейсхолдер со сводкой частей (имя поля, имя файла, тип, размер — без содержимого),
  например `multipart/form-data\n- part 1: name="file"; filename="invoice.pdf"; …`. Для multipart
  снят пер-узловой лимит тела (`max_body_size`) — тело в логах и так не хранится; действуют только
  транспортные ограничения (5 МиБ на запрос, лимит Kafka-сообщения для async). Повтор (replay)
  такого запроса возможен только с телом, введённым вручную (тело оригинала не сохранено) — диалог
  повтора показывает предупреждение. Без миграций и новых параметров конфигурации.

  после `IP`) — имя машины отправителя из reverse DNS (PTR-записи корпоративного DNS), например

  доставки не затрагивается), кеш IP→имя в Redis, общий для реплик Sender'а; конфиг —
  `sender.rdns` (включён по умолчанию, `timeout_ms`/`cache_ttl_sec`/`negative_ttl_sec`).

  таблицы узла, как у «Метод»); поля дат получили метки «Дата с»/«Дата по» и компактную ширину.
  Управляемые таблицы получают колонку автоматически при старте сервисов.

  > вручную ДО или сразу после деплоя (имя БД/таблицы подставьте своё):
  >
  > ```sql
  > ALTER TABLE <db>.<table> ADD COLUMN IF NOT EXISTS client_host String DEFAULT '' AFTER IP
  > ```
  >
  > До выполнения ALTER вкладка «Логи» такого узла показывает штатный баннер «Логи временно
  > недоступны» (мягкая деградация, не ошибка), а новые записи буферизуются в retry-топик

- **Sentry NEXUS-8: `EOF` в Web-прокси (69 событий) — разобран и устранён.** События совпадали с
  CH-логом узла секунда в секунду (+30с): боевой `receiver.write_timeout_ms=10000` рвал соединение
  до записи ответа долгого запроса → ReverseProxy Web ловил `EOF` → клиент получал 502
  `receiver unavailable`. Дефолт поднят до 610000 (> максимума таймаута узла); ErrorHandler прокси
  теперь логирует метод и путь (без query) — голый `EOF` был непривязываем к запросу.
  **На бою вручную**: поднять `receiver.write_timeout_ms` до 610000 в `config.yml`.
- **Replay GET-запросов больше не блокируется «тело не сохранялось» (§7.4.1).** У GET тела нет by
  design — пустой `request` в логе не повод для 422 (ошибка остаётся только для не-GET методов).
  Заодно массовое «Повторить все» на GET-узлах перестало падать построчно.
- **Потеря async-сообщений paused-узлов (§3.6).** kafka-go не передоставляет незакоммиченное
  сообщение при коммите соседнего offset'а — сообщение paused-узла терялось. Сначала retry-in-place,
  затем изоляция: paused-сообщения переезжают в delay-топик `nexus.async.paused` (новый топик,
  создаётся автоматически) и обрабатываются фоновым sweeper'ом — пауза одного узла больше не
  тормозит соседей по партиции. Вкладка «Очередь» (§35) видит оба топика.

### Added

- **Максимальный таймаут узла поднят до 600000 мс (10 минут).** Домен, БД (миграция
  `0024_nodes_timeout_600s`, автоматическая), UI-валидация, бакет 600с в гистограмме
  `nexus_request_duration_seconds` (иначе p95/p99 длинных узлов липли к +Inf); таймаут
  replay-диспетчера Web→Receiver поднят с 30с до 610с.
- **Basic-авторизация: раздельные Логин и Пароль (§41.7).** В форме узла для входящей и исходящей
  basic вместо одного секрет-поля «логин:пароль» — открытый Логин + скрытый Пароль. Формат хранения
  не менялся; существующие узлы работают как раньше, их логины видны в форме и в просмотре. Смена
  логина требует ввода пароля заново (сервер не может пересобрать креды, не зная пароля); пустой
  пароль = оставить прежние креды. API отдаёт `auth_login`/`incoming_auth_login` (логин — не секрет,
  пароль наружу не отдаётся никогда).
- **Replay: поле «Параметры» + тело для GET (§7.4.1).** В диалоге повтора появилось редактируемое
  поле query-параметров с предзаполнением из лога (`params_override`; служебный `__replay_of`
  добавляется поверх всегда); тело запроса доступно и для GET (необязательное — некоторые API
  принимают GET с телом).
- **Просмотр узла (вкладка «Конфиг»)**: строки «Входящая авторизация» и «Исходящая авторизация»
  (тип + логин при basic) и строка «Таймаут / повторы» (`timeout_ms · retry_count × backoff`).
- **Графики и UX узлов (§59–61).** Мини-графики трафика в таблице узлов, действие «Перенести» в
  форме узла, копирование URL лога; перенос узла между командами больше не утаскивает общую таблицу
  логов (§60); записи на общей таблице атрибутируются узлу + предпросмотр переноса (§61).

### Changed

- Комментарии конфигов: `sender.http_client.timeout_ms` помечен как fallback (per-node значение им
  не капается); `kafka.consumer.max_poll_interval_ms` — декларативный (kafka-go его не применяет,
  долгая обработка ребаланс не вызывает); `receiver.sender_grpc.timeout_ms` и
  `web.sender_grpc.timeout_ms` — фактически не применяются (задокументировано в IMPLEMENTATION.md).
- echosrv (тестовая оснастка стенда): режим `/delay/<sec>/*` для проверки длинных таймаутов.

### Changed

### Added

- **«Поделиться узлом» — прямая ссылка с авто-переключением команды (§58).** На странице просмотра
  узла и в форме правки появилась кнопка **«Поделиться»**: она даёт прямую ссылку вида `/nodes/:id`,
  которую можно отправить коллеге. При открытии такой ссылки, если узел принадлежит другой команде,
  интерфейс **сам переключает команду** на нужную (а не показывает пустой список) — за это отвечает
  новый резолвер `GET /nodes/:id/team`. Если узел недоступен (удалён или нет прав), вместо пустого
  экрана показывается понятное **«Узел не доступен»**.
- **Синхронизация схемы ClickHouse у существующей таблицы (§56).** Раньше смена ClickHouse-шаблона,
  кодеков, data-skipping индексов или native-TTL у уже созданного узла **не доезжала до таблицы** —
  она создаётся один раз (`CREATE TABLE IF NOT EXISTS`), и ALTER'ов не было. Теперь в настройках узла
  есть кнопка **«Синхронизировать схему»**: система читает текущую структуру таблицы (`SHOW CREATE`),
  показывает **план** (какие `ALTER … MODIFY COLUMN` / индексы / `MODIFY TTL` будут выполнены, а что
  требует пересоздания — движок, ORDER BY, PARTITION BY), и по подтверждению применяет его. Появились
  эндпоинты `POST /api/nodes/{id}/ch-schema/plan` (только чтение) и `/apply`.
- **Перевыпуск (rotate) значения API-токена (§7.14).** В списке токенов появилась операция
  **перевыпуска**: она генерирует новое значение токена, **сохраняя его настройки** (команда, срок,
  scope). Прежнее значение немедленно перестаёт работать — удобно при подозрении на утечку, не
  пересоздавая токен с нуля.
- **Мониторинг всех узлов и Kafka в Grafana + алерты по узлам (§7.6).** Добавлены два новых
  дашборда: **«Nexus — Nodes»** (сразу видно проблемные узлы — счётчики DOWN/DEGRADED/OK, таблица
  проблемных, сводка по каждому узлу: отправлено/ошибки/%/p95/статус с подсветкой, история статуса,
  секция RabbitMQ pull-узлов) и **«Nexus — Kafka & Async»** (lag по группам/топикам, конвейер
  produced→delivered→failed, ошибки async по узлам, DLQ, loop-detection). В `deploy/prometheus.alerts.yml`
  добавлена группа `nexus.nodes` (узел down/degraded/высокий error rate, RMQ-разрыв, потеря сообщений
  из DLQ). Дашборды в `deploy/grafana/` импортируются во внешнюю Grafana вручную.
- **Тестовый запрос подставляет входящую авторизацию и метод узла (§55.6).** Диалог диагностики узла
  теперь автоматически заполняет ожидаемое поле входящей авторизации и HTTP-метод из конфигурации
  узла — на один шаг меньше ручного ввода перед запуском.

### Changed

- **Изменения узла применяются к маршрутизации мгновенно (§57).** При правке узла в Web горячий кеш
  Receiver'а раньше мог какое-то время отдавать **устаревшую** конфигурацию (до истечения TTL). Теперь
  Web публикует событие изменения (новый пакет `nodeevents`), Receiver на него подписан и немедленно
  инвалидирует запись в своём кеше узлов — правки (адрес, авторизация, статус) вступают в силу без
  ожидания и без рестарта.
- **Предупреждение о смене схемы ClickHouse (§19).** Если у существующего узла поменять CH-шаблон
  без смены имени таблицы, новые кодеки/индексы/движок к ней сами не приедут (см. §56 выше). Форма

  таблицы, либо ручная «Синхронизировать схему». Срок хранения (Retention, дни) — исключение:
  он применяется автоматически фоновым housekeeping'ом.

### Fixed

- **Replay доступен только роли «менеджер» и выше (§58, RBAC).** Кнопка повторной отправки запроса
  (Replay) ошибочно показывалась роли «наблюдатель» (viewer); теперь доступ приведён в соответствие
  с матрицей прав. Заодно проведён аудит прав на кнопки в шапке узла.

## [1.14.0] - 2026-07-17

### Added

- **«Тестовый запрос» стал настоящей диагностикой узла (§55).** Раньше тест отвечал на вопрос
  «валиден ли конфиг», но не на вопрос «дойдёт ли запрос до получателя»: при снятой галке mock шаг
  «Ответ» просто сообщал, что реальный режим не поддерживается. Теперь **запрос можно реально
  отправить получателю** — тем же путём, что и боевой трафик, поэтому в отчёте видны настоящие
  статус, длительность, число попыток, редиректы и таймауты (ровно то, ради чего тест и открывают).
  Что важно: **тест не оставляет следов** — он не пишет в логи узла, не влияет на графики и метрики,
  не меняет статус узла на дашборде и не участвует в защите от сбоев (circuit breaker). То есть
  диагностика зависшего узла не может усугубить его состояние. Реальный режим требует адреса Sender
  в настройке `web.sender_grpc` (см. DEPLOYMENT.md); если она не задана, всё работает как прежде,
  а шаг «Ответ» объясняет причину.
- **Диалог теста заполнен целиком.** Появились поля **Заголовки** и **Query-параметры** (пары
  «имя → значение»), **Хвост пути** (для узлов, дописывающих путь к адресу получателя) и переключатель
  **«Использовать mock-сервер»** (включён по умолчанию; при снятии рядом с «Запустить» появляется
  предупреждение с реальным адресом). Для узла с входящей авторизацией диалог **подсказывает, какое
  именно поле он ожидает** (например, `Authorization: Basic base64(логин:пароль)`) и позволяет
  подставить его одним кликом. Раньше подставить заголовок было нечем, и тест такого узла всегда
  обрывался на первом шаге сообщением «authorization header missing».
- **Кнопка «Тестовый запрос» на странице просмотра узла** (рядом с «Обновить»/«Копировать»/
  «Изменить») — проверить сохранённый узел, не заходя в редактирование. Пароли и токены узла при
  этом подставляет сервер: наружу они не отдаются, поэтому без этого тест узла с авторизацией
  всегда получал бы 401. Доступна с ролью «менеджер» и выше.
- **Команда API-токена выбирается при создании и видна в списке.** Токен действует ровно в одной
  команде, но раньше выбора не было: он молча наследовал команду, выбранную в переключателе шапки в
  момент нажатия «Создать», и увидеть её было негде — отсюда сюрприз «токен видит не те узлы».
  Теперь в форме есть поле **Команда** (список — команды, в которых вы состоите), а в таблице
  токенов — колонка **Команда**. Попытка выписать токен в команду без членства отклоняется (403).

### Fixed

- **Срок действия токена больше не игнорируется.** Выбранный в интерфейсе срок (по умолчанию 365
  дней) не доходил до сервера — из-за расхождения имён полей он молча терялся, и **все выданные
  токены были бессрочными**. Теперь срок применяется и считается на сервере (часы браузера на него
  не влияют); пустое поле по-прежнему означает бессрочный токен. **Ранее созданные токены остались
  бессрочными** — если это нежелательно, отзовите их и выпустите заново со сроком.
- **Раздел «Настройки» больше не перезагружается при переключении команды.** Вкладки Общие,
  Пользователи, Команды, API-токены, Разрешённые хосты, Заголовки, ClickHouse, Sentry и Уведомления
  показывают данные, которые от команды не зависят, но при каждом переключении они зря
  перезапрашивались и мигали. Теперь Настройки живут вне скоупа команды: где данные всё же
  принадлежат команде, она задаётся явно внутри формы (как команда токена).
- **Логи узлов не-default команд больше не падают после деплоя (Sentry 158619).** На установке с
  несколькими командами открытие логов узла могло вернуть ошибку
  `Unknown expression identifier 'request_size'`: при старте Web добавлял новые колонки только в
  таблицы команды по умолчанию, а базы остальных команд (`nexus_<команда>.*` — там и живёт весь
  боевой трафик) не трогал вовсе. Схему чинил только рестарт Sender'а, поэтому в промежутке
  «новый Web уже поднят, новый Sender ещё нет» просмотр логов отдавал 500. Теперь Web мигрирует
  таблицы **всех** команд — симметрично Sender'у, порядок деплоя действительно не важен. Дефект
  существовал с 1.12.0 и затрагивал колонки `node_id`, `http_method`, `request_size`/`response_size`.
- **Таблица логов узла вмещается по ширине — горизонтальный скролл убран.** После появления колонки
  «Ответ» (размер тела, 1.12.0) таблица на вкладке «Логи» перестала помещаться в карточку: внизу
  возникала полоса прокрутки, а последние колонки уезжали за край. Причина — ширина таблицы
  подстраивалась под содержимое (колонка URL резервировала фиксированные 448 пикселей). Теперь
  служебные колонки (время, HTTP, статус, мс, ответ, повтор) имеют заданную ширину, а «Метод» и
  «URL» делят остаток и обрезаются многоточием — таблица вмещается на любой ширине экрана.
- **Полный «Метод» и «URL» видны во всплывающей подсказке.** Значения в этих колонках обрезаются,
  и раньше прочитать их целиком было негде — теперь полный адрес показывается при наведении.
- **Переключение команды при открытой странице узла больше не оставляет чужие данные на экране.**
  Узел принадлежит одной команде: после переключения он становится недоступен, но страница
  продолжала показывать его **старые данные** — без ошибки и без перехода, как будто всё в порядке.
  Теперь происходит переход к списку узлов выбранной команды.
- **Кнопка «Обновить» на странице узла больше не висит заблокированной.** Она реагировала на любой
  фоновый запрос во всём интерфейсе (а не только на данные этой страницы), а после смены команды
  недоступный узел ещё и опрашивался по кругу с повторными попытками — в результате кнопка крутилась
  практически постоянно. Теперь она отслеживает и обновляет только данные открытого узла.
- **Несохранённые правки в форме узла больше не пропадают.** Достаточно было переключиться в другое
  окно и вернуться (или сменить команду) — форма молча перезаполнялась данными с сервера, стирая

  `Settings → General` → «Приблизительный подсчёт уникальных запросов» (`app_settings.general.metrics_approx_counts`,
  дефолт — выкл = точно). Включённый режим считает счётчики дашборда и KPI узлов через
  `uniq`/`uniqIf` (HyperLogLog: приблизительно, ошибка ~0.3%, но в ~3× дешевле по CPU) вместо точного
  `countDistinct`. Для больших объёмов/много узлов, когда точный подсчёт за 30д упирает ClickHouse в
  100% CPU и рабочий стол грузится секунды. Применяется на лету; инвариант «шапка = Σ строк таблицы»
  сохраняется в обоих режимах.

### Fixed

- **Скролл таблицы логов «не двигает вниз» на узлах с массой записей (§44, keyset-пагинация).** Курсор
  подгрузки был по `date_request` секундной точности с `<=`; на узле с сотнями записей в одной секунде
  (на стенде до 624/сек) следующая страница возвращала те же строки той же секунды → дедуп по id →
  0 новых → стопор. Введён составной keyset-курсор `(date_request, ID)` (`before_id`): пагинация
  строго перешагивает плотные секунды до потолка строк.
- **Зависание скролла таблицы логов на узлах с сотнями тысяч записей (§44).** Бесконечный скролл без
  виртуализации копил DOM без предела — на большом узле прокрутка вниз вешала вкладку. Введён потолок
  накапливаемых строк (1000): по достижении подгрузка вниз останавливается, показывается подсказка
  сузить период/фильтр (точечный поиск — через фильтры).
- **Список логов больше не читает тела `request`/`response` из ClickHouse (§44).** Тела в списке не
  показывались (тянутся лениво при разворачивании строки — §42), но CH-запрос всё равно читал их с
  диска и гонял по сети для каждой строки страницы — на узлах с большими телами это тормозило
  пагинацию при скролле. Теперь список их не читает (`'' AS request/response`); контентный поиск (q)
  по-прежнему фильтрует по реальным телам.
- **Прыжки интерфейса из-за переменной высоты верхних KPI-счётчиков (§44).** Строка процента
  (delta) рендерилась только при наличии данных — карточка подрастала при дозагрузке и контент под
  ней сдвигался. Теперь строка delta резервируется всегда (nbsp), высота карточки постоянна.
- **Скоупинг команды при входе (§44.H).** Пользователь, чей `default_team_id` указывал на команду,
  в которой он больше не состоит (членство удалили, колонку не переписали), при входе попадал на
  ноды чужой команды, а переключатель был заблокирован (одна доступная команда ≠ текущая) — до своих
  узлов было не добраться. Теперь `current_team_id` новой сессии резолвится по фактическому членству
  (если `default_team_id` не среди членств — берётся первая команда пользователя). Уже выданные
  «битые» сессии самочинятся при загрузке (`GET /api/me/teams`), без ре-логина. Удаление пользователя
  из команды, бывшей его дефолтом, переводит `default_team_id` на другую его команду.
- **Невалидный UUID в пути `:id` → 404 вместо 500 (Sentry NEXUS-7).** Запросы к `/api/nodes/{id}/…`,
  `/api/users/{id}`, `/api/teams/{id}` с `id`, не являющимся UUID, доходили до приведения `$1::uuid`
  в PostgreSQL (SQLSTATE 22P02) и падали в 500 + событие Sentry. Теперь репозитории трактуют `22P02`
  как «не найдено» (`Err…NotFound` → 404), как и `pgx.ErrNoRows`.

### Changed

- **Дата+время в таблице логов и «последних запросах» узла — с годом** (`DD.MM.YY HH:MM:SS`, §44.J).
  Раньше показывалось только время.

## [1.7.2] - 2026-06-24

Исправление семантики лимитов размера тела (§43 из 1.7.0 был выполнен неверно) + видимость причины
ошибки в логах.

### Changed

- **Исправлена семантика лимитов размера тела (§43-rev).** Первая редакция §43 (в 1.7.0) ошибочно сделала
  per-node «Ограничить размер тела» (`max_body_size`) жёстким reject (413/502). Возвращено к §22.2:
  `max_body_size` режет **только** копию тела в ClickHouse-логе (в рунах), а ответ клиенту приходит
  **полностью**, checksum по полному телу. Жёсткие лимиты — транспортные, **из конфига**:
  - тело ЗАПРОСА больше `receiver.max_body_bytes` → **413** (Receiver, sync/async/callback; раньше 400);
  - тело ОТВЕТА апстрима больше `sender.grpc_max_message_bytes` → **502** (Sender; чтение оборвано на
    лимите — memory-safe, тело не затягивается в память; раньше — `ResourceExhausted` в gRPC).
  Связи лимитов задокументированы комментарием в `config.example.yml`/`config.yml`.

### Added

- **Колонка «Причина» (reason) в таблице логов** и показ reason в раскрытой записи — причина не-OK
  (4xx/5xx, circuit breaker, превышение лимита) видна сразу, без раскрытия записи (§43 self-explanatory).

### Fixed

- **Чистый 413 через Web-прокси** при превышении `receiver.max_body_bytes`: ранний отказ по
  `Content-Length` (для клиентов с `Expect: 100-continue`) + дренаж ограниченного остатка тела — раньше
  большое тело через единый вход (Web → Receiver) давало 502 «receiver unavailable» вместо 413
  (Receiver отвечал, не дочитав тело → TCP-reset).

Большие тела сквозь шину и в логах (§42): фикс зависания вкладки «Логи» на большом теле + устранение

Плюс §43: жёсткий лимит размера тела (reject вместо тихого усечения).

### ⚠️ Изменения при апгрейде

- **§43 — изменена семантика `max_body_size`** (узлы с **включённым** лимитом). Раньше тело > лимита
  тихо усекалось в логе, а клиент получал полный ответ. Теперь тело > лимита **отклоняется**: sync —
  `413` (тело запроса) / `502` (тело ответа), async — не доставляется; во всех случаях запись лога
  `done=0` с `reason`, тело не сохраняется, `checksum` по полному телу. Узлы с **выключенным** лимитом
  (дефолт) — без изменений (большие тела проходят, показываются через §42). Миграций/ENV нет.

- **Новые параметры конфига для размера gRPC-сообщения** (с дефолтами — обратная совместимость, задавать
  не обязательно): `receiver.sender_grpc.max_message_bytes` и `sender.grpc_max_message_bytes`, оба дефолт
  **64 МиБ (67108864)**. Поднимают прежний предел gRPC 4 МиБ, из-за которого большой ответ апстрима
  (десятки МБ) рвался `ResourceExhausted desc = grpc: received message larger than max`. Значения двух
  сервисов **должны совпадать**; держите `≥ receiver.max_body_bytes`. Если в проде ожидаются ответы
  крупнее 64 МиБ — поднимите оба параметра согласованно. Новых миграций/ENV нет.

### Fixed

- **Большой ответ/запрос рвался в gRPC `ResourceExhausted` (лимит 4 МиБ).** Транспорт Receiver↔Sender
  использовал дефолтный лимит gRPC-сообщения 4 МиБ в обе стороны: уже 5-МиБ тело запроса (предел
  `receiver.max_body_bytes`) не доезжало до Sender, а ответ апстрима в десятки МБ — обратно к
  Receiver/клиенту. Лимиты подняты на сервере Sender (`MaxRecvMsgSize`/`MaxSendMsgSize`) и клиенте
  Receiver (`MaxCallRecvMsgSize`/`MaxCallSendMsgSize`) из новых конфиг-параметров (дефолт 64 МиБ).
- **Async (Kafka): большое тело не публиковалось.** Producer `BatchBytes` равнялся `producer.batch_size`
  (64 КиБ в дефолте), и segmentio kafka-go отвергал единичное сообщение крупнее него
  (`MessageTooLargeError`) ещё до брокера — хотя топик допускал `topic.max_message_bytes` (10 МиБ).
  `BatchBytes` теперь = `max(producer.batch_size, topic.max_message_bytes)`.
- **Вкладка «Логи» зависала при разворачивании большого тела.** `Get` тянул всё тело, фронт синхронно
  делал `JSON.parse`+`stringify` и рендерил гигантскую строку в `<pre>` — главный поток вставал.

### Added

- **§42 — динамическая подгрузка тел логов.** `Get` отдаёт превью (первые 64K рун, нарезка `substringUTF8`
  в ClickHouse) + полные длины; остаток — срезами по рунам (`GET …/log/{logId}/body`); очень большое —
  потоковым скачиванием файлом (`…/log/{logId}/body/download`). UI: «показать весь» (с предупреждением
  > 2 МБ), «скачать файлом», «копировать»; pretty-print JSON отключается для тел > 256K (убирает фриз).
- **Уточнена подсказка параметра «Ограничить размер тела»** — лимит режет только тело в логе; ответ
  клиенту приходит полностью, checksum считается по полному телу.

- **ClickHouse-таблицы логов: новая колонка `http_method`** добавляется автоматически на старте `web`
  и `sender` (идемпотентный `ALTER TABLE … ADD COLUMN IF NOT EXISTS http_method String DEFAULT ''
  AFTER type`, по образцу §37) — отдельного шага не требуется.
- **Изменена семантика колонки `method`** в логах: теперь хранит подпуть запроса (хвост passthrough,
  напр. `v1/GetParcelsInfo`), а **HTTP-глагол** (GET/POST) переехал в новую колонку `http_method`.
  Миграции данных нет — старые записи остаются как есть, новый трафик пишется по новой схеме.
- Изменений `config.yml` в этом релизе нет.

### Added

- **§39 — path-passthrough маршрутизация.** Опциональный per-node флаг `path_passthrough` (тумблер
  «Проксировать хвост пути» в форме узла). Когда включён, хвост входящего пути после пути узла
  приклеивается к `target_url`: один узел обслуживает много методов приёмника (напр. узел `ozon` +
  запрос `…/ozon/GetAuthToken` → `<target>/GetAuthToken`). Резолв через longest-prefix (первый
  существующий узел-префикс «выигрывает»), приклеивание через `url.URL.JoinPath` (кодирование сегментов
  + резолв `..` — защита от path-traversal). Работает для sync и async, обоих URL-режимов
  (`static`/`from_request`); **точный матч узла приоритетнее** префиксного (пересечение адресов
  детерминировано). По умолчанию выключен — точный матч и `404` на лишний хвост сохраняются.
  Спека: [specs/sections/39-path-passthrough.md](specs/sections/39-path-passthrough.md).
- **Лог-колонка `http_method`** (HTTP-глагол вызова) в ClickHouse-таблице логов — рядом с `type`,
  заполняется всегда. Подпуть passthrough пробрасывается из Receiver в Sender (gRPC
  `SendRequest.request_path`, Kafka-envelope) и пишется в колонку `method`. Колонки `HTTP` и `Метод`
  показаны во вкладке логов узла.
- **§7.6 — контекстная справка к полям узла.** У каждого параметра формы узла — иконка-«?» с тултипом
  «зачем параметр» (`LabelHint`: `HelpCircle` + `Tooltip`, доступна с клавиатуры). Тексты в `node.help.*`
  (en/ru). Существующая короткая приписка `hint` сохранена.

### Changed

- **Replay для passthrough-узлов** реинъектит по полному подпути (`node.Path + "/" + method` из лога),
  иначе повтор уходил бы на корень узла; HTTP-глагол по-прежнему берётся из `incoming_method` (§34.5).

Релиз вокруг устойчивости к недоступности ClickHouse: durable-retry проваленных лог-батчей через
Kafka (§38) взамен локального NDJSON-fallback, мягкая деградация чтения логов в Web при простое CH,

### ⚠️ Изменения конфигурации (важно при апгрейде)

- **`config.yml` → новый `kafka.retry_topic`** (дефолт `nexus.logs.retry`) — топик durable-буфера

### Added

- **§38 — durable-retry проваленных ClickHouse-батчей через Kafka.** При недоступности ClickHouse
  INSERT лог-батча в Sender падает (отправка данных при этом **не** блокируется, §9.4 — падает только
  логирование). Раньше проваленный батч писался в локальный NDJSON-файл; теперь он продьюсится в топик
  `nexus.logs.retry`, а отдельная consumer-group (`<group>-clog-retry`) дренит его обратно в CH после
  восстановления — retry-in-place с экспоненциальным бэкоффом (1с→15с), без рестарта Sender. Реплицируемо,
  без локальных файлов; Kafka нагружается **только** во время простоя CH (сообщение на батч ~100 строк,
  не на запрос) — в норме прямой INSERT как прежде. Спека: [specs/sections/38-clog-retry-kafka.md](specs/sections/38-clog-retry-kafka.md).
- **Новые метрики:** `nexus_clickhouse_fallback_total{op="queued"|"restored"}`,
  `nexus_clickhouse_errors_total{op="insert"|"retry_produce"}`; lag топика `nexus.logs.retry` —
  в `nexus_kafka_lag`.

### Changed

- **Read-path логов в Web мягко деградирует при недоступности ClickHouse** (List/CountFailed/Get/Stream):
  `200` + `logs_available=false` и WARN вместо шторма `500` и Sentry-flood. Фронт показывает индикатор
  «Логи временно недоступны (ClickHouse)».
- Формат сообщения retry-буфера — `Envelope{table, logs}` с резкой по `max.message.bytes` (`clogwire`).

### Fixed

- **Ложный суффикс `-dirty` в версии при сборке образов на сервере** (`deploy/docker/*.Dockerfile`).
  Перед `git describe --tags --always --dirty` добавлен `git update-index -q --refresh`: после
  `COPY . .` у файлов в Docker-слое новые `mtime`/`inode`, а `git describe` (в отличие от
  `git status`) сам индекс не освежает — и принимал неизменённое дерево за грязное. Из-за этого
  `/api/version` и футер SPA показывали, например, `v1.2.0-dirty` при **чистом** `git status` на
  сервере. Refresh обновляет stat-кэш индекса по содержимому; реальная грязь (изменённое
  содержимое отслеживаемых файлов) по-прежнему корректно даёт `-dirty`. См. DEPLOYMENT.md §9.4.
- CI loadtest: добавлена колонка `node_id` в ClickHouse-таблицу загрузочного теста (§37).

### Removed

- Локальный NDJSON-fallback Sender'а (`internal/sender/adapter/out/chlog/fallback.go`) и параметр
  `clickhouse.fallback_dir` — заменены durable-retry через Kafka (§38).

- **`config.yml` → новая опциональная секция `sender.reprocessor`** (есть дефолты — можно не
  добавлять; образец в [config/config.example.yml](config/config.example.yml)):
  - `disabled` (bool, дефолт `false`) — рубильник DLQ-репроцессора;
  - `interval_sec` (int, **дефолт `60` = раз в минуту**) — период прохода sweeper'а. Эффективная пауза
    повтора сообщения = `max(interval_sec, dlq_retry_delay_seconds узла)`; держите `interval_sec` ≤
    минимального per-node `dlq_retry_delay_seconds`, который хотите задавать (иначе его уменьшение ниже
    `interval_sec` не даёт эффекта). На dev-стенде ([config_debug.yml](config/config_debug.yml))
    `interval_sec: 30`;
  - `max_scan` (int, дефолт `1000`) — максимум сообщений за один проход (защита брокеров).
- **Новые per-node параметры (миграции PostgreSQL `0017`/`0018` — применяются автоматически на старте,
  аддитивные; редактируются в форме узла):**
  - `nodes.dlq_ttl_seconds` (`NOT NULL DEFAULT 86400` = 24 ч) — до какого срока (от приёма) репроцессор
    повторяет неудачную async-доставку;
  - `nodes.dlq_retry_delay_seconds` (`NOT NULL DEFAULT 300` = 5 мин) — минимальная пауза перед повтором.
  - Обе с `NOT NULL DEFAULT` → существующие узлы заполняются дефолтами атомарно (backfill не нужен).
- **Новая колонка ClickHouse-логов `node_id` (§37)** — добавляется **автоматически** на старте Web и
  Sender (`ALTER TABLE … ADD COLUMN IF NOT EXISTS node_id String DEFAULT ''`, идемпотентно; новые
  таблицы — из шаблона). Конфиг менять не нужно. Старые записи получают пустой `node_id` (legacy,
  истекают по TTL); per-node разделение метрик/логов вступает в силу на новом трафике.

### Added

- **§36 — авто-репроцессор DLQ.** Фоновый sweeper в Sender повторно доставляет неудачные async-сообщения
  из `nexus.async.dlq` (отдельная consumer-группа `<group>-dlq-reprocess`) до per-node TTL; при
  восстановлении приёмника сообщения уходят автоматически. Уважает circuit breaker, tombstone'ы (§34.4)
  и статус узла. Метрики `nexus_dlq_reprocess_total{node,result}` и `nexus_dlq_reprocess_duration_seconds`.
- **§36.10 — очистка «Неудачных доставок» узла** (`POST /api/nodes/{id}/async-queue/purge-failed`,
  admin): отменяет авто-повтор (qcancel) и удаляет записи `done=0` из CH-логов узла.
- **§36.11 — «Повторить все сейчас»** (`POST .../async-queue/replay-failed`, admin): массовый форс-повтор
  всех неудачных узла через Receiver с отменой оригиналов в DLQ (без двойной доставки).
- **§37 — идентификатор узла в логах** (`node_id`): per-node атрибуция для узлов, делящих одну
  CH-таблицу (счётчики/графики/очистка/replay фильтруют по узлу; `DeleteFailed` не задевает чужие
  записи). Node id выведен во вкладку «Конфиг» узла.
- **§35 — переработка вкладки «Очередь»**: KPI, секции «Ожидают отправки»/«Неудачные доставки»,

### Changed

  throughput рабочего стола (таблица/карточки) считаются по CH-логам узла — точные мгновенные счётчики
  по уникальным запросам, без неточного `increase()` и без мерцания; цифры стола и страницы узла

- Очистка pending-очереди узла доступна в **любом** статусе (не только на паузе).

### Fixed

- **§36 критбаги:** потеря DLQ-сообщения в sweeper'е (seen-break до commit); Sender не читал
  `dlq_ttl`/`dlq_retry_delay` из БД → репроцессор всё дропал как `ttl_dropped`.
