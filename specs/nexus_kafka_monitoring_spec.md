# Nexus — ТЗ-фрагмент: мониторинг Kafka

Этот файл — дополнение к основному ТЗ (`data_bus_spec.md`). Описывает новый раздел админ-панели **Settings → Kafka**: dashboard с метриками Kafka за выбранный период, доступный только администраторам.

Где встраивается в основное ТЗ: §6 (метрики Prometheus), §7 (веб-интерфейс — новый подраздел), §11 (Web API — новый эндпоинт), §15 (критерии приёмки).

---

## 1. Цель раздела

Один экран, открыв который администратор за **30 секунд** понимает:

- Шина живёт нормально или есть просадка throughput.
- Сообщения не накапливаются в Kafka — Sender справляется с темпом.
- Нет деградаций со стороны брокера (под-репликация партиций, недоступные ISR).
- Сколько сообщений прошло за период и какая доля их провалилась.
- Кто из узлов — top consumer / top producer (для понимания нагрузки).

Это **не** Grafana-замена. В Grafana уйдёт всё детальное расследование с произвольными запросами по labels. Этот экран — alarm dashboard: «всё ли в порядке прямо сейчас и в последние N часов».

---

## 2. Доступ

Раздел виден **только админам**. Для `viewer` пункт «Kafka» в боковой навигации настроек не отображается. Прямое обращение к API эндпоинтам без админских прав → 403 Forbidden.

Это решение: Kafka-метрики не содержат чувствительных данных как таковых, но показывают подробности инфраструктуры (адреса брокеров, размеры топиков), которые `viewer` знать не должен.

---

## 3. Источники данных

### 3.1 Prometheus-метрики Nexus

Уже существуют в основном ТЗ (§6) и используются здесь:

```
databus_kafka_produced_total{topic, status="ok|failed"}    counter
databus_kafka_consumed_total{topic, status="ok|failed"}    counter
databus_kafka_produce_duration_seconds{topic}              histogram
databus_kafka_consumer_lag{topic, partition, group}        gauge
databus_messages_in_flight{component}                       gauge
```

Эти метрики счётчики/гистограммы, и для отображения графиков «в реальном времени» используется PromQL: `rate(databus_kafka_produced_total[1m])` — мгновенная скорость, `sum_over_time(...)` — суммарные значения за период.

### 3.2 Kafka Admin API

Метрики, которые есть только у брокера и которых нет в Prometheus:

- Список топиков с числом партиций, replication factor.
- Размер каждого топика на диске (через `DescribeLogDirs`).
- Состояние ISR (in-sync replicas) на партицию.
- Список consumer groups и их offsets.
- Состояние самих брокеров (online/offline, leader для partition).

Web Service использует тот же Kafka-клиент, что Receiver/Sender (`segmentio/kafka-go` или `IBM/sarama`, выбирается единый клиент в проекте). Создаёт отдельный `kafka.Client` с правами read-only на cluster metadata, кеширует ответы в Redis с TTL 30 секунд (детальное обновление — кнопкой «Обновить» в UI или автоматически каждые 10 секунд при открытом экране).

### 3.3 Что НЕ берём из Kafka

- Тела сообщений. Они уходят в ClickHouse-логи узлов (см. §4.3 основного ТЗ), а не в Kafka-мониторинг.
- Историю старше retention топика (по умолчанию 30 дней). Для long-term хранения метрик есть Prometheus — он и используется для графиков за длинные периоды.

## 4. Endpoints Web API

### 4.1 `GET /api/kafka/overview?period=1h|3h|24h|7d|14d|30d|custom&from=&to=`

Сводка для главного блока. Возвращает:

```json
{
  "period": { "from": "2026-05-31T08:00:00Z", "to": "2026-05-31T14:00:00Z" },
  "summary": {
    "produced_total": 1248302,
    "consumed_total": 1248104,
    "failed_produced": 12,
    "failed_consumed": 184,
    "current_lag": 312,
    "in_flight_now": 47
  },
  "delta_vs_previous_period": {
    "produced": "+8.2%",
    "consumed": "+7.9%"
  },
  "broker_health": {
    "brokers_total": 3,
    "brokers_online": 3,
    "under_replicated_partitions": 0,
    "offline_partitions": 0
  }
}
```

`period=custom` принимает `from` и `to` в ISO-8601. Лимит на произвольный период — 90 дней (защита от слишком тяжёлых запросов).

### 4.2 `GET /api/kafka/timeseries?period=...&metrics=produced,consumed,lag,errors`

Возвращает несколько временных рядов в одном запросе для построения графика. Шаг (bucket) выбирается автоматически по периоду: 1ч → 30 сек, 24ч → 5 минут, 30д → 1 час.

```json
{
  "step_seconds": 30,
  "series": {
    "produced": [{"t": "...", "v": 412}, ...],
    "consumed": [{"t": "...", "v": 408}, ...],
    "lag":      [{"t": "...", "v": 23}, ...],
    "errors":   [{"t": "...", "v": 1}, ...]
  }
}
```

Под капотом — PromQL-запросы к Prometheus через стандартный `/api/v1/query_range`. Web Service не делает агрегации сам, перекладывает на Prometheus.

### 4.3 `GET /api/kafka/topics`

Список топиков с подробностями. Используется для блока «Топики» на экране.

```json
{
  "topics": [
    {
      "name": "databus.async",
      "partitions": 4,
      "replication_factor": 3,
      "size_bytes": 12483920384,
      "messages_estimate": 8421033,
      "retention_ms": 2592000000,
      "consumer_groups": [
        { "group": "sender-1", "lag_total": 312, "members": 4 }
      ],
      "under_replicated": 0,
      "offline_partitions": 0
    }
  ]
}
```

`messages_estimate` — приблизительное число сообщений (high_watermark - low_watermark по всем партициям). Точное число Kafka не возвращает.

### 4.4 `GET /api/kafka/by-node?period=...`

Распределение нагрузки по узлам шины. Возвращает топ-узлов по числу обработанных async-сообщений за период:

```json
{
  "top_producers": [
    { "node_path": "billing-events", "produced": 482103, "share": "38.6%" },
    { "node_path": "geo/notify",     "produced": 312044, "share": "25.0%" }
  ],
  "top_failures": [
    { "node_path": "old/legacy",     "failed": 142,    "rate": "12.4%" }
  ]
}
```

Полезно для понимания «кто грузит» и «у кого болит».

### 4.5 `POST /api/kafka/test` (только admin)

Простой ping брокеров: подключение, выполнение `Metadata` запроса. Возвращает время отклика каждого брокера и предупреждения, если что-то не так. Используется кнопкой «Проверить кластер» в шапке экрана.

```json
{
  "ok": true,
  "brokers": [
    { "addr": "kafka-1:9092", "elapsed_ms": 12, "ok": true },
    { "addr": "kafka-2:9092", "elapsed_ms": 14, "ok": true },
    { "addr": "kafka-3:9092", "elapsed_ms": 41, "ok": true, "warn": "elevated latency" }
  ]
}
```

## 5. UI экрана (§7.17 в основном ТЗ)

Расположение: **Settings → Kafka**. Структура сверху вниз:

### 5.1 Шапка экрана

- Хлебные крошки: `Настройки / Kafka`.
- Подзаголовок: «Мониторинг и состояние кластера».
- **Селектор периода** (унифицирован с другими экранами): сегментированный контрол `1ч · 3ч · 24ч · 7д · 14д · 30д · Произвольный`. По умолчанию выбран `1ч`. Произвольный открывает date-range picker.
- **Индикатор актуальности данных** — `Обновлено N секунд назад`, с автообновлением раз в 10 секунд.
- Кнопка «Обновить» (ручное обновление вне таймера).
- Кнопка «Проверить кластер» — вызывает §4.5.

### 5.2 Health banner

Полоса баннера сразу под шапкой, цвет зависит от состояния:

- 🟢 **Зелёный «Кластер здоров»** — все брокеры online, нет under-replicated партиций, lag не растёт.
- 🟡 **Жёлтый «Внимание»** — lag растёт быстрее, чем consumer обрабатывает; ИЛИ есть under-replicated партиции; ИЛИ один брокер недоступен, но cluster держится. Текст конкретный, не общий: «Lag вырос с 0 до 1,200 за 5 минут».
- 🔴 **Красный «Критично»** — offline партиции; ИЛИ больше половины брокеров недоступны; ИЛИ producer не может писать. Это требует немедленной реакции.

Главный принцип: баннер **всегда** показывает то, что должен сделать админ. Не «у вас 12 ошибок» — это и так видно в KPI ниже, — а «consumer-group sender-1 встал, lag растёт со скоростью 200/сек, восстановите Sender».

### 5.3 KPI-блок (4 карточки)

В одной строке, расширенные KPI по сравнению с Overview:

1. **Сообщений за период**
   - Большое число (например, `1.24M`).
   - Под ним: `↑ produced: 1.24M · ↓ consumed: 1.23M`.
   - Дельта к предыдущему такому же периоду (`+8.2% vs last week`).

2. **Текущий lag**
   - Большое число (`312`).
   - Под ним: спарклайн за выбранный период.
   - Цвет: зелёный если < 100, жёлтый 100–1000, красный > 1000 ИЛИ растёт > 50/сек.

3. **Ошибок за период**
   - Число (например, `196`).
   - Распределение: `12 produce · 184 consume`.
   - Доля от общего числа (`0.016%`).
   - Цвет: зелёный < 0.1%, жёлтый 0.1–1%, красный > 1%.

4. **In-flight сейчас**
   - Сколько сообщений в данный момент в обработке (между produce и consume).
   - Под ним: ожидаемое время обработки очереди при текущем темпе.

### 5.4 Главный график (большой)

Multi-line chart на всю ширину, высота ~280 пикселей.

- **Линии**: produced (синяя сплошная), consumed (зелёная сплошная), errors (красная пунктирная).
- **Ось X**: время от начала до конца периода. Подписи адаптируются: `14:32`, `Mon 31`, `May 15` в зависимости от масштаба.
- **Ось Y слева**: rate (messages/sec) для produced/consumed/errors.
- **Hover**: вертикальная линия + tooltip с точными значениями для всех серий на этом моменте.
- **Live-индикатор**: если выбран период до 24ч и текущее время попадает в диапазон, последняя точка пульсирует.

Под графиком — селектор резрешения по умолчанию автоматический (зависит от периода), но с возможностью переключиться: `Auto · 10s · 1m · 5m · 1h`.

### 5.5 Lag chart (отдельный)

Меньший график (~180 пикселей), но не менее важный — показывает Kafka consumer lag:

- **Линия**: текущий lag (gauge, не rate).
- Если lag поднялся выше порога (1000) — на графике появляется красная зона над пороговой линией. Это визуально показывает «время, когда было плохо».
- При hover — разбивка по партициям (4 столбика mini-bar внутри tooltip).

Lag — главный сигнал «что-то не так», поэтому он на отдельном графике, не смешан с throughput.

### 5.6 Топики (таблица)

Таблица всех Kafka-топиков. Для каждого:

- Имя топика (`databus.async`, `databus.dlq`, …) — моноширинный.
- Партиций · replication factor.
- Размер на диске (форматированный — `12.5 GB`).
- Оценочное число сообщений.
- Consumer groups (chips с именем группы и текущим lag, если есть).
- Здоровье: chip `OK` / `under-replicated: 1` / `offline: 1`.

Колонка действий: «Открыть в Grafana» (если задана интеграция в config), «Перейти к узлам, использующим топик».

### 5.7 Топ-узлов по нагрузке (два блока side-by-side)

Левый: **Top producers** — таблица топ-10 узлов по числу сообщений, отправленных в Kafka за период. Каждая строка: имя узла (link на detail-страницу), число сообщений, доля от общего, мини-спарклайн.

Правый: **Top failures** — таблица топ-10 узлов с наибольшим числом ошибок. Колонки: имя узла, число ошибок, error rate в процентах. Подсветка строк: жёлтый > 1%, красный > 5%.

Если в `Top failures` пусто за период — показывается «✓ Никаких ошибок не зафиксировано», зелёный текст.

### 5.8 Состояние брокеров

Карточки по числу брокеров (3 для production-кластера, 1 для compose-сценария). Каждая:

- Адрес брокера (`kafka-1:9092`).
- Online/Offline индикатор.
- Время отклика на последний ping (от §4.5).
- Сколько partitions считают этот брокер leader.
- Предупреждение, если есть (например, «высокая задержка», «не в ISR для X партиций»).

## 6. Что считается «проблемой»

Конкретные пороги для UI-индикации (жёлтый/красный). Все пороги настраиваются в `web.kafka_alerts_thresholds.*`, но дефолты:

| Состояние | Порог жёлтый | Порог красный |
|---|---|---|
| Consumer lag (текущий) | > 100 сообщений | > 1000 ИЛИ растёт > 50/сек 5 минут подряд |
| Error rate (produced + consumed) | > 0.1% за период | > 1% за период |
| Under-replicated partitions | ≥ 1 | ≥ 1 если кластер > 1 брокера и `replication_factor > 1` |
| Offline partitions | – | ≥ 1 (всегда критично) |
| Brokers offline | 1 из N | > N/2 |
| Produce latency p95 | > 100ms | > 500ms |

Эти пороги вычисляются на каждом запросе `/api/kafka/overview`, результат идёт в `broker_health` и используется для health banner.

## 7. Обновление в реальном времени

При открытом экране — автообновление **каждые 10 секунд**. Это компромисс: чаще нагрузит Prometheus и Kafka AdminClient без пользы (Prometheus сам собирает scrape раз в 15с), реже — админ начнёт сомневаться, актуальны ли данные.

Кнопка «Обновить» рядом с индикатором актуальности — для случаев, когда нужно «сейчас же, не жди».

При переключении периода график перерисовывается мгновенно, остальные блоки запрашиваются заново.

## 8. Out of scope в v1

- **Тревоги по email/Slack.** Этот экран — пассивный мониторинг. Алертинг с уведомлениями вне UI — out of scope (планируется в v2 как часть «Notifications», см. §16 основного ТЗ).
- **Управление топиками.** Создание/удаление топиков, изменение конфигурации (retention, partitions) — out of scope. Этот экран read-only. Управление — через Kafka-CLI или внешний инструмент типа Conduktor.
- **Просмотр сообщений в Kafka.** Browse конкретных сообщений в топике — не делаем; для этого есть kcat, kafka-console-consumer. Если в Nexus понадобится — отдельный экран.
- **Per-topic графики.** Разбивка throughput по топикам в виде отдельных линий — не делаем в v1. В типовой инсталляции топиков 3-5, и общий график достаточно информативен.
- **Графики ресурсов брокера** (CPU, RAM, disk usage). Это уже зона ответственности кластерного мониторинга (Prometheus + node_exporter + Grafana), не Nexus.

## 9. Acceptance criteria (дополнение к §15 основного ТЗ)

- Раздел Settings → Kafka виден только админам. Для viewer прямой GET к `/api/kafka/*` возвращает 403.
- Селектор периода 1ч/3ч/24ч/7д/14д/30д работает, перетягивает все блоки экрана. «Произвольный» открывает date-picker с лимитом 90 дней.
- Health banner показывает зелёный/жёлтый/красный согласно порогам §6, с текстом, описывающим конкретную причину для не-зелёных состояний.
- 4 KPI-блока показывают значения за период, с дельтами к предыдущему такому же периоду.
- Главный график рисует produced/consumed/errors, разрешение шкалы выбирается автоматически по периоду.
- Lag-график рисует текущий lag с подсветкой зон выше порогов.
- Таблица топиков показывает все известные топики с размером, числом партиций, состоянием.
- Top producers / Top failures показывают по топ-10 узлов; пустой Top failures — зелёное сообщение.
- Состояние брокеров отображается карточками для каждого known broker'а.
- Автообновление работает раз в 10 секунд при открытом экране, кнопка «Обновить» инициирует немедленный запрос.
- Все эндпоинты `/api/kafka/*` имеют отдельный rate limit 60 req/min на пользователя (для предотвращения dashboard-флуда).
