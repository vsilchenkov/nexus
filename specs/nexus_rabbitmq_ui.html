§3.3 + §7.5 (RabbitMQAsync)

RabbitMQAsync — узел с забором из RabbitMQ

Третий тип узла. В отличие от request / requestAsync, не ждёт HTTP-вызова от клиента — сам периодически забирает сообщения из заданной RabbitMQ-очереди, кладёт в Kafka, дальше Sender отправляет их на target URL так же, как для requestAsync. Полезно для интеграций, где события уже лежат в корпоративной шине, и нужен RabbitMQ → HTTP мост без отдельного прокси-сервиса.

Параметры забора

Отдельная секция под подключением. pull_interval_sec — насколько часто опрашивать очередь; pull_batch_size — сколько сообщений брать за раз. Дефолты: 5 секунд / 100 сообщений — это разумная середина: быстрая реакция и без излишней нагрузки на брокер.

5

Куда отправлять

После забора сообщения пройдут через Sender и уйдут на target URL. Динамический URL from_request для этого типа скрыт — нет «входящего HTTP-запроса», в котором мог бы быть параметр. Только статичный адрес.

6

Поток данных

Что именно происходит после сохранения узла. Тот же путь через Kafka + Sender, что у requestAsync, но добавлен Puller-воркер впереди.

1 Puller (в Receiver) опрашивает billing.events.outbound каждые 5 секунд
2 Достал до 100 сообщений батчем через basic.get, не ack'ает их
3 → Публикует в databus.async topic, ключ = billing-events
4 Kafka подтверждает запись (acks=all)
5 → basic.ack в RabbitMQ — теперь сообщение точно не потеряется
6 Sender забирает из Kafka, отправляет POST https://api.partner.com/billing/webhook
7 Лог в ClickHouse: type=RabbitMQAsync, IP=rabbitmq://rmq.internal.company.ru:5672//
At-least-once. Если Receiver упадёт между Kafka-ack (шаг 4) и RabbitMQ-ack (шаг 5) — сообщение пройдёт повторно после рестарта. Получатель должен быть идемпотентен (по message_id из envelope) или мириться с редкими дублями.

Состояние · degraded (RabbitMQ недоступен)

Если RabbitMQ недоступен дольше 5 минут — узел автоматически переходит в degraded. Это не «отключён» (его никто не выключал, и он сам попытается восстановиться) — это «работает, но не может работать». В UI красный баннер с конкретной причиной и числом неудачных попыток.

Узел вернётся в active автоматически после восстановления связи. До этого момента новые сообщения в очереди не теряются — они остаются в RabbitMQ. Накопление видно в метрике databus_rmq_queue_depth.

Что Claude Code должен учесть

  • В Go использовать github.com/rabbitmq/amqp091-go — официальный поддерживаемый клиент. streadway/amqp заархивирован.
  • Puller-воркер живёт в Receiver-сервисе, не в Sender. Sender ничего не знает про RabbitMQ — он просто потребляет из Kafka как обычно.
  • Один amqp.Connection и amqp.Channel на узел; переоткрываются на ошибках. Не создавать соединение на каждый тик — это убьёт брокер при 50+ узлах.
  • Graceful shutdown: при SIGTERM или удалении узла — basic.nack всех необработанных, дождаться текущий батч (до 10с), закрыть канал.
  • Тест подключения через queue.declare с passive=true — это не создаёт очередь, только проверяет существование. Не использовать basic.get или consume для проверки — они изменят состояние очереди.
  • UI селектора типа — три карточки в одной сетке через компонент method-pick; при добавлении новых типов узлов сетка переключается на 4 колонки.
