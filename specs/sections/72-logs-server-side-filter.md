## 72. Серверная фильтрация логов узла (развивает §7.4/§35/§44/§48/§64/§67)

Боевой инцидент 2026-07-29 (узел `task/task_vika`): на вкладке «Логи» при фильтре «Ошибки» шапка
показывала **«Показано 3 из 33»**, скролл дальше не шёл, а остальные 30 ошибок посмотреть было
нельзя ни при каком размере страницы. То же — при фильтре «В работе».

Причина: быстрые фильтры применялись **в двух разных местах**.

| | список (`useInfiniteQuery`) | счётчик «из M» (`/logs/count`) |
|---|---|---|
| где фильтруется | в браузере, по уже загруженной странице | на сервере, `searchConds` |
| что показывает | 3 из 50 скачанных строк | 33 из всей таблицы |
| подгрузка | замирает, едва появился скроллбар | — |

Раздел переносит фильтрацию на сервер целиком, попутно чинит семантику «ошибки», распространяет
пагинацию на вкладку «Очередь» и сокращает объём чтения ClickHouse.

### 72.1 Семантика «ОК» / «Ошибки» — полное дополнение

Определений ошибки в коде было четыре, и они расходились. SQL считал `ok = status BETWEEN 200 AND
299`, `err = (status >= 400 OR status = 0)`; клиентский фильтр списка — «всё, что не завершено
успешно»; подсветка строки — третье; `CountErrors` §20.3 — четвёртое.

Практические последствия первых двух:

- запись с **3xx** (редирект §50) не проходила НИ ОДИН из быстрых фильтров и пропадала из UI при
  любом выборе, кроме «Все»;
- **незавершённая** запись с кодом 2xx числилась успехом.

Закреплена одна пара предикатов:

```
ok  = (done = 1 AND status >= 200 AND status < 400)
err = NOT ok
```

Свойство, ради которого так: `ok ∪ err` = все записи, `ok ∩ err` = ∅. Взят ровно тот предикат,
который применял клиентский фильтр и применяет красная подсветка строки, — то есть **видимое
поведение списка не изменилось**, изменились счётчик и раскраска пограничных случаев.

Реализаций две и они обязаны меняться только вместе: SQL (`condLogOK`/`condLogErr` в
`adapter/out/clickhouse/log_reader.go`) и in-memory зеркало live-tail (`logRecordOK` в
`usecase/logs.go`). На фронте тот же предикат — `isLogOK` (`lib/logsQuery.ts`), им подсвечиваются
строки и в журнале логов, и в «Последних запросах» вкладки «Обзор».

Семантика `done` (`yes`/`no` → `done = 1`/`done = 0`) **не менялась**: на ней держатся KPI неудачных
доставок §35 (`CountFailed`), `FailedIDs`, `DeleteFailed` и счётчики дашборда §44.

Осознанное расхождение: `CountErrors` §20.3 (`status >= 400 OR status = 0 OR done = 0`) остаётся как
есть — она питает пороги Telegram-уведомлений, и её сдвиг менял бы условия срабатывания алертов.
Отличие от §72.1 — только по статусам 1xx.

### 72.2 Список, счётчик и стрим спрашивают один набор фильтров

Параметры запроса собирает единственный модуль `web-ui/src/lib/logsQuery.ts`
(`logsFilterParams` для `/logs` и `/logs/count`, `logsFilterSearch` для URL SSE-стрима). Быстрые
`status`/`done` входят в набор наравне с расширенными фильтрами §48/§67.

Требования:

- `status`/`done` **обязаны входить в `queryKey`** списка: без этого react-query отдаёт прежний кеш,
  список не перезапрашивается, и фильтр снова превращается в «спрятать строки уже загруженной
  страницы». Это самая незаметная часть — без неё всё выглядит рабочим, пока не посмотришь в сеть;
- клиентского пост-фильтра нет: строки таблицы — ровно то, что вернул сервер, поэтому «Показано N»
  и «из M» считают одно множество и сходятся по мере скролла;
- признак конца истории остаётся прежним (`items.length < limit`): `LIMIT` в ClickHouse применяется
  ПОСЛЕ `WHERE`, значит недобор страницы — это конец отфильтрованного набора;
- дип-линки §33.4/§35/§47.1 (`status=err`, `done=no`) фильтруются **первым же** запросом, а не после
  загрузки неотфильтрованной страницы;
- live-буфер очищается при (пере)подключении стрима: раньше не подходящие под фильтр записи дочищал
  клиентский фильтр, теперь их убирать некому;
- неразбираемое значение поля даты не отправляется. Это страховка, а не наблюдавшийся сбой:
  `LogDateField` собирает значение сам и битого не отдаёт, но `new Date("…").toISOString()` на
  невалидном входе бросает `RangeError` и уронил бы всю вкладку.

Потолок накопленных строк `MAX_INFINITE_ROWS = 1000` (§44.K) сохранён: теперь это 1000
отфильтрованных записей, и подсказка «Показаны первые 1000 записей» появляется только когда их
действительно больше.

### 72.3 «Неудачные доставки» вкладки «Очередь» листаются так же

Симптом тот же, но код был другой: список неудач читался обычным `useQuery` с жёстким `limit=50` и
**без пагинации вообще** — KPI показывал, скажем, 340 неудач, а посмотреть можно было 50.

Keyset-пагинация вынесена в общий хук `web-ui/src/lib/useInfiniteLogs.ts` (курсор `to` + `before_id`,
дедуп по `id`, потолок §44.K, подгрузка по скроллу и при недоборе высоты) и используется обеими
вкладками. Секция неудач получила свой скролл-контейнер, строку загрузки и подсказку о потолке.
Семантика `done=no` не менялась, поэтому KPI (`CountFailed`) и список остаются согласованными.

### 72.4 Сужение чтения ClickHouse по колонке партиционирования

Таблица логов партиционируется `PARTITION BY toYYYYMM(date_create)`, а временной фильтр read-path
строился только по `date_request`. Замер на 200 000 строк (окно в сутки, `system.query_log`):

| | read_rows | прочитано частей |
|---|---|---|
| только `date_request` | 200 000 | 3 из 3 |
| + границы по `date_create` | 8 192 | 1 из 3 |

То есть без явного условия по `date_create` ClickHouse читает таблицу целиком. Теперь `searchConds`
дублирует то же окно по `date_create` с запасом **±1 день** (часовые пояса, перекос часов между
инстансами Sender'а, записи, дошедшие до ClickHouse позже своего `date_request` через Kafka-retry
§38). Границы считаются в Go как UTC (`dayUTC`): `date_create` — UTC-день записи, а `DateTime`
рендерится в поясе сервера, поэтому `toDate(date_request)` в SQL дал бы сдвиг.

Сужение опирается на инвариант write-path Nexus — `DateCreate == DateRequest` (`sender/usecase/
send.go`, `dlq_reprocess.go`) — и поэтому **выключено для внешних таблиц §64**: туда пишет
посторонний сервис, инвариант не гарантирован, а сужение молча теряло бы записи. Разрешение доезжает
до адаптера как **capability порта** (`LogQuery.DateCreateAligned`), а не как копия поля узла: порт
описывает, что адаптеру разрешено, и нулевое значение безопасно.

Границы применимости, которые важно понимать:

- сужение работает только когда **задано окно**. На вкладке «Логи» без периода первая страница
  по-прежнему читает всю таблицу; со второй страницы верхняя граница приходит из keyset-курсора, и
  прунинг включается сам. Вкладка «Очередь» всегда шлёт период и выигрывает целиком;
- `count()` (счётчик «из M») сканирует набор без `LIMIT`, поэтому на больших таблицах он остаётся
  дороже списка; при превышении `countTimeout` (10 с) UI штатно деградирует до «Показано N» (§67).

### 72.5 Авто-рефетч не перезапрашивает всю накопленную историю

`useInfiniteQuery` при авто-рефетче перезапрашивает **все** накопленные страницы. Пользователь,
пролиставший журнал до потолка (20 страниц) и вернувшийся наверх, давал 20 запросов к ClickHouse
каждые 5 секунд с одной открытой вкладки. При возврате к верху контейнера кеш схлопывается до первой
страницы; вниз страницы догружаются обычным путём.

Штатный `maxPages` react-query для этого не подходит: он выбрасывает ПЕРВЫЕ страницы при
`fetchNextPage` и ломает накопительный список §44.K.

### 72.6 Что раздел НЕ закрывает

- **`CountErrors` §20.3** и пороги Telegram-уведомлений — семантика ошибки там своя (см. §72.1).
- **`ListSince`** (поллинг live-tail) сужения по `date_create` не получил: потребовалась бы смена
  сигнатуры порта, а запрос уходит раз в секунду на каждого подписчика — отдельная задача.
- **Виртуализация таблицы логов** и снятие потолка `MAX_INFINITE_ROWS = 1000`.
- **Data-skipping индексы** по `status`/`done` в шаблонах §19: применение к существующим таблицам
  требует §56-синхронизации и гейта владения §70, а для внешних таблиц §64 невозможно.
- **Чтение в порядке ключа сортировки** (`ORDER BY date_create DESC, …`, read-in-order с ранней
  остановкой по `LIMIT`). Замер показал сокращение чтения примерно вдвое на 200 000 строк — меньше,
  чем даёт §72.4, и с риском деградации на фильтрах, не находящих ничего свежего. Кандидат на
  отдельную задачу с профилированием.
- **Общая таблица §37 в момент недоступности PostgreSQL.** Тогда снимок фактов о таблицах не
  строится и фильтр атрибуции §61 деградирует в мягкий (`node_id = ? OR node_id = ''`); в это узкое
  окно сужение §72.4 может отсечь чужие записи, попавшие под послабление. Запас ±1 день покрывает
  случай частично. В обычной работе (с 1.22.5) фильтр строгий везде, кроме внешних таблиц §64,
  поэтому окно сузилось до времени недоступности базы.
