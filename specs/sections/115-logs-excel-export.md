# 115. Выгрузка логов узла в Excel и иконка вкладки

Раздел добавляет на вкладку «Логи» узла кнопку **«Выгрузить»**: она открывает форму, которая
выгружает журнал узла в файл Excel (`.xlsx`) по фильтрам вкладки — все колонки таблицы логов
ClickHouse. Заодно чинится иконка вкладки браузера.

Развивает [§7.4](07-web-ui.md) (вкладка «Логи»), [§42](42-log-body-streaming.md) (ленивые тела),
[§48](48-log-search-extended.md) (расширенный поиск), [§61](61-log-attribution-and-move-preview.md) и
[§64](64-manual-external-table.md) (приписка строк узлу, внешняя таблица), [§72](72-logs-server-side-filter.md)
(единый набор фильтров), [§77](77-logs-ux-and-scale.md) (стоимость чтения журнала), [§78.6](78-node-url-and-log-counters.md)
(запись ≠ прогон), [§95](95-log-secret-masking.md) (маскирование), [§26](26-roles-access-control.md) (роли).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций нет.** Новые ключи
`config.yml` — секция `web.logs_export` (115.6). Выкатывается только Web.

---

## 115.1 Повод

- **Иконка.** На вкладке браузера вместо логотипа — пустой документ. `index.html` ссылался на
  `/nexus.svg`, но такого файла в репозитории не было, а встроенная файловая система Web содержит
  только `index.html` и `assets/`: запрос уходил в SPA-fallback и получал `index.html` с
  `text/html`, который браузер иконкой не считает.
- **Выгрузка.** Журнал узла можно было только листать и раскрывать по одной записи. Для разбора
  инцидента, сверки с приёмником или передачи смежной команде нужен файл: строки по фильтру со
  всеми полями, которые хранит ClickHouse.

## 115.2 Иконка вкладки

Знак из сайдбара (скруглённый квадрат с градиентом `accent → ok` тёмной темы и белой стрелкой
`ArrowLeftRight`) лежит в `web-ui/src/assets/nexus.svg`; `index.html` ссылается на него как на
исходник, и сборка выпускает хешированный `/assets/nexus-<hash>.svg`. Этот путь Web уже отдаёт как
статику с правильным MIME и годовым кешем. Правок Go нет: файл в корне (`/nexus.svg`) потребовал бы
и директивы встраивания, и отдельного маршрута с другим заголовком кеша (имя не хешировано).

## 115.3 Что выгружается

- **Колонки** — все 25 колонок таблицы логов узла, в порядке схемы и под их именами в ClickHouse:
  `ID, type, http_method, url, method, parameters, request, response, status, reason,
  date_create, date_request, date_response, duration, done, checksum_request, checksum_response,
  Host, IP, client_host, attempts, attempts_details, node_id, request_size, response_size`.
  Заголовки не переводятся: это идентификаторы хранилища, по которым их ищут в документации и SQL.
  Если в форме снят флажок «Тела запроса и ответа», колонок `request` и `response` в файле нет.
- **Единица — запись**, как в списке журнала и счётчике «Показано N из M» (§78.6): по каждому `ID`
  берётся новейший прогон доставки, подходящий под фильтр. Остальные прогоны видны в
  `attempts`/`attempts_details`.
- **Порядок** — как на вкладке: новые сверху (`date_request DESC, ID DESC`).
- **Типы ячеек**: числа — числами, `done` — логическим значением, даты — настоящими датами Excel в
  часовом поясе браузера (передаётся IANA-именем; неизвестное имя → UTC). Нулевая дата
  (`date_response` незавершённого прогона) — пустая ячейка.
- **Строки — только как текст** (`inlineStr`), формулы файл не содержит никогда: значение
  `=HYPERLINK(…)` в теле или URL остаётся текстом и не исполняется при открытии.

Файл содержит два листа:

| Лист | Содержимое |
|---|---|
| «Логи» / «Logs» | данные; закреплённая строка заголовка, автофильтр, ширины колонок |
| «Параметры» / «Parameters» | узел, команда, таблица ClickHouse, период, фильтры, единица выгрузки, найдено и выгружено, лимиты, число обрезанных тел, **статус полноты**, часовой пояс, кто и когда выгрузил, версия Nexus |

Имя файла — `nexus-logs-<путь узла>-<ГГГГММДД-ЧЧММСС>.xlsx`.

## 115.4 Форма выгрузки

Кнопка **«⬇ Выгрузить»** стоит справа от «Сбросить» в панели расширенных фильтров вкладки «Логи»
узла (видна, когда панель раскрыта). Панель общая с вкладкой «Метрики» и диалогом «Повтор за
период» — там кнопки нет.

```
Поиск [order_id:123.................. Aa ab| .*]            Method [▾ все      ]
Дата с [07.10 00:00]  Дата по [07.10 23:59]  Клиент [▾ все]   [Сбросить] [⬇ Выгрузить]
```

Форма — один экран:

```
┌─ Выгрузка логов в Excel ──────────────────────────────── ✕ ┐
│ gate/PDT_PDTExchange · request                              │
│ ФИЛЬТРЫ ВКЛАДКИ «ЛОГИ»                                      │
│ ┌─────────────────────────────────────────────────────────┐ │
│ │ Поиск       order_id:123  [Aa .*]                       │ │
│ │ Период      07.10.2026 00:00 — 07.10.2026 23:59         │ │
│ │ Состояние   Ошибки                                      │ │
│ │ Method      любой                                       │ │
│ │ Клиент      любой                                       │ │
│ │ Прогон      Не завершён      (только с дип-линка done)  │ │
│ └─────────────────────────────────────────────────────────┘ │
│ Выгружается ровно то, что показывает журнал. Чтобы изменить │
│ фильтры, закройте форму и поправьте их на вкладке.          │
│ ОБЪЁМ                                                       │
│ Строк не более [ 50 000 ▾ ]   (1 000 / 10 000 / 50 000)     │
│ [x] Тела запроса и ответа (до 32 767 символов в ячейке)     │
│ ┌ Оценка ─────────────────────────────────────────────────┐ │
│ │ Найдено записей: 12 345 · В файл: 12 345                │ │
│ │ Объём данных: ≈ 38 МБ — по среднему размеру записи      │ │
│ │ [!] Оценка выше лимита 100 МБ — выгрузка может          │ │
│ │     остановиться раньше (только при упоре)              │ │
│ └─────────────────────────────────────────────────────────┘ │
│ ⚠ Тела не маскируются: возможны персональные данные и      │
│   секреты. Выгрузка фиксируется в журнале аудита.           │
│                          [Отмена] [⬇ Выгрузить .xlsx]       │
└─────────────────────────────────────────────────────────────┘
```

- **Фильтры** — сводка фильтров вкладки **только для чтения** (поиск с режимами, период, состояние,
  method, клиент и `done` из дип-линка «Очереди»): выгружается ровно то, что показывает журнал.
  Второй панели фильтров в форме нет — два поля «Поиск» на экране путали, а правка в форме
  расходилась бы с журналом за ней. Чтобы изменить фильтр, форму закрывают и правят его на
  вкладке. Поиск, набранный в панели без Enter, кнопка «Выгрузить» применяет к вкладке до
  открытия формы — он попадает и в журнал, и в выгрузку. Без дат при заданном поиске форма
  предупреждает: выгружаются последние записи всей истории.
- **Строк не более** — 1 000 / 10 000 / потолок `max_rows` (по умолчанию выбран потолок).
- **Тела** — по умолчанию включены (выгружаются все колонки). Тело в ячейке режется до
  `max_body_chars` (не больше 32 767 — предела ячейки Excel) с пометкой об обрезке.
- **Оценка** пересчитывается сама при смене предела строк и флажка тел: найдено записей, сколько
  попадёт в файл (по пределу строк), примерный объём данных и предупреждение, если оценка выше
  лимита объёма. Источник — `request_size`/`response_size` (§42.10), тела с диска ради неё не
  читаются. Объём считается **по среднему размеру записи** (на запись — среднее тело на прогон,
  урезанное до `max_body_chars`), поэтому сколько записей войдёт в лимит объёма, форма **не
  называет**: записи пишутся от новых к старым, и при неравномерных телах среднее даёт ошибку в
  разы (на стенде — «≈ 397» против фактических 1 579). Недоступная оценка (ClickHouse не ответил
  за 10 с) выгрузку не блокирует.
- **Во время выгрузки** — полученный объём, кнопка «Остановить» (рвёт запрос в браузере, Web и
  ClickHouse). Закрытие формы тоже прерывает выгрузку.
- **Ошибки** — текстом в форме: неверный поисковый запрос, узел не найден, ClickHouse недоступен,
  слишком много выгрузок сейчас, превышена частота.

## 115.5 API

Оба маршрута — для всех ролей (viewer и выше), **только браузерная сессия**: API-токен получает
403 (как live-tail `/logs/stream`). Узел чужой команды — 404, как у остальных маршрутов журнала.
Фильтры — те же параметры, что у `GET /api/nodes/{id}/logs` (`q`, `q_case`, `q_word`, `q_regex`,
`method`, `ip`, `client_host`, `from`, `to`, `status`, `done`).

- `GET /api/nodes/{id}/logs/export/estimate` → `{records, rows, request_bytes, response_bytes,
  max_rows, max_bytes, max_body_chars, logs_configured, logs_available}`. `records` — уникальные
  записи (`uniqExact(ID)`), `rows` — строки-прогоны, размеры — сумма `least(size, кап ячейки)`.
  Таймаут 10 с; недоступный ClickHouse → 200 с `logs_available=false`; у узла без таблицы логов —
  200 с `logs_configured=false` (выгрузка такого узла — 404). Лимиты в ответе есть всегда.
- `GET /api/nodes/{id}/logs/export.xlsx?rows=&bodies=1&tz=Europe/Moscow` → файл, потоком.
  Заголовки: `Content-Disposition: attachment`, `Cache-Control: no-store`,
  `X-Accel-Buffering: no`, `X-Nexus-Export-Rows` — сколько записей отобрано.

| Ответ | Когда |
|---|---|
| 400 `error.bad_search_query` | синтаксис поиска |
| 404 | узла нет или он чужой |
| 429 + `Retry-After` | превышена частота запусков на пользователя |
| 503 + `Retry-After` | на реплике уже идёт `max_concurrent` выгрузок (nginx перекидывает GET на соседнюю реплику) |
| 500 `error.logs_unavailable` | ClickHouse недоступен до начала потока |
| 500 `logs_export.timeout` | ClickHouse не успел отобрать записи за `query_timeout_sec` («задайте период или сузьте поиск») |

Отказ ClickHouse — **500, а не 503/504**, намеренно: их nginx (`proxy_next_upstream http_502
http_503 http_504`) повторяет на соседней реплике, а ClickHouse у реплик общий — тот же тяжёлый
отбор ключей ушёл бы второй раз и съел вторую единицу лимита частоты. 503 остаётся только у
«занято», где соседняя реплика действительно может помочь. В Sentry 500 событием не уходит
(только предупреждение в логе).

## 115.6 Лимиты и защита

Секция `web.logs_export` конфигурации Web (меняется только конфигом, рестарт Web):

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `max_rows` | 50 000 | потолок записей в файле (≤ 1 048 575 — строк листа Excel) |
| `max_bytes` | 104 857 600 (100 МиБ) | бюджет текста ячеек; на исчерпании выгрузка останавливается со статусом «ограничена объёмом» |
| `max_body_chars` | 32 767 | символов тела в ячейке (≤ 32 767) |
| `max_concurrent` | 2 | одновременных выгрузок на реплику Web |
| `rate_limit_per_user_per_min` | 5 | запусков выгрузки на пользователя в минуту (оценка не считается) |
| `query_timeout_sec` | 60 | таймаут шага в ClickHouse: отбор ключей целиком (все раунды) и каждый батч строк |

Как это бережёт хранилища и машины:

- **ClickHouse.** Сначала отбираются только ключи записей — `ID` и время — top-N по лёгким
  колонкам (115.7). Тела читаются батчами по 50–100 записей, каждый батч — по своим `ID` в узком
  окне времени с отсечением партиций. Тело режется в ClickHouse (`substringUTF8`), в Web приезжает
  не больше кап'а. Каждый шаг — отбор ключей (все раунды вместе) и каждый батч строк — со своим
  таймаутом (clickhouse-go переводит дедлайн в `max_execution_time`). Разрыв соединения отменяет
  текущий запрос.
- **Web.** Файл пишется потоком прямо в ответ: память держит один батч, а не файл. Батч
  дочитывается из ClickHouse целиком до записи клиенту, поэтому медленный клиент не держит
  соединение пула. Слот на реплику и частота на пользователя.
- **ПК пользователя.** Не больше `max_rows` строк и `max_bytes` текста; ячейка — не больше предела
  Excel. Файл сжат (типично в 3–10 раз меньше бюджета).

## 115.7 Чтение: ключи, затем строки

1. **Ключи.** `SELECT ID, ts … WHERE <фильтр журнала> ORDER BY date_request DESC, ID DESC LIMIT n`
   по **строкам**, без `LIMIT 1 BY ID`: с ним ClickHouse не применяет top-N-сортировку и сортирует
   все пары «ID × время» под фильтром (на 11 млн строк без периода — сотни мегабайт). Дубли `ID`
   (несколько прогонов) отбрасываются в Web по первому вхождению — это новейший подходящий прогон,
   то есть ровно то, что выбирает `LIMIT 1 BY ID` списка. Если после отбрасывания не хватило,
   чтение продолжается keyset-курсором `(date_request, ID)`; нулевое время (`date_request`, не
   заполненный писателем внешней таблицы §64) идёт отдельным условием — курсор списка его не
   выражает («0 — без границы»), и без этого чтение остановилось бы, а выгрузка вышла «полной».
   Берётся `rows + 1` запись — так видно, что подходящих больше лимита. Ключ несёт `ID`, время
   прогона и его `date_create`.
2. **Строки.** Для батча ключей — `WHERE <фильтр журнала> AND ID IN (…) AND date_create IN (…)
   AND date_request BETWEEN <мин> AND <макс> … LIMIT 1 BY ID`. Фильтр повторяется, чтобы из
   нескольких прогонов взять тот же, что отобран ключом. Узкое окно держат два условия по ключу
   сортировки `(date_create, date_request)`: `date_create IN` — значения из самих ключей, поэтому
   сужение верно и на внешней таблице §64, где `date_create` не связан с `date_request` (без него
   ClickHouse не отсекает гранулы и по `date_request`: батч на внешней таблице читал 200 000 строк
   из 200 000, с ним — одну гранулу); `date_request` — голый, без обёртки в `toDateTime64`, иначе
   гранулы внутри дня не отсекаются. Строки батча раскладываются в порядке ключей; запись,
   исчезнувшая между запросами (очистка неудачных §79.2, TTL), пропускается и считается.
3. Автоокно §77 к выгрузке не применяется: лимит выгрузки и top-N сами ограничивают чтение, а
   пробы окон лишь умножили бы запросы.

## 115.8 Полнота выгрузки

Статус пишется на лист «Параметры»:

| Статус | Когда |
|---|---|
| полная | выгружены все подходящие записи |
| ограничена строками | подходящих больше `rows` |
| ограничена объёмом | исчерпан `max_bytes` |
| **НЕПОЛНАЯ** + причина | ClickHouse отказал посреди выгрузки; файл закрывается корректно и открывается на листе «Параметры» |

Заголовки ответа уже отправлены, поэтому HTTP-статус неполноту не сообщает — только файл. Форма
говорит об этом прямо: «полнота — на листе «Параметры»». Разрыв со стороны клиента (Остановить,
закрытие вкладки) файл не дописывает.

## 115.9 Аудит

Действие `node.logs_export`, объект — узел. В деталях: фильтры (поисковая строка — до 200
символов), число строк и байт, включены ли тела, статус. Тела и значения ячеек в журнал аудита не
попадают. Запись делается и при прерванной выгрузке (контекст без отмены).

## 115.10 Границы

- **Тела не маскируются** (§95.8): любой пользователь, видящий узел, может выгрузить тела
  массово — так же, как раскрыть их по одной в журнале. Смягчение — предупреждение в форме и аудит.
- Лимит частоты при недоступном Redis не действует (fail-open, как у повтора); слот — на реплику,
  по кластеру одновременно идёт до «реплики × `max_concurrent`» выгрузок.
- Полнотекстовый поиск без периода остаётся дорогим (§77) — выгрузка упирается в таймаут запроса,
  форма предупреждает об отсутствии дат.
- `substringUTF8` ограничивает передачу в Web, но ClickHouse читает тело с диска целиком.
- Неполнота после начала потока видна только в файле.
- Плавная остановка Web ждёт 30 с: более долгая выгрузка на гасимой реплике обрывается (браузер
  покажет ошибку сети).
- Оценка объёма — верхняя граница: размеры полного тела, а не сохранённой копии.
- **«Остановить» после того, как сервер дописал файл**, загрузку в браузере обрывает, а в аудите
  остаётся завершённая выгрузка: ответ уже целиком ушёл в сокет (буферы nginx и ОС), и Web о
  разрыве не узнаёт. Аудит фиксирует, что файл ВЫДАН, а не что его сохранили.
- Предел ячейки Excel — 32 767 единиц UTF-16, а `max_body_chars` — символы: тело с эмодзи (две
  единицы на символ) может не влезть в ячейку и при длине в пределах `max_body_chars` — тогда оно
  тоже режется с маркером и учитывается в «Обрезано тел».
- Даты до 1970 года во внешней таблице §64 (`DateTime64` с отрицательным временем) батч строк не
  находит: голый `date_request BETWEEN` строится через `toDateTime`, а тот насыщает отрицательные
  секунды до `1970-01-01 00:00:00` (проверено на ClickHouse 24.10). Такие записи считаются
  исчезнувшими.

## 115.11 Вне рамок

- Выгрузка нескольких узлов разом, по расписанию, в CSV/JSON.
- Все прогоны доставки построчно (сейчас — запись = новейший подходящий прогон).
- Выбор колонок, кроме отключения тел.
- Выгрузка по API-токену.
- Настройка лимитов в интерфейсе.
