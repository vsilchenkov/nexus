# 112. Ротация логов контейнеров Docker

Раздел ограничивает рост логов контейнеров стека Nexus на диске docker-хоста. До §112 ни один
compose-файл не задавал `logging:`, и Docker писал вывод каждого контейнера драйвером `json-file`
**без ограничения размера**: файл `/var/lib/docker/containers/<id>/<id>-json.log` рос всё время
жизни контейнера и обнулялся только при его пересоздании.

Развивает [§5.4 DEPLOYMENT](../../DEPLOYMENT.md) (ресурсы сервера), [§93](93-ha-replicas.md)
(пары реплик — вдвое больше контейнеров приложения).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций нет, ключей
`config.yml` нет, интерфейс не меняется.** Новые переменные `.env` необязательны — у обеих есть
дефолт.

---

## 112.1 Повод

Разбор диска боевого `srv-p-1c-bus` 01.10.2026 (корневой раздел занят на 80 %):

| Контейнер | Лог `json-file` | Возраст контейнера |
|---|---|---|
| `nexus-nginx-1` | **1.2 ГБ** | 4 недели |
| `nexus-kafka-1` | 17 МБ | 4 недели |
| остальные | единицы МБ | от 10 минут до 2 месяцев |

Балансировщик пишет access-лог на каждый запрос шины — около 43 МБ в сутки, то есть ~15 ГБ в год
на один контейнер. Остальные сервисы растут медленнее, но тоже без потолка. `/etc/docker/daemon.json`
на сервере отсутствует, `docker inspect` у всех семи контейнеров показывает `LogConfig` без опций.
Основной объём того диска занимают не логи Nexus (журнал событий 1C ESB — 124 ГБ), но неограниченный
рост — дефект поставки: его нельзя исправить «настройкой сервера», не зная о нём.

## 112.2 Решение

Каждый сервис, который **создаёт контейнер** (у него есть `image:` или `build:`), объявляет:

```yaml
x-logging: &logging
  driver: json-file
  options:
    max-size: ${DOCKER_LOG_MAX_SIZE:-50m}
    max-file: "${DOCKER_LOG_MAX_FILE:-5}"

services:
  web:
    logging: *logging
```

- **Потолок на контейнер** = `max-size × max-file` = 250 МБ по умолчанию. Одиночный стек
  (8 контейнеров с nginx) — не больше 2 ГБ, пары реплик §93 (11 контейнеров) — не больше 2.75 ГБ.
- **Глубина `docker logs`** у nginx при нынешнем темпе — около 6 суток; у сервисов приложения —
  больше. Журнал запросов шины хранится в ClickHouse и от этого не зависит.
- **Драйвер остаётся `json-file`.** Формат файлов, `docker logs`/`docker compose logs` и внешние
  сборщики, читающие `*-json.log`, работают как раньше. Ротированные куски (`…-json.log.1` … `.4`)
  `docker logs` читает тоже.
- **Параметры из `.env`**, один набор на весь стек:

| Переменная | Назначение | Дефолт |
|---|---|---|
| `DOCKER_LOG_MAX_SIZE` | Размер одного файла лога контейнера до ротации (`k`, `m`, `g`) | `50m` |
| `DOCKER_LOG_MAX_FILE` | Сколько файлов хранить на контейнер, включая текущий | `5` |

### 112.2.1 Почему в compose, а не в `/etc/docker/daemon.json`

| | compose (`logging:` у сервиса) | `daemon.json` (`log-opts`) |
|---|---|---|
| Приезжает с тегом релиза | да | нет — ручная правка хоста, о которой надо знать |
| Затрагивает чужие контейнеры хоста | нет | да — на боевом хосте живут и не-Nexus процессы |
| Применение | пересоздание контейнеров Nexus | **рестарт dockerd** (все контейнеры хоста) + пересоздание |
| Видно в репозитории и в `docker compose config` | да | нет |

`daemon.json` остаётся доступным оператору как общая политика хоста; явный `logging:` сервиса её
перекрывает.

### 112.2.2 Почему не драйвер `local`

`local` ротирует по умолчанию (20 МБ × 5) и сжимает, но меняет формат файлов на диске: сломались бы
сборщики логов, читающие `*-json.log`, и привычные ручные `tail`/`grep` по этим файлам. Выигрыш по
месту при потолке 250 МБ на контейнер не стоит смены формата.

## 112.3 Какие файлы

Правило — **«каждый сервис с `image:`/`build:` в каждом compose-файле»**. Сервисы-заплатки в
оверлеях (только `ports`, `profiles`, `mem_limit` и т. п.) `logging` не объявляют: при наложении
compose сохраняет его из базового файла.

| Файл | Сервисы с `logging` |
|---|---|
| `docker-compose.yml` (прод, вариант C) | postgres, redis, kafka, prometheus, receiver, sender, web, nginx |
| `deploy/docker-compose.yml` (вариант A) | postgres, redis, clickhouse, kafka, prometheus, rabbitmq, receiver, sender, web, loadtest |
| `deploy/docker-compose.app.yml` (вариант B) | receiver, sender, web |
| `deploy/docker-compose.deps.yml` | postgres, redis, clickhouse, kafka, prometheus |
| `deploy/docker-compose.ha.yml` (§93) | nginx и пары `web-*`, `receiver-*`, `sender-*` (через якорь `x-app-base`) |
| `deploy/docker-compose.stand-ha.yml` | nginx и пары реплик (через якорь) |
| `deploy/docker-compose.standalone.override.yml`, `deploy/docker-compose.ha.standalone.override.yml` | clickhouse (сервис добавляется оверлеем) |

Якоря YAML не видны между файлами, поэтому `x-logging` повторён в каждом файле, где он нужен.
Расхождение значений между файлами ловит тест-страж (§112.5).

## 112.4 Применение на работающем стеке

`logging` — параметр **создания** контейнера: `docker compose restart` его не применяет, нужен
`up -d` (пересоздание). Отсюда три следствия.

1. **Обычный `docker compose up -d` после обновления пересоздаст ВСЕ контейнеры стека**, у которых
   изменилась спецификация, — включая Kafka (брокер недоступен 30–60 с, async-приём в это время
   отвечает ошибкой), Redis, Prometheus и nginx.
2. **Посервисный выкат с `--no-deps`** (порядок v1.36/v1.39: Receiver → Sender → Web) зависимости не
   трогает: Kafka, Redis, Prometheus и nginx продолжают писать без потолка, пока их не пересоздать.
   Пересоздать их отдельно, в тихое время:
   ```bash
   docker compose up -d --no-deps nginx prometheus redis
   docker compose up -d --no-deps kafka      # брокер недоступен 30–60 с
   ```
3. **Пересоздание удаляет старый файл лога** вместе с каталогом контейнера — место освобождается
   сразу (на боевом сервере — 1.2 ГБ nginx), но история `docker logs` до этого момента теряется.
   Нужна — сохранить заранее: `docker compose logs --no-color nginx > nginx-before-112.log`.

Проверка после применения:

```bash
docker inspect --format '{{.Name}} {{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}' $(docker ps -q)
# ожидается у каждого: json-file map[max-file:5 max-size:50m]
```

## 112.5 Тест-страж

`tests/deploy/compose_logging_test.go` разбирает каждый отслеживаемый compose-файл (корневой и
`deploy/docker-compose*.yml`) и для каждого сервиса с `image:`/`build:` — после разворачивания
якорей и `<<:` — требует `logging.driver: json-file` и опции `max-size`/`max-file` **ровно** в виде
`${DOCKER_LOG_MAX_SIZE:-50m}` / `${DOCKER_LOG_MAX_FILE:-5}`. Тест краснеет, если:

- в файл добавили сервис и забыли `logging` (так и появился бы следующий неограниченный лог);
- в одном файле поменяли дефолт, а в другом нет (один набор переменных на весь стек);
- шаблон файлов перестал находить compose-файлы (защита от пустого прогона).

Эффективную конфигурацию для основных сочетаний файлов дополнительно проверяет
`docker compose config` (ручная процедура в IMPLEMENTATION.md, нужен Docker).

## 112.6 Границы

§112 ограничивает **только stdout/stderr контейнеров Nexus**, которые пишет Docker. Не закрывает:

- **файлы внутри контейнеров**: GC-лог JVM Kafka (`/opt/kafka/logs/kafkaServer-gc.log`) уже
  ограничен самим JVM (`filecount=10,filesize=100M`); прочих файловых логов сервисы Nexus не пишут;
- **тома данных**: Prometheus (`PROMETHEUS_RETENTION`), Kafka (retention топиков), PostgreSQL,
  ClickHouse — у каждого своя политика хранения;
- **file-fallback NDJSON Sender'а** при недоступном ClickHouse — отдельный механизм;
- **контейнеры, поднятые не этими compose-файлами**, и чужие процессы хоста (journald, 1C ESB и т. п.);
- **внешний ClickHouse** и его системные таблицы-логи.

## 112.7 Вне рамок

- Централизованный сбор логов (Loki/ELK) — в Nexus логи запросов уже в ClickHouse, логи сервисов —
  в консоли «Логи» (§51) и Sentry.
- Сжатие ротированных файлов (`compress: "true"`) — при потолке 250 МБ на контейнер не нужно;
  включается правкой якоря, если понадобится.
- Разные потолки для разных сервисов — один набор на стек проще в эксплуатации; nginx при нынешнем
  темпе укладывается в 6 суток истории.
