# 70. Несколько нод Nexus на одном ClickHouse

Раздел вводит понятие **ноды (инстанса) Nexus** — самостоятельного развёртывания шины со своими
PostgreSQL, Redis и Kafka, которое пишет логи в **общий** с другими нодами ClickHouse.

Мотивация: разворачивается вторая нода (тестовый код — `kz`), а хранилище логов остаётся одно.
Сегодня это небезопасно: имя базы ClickHouse жёстко выводится из слага команды
(`CHDatabaseForSlug` = `"nexus_" + slug`, [domain/team.go](../../internal/domain/team.go)), поэтому
пространства имён двух нод совпадают — база `nexus_default` есть у каждой. При этом все
обслуживающие процедуры (housekeeping, поиск бесхозных таблиц, синхронизация схемы, стартовые
`ALTER`) берут список таблиц из **своего** PostgreSQL и не умеют отличить чужую таблицу от своей.
Вторая нода штатными фоновыми операциями удалит и перестроит данные первой — без единой ошибки в
логах, потому что с её точки зрения всё корректно.

Раздел развивает §18 (multi-tenancy: БД на команду), §19 (шаблоны таблиц), §4.3 (housekeeping),
§56 (синхронизация схемы), §64 (внешняя таблица), §14 (логирование и Sentry), §6 (метрики).
Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

**Принцип раздела:** нода **никогда** не выполняет разрушающую операцию над объектом ClickHouse,
владельцем которого она не является. Владение проверяется программно, а не «по договорённости об
именах».

## 70.1 Идентификатор ноды

Новая секция конфига (см. §8.3):

```yaml
instance:
  id: ${NEXUS_INSTANCE_ID:}           # пусто = текущая (первая) нода; иначе 1..8 символов
  adopt_unowned: ${NEXUS_ADOPT:false} # аварийное усыновление базы без маркера владения
```

- **Формат `id`: `^[a-z][a-z0-9]{0,7}$`** — от 1 до 8 символов (`kz`, `edo`, `pr2`); один символ не
  является обязательным или предпочтительным. Подчёркивание запрещено: иначе граница
  `nexus_<id>_<slug>` перестаёт читаться однозначно.
- **Пустое значение — валидно и означает «нода, существовавшая до этого раздела»**. Действующая
  боевая нода не мигрируется: у неё `instance.id` пуст, базы остаются `nexus_<slug>`, поведение
  сохраняется без изменений.
- Значение неизменяемо после первого запуска (§70.5).

`instance.id` — единственный идентификатор ноды на всю систему: он же суффикс имени базы (§70.2),
тег Sentry, метка метрик и атрибут логов (§70.7). Заводить отдельные идентификаторы для
наблюдаемости запрещено — они разъедутся.

## 70.2 Именование баз ClickHouse

| `instance.id` | База команды `default` | База команды `<slug>` | Таблица узла |
|---|---|---|---|
| пусто | `nexus_default` | `nexus_<slug>` | `nexus_<slug>.<table>` |
| `kz` | `nexus_kz_default` | `nexus_kz_<slug>` | `nexus_kz_<slug>.<table>` |

- Имя базы собирается **в одном месте** — `InstanceID.CHDatabase(slug)` в
  [domain/team.go](../../internal/domain/team.go); прежняя `CHDatabaseForSlug` остаётся как обёртка
  для пустого идентификатора. Больше литерал `"nexus_"` в коде не встречается: имя таблицы узла
  строится из `teams.ch_database` (`normalizeCHTable`,
  [web/usecase/node.go](../../internal/web/usecase/node.go)), а интерфейс получает префикс с
  бэкенда (§70.8).
- **Бюджет длины.** Ограничение `teams.ch_database` — `^nexus_[a-z][a-z0-9_]{0,31}$`, то есть 31
  символ после `nexus_`, тогда как слаг сам может занимать 32. С суффиксом длинная команда упёрлась
  бы в CHECK-ограничение с невнятной ошибкой. Поэтому формат релаксируется до
  `^nexus_[a-z][a-z0-9_]{0,40}$` (миграция, 6 + 41 ≤ `VARCHAR(64)`), симметрично правятся доменный
  и адаптерный шаблоны. Если суффикс всё же не оставляет места для слага, отдаётся отдельная
  доменная ошибка «слаг слишком длинный для этого инстанса», а не отказ PostgreSQL.
- Обратная миграция ограничения не восстанавливает прежний CHECK: при существующих длинных именах
  он не наложится. Это фиксируется комментарием в файле миграции.

**Одного разведения имён недостаточно.** Слаг команды допускает подчёркивание, поэтому нода без
суффикса с командой `kz_edo` и нода `kz` с командой `edo` дают одно и то же имя `nexus_kz_edo`.
Регулярным выражением такая коллизия не ловится — её ловит только маркер владения (§70.3).

## 70.3 Маркер владения базой

В каждой своей базе нода держит служебную таблицу:

```sql
CREATE TABLE <db>.__nexus_owner (
    instance_id String,      -- '' у ноды без суффикса
    claimed_at  DateTime,
    claimed_by  String,      -- "web@host-a", только для диагностики
    schema_ver  UInt8
) ENGINE = TinyLog
COMMENT 'nexus instance ownership marker — do not drop'
```

Движок `TinyLog` выбран намеренно: поиск бесхозных таблиц фильтрует `engine LIKE '%MergeTree%'`
([web/usecase/orphan_scanner.go](../../internal/web/usecase/orphan_scanner.go)), поэтому маркер не
попадает в интерфейс «Orphans» и его нельзя удалить кнопкой. Дополнительно в тот же запрос
добавляется `AND name NOT LIKE '\_\_nexus\_%'` — заодно перестают всплывать брошенные временные
таблицы `__nexus_tmpl_check_*` от проверки шаблона (§19.4).

**Захват базы атомарен и не требует внешних блокировок:**

1. `CREATE DATABASE IF NOT EXISTS <db>`;
2. `CREATE TABLE <db>.__nexus_owner (…)` — **без** `IF NOT EXISTS`;
   - успех → мы создатели → `INSERT` своей строки → владение наше;
   - ошибка `57 TABLE_ALREADY_EXISTS` → базу уже кто-то заявил → шаг 3;
3. `SELECT instance_id FROM <db>.__nexus_owner`:
   - ноль строк — попали в окно между `CREATE` и `INSERT` соседа: пять повторов по 200 мс, иначе
     конфликт;
   - один идентификатор, равный нашему — владение наше;
   - один идентификатор, отличный от нашего — **чужая база**;
   - несколько разных идентификаторов — расщепление владения (возможно после ручного `INSERT` или
     восстановления резервной копии ClickHouse): операции по базе запрещены, чинится вручную
     (`DROP TABLE __nexus_owner` и перезапуск нужной ноды).

`CREATE TABLE` без `IF NOT EXISTS` работает как атомарная проверка-и-установка: ClickHouse
сериализует создание одноимённой таблицы, проигравший получает код 57.

**Кеш.** Проверка владения вызывается на каждый запрос логов и метрик, поэтому вердикт кешируется
по имени базы: 5 минут для «наша», 30 секунд для отрицательных и ошибочных ответов, один запрос в
полёте на базу (по образцу кеша `tableCounts` в
[log_reader.go](../../internal/web/adapter/out/clickhouse/log_reader.go)). Кеш сбрасывается при
горячей смене ClickHouse-соединения (§8.4): администратор может перенастроить адрес ClickHouse из
интерфейса, и на новом сервере наших маркеров может не быть. Процесс в этом случае не убивается —
пишется ошибка в лог и Sentry, поднимается счётчик «владение не подтверждено», состояние
healthcheck деградирует.

**Поведение при недоступном ClickHouse:** неизвестный вердикт трактуется мягко для чтения и
создания (они всё равно упрутся в сам ClickHouse) и **строго** для разрушающих операций —
`DROP PARTITION`, `DROP TABLE`, `DELETE`, `ALTER`.

## 70.4 Гейт разрушающих операций

Каждая операция ниже до этого раздела работала по списку из своего PostgreSQL без проверки
владельца. Таблица — одновременно карта проблем и карта гейтов.

| Операция | Где | Запуск | Чем грозило | Гейт |
|---|---|---|---|---|
| `ALTER TABLE … DROP PARTITION` | [sender/usecase/ch_housekeeping.go](../../internal/sender/usecase/ch_housekeeping.go) | Sender: старт + раз в 24 ч | **Потеря данных**: партиция удаляется целиком, у кого меньше `retention_days` — тот и вырезает месяц логов обеих нод | проверка владения таблицей перед каждым `DROP PARTITION` |
| `DROP TABLE IF EXISTS` | [web/usecase/orphan_scanner.go](../../internal/web/usecase/orphan_scanner.go) | кнопка, admin | **Потеря данных**: таблицы соседа не числятся в своём PostgreSQL и показываются «бесхозными» | базы соседа не сканируются, удаление чужой таблицы отклоняется |
| `ALTER … MODIFY TTL / MODIFY COLUMN / ADD·DROP INDEX` | §56, [domain/ch_schema_sync.go](../../internal/domain/ch_schema_sync.go) | кнопка, manager+ | Ретеншен и кодеки чужой таблицы переписываются под шаблон и `retention_days` чужого узла | отказ на этапе плана и на исполнении |
| `ALTER … UPDATE request_size/response_size` | [platform/clickhouse/ensure_schema.go](../../internal/platform/clickhouse/ensure_schema.go) | старт Web **и** Sender | Мутация по всей таблице без условия по `node_id` — переписывает и чужие строки | список таблиц фильтруется по владению |
| `ALTER … ADD COLUMN IF NOT EXISTS` (§37/§39/§42/§67) | там же | старт Web **и** Sender | Идемпотентно, но `AFTER type` / `AFTER IP` фиксируют физический порядок колонок в чужой таблице | тот же фильтр |
| `CREATE DATABASE` | [adapter/out/clickhouse/team_provisioner.go](../../internal/web/adapter/out/clickhouse/team_provisioner.go) | создание команды | Две ноды делят одну базу — далее все строки выше | заменяется на захват базы (§70.3); чужая база → отказ создания команды с откатом записи в PostgreSQL |
| `CREATE TABLE IF NOT EXISTS` | там же | создание/копирование/правка узла | Узел молча садится на чужую схему; расхождение всплывает позже на вставке | отказ на чужой базе |
| `RENAME TABLE` | там же | перенос узла между командами | Узел «подключается» к чужим данным вместо пустой таблицы | проверка обеих сторон переименования |
| Временная `__nexus_tmpl_check_*` | там же | проверка шаблона, admin | Создание/удаление таблицы в чужой базе | отказ на чужой базе |
| `DELETE FROM … WHERE done = 0` | [log_reader.go](../../internal/web/adapter/out/clickhouse/log_reader.go), «Очистить неудачные» (§34.4/§35) | кнопка, manager+ | Удаление строк чужой ноды на разделяемой таблице | отказ на чужой таблице (409) |
| Послабление `node_id = ''` при чтении (§61) | [log_reader.go](../../internal/web/adapter/out/clickhouse/log_reader.go) | любое чтение логов | «Личность» таблицы считается по своему PostgreSQL, поэтому на межнодовой таблице узел засчитывает себе чужие legacy-строки | на не своей таблице действует строгий фильтр `node_id = ?` |
| Сохранение узла с таблицей в чужой базе | [web/usecase/node.go](../../internal/web/usecase/node.go) | создание/правка/копирование узла | Узел легально начинает работать в чужой базе | 400, кроме режима внешней таблицы (§70.6) |

Отбор «своих» таблиц выполняется по множеству своих `teams.ch_database` **и** маркеру, а не по
маске имени `nexus_<id>_*`: маска не покрывает ни базы ноды без суффикса, ни внешние таблицы (§64).

Проверка обязана срабатывать не только на старте, но и в рантайме — прежде всего при создании
команды: именно там ловится коллизия имён из §70.2.

## 70.5 Первый запуск, сверка и запрет смены идентификатора

Идентификатор ноды фиксируется в её PostgreSQL — таблица `instance_identity` (одна строка,
создаётся миграцией, не сидируется: отсутствие строки означает «ещё не заявлено»).

Шаг сверки выполняется всеми тремя сервисами сразу после подключения к PostgreSQL (миграции
накатывают Web и Receiver, Sender — нет, поэтому шаг не должен зависеть от порядка):

1. Заявка `INSERT … ON CONFLICT DO NOTHING` — гонка сервисов безопасна, значение у них одно и то же
   из конфига. Факт вставки означает первый запуск ноды.
2. Сохранённое значение отличается от конфигурации → **сервис не стартует**: смена идентификатора
   на живой ноде запрещена, поскольку имена уже созданных баз она не меняет. Обход — одноразовый
   флаг запуска, который перезаписывает значение и предупреждает, что базы в ClickHouse нужно
   переименовывать вручную.
3. Отдельно вычисляется признак «свежий PostgreSQL» — ни одного узла и ровно одна команда.

Сервисы с подключением к ClickHouse (Web, Sender) дополнительно проверяют владение:

| Кто | Свежий PG | База в CH | Маркер | Действие |
|---|---|---|---|---|
| Web | — | нет | — | захват (создать базу и маркер) |
| Web | **да** | есть | любой | **старт прекращается**: «в ClickHouse уже развёрнута другая нода Nexus — задайте `instance.id`». Обходится `adopt_unowned` |
| Web | нет | есть | нет | усыновление: ставим свой маркер (это обновление действующей ноды) |
| Web | нет | есть | наш | норма |
| любой | — | есть | **чужой** | **старт прекращается**; никакими флагами не перебивается |
| Sender | — | — | нет / чужой | не усыновляет: предупреждение и пропуск таблиц этой базы (доставка важнее стартовых `ALTER`) |
| Receiver | — | — | — | не участвует: в ClickHouse не ходит |

**Почему гейт первого запуска опирается на «свежий PostgreSQL», а не на маркер.** Пустой
`instance.id` не является идентичностью: маркер `instance_id = ''` одинаков у двух нод без
суффикса, и новая нода приняла бы чужой маркер за свой. Признак «в PostgreSQL ещё нет ни узлов, ни
команд, кроме сидированной» однозначно означает «эту ноду только что подняли».

Sender не усыновляет базы намеренно: он может стартовать раньше Web и «застолбить» базу, которую
Web ещё не связал с командой.

**Ребейз сидированной команды.** Миграция §18 создаёт команду `default` с именем `nexus_default`.
При непустом `instance.id` на первом запуске имя переписывается на `nexus_<id>_default` — строго
при условиях: идентификатор только что заявлен, `ch_database` всё ещё равен сидированному значению
и в этой базе нет ни одного узла. Если суффикс задан, а условия не сошлись — старт прекращается с
требованием разобраться вручную: молчаливое продолжение оставило бы новую ноду пишущей в базу
действующей.

## 70.6 Что остаётся разрешённым между нодами

Узел может ссылаться на таблицу в чужой базе **только** в режиме внешней таблицы (§64); обычному
узлу такое сохранение отклоняется с 400.

Внешняя таблица при этом остаётся полноценной: Sender в неё **пишет**, интерфейс из неё читает.
Это осознанное решение, а не упущение — режим §64 задуман как «Nexus как фронт логирования», и
запись в него является его смыслом. Гейт §70.4 закрывает только разрушающее: DDL, `DROP PARTITION`,
`DROP TABLE`, `DELETE`, `RENAME`, `ALTER`.

Следствия, которые принимаются:

- нода `kz` может показывать и дополнять журнал в таблице другой ноды, если оператор явно указал
  внешнюю таблицу;
- чтение конкретной записи по идентификатору (`GET …/log/{id}` и подгрузка тела) не фильтруется по
  `node_id` — на разделяемой таблице видна любая строка;
- `POST /api/ch-tables/verify` (§64) читает структуру любой таблицы без ограничения по базе: это
  read-only обращение к `system.columns`, оно оставлено рабочим для диагностики.

## 70.7 Наблюдаемость

Все сигналы ноды должны быть отделимы, иначе разбор инцидента на двух нодах невозможен.

- **Sentry** — общий проект, к событиям и транзакциям добавляется тег `instance` (рядом с
  существующим `service`). При пустом идентификаторе тег **не** добавляется: иначе у действующей
  ноды изменится группировка событий.
- **Метрики Prometheus** — постоянная метка **`nexus_instance`**. Имя `instance` использовать
  нельзя: его занимает сам сбор метрик, и одноимённая метка была бы переименована в
  `exported_instance`. При пустом идентификаторе метка не добавляется — иначе меняется
  идентичность всех рядов и ломаются существующие панели.
- **Логи сервисов** (§51) — атрибут `instance` в стартовой записи и в записях кольца логов; поле
  необязательное, поэтому прежние записи читаются без изменений.
- **Уведомления Telegram** (§20) — префикс `[<id>]` в тексте: две ноды могут писать в один чат.

Запросы панели метрик к Prometheus (§21/§44) селектора ноды не содержат и не получают его в этом
разделе — вместо этого требуется отдельный Prometheus на ноду (§70.9). Ограничение фиксируется
явно: на общем Prometheus шапка дашборда и графики сложат трафик обеих нод.

## 70.8 Интерфейс

- `GET /api/version` дополняется полем `instance` (необязательное).
- `GET /api/settings/public` дополняется полем `ch_database_prefix` (`nexus_` либо `nexus_kz_`).
  Диалог создания команды показывает предварительное имя базы из него, а не склеивает литерал на
  клиенте.
- В шапке появляется бейдж ноды — слева от переключателя команд. При пустом идентификаторе бейдж не
  отображается вовсе, то есть интерфейс действующей ноды не меняется.

```
┌──────────────────────────────────────────────────────────────────────┐
│ Узлы › Обзор        [🔎 поиск]      ⟨KZ⟩ [Команда ▾] [RU] [☾] [Выйти] │
└──────────────────────────────────────────────────────────────────────┘
                                       ▲
        моноширинный чип, заглавные буквы, рамка border-line, text-fg-muted,
        подсказка «Инстанс: kz · БД ClickHouse: nexus_kz_*»
```

Данные бейджа берутся из уже существующего запроса версии — дополнительных сетевых вызовов нет.
Новые ключи локализации: подпись бейджа, «таблица принадлежит другой ноде», «конфликт владения
базой», «слаг слишком длинный для этого инстанса» — в обеих локалях и на бэкенде (§14).

## 70.9 Требования к развёртыванию

- **PostgreSQL, Redis и Kafka у каждой ноды свои.** Redis нельзя разделять даже разными номерами
  баз: каналы `nexus:config:reload` и `nexus:nodes:invalidate` (§8.4/§57) глобальны для сервера, и
  перезагрузка настроек одной ноды применилась бы к другой. Имена топиков и группа консьюмера
  (`nexus.async`, `nexus.async.dlq`, `nexus.logs.retry`, `nexus-sender`) совпадают, поэтому общий
  кластер Kafka означал бы, что Sender одной ноды читает сообщения другой.
- **Prometheus у каждой ноды свой** (см. §70.7).
- **Рекомендуется отдельный пользователь ClickHouse на ноду** с правами только на свои
  `nexus_<id>_*` и `SELECT` на `system.tables` / `system.parts` / `system.columns` — физическая
  страховка поверх программного гейта.
- Два стека на одном хосте — разные имена проекта Compose и разные порты.
- **Предупреждение:** гейт защищает начиная с версии, в которой он появился. Вторая нода, поднятая
  на более старой сборке с пустым `instance.id`, по-прежнему затрёт данные первой.

## 70.10 Совместимость

При пустом `instance.id` поведение обязано совпадать с предыдущими версиями: те же имена баз, те же
запросы, отсутствие тега Sentry, отсутствие метки метрик, отсутствие новых полей в JSON-ответах,
отсутствие бейджа в интерфейсе.

Единственное намеренное отклонение — маркер владения создаётся и на ноде без суффикса (иначе вторая
нода не отличит занятую базу от свободной). Маркер невидим для поиска бесхозных таблиц и не влияет
на чтение и запись логов.

Действующая нода миграции данных не требует: её базы остаются `nexus_<slug>`, идентификатор пустой.

## 70.11 Вне рамок раздела

- Переезд существующей ноды на непустой идентификатор (переименование баз ClickHouse и массовое
  обновление `nodes.clickhouse_table`) — выполняется вручную, автоматизация не предусмотрена.
- Раздельные проекты Sentry на ноду — при необходимости настраивается конфигурацией, кода не
  требует.
- Селектор ноды в запросах панели метрик к Prometheus — вместо этого требование «свой Prometheus»
  (§70.7/§70.9).
- Кластеризация нод, общий PostgreSQL, репликация конфигурации между нодами.

## 70.12 Критерии приёмки

1. Нода `kz` (`instance.id = kz`) с собственными PostgreSQL/Redis/Kafka и общим ClickHouse создаёт
   команды в базах `nexus_kz_*` и пишет туда логи; интерфейс показывает бейдж `KZ`.
2. Нода без суффикса после обновления работает как прежде; её базы получают маркер владения.
3. Суточный проход housekeeping ноды `kz` не удаляет ни одной партиции в базах первой ноды.
4. Поиск бесхозных таблиц ноды `kz` не показывает таблицы первой ноды, а попытка удаления чужой
   таблицы отклоняется.
5. Синхронизация схемы (§56) и перенос узла между командами на чужой базе отклоняются с внятной
   ошибкой.
6. Попытка поднять новую ноду с пустым `instance.id` при существующей `nexus_default` завершается
   остановкой старта с сообщением, требующим задать `instance.id`.
7. Смена `instance.id` на уже работавшей ноде прекращает старт.
8. Сохранение узла с таблицей в чужой базе отклоняется (400), кроме режима внешней таблицы.
9. В журнале логов каждая нода видит только свои записи; счётчики дашборда не включают чужие.
10. События Sentry, метрики и служебные логи различаются по ноде.
