# 77. Логи узла: живое раскрытое тело, автопоиск и скорость на десятках миллионов записей

Раздел закрывает четыре жалобы по вкладке «Логи» узла (развивает §7.4/§42/§44.K/§48/§64/§67/§72):

1. раскрытое тело запроса схлопывалось через 5 секунд — автообновление пересоздавало список;
2. кнопка «Применить» в расширенных фильтрах — лишнее действие;
3. фильтры «Завершено»/«В работе» дублировали «OK»/«Ошибки»;
4. прокрутка списка тормозила на больших таблицах (боевой узел `gate`, 11 млн записей: каждая
   страница из 50 строк стоила ~900 мс).

Три из четырёх жалоб упираются в одну корневую причину: список перезапрашивался целиком и
без временно́го окна. Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 77.1 Инкрементальное обновление списка (раскрытое тело живёт)

**Проблема.** Snapshot-список обновлялся `refetchInterval: 5000` у `useInfiniteQuery`: каждые
5 секунд перезапрашивались ВСЕ накопленные страницы, react-query подменял данные, граница первой
страницы сдвигалась приехавшими записями — и строка, чьё тело пользователь читал, выпадала из
склейки страниц. `expandedId` указывал в пустоту, тело схлопывалось. Вторая причина того же
симптома — «возврат к верху» (§72.5): `collapseToFirstPage` выбрасывал страницы 2+ вместе с
раскрытой строкой.

**Решение — tail-poll вместо полного рефетча:**

- у `useInfiniteQuery` списка авто-рефетча больше нет; раз в 5 секунд (пока пользователь у верха
  и не в Live) уходит лёгкий запрос «что появилось ПОСЛЕ самой свежей загруженной строки»:
  `GET /logs?{фильтры}&from=<ts самой свежей − 1 с>&limit=<pageSize>`;
- результат вливается в начало первой страницы через `setQueryData` с дедупом по `id` (секунда
  запаса и дедуп — из-за секундной точности `date_request`, та же причина, что у keyset-курсора
  §44/45-fix). Существующие элементы массива не пересоздаются — раскрытая строка и её тело
  остаются на месте;
- tail-poll вернул ровно `limit` строк → между хвостом и первой страницей возможна дыра; этот
  редкий путь честно сбрасывает список к первой странице (Debug-лог), а не склеивает с дырой;
- tail-poll не запускается, когда новые записи в принципе не могут попасть под фильтр: задана
  ручная «Дата по» в прошлом;
- `collapseToFirstPage` не срабатывает, пока есть раскрытая строка (опция `collapseEnabled`
  хука `useInfiniteLogs`) — свернул тело → следующее событие скролла у верха схлопнет страницы
  как раньше;
- счётчик «Показано N из M» продолжает обновляться отдельным запросом (§67) — он на раскрытие
  не влияет;
- пилюля «N новых записей ↑» (была только в Live) показывается и в snapshot-режиме, когда
  tail-poll добавил строки, а пользователь не у самого верха.

## 77.2 Автоокно чтения и непрерывная прокрутка

**Проблема.** Первая страница и каждая порция скролла без пользовательского периода читались
запросом без временно́го окна: `WHERE node_id=? ORDER BY date_request DESC, ID DESC LIMIT 50`
заставляет ClickHouse прочитать широкие колонки (`url`, `parameters`, `reason`) практически по
всей таблице. Замер на бою (§77.5): 870–980 мс на страницу против 75–185 мс с окном в сутки —
задержка не зависит от глубины скролла и лечится только сужением.

**Решение — серверное автоокно.** Если запрос списка пришёл без пользовательской нижней границы
(`from`), usecase подбирает её сам:

- якорь — курсор пагинации `to` (для первой страницы — `max(date_request)` из `DateRange`);
- окна нарастающей ширины от якоря: `1ч → 6ч → 24ч → 7д → 30д → 90д → без нижней границы`;
  первое окно, набравшее `limit` строк, — ответ;
- окно, ушедшее ниже `min(date_request)` таблицы, — последняя попытка: перебор не продолжается,
  недобор строк после неё означает настоящий конец истории;
- `DateRange` (min/max) кешируется per-table с коротким TTL — дешёвый запрос (~50 мс на 11 млн
  строк), но дёргается на каждую страницу скролла;
- каждый шаг расширения — Debug-лог (§51.9): окно, число строк, номер попытки, длительность.

Это и есть «смещение периода при прокрутке»: якорь каждой следующей страницы — её курсор, окно
едет вслед за скроллом, прокрутка непрерывна при любой глубине истории. Смещение сделано на
сервере, а не на клиенте, по двум причинам: один HTTP-запрос на страницу вместо 5–6
последовательных у «редких» узлов, и неизменный контракт конца истории на фронте
(`items.length < pageSize`, §72.2) — с клиентским смещением «окно пустое» было бы неотличимо от
«история кончилась».

**Пресетов периода в шапке вкладки нет — решение осознанное.** При непрерывной прокрутке видимый
пресет не менял бы ни содержимое списка (вся история), ни счётчик M — только скорость страницы,
которую и так даёт автоокно; переключатель без видимого эффекта путал бы пользователей. Период
как «фильтр для анализа» — существующие поля «Дата с/по» расширенных фильтров: заданная руками
нижняя граница отключает автоокно и честно останавливает прокрутку на границе периода.

**Границы применения:**

- автоокно действует только на список (`Search`); на `Count` не действует — там окно меняло бы
  сам результат, а не скорость (счётчик «из M» обязан считать всё множество под фильтром §72.2);
- пользовательский `from` отключает автоокно полностью;
- полнотекстовый `q`-фильтр автоокно НЕ спасает по построению: совпадения могут лежать где угодно
  в истории, и узкие окна лишь умножат число проб. Замер: `q` без периода на 11 млн строк —
  28 с (список) и гарантированный таймаут `count` (10 с, §67). Защита пользователя — §77.3
  (индикатор с отменой), а не окно;
- расширение §72.4 (прунинг `date_create`) на внешние таблицы §64 рассмотрено и отклонено: замер
  на бою показал, что на внешней таблице `gate` окно по `date_request` уже отсекает гранулы через
  minmax первичного ключа (75 мс), выигрыша прунинг не даст, а риск молча потерять строки
  постороннего писателя с `date_create ≠ день(date_request)` — реальный.

## 77.3 Автопоиск без кнопки «Применить», отмена долгого поиска

**Проблема.** Расширенные фильтры применялись только кнопкой «Применить» — лишнее действие;
выбор метода/хоста/даты не действовал, пока пользователь не найдёт кнопку.

**Решение.** Кнопки «Применить» нет; фильтры применяются по завершении ввода:

- поле «Поиск»: Enter или уход фокуса (blur); НЕ на каждую букву (полнотекст дорог — §77.5);
  Esc откатывает черновик к применённому значению;
- комбобоксы «Метод»/«Хост клиента»: сразу при выборе значения;
- «Дата с»/«Дата по»: при выборе даты;
- тумблеры Aa / ab| / .*: сразу при клике;
- коммит идемпотентен: применение происходит, только если черновик отличается от применённого
  (иначе Enter+blur дают двойной запуск, а blur по клику на «Сбросить» — лишний поиск);
- смена любого фильтра во время выполняющегося поиска отменяет текущий запрос и запускает новый
  (см. ниже — отмена настоящая, до ClickHouse).

**Индикатор долгого поиска.** Если запрос списка идёт дольше ~0.7 с, между фильтрами и таблицей
появляется строка «Поиск…» с кнопкой «Отменить»; при непустом «Поиске» без заданных дат — плюс
подсказка «период не ограничен — читается вся история». Отмена:

- разрывает HTTP-запрос настоящим `AbortSignal` (проброшен из react-query через `api.get` в
  axios) — хендлер живёт на `c.Request.Context()`, разрыв соединения отменяет контекст, и
  clickhouse-go снимает запрос в самом ClickHouse, а не оставляет его молотить;
- показывает состояние «Поиск отменён. Уточните период или фильтры» с кнопкой «Повторить»;
  автообновление в этом состоянии не перезапускает запрос само.

**Автопауза обновления на дорогих фильтрах.** Если последний успешный запрос списка шёл дольше
2 с, tail-poll и рефетч счётчика для текущего набора фильтров выключаются (иначе 5-секундный тик
накладывает дорогие запросы друг на друга); в шапке — подпись с кнопкой ручного обновления.
Смена фильтров сбрасывает паузу.

## 77.4 Фильтр «Завершено»/«В работе» удалён из UI (дубль «OK»/«Ошибок»)

Сегментный переключатель «Все/Завершено/В работе» удалён из шапки вкладки. Доказательство
дублирования — не рассуждение, а замер: `count` по 7 комбинациям фильтров на 17 боевых узлах
трёх команд дал `err ≡ done=no`, `ok ≡ done=yes`, и `err∧done=yes = ok∧done=no = 0` — везде.
Причина в write-path: Sender пишет `Done = (2xx)` (`send.go`), поэтому `done=1 ⟹ status 2xx`, и
предикат §72.1 `ok = (done=1 AND 200≤status<400)` вырождается в `done=1`. Запись «завершено с
кодом ≥400» write-path Nexus породить не может; комбинация «В работе»+«OK» была заведомо пустой.

Что осталось:

- **API не менялся**: query-параметр `done=yes|no`, поле `LogsFilterState.done`, серверный фильтр
  и предикаты §72.1 живут — на них дип-линки §47 (вкладка «Очередь» → «Логи» с `done=no`) и
  внешние потребители;
- активный `done`-фильтр из дип-линка показывается **чипом** «В работе ✕» рядом со счётчиком —
  фильтр, который нельзя увидеть и снять, хуже лишнего сегмента;
- на внешней таблице §64 посторонний писатель теоретически может дать `done=1 AND status>=400` —
  такие записи по-прежнему корректно ловятся фильтром «Ошибки» (§72.1 — полное дополнение);
  отдельный UI-переключатель ради этого не оправдан.

## 77.5 Замеры (боевой узел gate, 2026-08-03)

Узел `gate/PDT_PDTExchange`, внешняя таблица `gate_logs.PDT_PDTExchange` (§64), 11.1 млн записей,
Nexus 1.22.5. Методика: прямые запросы `GET /api/nodes/{id}/logs*` c Bearer-токеном, тайминги
клиентские (сеть ~20–40 мс сверх серверного времени).

| Сценарий | Время |
|---|---|
| страница 50 строк без периода (страницы 1–12 скролла одинаково) | 870–980 мс |
| страница 50 в окне 1 сутки (167 тыс. записей в окне) | 75–185 мс |
| страница 50 в окне 7 суток | 189 мс |
| страница 50 + фильтр «Ошибки» (2 312 записей) | 113–141 мс |
| страница 50 + `method=` (неселективный, половина таблицы) | 938 мс |
| полнотекст `q=photo` без периода | 27 954 мс |
| полнотекст `q=photo` в окне 1 сутки / 7 суток | 775 мс / 3 520 мс |
| `count` без фильтров / в окне 1 сутки / «Ошибки» | 44 / 42 / 78 мс |
| `count` полнотекста без периода | таймаут 10 с → деградация §67 |
| фасеты `methods` / `client-hosts`, `date-range`, `failed-count` | 55–97 мс |

Выводы, на которых стоит раздел: задержка списка не зависит от глубины скролла; любое временно́е
окно даёт 6–12×; полнотекст без окна не спасается ничем, кроме окна или отмены; `count` дёшев
всегда, кроме полнотекста. Экстраполяция на 50 млн строк: ~4 с на страницу без окна (при
автоокне — те же десятки-сотни мс), полнотекст без окна — минуты.

Дублирование фильтров (§77.4): `logs/count` с комбинациями
`status=ok|err × done=yes|no` по всем узлам команд `gate`/`vika`/`task` — 17 узлов, расхождений 0.

**Проверка автоокна на масштабе** (`TestClickHouse_ScrollScale_E2E`, ClickHouse в testcontainers,
20 страниц по 50 строк подряд по keyset-курсору):

| Объём таблицы | Страница с автоокном (avg / max) | Страница без автоокна |
|---|---|---|
| 1 млн строк | 7 мс / 15 мс | 86 мс |
| 50 млн строк | 7 мс / 27 мс | 1 153 мс |

Главное в этой таблице не абсолютные числа (у стенда свои диски), а **форма зависимости**: без
окна стоимость страницы растёт линейно с объёмом таблицы (86 мс → 1 153 мс при росте в 50 раз), с
автоокном она от объёма не зависит вовсе — читается только то окно, где лежит страница. Именно
поэтому прокрутка остаётся мгновенной и на 50 млн записей.

## 77.6 Что раздел НЕ закрывает

- виртуализация таблицы и снятие потолка `MAX_INFINITE_ROWS = 1000` (§72.6 — по-прежнему
  кандидат);
- data-skipping индексы по `status`/`done` и ngrambf/tokenbf для полнотекста (§48.5/§19);
- read-in-order с ранней остановкой по LIMIT (§72.6);
- автоокно для `ListSince` (live-tail SSE) — поллинг и так идёт узким окном от последнего
  курсора;
- прунинг `date_create` для внешних таблиц §64 — осознанно отклонено (см. §77.2);
- скорость `count` полнотекста — остаётся деградация §67 по таймауту.
