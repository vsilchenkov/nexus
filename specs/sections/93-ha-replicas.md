## 93. Развёртывание без простоя: две реплики каждого сервиса

Раздел закрывает обещание §9.1 («целевой даунтайм при штатном обновлении — 0, rolling deploy»),
которое до сих пор существовало только на бумаге, и опирается на §74 (безопасный откат, контракт
аддитивных миграций), §70 (нода и её идентификатор), §51 (консоль служебных логов), §27
(RabbitMQAsync-узлы), §31 (мониторинг).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).
Аналитическая записка с оценками ресурсов и эксплуатации — [../../docs/HA_ZERO_DOWNTIME.md](../../docs/HA_ZERO_DOWNTIME.md).

### 93.1 Проблема

Каждый сервис развёрнут в одном экземпляре, обновление идёт `docker compose up -d --build`, то есть
через пересоздание контейнера. Простой при этом получают и плановое обновление, и падение процесса;
второе — ещё и ночью, без оператора.

Точек отказа на пути одного синхронного запроса не одна, а три подряд, и это не очевидно:

```
клиент → nginx на хосте → web:8000 → receiver:8080 → sender:9190 (gRPC) → внешний узел
```

**Web стоит на боевом пути.** Он реверс-прокси `/api/v1/*` в Receiver (§17.1, `receiver_proxy.go`),
и в боевом профиле наружу опубликован только он. То есть выкат «всего лишь панели» рвёт приём
запросов. Отсюда следствие для scope: дублировать только Receiver и Web бессмысленно — пока Sender
один, его обновление даёт клиенту 503 через `Unavailable` по gRPC.

### 93.2 Модель развёртывания

Профиль двух реплик — оверлей [deploy/docker-compose.ha.yml](../../deploy/docker-compose.ha.yml)
поверх корневого compose. Одиночная установка остаётся рабочей и запускается как раньше: оверлей
просто не подключают.

| Решение | Почему так, а не иначе |
|---|---|
| Пары именованных сервисов `web-1`/`web-2` вместо `deploy.replicas: 2` | Обновлять надо ПО ОДНОЙ реплике. `--scale`/`replicas` пересоздаёт обе разом, то есть даёт ровно тот простой, ради которого профиль и заведён |
| Общий сетевой алиас пары (`web`, `receiver`, `sender`) | `config.yml` не меняется ни на строку: `web.receiver_url: http://receiver:8080` и `receiver.sender_grpc.addr: sender:9190` продолжают резолвиться — теперь в два адреса |
| `image:` задан явно (`nexus-web:latest`) | Иначе compose назвал бы образ по сервису (`nexus-web-1`), и `images.sh`, который тегирует и откатывает `nexus-web:latest`, перестал бы находить образы — откат сломался бы молча и обнаружился в аварии |
| Наружу публикует порты только nginx, и те же (8000, 8080) | Для внешнего nginx на хосте и для клиентов адреса не меняются |
| Инфраструктура (PostgreSQL, Redis, Kafka, ClickHouse) не реплицируется | Вне рамок раздела, см. §93.9 |

### 93.3 Балансировщик

nginx внутри стека ([deploy/docker/nginx.conf](../../deploy/docker/nginx.conf)), собственный образ, а
не bind-mount конфига: конфиг обязан версионироваться вместе с кодом.

**Боевой `/api/v1/*` уходит сразу в Receiver, мимо Web.** Это снимает Web с горячего пути (его выкат
и падение перестают влиять на приём), убирает лишний хоп и лишний буфер тела. Прокси в Web остаётся
для replay §85 и dry-run §55, где инициатор — сам Web.

Требования к конфигурации, каждое из которых уже было бы инцидентом:

- `proxy_read_timeout 600s` — синхронный вызов живёт по таймауту внешнего узла, дефолтные 60 с его
  оборвут;
- `client_max_body_size 140m` — не ниже `receiver.max_body_bytes` (124 МиБ) плюс запас, иначе клиент
  получает 413 от nginx и в логах шины запроса нет вовсе;
- `proxy_request_buffering off` на боевом пути — иначе 124-МиБ тело оседает во временном файле;
- `proxy_buffering off` для SSE-стрима логов узла (§77) — иначе события копятся в буфере;
- `X-Forwarded-For`/`X-Forwarded-Proto` — без них `client_host` (§67) и rate-limit по IP видят адрес
  прокси, а не клиента.

**POST боевого трафика НЕ повторяется на второй реплике.** `proxy_next_upstream` для `/api/v1/`
оставлен дефолтным (без `non_idempotent`) сознательно: повтор запроса, который апстрим мог уже
принять, — это дубль доставки во внешнюю систему, что хуже одиночного 502. Мёртвая реплика уходит из
ротации по `max_fails` за пару запросов, а на выкате её выводит скрипт ДО остановки. Для GET-запросов
панели повтор, наоборот, включён: они идемпотентны, и падение `web-1` остаётся невидимым.

Состав upstream'ов лежит в `/etc/nginx/dyn/*.conf` и генерируется при КАЖДОМ старте контейнера —
оборванный выкат не должен оставить реплику помеченной `down` навсегда.

### 93.4 Балансировка gRPC (Receiver → Sender)

Sender за nginx не стоит: к нему ходит только Receiver, и балансировка там клиентская
([platform/grpcsender](../../internal/platform/grpcsender/client.go)) — `dns:///`-target,
`round_robin`, `healthCheckConfig`.

Балансировок в этом клиенте теперь ДВЕ, и они про разное: пул из N `ClientConn` — про параллелизм
одного Receiver'а (§9.3), `round_robin` внутри каждого соединения — про несколько реплик Sender'а.
Без второй пул из восьми соединений целиком улёгся бы в одну реплику при дефолтном `pick_first`, и
по метрикам самого Receiver'а это неотличимо от нормы.

`healthCheckConfig` требует пустого импорта `google.golang.org/grpc/health`: без него gRPC молча
игнорирует настройку, а конфиг выглядит правильным.

### 93.5 Дренаж перед остановкой

По SIGTERM сервис сначала объявляет себя неготовым и только потом останавливает сервер:

1. `/ready` → 503 `{"ready":false,"draining":true}`; Sender вдобавок переводит gRPC-health в
   `NOT_SERVING` — это его единственный способ уйти из ротации;
2. пауза `shutdown.drain_sec` — балансировщик успевает перестать слать новые запросы;
3. остановка сервера с потолком `shutdown.timeout_sec` на доигрывание принятых запросов.

`/health` при этом продолжает отвечать 200: по нему docker решает, не убить ли контейнер, и 503 там
означал бы, что штатная остановка выглядит как отказ процесса.

Новая секция конфига:

| Ключ | Дефолт | Смысл |
|---|---|---|
| `shutdown.drain_sec` | 5 | Пауза между «не готов» и остановкой. `0` = дефолт; выключить — отрицательным значением |
| `shutdown.timeout_sec` | 30 | Потолок доигрывания. Заменяет зашитую константу 30 с, которая рвала долгие sync-вызовы на 30-й секунде при таймауте узла до 600 с |

Одиночная установка получает +5 с к остановке — цена названа явно, отключается `drain_sec: -1`.

### 93.6 Различение реплик в наблюдаемости

`instance` (§70.7) для этого не годится: он идентифицирует НОДУ, и у двух реплик одной ноды он
одинаков. Введено имя реплики — hostname контейнера (`web-2`), переопределяется переменной
`NEXUS_REPLICA`:

- поле `replica` в записи консоли служебных логов §51; колонка в интерфейсе появляется сама, когда в
  выборке есть записи от разных экземпляров (в одиночной установке hostname совпадает с именем
  сервиса, и колонка не показывается), поиск по консоли находит строки по имени реплики;
- тег `replica` в Sentry — «падает только на одной реплике» иначе неразличимо.

Попутно закрыто расхождение: `instance` в кольце Redis писался с §70.7, но до интерфейса не доезжал —
`domain.ServiceLogEntry` не разбирал это поле.

### 93.7 Периодические задачи

С двумя репликами каждый тикер срабатывает дважды. Задачи, которым это вредит, берут лок на цикл
([platform/redislock](../../internal/platform/redislock/redislock.go), схема §20.4):

| Задача | Что было бы без лока |
|---|---|
| Уборка партиций ClickHouse (Sender) | Двойной `DROP PARTITION`: данные целы, но ClickHouse получает лишнюю работу, а в логах появляются ошибки «партиции нет» ровно там, где потом ищут причину пропавших логов |
| Чистка журнала аудита (Web) | Второй полный проход `DELETE` по выросшей таблице (§91) |

Ошибка Redis трактуется как запрет цикла: fail-open включал бы двойное выполнение именно тогда, когда
инфраструктура нездорова.

### 93.8 Узлы RabbitMQAsync — аренда

Воркер §27 тянет сообщения через `basic.get`. Дублей две реплики не создадут (брокер отдаёт сообщение
одному потребителю), но темп вычитки удвоился бы против настроенного `pull_batch_size` ×
`pull_interval_sec`, а порядок доставки во внешний узел перемешался бы сильнее. Узел настраивали под
конкретный темп, и менять его молча, просто потому что появилась вторая реплика, нельзя.

Поэтому узел арендуется одной репликой (`redislock.Lease`): аренда продлевается тем же
reconcile-тиком, TTL — два периода reconcile, при штатной остановке аренда отдаётся явно, чтобы сосед
подхватил узлы сразу, а не через TTL. Ошибка Redis = «не ведём»: сообщения останутся в очереди
RabbitMQ до восстановления, это безопасно для pull-модели.

**Альтернатива «делить `pull_batch_size` пополам» отвергнута:** она уполовинивает пропускную
способность, когда одна реплика лежит, и не чинит перемешивание порядка.

### 93.9 Мониторинг

[deploy/prometheus.ha.yml](../../deploy/prometheus.ha.yml) перечисляет обе реплики поимённо. Прежний
`static_configs` с одним именем сервиса в HA стал бы дефектом: Docker DNS отдаёт по алиасу два адреса
вперемешку, Prometheus скрейпил бы то одну реплику, то другую под ОДНОЙ меткой instance — два ряда
счётчиков схлопнулись бы в один, и `increase()` на каждом переключении видел бы «счётчик уехал
назад». Панель §21 получала бы правдоподобный мусор.

Все PromQL панели уже агрегируют (`sum`, `sum by (node)`), правила алертов — `max by (...)`, поэтому
два ряда вместо одного они переживают без изменений.

Новый алерт `NexusReplicasDegraded` (`sum by (job) (up) < 2`) вынесен в отдельный файл: в одиночной
установке он висел бы вечно. Без него самый неприятный сценарий раздела невидим — одна реплика в
crash-loop выглядит снаружи как «всё работает, но иногда 502».

### 93.10 Процедура обновления

[scripts/deploy/rolling.sh](../../scripts/deploy/rolling.sh), порядок шагов значим:

1. сохранить образы (`images.sh tag`) — ДО сборки, иначе она перетрёт `:latest` и откат превратится в
   пересборку трёх образов под нагрузкой (§74.5);
2. дамп PostgreSQL (`pg_dump.sh`) — ДО миграций (§10.3);
3. сборка образов **по одному**: параллельная сборка трёх Go-образов упирается в память линкера на
   слабом сервере и подвисает без внятной ошибки (§5.4 DEPLOYMENT);
4. миграции отдельным шагом, пока СТАРЫЕ реплики работают: схема аддитивна (§74.2), поэтому старый код
   на новой схеме жив, а новый на старой — нет;
5. по одной реплике: вывести из ротации → пересоздать → дождаться healthy → вернуть;
6. уборка кэша сборки.

Два гейта в скрипте: он отказывается помечать `down` последнюю живую реплику и отказывается
обновляться, когда избыточность уже нарушена (без `--force`).

`nginx -s reload` после каждой реплики обязателен не только ради состава upstream'а: имена в нём
резолвятся в момент reload, а пересозданный контейнер получает новый IP.

**Уборка после выката — только `docker builder prune` и `docker image prune -f`.**
`docker image prune -a` запрещён: он удаляет образы, на которые не ссылается контейнер, то есть
сохранённые на шаге 1 версионные `nexus-*:<версия>` — вместе с возможностью быстрого отката.

### 93.11 Что вне рамок

Раздел даёт «обновление приложения без простоя» и «переживание падения процесса», не более:

- **PostgreSQL, Redis, Kafka, ClickHouse** — по одному экземпляру; их обновление или падение остаётся
  простоем, полным либо частичным (§9.4);
- **сам сервер, ядро, Docker daemon, диск** — один хост это один хост; реальная отказоустойчивость
  требует второго;
- **nginx-контейнер** — сам единая точка; смягчено тем, что смена конфига идёт `nginx -s reload` без
  разрыва соединений;
- **долгие синхронные запросы** на выводимой реплике: выкат либо ждёт их до `shutdown.timeout_sec`,
  либо рвёт;
- **неаддитивные миграции** — во время выката несовместимы в принципе (§74.2), и это требование
  ужесточается: неаддитивная миграция теперь ломает не откат, а сам выкат.
