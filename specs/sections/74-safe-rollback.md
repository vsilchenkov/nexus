# 74. Безопасный откат на предыдущую версию

Nexus работает круглосуточно, и принятая стратегия аварии простая: **при критическом дефекте
возвращаемся на предыдущую версию, потом спокойно чиним и выпускаем фикс**. Раздел делает этот
путь выполнимым за секунды и предсказуемым: убирает стартовый гейт, из-за которого откаченный
код вообще не поднимался, даёт инструмент на случай оборванной миграции, фиксирует контракт
совместимости схемы и версионирует образы, чтобы возврат не требовал пересборки.

Развивает §5.1 (миграции применяются на старте), §14.1/§14.2 (логи и Sentry), §6 (метрики и
алерты), §70 (идентичность инстанса). Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md);
пошаговые процедуры для оператора — [DEPLOYMENT.md §10](../../DEPLOYMENT.md).

**Принцип раздела:** откат кода — рядовая операция, откат схемы — исключение. Схема обязана быть
совместимой с предыдущей версией кода по построению (74.2), поэтому в типичной аварии достаточно
вернуть образы, а базу не трогать вовсе.

## 74.1 Что мешало откату

Исходное состояние (до этого раздела) проверено на PostgreSQL 12 с реальными миграциями репозитория.

| Симптом | Причина | Следствие |
|---|---|---|
| Откаченный Web/Receiver не стартует: `migrate up: no migration found for version 32: read down for version 32 .: file does not exist` | `golang-migrate` перед `Up()` требует, чтобы версия из `schema_migrations` существовала в каталоге миграций; у старого образа миграции 0029–0032 нет. `AutoMigrate` считает это фатальным → `os.Exit(1)` | `restart: unless-stopped` крутит crash-loop; откат «только кодом» невозможен, хотя сама схема совместима |
| Откатить схему старым образом тоже нельзя: `--migrate-down 1` падает с тем же текстом | тот же гейт: `readDown` начинается с проверки текущей версии | оператор, который сначала пересобрал старый тег, остаётся без инструмента отката |
| После оборванной миграции не работают ни `up`, ни `down`: `Dirty database version 28. Fix and force version.` | `dirty=true` в `schema_migrations`; `Force` у `golang-migrate` есть, но наружу не выведен | лечение только руками в psql — худший вариант под давлением аварии |
| Возврат на прежний образ требует пересборки | образы собираются на сервере (§9.2 DEPLOYMENT), `docker compose up --build` перетирает тег `nexus-<service>:latest`, прежний образ остаётся безымянным (`<none>`) | RTO измеряется временем сборки трёх образов вместо секунд |
| Оператор не знает, нужен ли откат схемы | CHANGELOG не сообщает, сколько миграций добавил релиз | решение принимается на глаз в момент аварии |

При этом **схема обратно совместима**: все `ADD COLUMN` в репозитории — либо nullable, либо
`NOT NULL DEFAULT`, а в коде нет ни одного `SELECT *`, поэтому лишние колонки старому коду не
мешают. То есть единственным реальным препятствием был стартовый гейт, а не сама база.

## 74.2 Контракт схемы: откат кода не требует отката схемы

Правила, которые делают откат дешёвым. Соблюдаются де-факто с самого начала проекта; раздел
превращает их в обязательство.

1. **Только аддитивные миграции в релизе.** `ADD COLUMN` — nullable либо `NOT NULL DEFAULT …`;
   `CREATE TABLE`; расширяющий `CHECK`. Такая миграция не ломает предыдущую версию кода.
2. **Никаких `SELECT *`** — каждый запрос перечисляет колонки. Иначе новая колонка ломает
   позиционное сканирование в старом коде и наоборот.
3. **Удаление/переименование колонки — только через два релиза** (expand/contract): релиз N
   добавляет новое и начинает писать в оба места, релиз N+1 (после того как откат на N-1 уже
   неактуален) удаляет старое. Один релиз, который и переименовывает, и читает по-новому, лишает
   права на откат — это допускается только с явным решением и записью в CHANGELOG (74.6).
4. **Сужающие `CHECK`/`NOT NULL` без дефолта** приравниваются к п. 3.
5. **ClickHouse, Kafka и Redis не откатываются никогда.** CH-колонки добавляются
   `ADD COLUMN IF NOT EXISTS … DEFAULT`, поэтому старый код продолжает писать подмножество колонок;
   конверт Kafka — JSON с `omitempty` (неизвестные поля игнорируются, offsets сохраняются); кеш узла
   в Redis живёт 300 с и протухает сам. Если релиз меняет **семантику** уже существующего поля
   кеша (как §50, где креды стали шифроваться), он обязан сказать в CHANGELOG, что при откате
   ключи `node:*` нужно удалить.

## 74.3 Толерантный старт: схема новее бинаря

Стартовая проверка миграций различает три состояния и ведёт себя так:

| Состояние | Условие | Поведение |
|---|---|---|
| Штатное | версия в БД ≤ максимальной версии в каталоге образа | применить непримененные миграции (как раньше) |
| **Схема новее бинаря** | `dirty = false` **и** версия в БД строго больше максимальной версии каталога | **сервис стартует**; миграции не применяются; событие уровня `error` + метрики (см. ниже) |
| Оборванная миграция | `dirty = true` | старт прекращается (`exit 1`) — состояние схемы неизвестно, работать на ней нельзя; лечение — 74.4 |

Послабление даётся **по умолчанию, без ключей конфига и флагов запуска**: в аварии правка
`config.yml` или `docker-compose.yml` на боевом сервере — это те же потерянные минуты, ради
которых всё и затевалось. Проверка выполняется до вызова `Up()`, поэтому текст ошибки
`golang-migrate` не разбирается — сравниваются версии.

**Сигнал.** Состояние «нода едет на схеме новее своего кода» законно только на время незавершённого
отката, поэтому оно объявляется громко:

- запись уровня **`error`** в стартовом логе (видна в консоли «Логи» §51) с атрибутами
  `db_version` и `binary_max_version`. Уровень выбран не для драматизма: Sentry-хендлер цепочки
  логгера имеет собственный порог `sentry.level` (по умолчанию `2` = error), и `warn` в Sentry не
  доехал бы;
- метрики Web и Receiver: `nexus_pg_schema_version` (версия схемы в БД) и `nexus_pg_schema_ahead`
  (0/1). Лейблы `service`/`nexus_instance` навешиваются общим механизмом §6/§70.7;
- алерт `NexusSchemaAheadOfBinary` в `deploy/prometheus.alerts.yml` — срабатывает, если признак
  держится дольше 15 минут (то есть откат не довели до конца или забыли про него).

Sender схему не мигрирует и этих метрик не отдаёт — у него нет `AutoMigrate` (см. §5.1).

**Границы — что послабление НЕ закрывает:**

- оно не делает совместимой схему, нарушающую 74.2: если релиз удалил или переименовал колонку,
  старый код упадёт на первом же запросе — не на старте, а в работе. Такие релизы обязаны
  откатываться вместе со схемой;
- оно не заменяет `pg_dump` перед обновлением с миграциями;
- оно не влияет на `dirty` — оборванная миграция по-прежнему останавливает старт;
- оно ничего не делает автоматически: решение «оставить схему новой» или «откатить» принимает
  оператор, а признак `nexus_pg_schema_ahead` лишь не даёт про это забыть.

## 74.4 Принудительная установка версии схемы (`--migrate-force`)

Флаг `--migrate-force <N>` есть у всех трёх бинарей (как и остальные `--migrate-*`) и делает ровно
одно: записывает версию `N` в `schema_migrations` и снимает флаг `dirty`. Значение `-1` означает
«версий нет» (состояние чистой базы).

**Что он не делает: SQL не выполняется.** Привести саму схему в состояние, соответствующее
заявленной версии, обязан оператор — вручную дописав или откатив то, что не доделала оборванная
миграция. Поэтому:

- версия проверяется по каталогу: `--migrate-force` на номер, которого нет среди `*.up.sql`,
  отклоняется (защита от опечатки, из-за которой база «числилась бы» в несуществующем состоянии);
- команда логирует предупреждение с явной формулировкой «SQL не выполнен» — чтобы в разборе
  инцидента было видно, что состояние объявлено, а не достигнуто.

Штатный сценарий применения — 74.1, строка про `dirty`: посмотреть, что успела сделать упавшая
миграция, довести до состояния «до» или «после», выставить соответствующую версию, стартовать.

## 74.5 Мгновенный откат кода: версионирование образов

Образы собираются на сервере и не публикуются в registry, поэтому единственный способ вернуться на
прежний код за секунды — сохранить предыдущий образ под версионным тегом **до** обновления.

- имена образов приложения — `nexus-web`, `nexus-receiver`, `nexus-sender` (имя compose-проекта
  `nexus` + имя сервиса);
- перед обновлением: `scripts/deploy/images.sh tag <текущая версия>` — вешает версионный тег на
  текущие `:latest`;
- при аварии: `scripts/deploy/images.sh rollback <версия>` — возвращает `:latest` на сохранённые
  образы и перезапускает сервисы **без сборки** (`docker compose up -d --no-build --force-recreate`);
- `scripts/deploy/images.sh list` — какие версии сохранены на сервере.

Скрипт не заменяет `git checkout` прежнего тега: рабочее дерево нужно вернуть, чтобы следующая
сборка шла от правильного кода, а compose-файл соответствовал образам. Но в момент аварии порядок
обратный — сперва поднять сервис из сохранённого образа, потом приводить в порядок дерево.

## 74.6 Строка «Откат» в CHANGELOG

Каждый релиз в `CHANGELOG.md` содержит строку вида:

```
**Откат:** без отката схемы (миграций нет).
**Откат:** 4 миграции (0029–0032); down теряет реестр инстансов §73 и сохранённые периоды §71.
```

Оператору в аварии нужно одно число — сколько миграций откатывать, — и предупреждение о потерях.
Считать это по `git ls-tree` в момент инцидента недопустимо, поэтому значение готовится заранее
хелпером `scripts/release/rollback_info.py <от-тега> <до-тега>`: он выводит количество миграций
между тегами, их список и помечает те, чей `down` теряет данные (`DROP TABLE`, `DROP COLUMN`,
`DELETE FROM`).

Шаг «добавить строку Откат» входит в процедуру выпуска релиза (DEPLOYMENT §9.5).

## 74.7 Порядок операций при откате

Полные процедуры — в DEPLOYMENT §10; здесь фиксируются инварианты, которые нельзя нарушать:

1. **Откат схемы выполняется образом НОВОЙ версии** — до того, как `:latest` вернули на старый
   образ или пересобрали дерево. Старый образ не умеет откатывать миграции, которых не знает (74.1).
2. **Перед `--migrate-down` сервисы останавливаются** — все три: работающий код новой версии
   обращается к колонкам, которые down удалит.
3. **Откат схемы нужен только при нарушении 74.2.** В остальных случаях схема остаётся новой,
   а сервисы едут на старом коде с активным признаком `nexus_pg_schema_ahead` — это штатное
   временное состояние.
4. **Дамп PostgreSQL снимается перед обновлением с миграциями**, а не перед откатом: в момент
   аварии данных для снятия дампа уже может не быть времени.

## 74.8 Вне рамок

- **Горизонтальное масштабирование** (несколько экземпляров Receiver/Web за балансировщиком ради
  нулевого простоя при плановом обновлении) — отдельное ТЗ. Сейчас у каждого сервиса один
  экземпляр, и пересоздание контейнера означает короткий перерыв.
- **Автоматический откат** по метрикам/healthcheck: решение о возврате принимает человек.
- **Откат ClickHouse, Kafka и Redis** — не требуется по 74.2 и не реализуется.
- **Автоматическая генерация down-миграций** и проверка их обратимости в CI: down-файлы
  пишутся вручную, как и раньше.
- **Гарантия отката более чем на одну минорную версию назад**: контракт 74.2 обеспечивает
  совместимость соседних релизов; прыжок через несколько релизов проверяется отдельно.
