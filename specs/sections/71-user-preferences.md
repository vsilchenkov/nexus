## 71. Персональные предпочтения пользователя: дефолтный период рабочего стола per-team

Раздел вводит серверное хранилище персональных настроек интерфейса (per-user, опционально
per-team) и переводит на него первую такую настройку — **дефолтный период рабочего стола**
(«звёздочка» [§44.B](44-dashboard-counters.md)).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

### 71.1 Проблема и scope

**Проблема.** Дефолтный период жил в `localStorage` под ключом `nexus.overview.period`: один на
браузерный профиль, без привязки к пользователю и к команде. Следствия:

- у оператора разные команды означают разные горизонты наблюдения (в одной осмысленны 1ч, в другой
  — 7д), а дефолт был общий;
- настройка не переезжала на другое устройство;
- два человека за одной машиной перетирали дефолты друг другу.

**В scope:** дефолтный период страницы «Узлы» (Overview) и generic-хранилище под будущие префы.

**Вне scope:**

- вкладки узла «Обзор»/«Метрики»/«Очередь» и Kafka-монитор — там период по-прежнему стартует с
  системных 24ч и «звёздочку» не читает;
- удаление префа отдельным запросом: UI сбрасывает значение записью нового, DELETE-эндпоинта и
  метода в порту нет;
- перенос в это хранилище прочих браузерных настроек (`nexus.overview.view`,
  `nexus.overview.autorefresh`, тема, живые фильтры §54) — они остаются эргономикой одного
  устройства.

### 71.2 Модель данных

Миграция `0031_user_preferences`:

```sql
CREATE TABLE user_preferences (
    user_id    UUID        NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    team_id    UUID,                    -- NULL = глобальный преф пользователя
    key        VARCHAR(64) NOT NULL,
    value      JSONB       NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT user_preferences_membership_fkey
        FOREIGN KEY (user_id, team_id) REFERENCES user_teams (user_id, team_id) ON DELETE CASCADE,
    CONSTRAINT user_preferences_key_format
        CHECK (key ~ '^[a-z][a-z0-9_]*(\.[a-z0-9_]+)*$'),
    CONSTRAINT user_preferences_value_not_null
        CHECK (jsonb_typeof(value) <> 'null'),
    CONSTRAINT user_preferences_value_size
        CHECK (octet_length(value::text) <= 4096)
);

CREATE UNIQUE INDEX user_preferences_uniq
    ON user_preferences (
        user_id,
        COALESCE(team_id, '00000000-0000-0000-0000-000000000000'::uuid),
        key
    );
```

Решения схемы:

- **Уникальность — индекс по выражению `COALESCE`, а не `UNIQUE` по колонкам.** С обычным `UNIQUE`
  две строки `(user, NULL, 'overview.period')` считались бы различными (`NULL <> NULL`): копились
  бы дубли глобальных префов, а `ON CONFLICT` для них не срабатывал бы — upsert превратился бы в
  append. Просится `UNIQUE NULLS NOT DISTINCT`, но это PostgreSQL 15+, а **минимальная
  поддерживаемая версия — 12** (на ней работают боевые инсталляции): такая миграция там не
  применится и сервис не поднимется. Выражение в `ON CONFLICT` репозитория обязано совпадать с
  выражением индекса — по нему PostgreSQL и находит индекс.
- **Два внешних ключа намеренно.** Составной FK на `user_teams` (приём §49) даёт БД-инвариант
  «преф ⊆ членство» и один каскад сразу на три события (удаление пользователя, удаление команды,
  исключение из членства). Но по правилу MATCH SIMPLE он не проверяет строки с `team_id IS NULL` —
  их каскад закрывает отдельный FK на `users(id)`.
- Отдельный индекс не нужен: UNIQUE-констрейнт создаёт индекс с ведущей `user_id`, обслуживающий
  единственный SELECT и обе ветки upsert'а.
- Потолок числа записей на пользователя — `maxPreferencesPerUser = 200`, проверяется атомарно в
  самом INSERT'е. Ограничение действует только на добавление нового ключа; обновление
  существующего проходит и при достигнутом потолке. Строгой гарантии нет: два параллельных запроса
  могут дать запись сверх лимита — это защита от раздувания, а не инвариант.

### 71.3 API

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/api/me/prefs` | все префы пользователя одним ответом (глобальные + по всем командам) |
| `PUT` | `/api/me/prefs` | upsert одного префа `{team_id?, key, value}` |

Оба — только session-cookie (`RequireSessionOnly`): у API-токена нет настроек интерфейса.
`user_id` берётся строго из сессии, из тела не принимается никогда.

**Значение непрозрачно для сервера.** `value` — произвольный валидный JSON (не `null`) до 4096
байт; семантику держит клиент. Это осознанный контракт: добавление нового префа не должно требовать
правки бэкенда. Формат ключа — `^[a-z][a-z0-9_]*(\.[a-z0-9_]+)*$`, до 64 символов
(namespace'ы через точку).

**Чтение деградирует, а не падает.** При сбое хранилища `GET` отдаёт `200 {"items": []}`, а не 500:
рабочий стол ждёт префы, прежде чем запросить метрики, и 500 отсюда лишил бы страницу основной
функции из-за настройки интерфейса.

`PUT` отвечает 400 на невалидный ключ/значение, превышение потолка и на команду вне членств
пользователя. Для чужой и несуществующей команды ошибка одинакова — по коду ответа нельзя проверять
существование команды.

Первый и пока единственный ключ — **`overview.period`**, значение — сериализованный `Period` фронта:
`{"kind":"preset","range":"7d"}`. Произвольный календарный диапазон дефолтом не сохраняется.

### 71.4 Решения

- **Почему PostgreSQL, а не localStorage.** Настройка «под себя» должна переезжать между
  устройствами и быть персональной. §44.B выносил серверное хранение из scope не по принципу, а
  чтобы не тянуть бэкенд ради одной кнопки; с появлением второй такой потребности (§48
  «сохранённые фильтры per-user») цена generic-таблицы окупается.
- **Почему generic-таблица, а не узкая «под период».** В репозитории конвенция «одна узкая таблица
  на фичу» относится к доменным сущностям с инвариантами. У настроек UI инвариантов нет, зато есть
  очередь потребителей: новый преф — это новый `key`, без миграции и без правки слоёв бэкенда.
- **Почему отдельный `PreferenceUsecase`, а не builder на `AuthUsecase`.** Тот уже несёт
  login/logout, пароли, team-switcher, избранное и историю поиска. Builder в §49/§62 был
  компромиссом обратной совместимости («существующие вызовы `NewAuthUsecase` не меняются»), а не
  архитектурным выбором — для нового типа этого ограничения нет.
- **Аудит не пишется.** Клик по кнопке «По умолчанию» — высокочастотное личное действие без
  ценности для расследования; то же правило, что для истории поиска (§62).

### 71.5 Поведение UI

- **Резолв дефолта:** преф команды → глобальный преф пользователя → системные 24ч
  (`defaultPeriod`).
- **Переключение команды.** Период рабочего стола производен от URL. Если пользователь его вручную
  не трогал (URL чист), смена команды пересчитывает фильтры с новым дефолтом — показывается дефолт
  новой команды. **Принудительного сброса нет:** явно выбранный период (`?range=30d`) переживает
  переключение. Эффекта, переписывающего период при смене `teamId`, в коде быть не должно —
  поведение закреплено тестом «явный `?range=1h` переживает переключение команды».
- **Прямая ссылка** `?range=…` уважается всегда, в том числе при первой загрузке.
- **Пока префы не загружены** (`periodReady = teamId !== "" && !isPending`): вместо переключателя
  периода — плейсхолдер той же высоты, запрос метрик не уходит, метка периода в KPI пустая.
  Показывать 24ч и затем переключаться на настоящий дефолт нельзя: это и мигание, и второй запрос
  `/api/metrics/nodes` на каждый заход.
- **Кнопка «По умолчанию»** сохраняет пресет как дефолт **текущей** команды; подсказка называет
  команду. Подсветка звёздочки производна от дефолта команды (раньше это был `useState` с ленивой
  инициализацией, из-за чего после переключения команды подсвечивался дефолт прежней).
- **Разовая миграция.** При первом заходе после обновления значение из `nexus.overview.period`
  переносится в **глобальный** преф пользователя и ключ удаляется из браузера. Условия все сразу:
  префы загружены, значение валидно, глобального префа на сервере ещё нет. Ключ удаляется только
  после успешного `PUT` — иначе миграция повторится в следующей сессии (она идемпотентна).
  Глобальный, а не командный: старое значение было глобальным по смыслу, и так пользователь с
  пятью командами сохраняет привычный период везде.
  **Срок жизни:** удалить `useMigrateLegacyPeriodPref` и обработку старого ключа через два релиза
  после выпуска §71.

### 71.6 Границы и неочевидности

- **Липкость явного выбора.** Выбранный вручную период держится, пока пользователь не выберет
  период, равный дефолту текущей команды (тогда `range` уходит из URL по `serializeFilters`), либо
  пока не закроется вкладка (зеркало фильтров §54 живёт в `sessionStorage`).
- **§58 (шаринг узла).** Открыли шаренный узел чужой команды → сессия авто-переключилась → возврат
  на «Узлы» покажет дефолт новой команды, если период не выбирали руками; выбранный руками
  восстановится из зеркала §54, потому что оно общее для всех команд. Это следствие решения
  «явный выбор липкий», а не дефект.
- **«Выбрал период, равный дефолту» неотличимо от «не выбирал»** — следствие §54.2, где дефолтное
  значение не сериализуется в URL. Поведение существующее, §71 его не меняет.
- **Гейт по `!isPending`, а не `isSuccess`.** При недоступном `/api/me/prefs` (5xx, сеть, старый
  бэкенд без эндпоинта) `isSuccess` не наступит никогда, и рабочий стол навсегда остался бы без
  метрик. Два независимых рубежа: `settled = !isPending` на фронте и чтение, не возвращающее
  ошибку, на бэке.
- **Префы читаются одним запросом на всего пользователя.** Иначе при переключении команды её дефолт
  приходил бы позже смены `teamId`, и период успел бы мигнуть, а фильтры — записать в URL не то
  значение. По той же причине ключ `me-prefs` входит в `TEAM_INDEPENDENT_KEYS`: инвалидация на
  смене команды дала бы рефетч ровно тех же данных.
- **Совместимость по версиям.** Старый бандл + новый бэкенд — работает по-старому (localStorage).
  Новый бандл + старый бэкенд — `GET` даёт 404, react-query 4xx не ретраит, `settled` наступает,
  страница работает с 24ч; миграция ключа не отрабатывает и localStorage не очищается — она пройдёт
  позже.
- **Пока дефолт команды не загружен, период всегда пишется в URL явно.** Модуль фильтров получает
  `null` вместо дефолта, и «дефолтность» периода в это окно не вычисляется. Иначе правка любого
  другого фильтра (статус, метод, поиск) в первые сотни миллисекунд — а на медленной сети и в
  секунды — сравнила бы период с системными 24ч и стёрла бы из URL явно выбранный `range=24h`;
  после прихода префов период молча сменился бы на дефолт команды.
- **Ошибка сохранения дефолта пользователю не показывается.** При неуспешном `PUT` оптимистичное
  обновление кеша откатывается (звёздочка гаснет), тоста нет — отдельного i18n-ключа под это не
  заводилось. Практически единственная достижимая ошибка — потолок в 200 записей.
- **Минимальная поддерживаемая версия PostgreSQL — 12** (на ней работают боевые инсталляции;
  docker-поставка и testcontainers используют более свежие). Схема §71 намеренно обходится без
  `UNIQUE NULLS NOT DISTINCT` (15+) — первая редакция миграции его использовала, тесты на
  PostgreSQL 16 этого не заметили, и на боевом сервере сервис просто не поднялся бы. После этого
  дефолтный образ в integration-тестах переведён на минимальную версию
  (`postgres:12-alpine`, переопределяется `NEXUS_TEST_PG_IMAGE`).
