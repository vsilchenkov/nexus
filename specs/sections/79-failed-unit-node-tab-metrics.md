# 79. Неудачные доставки как записи, вкладка узла в адресе, фильтры и шаг графика метрик, goleak

Раздел закрывает четыре замечания, три из которых получены из боевого разбора 2026-08-05
(узел `kz`, команда `conv`, `root_method=requestAsync`):

1. **«Неудачные доставки» не очищаются после успешного повтора.** В списке висели 17 записей, из
   которых **16 уже доставлены** (свежайший прогон — `200 OK`). Хуже: «Повторить все сейчас» взяло
   их же и отправило заново — получатель (1С `acc_kz`) получил **15 дублей**.
2. **Вкладку узла нельзя передать ссылкой** — адрес не меняется при переключении вкладок, а
   входящий `?tab=` распознаётся только как `logs`.
3. **Метрики узла нельзя отфильтровать**, а плотность графика выбирает сервер: «14 столбцов по
   суткам за две недели» получить нечем.
4. **`goleak` объявлен политикой** ([CLAUDE.md §8](../../CLAUDE.md), [CONTRIBUTING.md](../../CONTRIBUTING.md)),
   но реально стоит в 5 пакетах из ~51.

## 79.1 Единица «неудачной доставки» — запись без единого успешного прогона

**Проблема.** Строка таблицы логов — это **прогон доставки**, а не запрос: у одной записи (`ID`)
столько строк, сколько раз шла доставка (redelivery Kafka, проход DLQ-репроцессора §36,
`ttl_expired`, replay, дренаж retry-топика §38) — это зафиксировано в §78.6. Успешный повтор
дописывает строку `done=1`, но **старая строка `done=0` остаётся навсегда** (до retention).

Предикат «неудачной доставки» смотрел только на строки: `uniqExact(ID) WHERE done = 0`. Значит
запись попадала в список и в счётчик, если у неё есть хоть один неуспешный прогон, — независимо от
того, доставлена она в итоге или нет.

Это прямо противоречит §36.9 и §36 п. 7, где обещано:

> «В CH появляется запись `done=true` → сообщение "восстановлено", **счётчик "Неудачные доставки" за
> период падает**».

Боевой слепок (узел `kz`, 05.08.2026, окно 24 ч):

| Источник | Значение | Выражение |
|---|---|---|
| KPI узла, «Ошибки» | **1** | `countDistinct(ID) − uniqExactIf(ID, done=1)` |
| Вкладка «Очередь», «Неудачные доставки» | **13** | `uniqExact(ID) WHERE done=0` |

Расхождение в 13 раз на одних и тех же данных: 12 записей уже доставил авто-репроцессор.

**Решение.** Единица «неудачной доставки» — **запись, у которой в окне НЕТ НИ ОДНОГО прогона
`done=1`**. Это ровно множество `Errors` из `NodeKPI`, поэтому KPI узла и вкладка «Очередь»
становятся тождественны по построению, а не по совпадению.

Вводится отдельное поле запроса `LogQuery.Unresolved bool`. Оно обслуживает **только** вид
«Неудачные доставки»: счётчик, список под ним, очистку и «Повторить все».

**Фильтр `done` журнала логов НЕ меняется.** Там `done=no` означает «прогон не завершён» — свойство
СТРОКИ, и менять его нельзя по трём причинам:

- смысл другой: в журнале это «в работе», у него есть парный «Завершено»;
- у фильтра есть in-memory зеркало live-tail: одну прилетевшую строку по правилу «в окне нет ни
  одного `done=1`» классифицировать физически невозможно, а расхождение зеркал запрещено §72.1;
- §72.1 фиксирует `ok ∪ err = все` и перпендикулярность `done` и `status`.

**Формы SQL.** Предикат выражается тремя способами — по одному на класс задач. Общий принцип:
платить за МАЛУЮ сторону (неудачных записей на порядки меньше доставленных).

| Задача | Форма |
|---|---|
| Счётчик (`CountFailed`, KPI вкладки) | один проход: `countDistinct(ID) − uniqExactIf(ID, done = 1)`; при `metrics_approx_counts` — `uniq` / `uniqIf` |
| Набор ID для действий (`FailedIDs` → cancel / replay / delete) | два шага: кандидаты `SELECT DISTINCT ID … done = 0 LIMIT cap+1`, затем проба `SELECT DISTINCT ID … done = 1 AND ID IN (кандидаты)`; разность множеств считается в Go |
| Постраничный список (`Search` при `Unresolved`) | страница кандидатов (keyset §72.3) → проба по ID страницы → отсев → добор страницы до `limit` |

Отвергнутые варианты и почему:

- `ID NOT IN (SELECT ID … WHERE done = 1 AND окно)` — строит множество по ДОСТАВЛЕННЫМ, то есть по
  большой стороне. На боевой таблице в 10 млн записей это сотни МБ хэш-сета на каждый запрос, а
  список поллится раз в 15 с;
- `GROUP BY ID HAVING max(done) = 0` — хэш-таблица по всем различным `ID` окна, та же память;
- `argMax(done, date_request) = 0` — **семантически другое** («последний прогон неуспешен»), плюс
  недетерминировано на «плотных» секундах (та же грабля, что лечил keyset §44/45-fix). Разошлось бы
  с `NodeKPI` — то есть воспроизвело бы исправляемый дефект.

**Вычитание — в Go, с клампом `delivered ≤ total`.** В приблизительном режиме (HLL) разность
`uniq − uniqIf` может уйти в минус, а в `uint64` это 1.8·10¹⁹ на экране. Так уже сделано в `NodeKPI`.

**Атрибуция в разрушающих операциях: очистка убирает ровно то, что видно.** Первая редакция раздела
предписывала строгий `node_id = ?` в `DELETE` (без послабления §61 для внешних таблиц §64) — как
защиту второго порядка. Integration-тест показал, что это ломает штатный случай: на внешней таблице
пустой `node_id` нормален для КАЖДОЙ строки, такие записи показываются в «Неудачных доставках», и
кнопка «Очистить» молча переставала работать. То же касается записей без идентификатора (legacy до
§37).

Действующее правило: node-фильтр разрушающей операции **совпадает с читающим** (`nodeFilter`). Данные
постороннего писателя защищают:

- гейт владения §70.4 — на чужой БД DML запрещён целиком (там нет маркера `__nexus_owner`);
- точный список ID — удаляются только записи, которые вернуло чтение с той же атрибуцией.

Симметрия «вижу → могу очистить» здесь важнее формальной узости фильтра: невидимую запись очистка не
тронет, а видимую обязана убрать.

**Побочный выигрыш.** Все три метода строятся общим `searchConds`, а не собственным набором условий,
поэтому путь «неудачных доставок» впервые получает сужение по `date_create` (§72.4) — партиции
начинают отсекаться (замер §72.4: 8 192 прочитанных строки против 200 000).

## 79.2 «Повторить все сейчас»: только нерешённые и очистка истории оригинала

**Проблема.** `ReplayFailed` брал набор из `FailedIDs`, то есть вместе с уже доставленными
записями, и слал их повторно. Боевой аудит 05.08.2026 15:02: `op=replay_all total=16 replayed=16
failed=0`, из них **15 сообщений уже были доставлены** авто-репроцессором ранее — 15 дублей у
получателя. Ни одна из 17 записей при этом из списка не исчезла: replay пере-инжектирует запрос как
НОВЫЙ (новый `ID`, маркер `__replay_of`), а строки `done=0` оригинала не трогает.

**Решение.**

1. Набор для повтора берётся по предикату §79.1 → **уже доставленные не переотправляются**. Это
   устраняет дубли без отдельного механизма.
2. После успешной реинъекции строки `done=0` оригиналов удаляются **одним batch-вызовом**
   (`DeleteFailedRows(query, ids)`) — запись исчезает из «Неудачных доставок» сразу, не дожидаясь
   ручной очистки. Успешные строки записи (`done=1`) остаются: история доставки не теряется.
3. Удаление **никогда по одному ID**: lightweight delete в ClickHouse не бесплатен, 500 подряд
   создадут мутационную нагрузку.

**Очистка — best-effort.** К моменту удаления сообщения уже пере-инжектированы; отказ гейта владения
не должен превращаться в ошибку всей операции. Отказ логируется (`Warn`), в результате возвращается
`cleaned=0`, HTTP-ответ остаётся успешным.

**Границы защиты (что НЕ закрыто):**

- на **внешней** таблице §64 и на таблице **чужой ноды** §70.4 история оригиналов не очищается —
  записи останутся в виде «Неудачные доставки» до истечения периода или до ручной очистки;
- дубли, отправленные до внедрения раздела, не отзываются;
- если реинъекция прошла, а доставка снова не удалась, запись останется неудачной — уже под новым
  `ID`. Это корректно: неудача новая.

**Очистка «Неудачных доставок» (§36.10) считает множество один раз.** Раньше `PurgeFailed` делал два
независимых прохода — `FailedIDs` для tombstone'ов и сплошной `DELETE … done=0` для удаления, из-за
чего в аудите жило расхождение (боевое `cancelled=5, deleted=10`). Теперь оба шага работают с одним
набором ID, и равенство становится конструктивным.

**Изменение поведения, о котором обязан знать оператор:** очистка ограничена `peekCap` записей за
вызов (сплошной `DELETE` был безлимитным). Превышение отдаётся как `capped=true` — UI просит нажать
ещё раз.

**Ответ операции** (`POST /api/nodes/{id}/async-queue/replay-failed`) дополняется полем `cleaned` —
сколько записей убрано из вида. Аудит `op=replay_all` — теми же ключами.

## 79.3 Вкладка узла в адресе: `?tab=`

**Проблема.** Активная вкладка жила в `useState`; в адрес не писалась никогда. Входящий `?tab=`
распознавался только как `logs` (§47.4) — остальные четыре значения молча давали «Обзор». Передать
коллеге ссылку «метрики этого узла» или открыть вкладку в новом окне браузера было нечем.

**Решение.** Источник истины активной вкладки — **адресная строка**:

```
/nodes/<id>?tab=overview | logs | config | metrics | queue
```

- параметр отсутствует или не распознан → «Обзор», адрес нормализуется записью `replace`
  (мусорное значение не должно копиться в истории);
- клик по вкладке пишется в историю через `push`: «Назад» возвращает предыдущую вкладку. Это
  осознанное отклонение от принятой в проекте конвенции `replace` (§54, §76): вкладка — навигация, а
  не фильтр;
- существующие ссылки `?tab=logs&from=…&to=…` из рабочего стола продолжают работать: парсер
  начинает понимать все пять значений вместо одного.

**Форма адреса — query-параметр, а не сегмент пути.** `/nodes/:id/:tab` соседствовал бы с занятым
`/nodes/:id/edit`, а неизвестный сегмент попадал бы в catch-all и уводил на рабочий стол, а не на
узел. Плюс `?tab=` уже де-факто зарезервирован §47.4.

**Дип-линк логов тоже переезжает в адрес.** Окно и быстрые фильтры вкладки «Логи» (`from`, `to` в
миллисекундах, `status`, `done`), которые ставятся кликом по графику (§33.4) и переходом из
«Очереди» (§35), раньше жили в `useState` родителя. Если оставить их там, а вкладку взять из URL,
после «Назад» состояние разъедется. Правила:

- уход с вкладки «Логи» удаляет `from`/`to`/`status`/`done` из адреса — иначе адрес продолжает
  обещать окно, которого уже нет (сегодня это делает обработчик клика, который при «Назад» не
  срабатывает);
- запись всегда функциональной формой над предыдущим значением: чужие ключи (в т.ч. будущие) обязаны
  выживать — правило §54;
- рендер вкладок остаётся **условным**: `LogsTab` читает начальный фильтр только при монтировании
  (контракт §48), поэтому переводить вкладки на скрытие через CSS нельзя.

**Кнопка «Поделиться»** (§58) отдаёт ссылку с текущей вкладкой: `…/nodes/<id>?tab=metrics`. Окно и
фильтры логов в неё не попадают — это сиюминутное состояние клика по графику, а не то, чем делятся.

## 79.4 Расширенные фильтры на вкладке «Метрики»

**Проблема.** Вкладка «Метрики» принимала только период. Ответить на вопрос «как выглядит трафик
конкретного подпути / только ошибки / только с этого хоста клиента» было нельзя — приходилось
переходить в журнал и считать глазами.

**Решение.** На вкладку выносится тот же набор фильтров, что и в журнале логов (§48/§67):
полнотекстовый поиск с режимами `Aa` / `ab|` / `.*`, метод (подпуть §39), хост клиента, быстрые
фильтры «Все/ОК/Ошибки» и «Все/Завершено/В работе». **KPI и график считаются под ними же** — иначе
цифры над графиком и сам график описывали бы разные множества.

Панель фильтров выносится из журнала в переиспользуемый компонент **без изменения поведения**:
сохраняются коммит по `Enter`/`blur`, откат по `Escape`, идемпотентность (повторный коммит того же
значения не порождает запрос) — всё, что введено §77.3.

**Полей «Дата с»/«Дата по» на этой вкладке нет.** Окно задаёт выбор периода (он умеет произвольный
диапазон). Два контрола, пишущих в одни и те же границы, затирали бы друг друга.

**Единственный источник условий.** Фильтры доезжают до ClickHouse тем же `searchConds`, что и
журнал: заводить для метрик отдельный набор условий нельзя — два источника гарантированно разойдутся
(эту болезнь §67 уже лечил, сделав `searchConds` общим для списка и счётчика).

**Сужение по партициям обязательно.** Агрегаты метрик обязаны получать `DateCreateAligned`
(`= !external_table`, §72.4). Без него фильтр по полнотексту читал бы таблицу целиком.

**Деградация.** Полнотекстовый фильтр читает тела с диска, а вкладка поллится каждые ~12 с. Поэтому:
серверный таймаут на пару запросов метрик (10 с) → `chart_available=false` вместо зависания;
на клиенте медленный (>2 с) набор фильтров выключает авто-обновление до его смены — та же механика,
что у журнала (§77.3).

## 79.5 «Шаг графика» и единица столбца

**Проблема.** Плотность графика выбирал сервер по длительности окна: 24 ч → 48 столбцов по 30 мин,
14 д → 84 столбца по 4 ч. Запрос «покажи 14 суток по одному столбцу на сутки» выразить было нечем.

**Решение — поле «Шаг графика»** рядом с периодом: `1ч | 3ч | 24ч | 7д | 14д | 30д` и `авто`
(прежнее поведение). Период 14 д + шаг 24 ч = ровно 14 столбцов, в каждом — статистика за сутки.

Параметр передаётся строкой (`step=24h`), а не числом секунд: `?range=14d&step=86400` нечитаем в
адресной строке. Правила согласования пары (окно, шаг):

| Ситуация | Поведение |
|---|---|
| шаг не задан / `auto` | прежний расчёт по длительности окна |
| шаг больше окна | шаг сжимается до окна — ровно один столбец |
| столбцов вышло больше 400 | шаг поднимается до `окно / 400` |

Потолок 400 — предел читаемости: при ширине графика ~900 px это уже 2 px на столбец.

**Фактический шаг возвращается в ответе** (`step_seconds`). Сегодня компонент графика угадывает
ширину столбца как разницу временных меток двух первых точек, а на ряде из одной точки берёт минуту
«с потолка» — из-за чего подсказка и переход в логи по клику показывают неверные границы.

**Единица столбца — ЗАПИСЬ, а не строка таблицы.** График считал `count()` строк, тогда как KPI над
ним — уникальные `ID` (§78.6). На узле с недоступным приёмником репроцессор добавляет прогон каждые
5 минут, поэтому столбцы были завышены в разы относительно «Всего».

**Запись относится к интервалу своего ПРИХОДА, а цвет берётся по ИТОГОВОМУ состоянию.** Это
отдельное требование, вытекающее из §79.1: список «Неудачных доставок» и KPI после успешного повтора
очищаются сами, и график обязан вести себя так же — иначе на одной вкладке будут три разных ответа
на один вопрос.

| | Интервал записи | Статус записи |
|---|---|---|
| **Принято (§79.5)** | по первому прогону (`min(date_request)`) — когда запрос пришёл | итоговый: доставлена, если в окне есть хоть один прогон `done=1` |
| Отвергнуто | по каждому прогону | по прогонам внутри интервала |

Отвергнутый вариант читается как хроника аварии («в 18:17 попытка провалилась»), но расходится с
KPI над графиком и со списком под ним: запись, доставленная повтором в другом интервале,
одновременно и ошибка (в первом столбце), и успех (во втором), а сумма столбцов превышает «Всего».

**Что это значит для чтения графика.** График показывает **актуальное состояние на момент
обновления**, а не журнал попыток:

- запрос пришёл в 18:17 и упал → столбец 18:00–19:00 показывает его как ошибку;
- авто-репроцессор доставил его в 19:40 → при следующем обновлении (поллинг ~12 с) красный сегмент
  в столбце 18:00–19:00 **исчезает**, столбец становится «доставлено». Нажимать «Повторить» не нужно;
- **исторические столбцы меняются задним числом**: вчерашний красный столбец может стать синим
  сегодня, если сообщение наконец доставили. Это ожидаемое поведение, а не сбой отрисовки — оно
  прямо следует из выбранной семантики и обязано быть в подсказке к графику;
- пока сообщение лежит в DLQ и повторяется, столбец остаётся красным — ровно до успешной доставки
  или истечения TTL.

Спарклайны рабочего стола считаются тем же кодом и тоже переходят на записи с итоговым статусом —
это исправление: спарклайн станет согласован с числами `In`/`Out` в своей же строке таблицы.

**Перцентили `p95`/`p99` остаются по попыткам** (строкам), а не по записям: это характеристика
внешнего вызова, а не запроса. Единица у них другая осознанно.

### 79.5.1 Стоимость точного режима и деградация

Итоговый статус требует свернуть строки в записи ДО раскладки по интервалам — то есть группировки
по `ID` за всё окно:

```sql
SELECT toStartOfInterval(first_req, INTERVAL <step> SECOND) AS bucket,
       count() AS total, countIf(ok) AS delivered
FROM (SELECT ID, min(date_request) AS first_req, max(done) AS ok
      FROM <table> WHERE <окно + фильтры> GROUP BY ID)
GROUP BY bucket ORDER BY bucket
```

**Где деградация реальна.** Первая стадия держит хэш-таблицу с одной строкой на запись окна
(ключ `ID` + два агрегатных состояния — порядка 60–80 байт на запись):

| Окно / узел | Записей | Оценка памяти |
|---|---|---|
| 24 ч, узел `kz` (боевой) | ~90 | пренебрежимо |
| 24 ч, самый нагруженный узел (~3,7 тыс/ч) | ~88 тыс. | ~7 МБ |
| 30 дней, крупнейшая боевая таблица §64 | ~10,2 млн | **~800 МБ** |

Критично то, что **приблизительный режим (`metrics_approx_counts`) этой стадии не помогает**: HLL
сжимает только счётчики уникальных, а группировка по `ID` обязана хранить сами ключи. То есть
страховка, которая спасает счётчики §78.6, здесь не работает — нужна своя.

**Правило переключения.** KPI узла считается тем же вызовом и раньше графика, поэтому число записей
окна уже известно бесплатно:

- `kpi.total ≤ порога` (конфиг `web.metrics_exact_chart_max_records`, дефолт **2 000 000**) →
  точный режим «по итогу записи»;
- иначе → режим «по прогонам в интервале» (дешёвая одностадийная агрегация), и ответ помечается
  флагом `chart_unit: "attempts"`;
- в помеченном режиме UI показывает подсказку у заголовка графика: «Окно слишком велико для точного
  режима: столбцы считаются по попыткам доставки, повторы видны в своих интервалах. Сузьте период
  или шаг». Молча подменять семантику нельзя — пользователь обязан понимать, что он видит.

Дополнительные страховки: тот же таймаут 10 с, что и у остальных запросов метрик (§79.4), и
`max_bytes_before_external_group_by` на запрос — при исчерпании памяти ClickHouse уходит на диск, а
не отваливается с ошибкой. Пороговое значение подтверждается замером в integration-тесте
(`read_rows` и `memory_usage` из `system.query_log` на сгенерированной таблице), а не выбирается на
глаз.

## 79.6 Гарантия отсутствия утечек горутин в тестах (goleak)

**Проблема.** `go.uber.org/goleak` — прямая зависимость, политика «в пакетах с горутинами — `TestMain`
с `goleak.VerifyTestMain`» записана в CLAUDE.md и CONTRIBUTING.md, но выполнена в 5 пакетах из ~51.
Утечка горутины в фоновом воркере или адаптере сегодня проходит все гейты незамеченной.

**Решение.** Политика доводится до кода в два эшелона.

**Эшелон A — 13 пакетов без опций** (`goleak.VerifyTestMain(m)`): `platform/safego`, `platform/clock`,
`platform/reloader`, `platform/ratelimit`, `platform/circuitbreaker`, `platform/queuecancel`,
`platform/nodestatus`, `platform/nodeevents`, `platform/clickhouse`, `platform/sentry`,
`web/adapter/out/kafkaadmin`, `receiver/adapter/out/nodecache`, `sender/adapter/in/kafka`.

**Эшелон B — 8 пакетов с исключениями** для фоновых горутин чужих библиотек: пул keep-alive
`net/http` (`persistConn.readLoop`/`writeLoop`, ожидание poller'а) и фон `grpc-go` (keepalive,
`controlBuffer`, сериализатор колбэков). Наборы исключений живут в одном месте — пакете
`internal/platform/testleak`, а не копипастой по файлам: при обновлении библиотек правится одна точка.

**Правило приоритета: сначала чиним, потом игнорируем.** Исключение допустимо только для чужих
горутин, которые мы не можем остановить. Свои — джойнятся в тесте (`t.Cleanup`, канал завершения,
`CloseIdleConnections`). `IgnoreTopFunction` подбирается по фактическому верхнему кадру из вывода
goleak, а не по догадке.

**Вне политики — `tests/integration`.** testcontainers держит reaper и docker-клиент, пул PostgreSQL —
фоновый health-check, ClickHouse — закрыватель простаивающих соединений, Kafka и RabbitMQ — свои
циклы. Список исключений вышел бы на 15+ записей и ломался бы на каждом обновлении библиотек, а
пользы (integration-тесты не про жизненный цикл горутин) — мало. Это осознанное решение, а не
недоделка.

**Известные подвисающие горутины продакшн-кода** (отложенная задача, вне рамок раздела): отложенное
закрытие соединения ClickHouse (до 15 с, владелец не ждёт), резолвер reverse-DNS без метода
остановки, write-back кеша узлов Receiver'а, фоновое обновление `last_used_at` API-токена. Если из-за
них покраснеет пакет эшелона A, пакет выносится в «отложено» — **глушить их исключением нельзя**,
иначе будущий фикс окажется прикрыт заглушкой.

## 79.7 Вне рамок раздела

- **Отзыв дублей**, отправленных до внедрения §79.2, — невозможен на стороне шины.
- **Фикс подвисающих горутин** продакшн-кода (см. §79.6) — отдельная задача.
- **Сохранение «Шага графика» в персональные предпочтения** (§71) — шаг живёт в состоянии экрана;
  при необходимости добавляется новым ключом префов без миграции.
- **Фильтры и шаг на рабочем столе** — раздел трогает только вкладку узла; спарклайны меняют лишь
  единицу столбца.
- **Пропускная способность async-очереди** (лаг `nexus.async`, изоляция медленных узлов) — отдельный
  раздел [§80](80-async-throughput.md).
