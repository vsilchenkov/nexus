# 103. Поиск узла по комментарию

Раздел добавляет комментарий узла (§29) к полям, по которым ищутся узлы. Это касается и глобального
поиска в шапке (§62), и поля «Поиск» на экране «Узлы» (§54). Повод: интеграции часто различаются не
адресом, а назначением. «Где у нас СДЭК», «какой узел шлёт в 1С акты», номер тикета — всё это оператор
пишет в комментарий, но найти узел по этим словам не может.

Развивает [§62](62-global-node-search.md) (глобальный поиск: «комментарий» снимается из «вне scope»
§62.6), [§29](29-node-comment.md) (комментарий узла), [§54](54-overview-filter-persistence.md)
(поиск экрана «Узлы» в URL), [§86](86-all-teams-scope.md) (сквозной режим `scope=all`),
[§100](100-click-targets.md) (растянутая ссылка строки и карточки).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций раздел не требует.**

---

## 103.1 Повод

Поиск узлов всегда шёл одним SQL-запросом (`NodeRepoPg.List`), и условие у него было одно:
`path ILIKE '%q%' OR target_url ILIKE '%q%'`. §62.6 прямо выносил комментарий «вне scope». Комментарий
до 2000 символов (§29) — единственное поле узла со свободным текстом на языке людей. Путь и адрес
технические, и по ним ищет тот, кто их уже знает.

## 103.2 Правило поиска

- Строка поиска ищется подстрокой без учёта регистра в **трёх** полях: `path`, `target_url`,
  `comment`. Одно условие на все три поля, один параметр запроса:
  `AND (path ILIKE $n OR target_url ILIKE $n OR comment ILIKE $n)`.
- Правка одна, и действует она на всех потребителей `ListNodesFilter.Search`:
  - глобальный поиск `GET /api/search/nodes` (§62);
  - поле «Поиск» экрана «Узлы» `GET /api/nodes?search=` — и в команде, и в сквозном режиме
    `scope=all` (§86).
- Остальное не меняется: скоуп команд, лимиты §62 (≥ 2 рун, 20/50), сортировка `ORDER BY path`.
- `%` и `_` во вводе по-прежнему не экранируются (как во всех ILIKE-поисках кодовой базы): они дают
  лишние совпадения, но не пропуски.

**Регистр и кириллица.** Регистронезависимость ILIKE для кириллицы зависит от `LC_CTYPE` базы. Образы
`postgres:*-alpine` создают кластер с `en_US.utf8`, и «СДЭК» находится по «сдэк». Регресс-тест
гоняется на образе integration-тестов — минимальной поддерживаемой версии, как на бою (с §116 —
`postgres:16.16-alpine`, до него — `postgres:12-alpine`). При `LC_CTYPE=C` кириллица
перестала бы сворачиваться, но так же уже сломался бы существующий поиск по пути и имени группы
(§99), так что это не новый риск.

## 103.3 API

- `GET /api/search/nodes`: в элемент ответа добавлено поле `comment` (строка, может быть пустой). Оно
  нужно фронту для подсказки совпадения (§103.4). Верхняя граница объёма: 50 результатов × 2000
  символов.
- `GET /api/nodes` комментарий уже отдавал (`NodeResponse.comment`), контракт не меняется.
- Swagger: описание параметра `search` и эндпоинта глобального поиска перечисляют три поля.

## 103.4 Подсказка совпадения

Узел, найденный только по комментарию, без подсказки выглядел бы случайным: в строке результата виден
путь и адрес, а искомого слова нет. Поэтому:

**Правило показа.** Строка-сниппет с комментарием показывается, **только если подстрока не найдена ни
в пути, ни в адресе**, то есть узел попал в выдачу благодаря комментарию. При совпадении в пути
подсказка лишняя: при запросе вроде «vika» почти каждая строка стала бы трёхстрочной.

**Содержимое.** Фрагмент комментария вокруг первого совпадения: до 40 символов слева и справа,
многоточие там, где текст реально обрезан. Совпадение подсвечено (`<mark>`). Переводы строк и табуляции
для показа схлопываются в пробел, но ищется исходный текст, как и в ILIKE.

**Где.**

```
Глобальный поиск, запрос «сдэк»
┌─────────────────────────────────────────┐
│ svc/cdek-orders            [Логистика]  │
│ https://api.cdek.ru/v2/orders           │
│ 💬 …интеграция со [СДЭК], тикет NX-41…  │ ← третья строка, 11 px
└─────────────────────────────────────────┘

«Узлы», таблица — ячейка «Путь»
│ svc/cdek-orders                     │ request │ 12 │ …
│ 💬 …интеграция со [СДЭК], см. тик…  │

«Узлы», карточка — строка над адресом
┌ svc/cdek-orders                  [Логистика] ┐
│ [request] ● Активен                          │
│ вход │ p95 │ ошибки                          │
│ ▁▂▅▂ спарклайн                               │
│ 💬 …интеграция со [СДЭК], тикет NX-41…       │ ← новое, до двух строк
│ https://api.cdek.ru/v2/orders                │
└──────────────────────────────────────────────┘
```

- **Таблица.** Сниппет стоит внутри ссылки узла вторым элементом, поднятым над растянутым
  псевдоэлементом так же, как текст пути (§100). Строка остаётся одной настоящей ссылкой, а текст
  сниппета можно выделить мышью.
- **Карточка.** Сниппет НЕ поднимается над ссылкой: клик по нему открывает узел, и в карточке не
  появляется мёртвой зоны.
- **Иконка** с доступным именем «совпадение в комментарии» отличает сниппет от адреса.

**Плейсхолдеры.** Поле экрана «Узлы»: «Поиск по пути, URL или комментарию…». Поле в шапке называет те
же три поля.

## 103.5 Неочевидности

- **Сниппет считается на клиенте, а сравнение должно совпадать с ILIKE.** Регистр сворачивается
  посимвольно (по кодпоинтам, `toLowerCase` без локали) с картой смещений в исходную строку. Свёртка
  всей строки разом дала бы контекстные формы (греческая финальная сигма), которых нет у посимвольного
  `lower()` PostgreSQL. `toLocaleLowerCase` в турецкой локали превращает `I` в `ı`. Длина строки после
  свёртки может измениться (`İ` → `i̇`), и индекс в свёрнутой строке без карты указывал бы не на тот
  символ исходной. Там, где правила JS и PG всё же разойдутся, сниппет просто не рисуется: узел в
  выдаче остаётся, пропадает только подсказка.
- **Сниппет строится по запросу, который ушёл на сервер, а не по тексту в поле.** Пока новый ответ не
  пришёл, на экране остаётся прошлая выдача (`keepPreviousData`). Подсветка по новому тексту искала бы
  в ней не то. Глобальный поиск кладёт в данные запроса его строку. Экран «Узлы» берёт строку из того
  же параметра, что и ключ запроса.
- **Окно считается в кодпоинтах**, чтобы не разрезать суррогатную пару (emoji) на границе многоточия.
- **История поиска (§62.4) не меняется.** Она хранит строки запросов, а не результаты.

## 103.6 Вне рамок

- поиск по заголовкам, группе, авторизации и прочим атрибутам узла;
- ранжирование («сначала совпадения в пути») — порядок по-прежнему `ORDER BY path`;
- индекс `pg_trgm`: ILIKE по `comment` идёт полным сканированием внутри выборки команд, как и поиск по
  пути; на сотнях узлов это единицы миллисекунд;
- экранирование `%` и `_` во вводе;
- показ комментария в строке или карточке без поиска.

## 103.7 Проверка результата

- узел с комментарием «Интеграция со СДЭК» находится по «сдэк» и «СДЭК» в шапке, на «Узлах» и в
  сквозном режиме;
- узел чужой команды с тем же комментарием в выдачу не попадает;
- у такого узла есть сниппет с подсвеченным словом; у узла, совпавшего по пути, сниппета нет;
- сниппет в середине длинного комментария обрезан с двух сторон, в начале — только справа;
- клик и Ctrl+клик по строке таблицы и по карточке с сниппетом открывают узел; текст сниппета
  выделяется мышью.
