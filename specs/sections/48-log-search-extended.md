# 48. Расширенный поиск по логам узла (log-search v2)

Переработка панели фильтров вкладки «Логи» узла (развивает §7.4/§42/§47): мини-язык поиска
(И/ИЛИ/НЕ/поле), режимы «регистр / целое слово / regex» как в VS Code, поиск по колонке
`parameters`, фильтр по `method` с ленивым списком значений, ограничение дат min/max из логов,
удаление полей IP/Host из UI.

## 48.1 Мини-язык поиска (plain-режим)

Поле «Поиск» (`q`) принимает выражение:

```
expr   = orPart { "|" orPart }          // ИЛИ (низший приоритет)
orPart = term { "&" term }              // И (приоритет выше, чем |)
term   = ["-"] [prefix ":"] text        // "-" = НЕ (исключение)
prefix = url | params | req | resp     // регистр префикса не важен
```

- Терм без префикса ищется **по четырём колонкам**: `url`, `parameters`, `request`, `response`
  (совпадение хотя бы в одной). Терм с префиксом — только по одной колонке.
- `-терм` — отрицание: запись подходит, если подстрока **не встречается ни в одной** из колонок
  скоупа терма.
- Пробелы по краям термов игнорируются; пробелы внутри текста — значимы (`foo bar` — одна
  подстрока с пробелом).
- Пустой терм (например, `a & & b`, `url:` без текста, `|` в начале) — ошибка → HTTP 400.

**Экранирование** — обратный слеш `\` перед символом даёт литерал:

| Ввод | Значение |
|---|---|
| `\&` | литеральный `&` |
| `\|` | литеральный `\|` |
| `\-` | литеральный `-` в начале терма (внутри текста `-` и так литерал) |
| `\:` | литеральный `:` (гасит распознавание префикса) |
| `\\` | литеральный `\` |
| `\x` (прочее) | литеральный `x` |

Префикс распознаётся **только из белого списка** (`url:`, `params:`, `req:`, `resp:`); любой
другой текст с `:` — литерал (`http://host` не ломается и ошибки не даёт).

**Совместимость**: простая подстрока без спецсимволов работает как раньше, но теперь ищет и в
`parameters` (раньше — только `url`/`request`/`response`).

## 48.2 Режимы поиска Aa / ab| / .*

Три кнопки-тумблера внутри поля «Поиск» (справа, как в VS Code), флаги API `q_case`, `q_word`,
`q_regex` (значения `1`/`true`):

- **Aa (`q_case`)** — с учётом регистра. По умолчанию поиск регистронезависимый
  (`positionCaseInsensitiveUTF8` / `strings.ToLower` — корректный UTF-8 case-fold, кириллица
  включительно).
- **ab| (`q_word`)** — целое слово: каждый терм оборачивается в `\b(?:…)\b` (RE2 word boundary;
  для не-ASCII границы «слова» — по семантике RE2). Работает и в plain-, и в regex-режиме.
- **.\* (`q_regex`)** — регулярное выражение: **весь ввод — одно RE2-выражение**, мини-язык §48.1
  отключён (`&`, `|`, `-`, префиксы не разбираются — `|` работает как альтернация RE2). Скоуп —
  все четыре колонки. Регистронезависимость даёт префикс `(?i)`, целое слово — обёртка
  `\b(?:…)\b`. Невалидное выражение → HTTP 400 с локализованной ошибкой.

Семантика Go и ClickHouse идентична: оба используют RE2 (`regexp` ↔ `match()`), поэтому snapshot
(SQL) и live-tail (in-memory зеркало) дают одинаковый результат.

## 48.3 API

`GET /api/nodes/:id/logs` и SSE `GET /api/nodes/:id/logs/stream` — новые query-параметры:

- `q_case`, `q_word`, `q_regex` — флаги режимов (`1`/`true`);
- `method` — точное совпадение по колонке `method` (подпуть запроса, §39; НЕ HTTP-глагол).

Параметры `ip`/`host` **сохраняются в API** (совместимость для токен-клиентов), но из UI
удаляются (§48.4). Невалидный `q` (regex/синтаксис) → `400 {"error": i18n
"error.bad_search_query"}`.

Новые фасет-эндпоинты (scope `logs:read`, деградация как у `/logs` — `logs_configured:false` при
ненастроенной таблице, `logs_available:false` при недоступном CH):

- `GET /api/nodes/:id/logs/methods` → `{"items": ["v1/GetParcelsInfo", …], "logs_configured":
  true, "logs_available": true}` — `SELECT DISTINCT method … AND method != '' ORDER BY method
  LIMIT 200`, скоуп узла (`node_id = ? OR node_id = ''`).
- `GET /api/nodes/:id/logs/date-range` → `{"min_ms": …, "max_ms": …, "logs_configured": true,
  "logs_available": true}` — min/max `date_request` (UnixMilli). Пустая таблица → `0/0` (guard от
  epoch-1970 у `min()` по пустому набору).

## 48.4 UI

Панель «Расширенные фильтры» перестраивается в два ряда:

- **Ряд 1**: «Поиск» (широкое поле; внутри справа три кнопки-тумблера Aa / ab| / .*; рядом с
  лейблом иконка-подсказка → popover с описанием: по каким полям ищет, синтаксис `&` `|` `-`
  префиксов и экранирования, примечание про regex-режим) + «Method» (combobox).
- **Ряд 2**: даты «С» / «По» + кнопки Сбросить/Применить.
- Поля **IP и Host удаляются** из UI (API-параметры остаются, §48.3).

Ленивые фасеты (страница может быть открыта долго — данные всегда свежие):

- **Method** — combobox (Popover + cmdk): список значений грузится **только при открытии**
  дропдауна и **заново при каждом открытии** (`useQuery` c `enabled: open`, `staleTime: 0`,
  `gcTime: 0`); первый пункт — «Любой» (сброс). Клиентская фильтрация по ≤200 значениям.
- **Даты** — при **каждом фокусе** поля даты запрашивается `/logs/date-range` и выставляются
  атрибуты `min`/`max` (`datetime-local`, локальная зона). Ошибка запроса глотается (атрибуты
  просто не ставятся).

Ошибка 400 (невалидный запрос/regex) показывается под полем поиска; 4xx не ретраится
react-query.

## 48.5 Производительность поиска на больших таблицах

Драйверы стоимости: свободный поиск читает String-колонки `request`/`response` целиком в
отобранных гранулах — это основная цена. Ключ таблицы `ORDER BY (date_create, date_request,
method)` + `PARTITION BY toYYYYMM(date_create)` даёт прунинг по датам; `method`-фильтр — по 3-й
компоненте ключа.

Внедрено в §48:

- **field-scoped термы не читают лишние колонки**: `url:foo` генерирует условие только по `url` —
  тела не сканируются (главная экономия при точечном поиске);
- keyset-пагинация `(date_request, ID)` + `LIMIT` сохранены — верхняя граница работы на страницу;
- фасет date-range подталкивает пользователя сужать окно дат (прунинг гранул);
- `q` без дат по-прежнему допустим, но стоимость линейна объёму периода.

Задокументировано (не внедрено):

- skip-индексы `ngrambf_v1`/`tokenbf_v1` через CH-шаблоны §19 — оговорка: `position*`/`match()`
  такими индексами **не ускоряются**; выигрыш дал бы перевод plain-термов на
  `hasToken`/`LIKE`-план — future work;
- `match()` (regex/word) дороже `position*` — режимы включаются осознанно;
- `multiSearchAny*` (батч игл по колонке) — сознательно не внедрён: помогает только для OR
  незанегированных plain-термов по одной колонке, усложняет биндинг; пересмотреть по результатам
  профилирования.

## 48.6 Ограничение live-tail

SSE live-tail фильтрует записи in-memory (зеркало `matchLogFilter`) по данным `ListSince`, где
тела `request`/`response` намеренно пустые (`listCols`, экономия I/O — §42). Поэтому **в live
термы по телам не матчатся** (безпрефиксный терм ищет фактически по `url`+`parameters`;
`req:`/`resp:`-термы не совпадают никогда; отрицание по телу пропускает всё). Это pre-existing
поведение (§48 его честно документирует: раньше `q` в live фактически искал только по `url`).
Snapshot-запрос (`/logs`) ищет по полным телам всегда.

## 48.7 Future work (предложения по развитию поиска)

1. **Сохранённые фильтры** per-user (JSONB в настройках пользователя + дропдаун пресетов).
2. **Подсветка совпадений** в развёрнутых телах детали лога (передать применённые термы в
   `LogBodies`).
3. **Структурные операторы** в мини-языке: `status:>=500`, `ms:>1000`, `attempts:>2`, `done:no`.
4. **Экспорт результата фильтра** (NDJSON/CSV, потоково по keyset-курсору).
5. **ngrambf_v1-индекс в дефолтном CH-шаблоне** + перевод plain-термов на `hasToken`/`LIKE`-план
   для использования skip-индексов (см. §48.5).
6. **История поисков** (localStorage, дропдаун последних запросов).

## 48.x Scope / неочевидности

- Ни миграций Postgres, ни изменений схемы CH: колонка `parameters` существует со старта
  (`RequiredLogColumns`), `method` — с §39.
- Парсер/матчер мини-языка — один пакет `internal/domain/logsearch`, используется и генератором
  SQL (CH-адаптер), и in-memory зеркалом live-tail (usecase) — расхождение семантики исключено по
  построению.
- Разбор `q` происходит в usecase (`Search`/`Subscribe`) **до** резолва узла — 400 о синтаксисе
  приоритетнее деградации «логи не настроены».
- В адаптере CH поле `LogQuery.Q` больше не используется — только распарсенный `QExpr`.
- Требуется пересборка встроенного SPA-бандла (`internal/web/static/`).
