# 83. Шаблон ответа приёма (ack) для async-узлов

Раздел даёт узлу возможность декларативно описать, **чем шина отвечает клиенту на успешный приём
запроса в очередь**, вместо жёсткого `{"result":true,"id":"<uuid>"}`.

Развивает [§3.1](03-receiver.md) (async-приём), [§3.6](03-receiver.md) (paused-узел),
[§16](16-out-of-scope.md) (callback), [§36](36-dlq-reprocessor.md) (DLQ),
[§78.1](78-node-url-and-log-counters.md) (короткая форма адреса),
[§82.3](82-sync-ceiling-and-async-ingress.md) (гейт async-входа). Карта реализации —
[../IMPLEMENTATION.md](../IMPLEMENTATION.md).

> **Почему это не решалось раньше.** §82.4 вынес поведение клиента «не двигает указатель после
> успешного ответа» за рамки шины: измерено, что приёмник отвечает за 0,3 с, ответ доходит дословно,
> а клиент всё равно шлёт тот же пакет каждые 10 секунд. Вывод был верным для sync-режима и
> **неполным**: в async шина отвечает СВОИМ телом, и там вопрос «что именно клиент считает
> подтверждением» — уже её ответственность. §83 пересматривает эту границу.

---

## 83.1 Диагноз: клиент с курсором не понимает ответ шины

Боевой узел `acs_sigur` (команда `webhook`): СКУД выгружает журнал проходов пакетами и двигает
внутренний указатель только получив **эхо-подтверждение** с максимальным `logId` пакета:

```
запрос : {"logs":[{"logId":79154,"time":1786034092,"empId":"000004627",…}]}
ответ  : {"confirmedLogId": 79154}
```

Стандартный async-ответ шины такого подтверждения не несёт, поэтому перевод узла в async
разрывает [§82.1](82-sync-ceiling-and-async-ingress.md) (обрывы долгого sync-вызова), но не
разрывает дубли: клиент не сдвигает курсор и шлёт тот же пакет бесконечно.

Тот же класс клиентов шире одного узла: callback-провайдеры (VK Callback API ждёт строку-код
подтверждения), любые интеграции с курсором. Поэтому решение — не «ответ для Sigur», а настройка
узла.

---

## 83.2 Спека и язык подстановок

Хранится в `nodes.async_ack_spec` (JSONB, `NULL` = «отвечать как раньше»):

```json
{
  "version": 1,
  "status": 0,
  "content_type": "application/json",
  "body": "{\"confirmedLogId\": \"${ body.logs[*].logId | max }\"}",
  "on_error": "default"
}
```

- `status` — `0` означает прежний код: 200, либо **202 у узла на паузе** (§3.6). Заданный обязан
  быть 2xx: код уходит в `nexus_requests_total{status}` и в алерты, а 4xx/5xx из успешной ветки
  означал бы «приняли, но отчитались об ошибке».
- `content_type` — белый список `application/json` | `text/plain`. Не свободная строка: значение
  идёт в заголовок ответа, где свободная строка означала бы инъекцию заголовка.
- `body` — **текст** шаблона (строка внутри JSONB): сохраняется порядок ключей, возможен не-JSON
  формат.

### Грамматика

```
template    = { text | "$${" | placeholder }
placeholder = "${" ws expr ws "}"
expr        = source "." path [ ws "|" ws fn ]
source      = "body" | "query" | "path" | "nexus"
path        = segment { "." segment | index }
index       = "[" ( int | "*" | jsonstring ) "]"
fn          = "max" | "min" | "first" | "last" | "count" | "default" "(" literal ")"
```

Путь возвращает **набор** значений: функция схлопывает его в одно; без функции набор ≠ 1 — отказ
(`ambiguous` / `path_not_found`). `count` на пустом наборе даёт 0 и не падает никогда, `default(x)`
закрывает и отсутствующий путь, и `null`. Экранирование самой последовательности — `$${`.

### Источники

| Источник | Что даёт |
|---|---|
| `body.*` | тело запроса; **только** JSON и **только** до 1 МиБ |
| `query.<имя>` | параметр строки запроса; `[*]` — все значения, `[n]` — по индексу |
| `path.suffix`, `path.segment[n]` | хвост пути после пути узла (§39) |
| `nexus.id`, `.node`, `.team`, `.received_at`, `.queued` | служебные значения приёма |

**Заголовки запроса источником не являются — намеренно и навсегда**: там `Authorization`.
Кроме того, шаблон получает тело и query **после** вырезания кред (§41), а query-поле входящей
авторизации вычищается отдельно: `CheckIncomingAuth` его не удаляет. То есть эхо не может вернуть
вызывающей стороне её же секрет.

### Правило типизации

Для `application/json`: плейсхолдер, **вплотную окружённый кавычками**, подставляется JSON-литералом
вместе с ними — `"${ body.logs[*].logId | max }"` даёт `79154`, а не `"79154"`. Плейсхолдер внутри
строки интерполируется с экранированием. Для `text/plain` правило выключено, кавычки буквальны.

Числа проходят через `json.Number`: значение обязано вернуться тем же литералом. Это не педантизм —
курсоры журналов доходят до величин, которые `float64` уже не различает (см. §83.7, попутный фикс).

### Лимиты (константы кода, не настройки узла)

Шаблон ≤ 8 КиБ · подстановок ≤ 32 · глубина пути ≤ 16 · набор ≤ 1000 значений · тело парсится до
1 МиБ · ответ ≤ 64 КиБ. Возможность поднять их на узле означала бы возможность его замедлить.

### Валидация

Спека проверяется при сохранении узла: версия, статус, формат, компиляция шаблона и **«скелетная»
проверка** — после подстановки заглушек результат обязан быть валидным JSON. Последнее ловит
`{"a": ${x}}` (подстановка вне кавычек) на форме, а не на боевом трафике.

## 83.3 Где применяется и где нет

| Ответ | Шаблон |
|---|---|
| async-приём, 200 | **да** |
| paused-узел, 202 (§3.6) | **да** — иначе постановка узла на паузу тихо возвращает дубли |
| callback §16 | **да** — те же провайдеры с эхо-подтверждением |
| ошибки приёма: 404/405/413/401/508/5xx | **никогда** — клиент сочтёт запрос принятым и сотрёт свой журнал |
| обычный sync-режим | нет — там отвечает получатель |

Рендер выполняется **до публикации в Kafka**. Это требование, а не деталь: при `on_error=error`
отказ обязан означать «не принято». Рендер после публикации вернул бы 400 на уже принятое
сообщение, клиент повторил бы пакет — и шина сама порождала бы дубли, ради устранения которых
раздел и написан.

К ответу добавляются два заголовка: `X-Content-Type-Options: nosniff` (тело собирает оператор) и
`X-Nexus-Id` — в кастомном теле идентификатора шины может не быть вовсе, а саппорту нужно связать
ответ с записью журнала.

## 83.4 Деградация и наблюдаемость

`on_error` — что делать, когда подстановка не удалась:

- **`default`** — ответить прежним `{"result":true,"id":…}`. Запрос при этом **принят**: отказывать
  из-за шаблона поздно и нечестно;
- **`error`** — отдать 400 и **не принимать** запрос в очередь.

Причины отказа — замкнутое множество: `body_not_json`, `body_too_large`, `path_not_found`,
`type_mismatch`, `ambiguous`, `too_many_values`, `output_too_big`, `output_not_json`.

Наблюдаемость обязательна, потому что при `default` клиент видит обычный 200 и деградация иначе
невидима:

- `warn` в Receiver'е (`op=receiver.async_ack`) с узлом, причиной и проблемной подстановкой;
- метрика `nexus_async_ack_render_failed_total{node,reason}`.

**Провал шаблона не деградирует узел.** `nexus_node_last_request_error` (§52) и
`nexus_request_incomplete_total` описывают доставку ПРИЁМНИКУ и живут на стороне Sender'а; ack —
ответ самой шины. Иначе узел с кривым шаблоном светился бы красным в интерфейсе и в алертах, хотя
доставка идёт нормально.

Стоимость рендера (замер, AMD 5700G): боевой пакет Sigur — 4,3 мкс; шаблон без обращения к телу —
364 нс; попадание в кеш скомпилированных шаблонов — 70 нс против 937 нс компиляции. Основная
стоимость линейна по размеру тела (~80–90 МБ/с) — отсюда потолок `body.*` в 1 МиБ.

## 83.5 Смена типа узла

Матрица переходов разобрана до реализации (см. IMPLEMENTATION.md, 4.69). Правила:

1. **Переопределение существует только у `requestAsync`, и форма это выражает буквально.** Ответ
   «принято в очередь» есть там, где есть очередь: у sync-узла клиент получает ответ приёмника, у
   pull-узла (`RabbitMQAsync`) входящего HTTP нет вовсе. Поэтому группа «Ответ при постановке в
   очередь» **показывается только у `requestAsync`**, а сохранение узла как `request` или
   `RabbitMQAsync` **выключает переопределение** — в `PUT` уходит `async_ack_spec: null`, изменение
   попадает в аудит наравне с прочими. Правило одно на показ и на сохранение
   (`ackSpecApplies`): пока условие было записано дважды, форма прятала карточку у pull-узлов, но
   спеку бы отправила.

   Прежняя редакция обещала обратное — «спека переживает `request ↔ requestAsync`, оператор
   временно переводит узел в sync и не должен заполнять шаблон заново». От этого отказались:
   настройка, которая видна и включена, но ни на что не влияет, читается как поломка, а на
   sync-узле она именно такова. **Цена названа явно:** временный перевод в sync и обратно теперь
   требует заполнить шаблон заново, а у переведённого узла перестаёт работать пересчёт ответа шины
   в журнале (§84.9) — пересчитывать больше нечем, хотя записи async-прогонов остаются.

   **Домен при этом не менялся:** `Node.Validate` по-прежнему обнуляет спеку только у pull-узла
   (входящего HTTP нет физически) и не запрещает спеку у sync-узла. Это не забытая половина
   правила, а граница: запрет в домене сделал бы невалидными уже сохранённые строки и потребовал
   бы миграции, а поведение §3.6 (узел на паузе отвечает шаблоном) осталось бы без определения.
   Через API спеку sync-узлу выставить по-прежнему можно, и там она работает как раньше.
2. **Узел, переведённый обратно в sync, накопленную очередь не доставляет.** До §83 доставлял:
   `root_method` не проверялся ни consumer'ом, ни репроцессором DLQ. Сообщение уходит в DLQ с
   `reason="node_not_async root_method=<текущий>"` и при возврате узла в async в пределах
   `dlq_ttl_seconds` доставляется репроцессором само.
3. **Сообщения §3.6 при этом доставляются.** У sync-узла в очереди законно лежат сообщения,
   попавшие туда на паузе. Различает их поле конверта `ingress_method` — режим узла **в момент
   приёма**. Конверты без него (приняты до §83) доставляются как раньше: выкат не должен обнулить
   очередь.
4. **Изменения вступают в силу сразу.** Правка узла делает write-through в Redis и публикует
   инвалидацию §57; окно — TTL L1-кеша (2 с), а не `redis.node_ttl_sec`.
5. **Клиент, ходивший на длинный `/api/v1/requestAsync/…`, после перевода узла в sync получит 404**
   (гейт §82.3). Короткая форма §78.1 того же адреса продолжит работать по sync-ветке. Это
   ожидаемое поведение, а не регресс.

## 83.6 Справка в интерфейсе

Карточка «Ответ при постановке в очередь» на форме узла (скрыта у pull-узлов) содержит иконку `?`,
открывающую подробную справку. ТЗ фиксирует её состав — иначе текст справки со временем разъедется
с поведением:

1. что это и зачем; 2. когда ответ применяется (и что на ошибки приёма — никогда); 3. разбор каждого
поля формы; 4. синтаксис подстановки и экранирование; 5. таблица источников с оговоркой про
заголовки; 6. пути внутри тела; 7. функции с поведением на пустом наборе; 8. правило кавычек с
примерами до-после; 9. готовые примеры с кнопкой «Использовать», подставляющей рабочий шаблон в
поле; 10. таблица ограничений; 11. расшифровка каждой причины отказа с рецептом починки;
12. предупреждение «ответ подтверждает приём, а не доставку».

Плюс предпросмотр: `POST /api/nodes/ack-preview` (manager+) прогоняет шаблон на образце запроса и
возвращает точный ответ. Работает по присланной спеке, а не по id узла, — то есть в форме ещё не
сохранённого узла. Кнопка «Взять последний запрос из логов» подставляет реальное тело узла
(в логе оно замаскировано, о чём предупреждает подсказка).

---

## 83.7 Контракт риска

Ответ по шаблону подтверждает **приём в очередь**, а не доставку получателю. Клиент, очистивший по
нему свой журнал, при провале доставки данные не вернёт — они останутся только в шине (DLQ, логи).

Поэтому узел с включённым шаблоном обязан иметь живой репроцессор DLQ (§36) и наблюдение за
«Неудачными доставками». Это не техническая блокировка, а зафиксированное условие эксплуатации;
предупреждение продублировано в интерфейсе.

## 83.8 Что осталось за рамками

- **XML и `application/x-www-form-urlencoded`** в ответе: v1 — только JSON и text/plain.
- **Произвольные заголовки ответа**: только `Content-Type` (+ служебные `X-Nexus-Id`, `nosniff`).
- **Заголовки запроса как источник** — намеренно и навсегда.
- **Условия и несколько правил** («если `body.type == confirmation`, ответить одно, иначе другое»).
  Спека версионирована, и форма `rules: [...]` добавляется без миграции — но VK-подобные интеграции
  v1 не покрывает.
- **Тело `multipart/*` (§68) и тела > 1 МиБ** как источник подстановок.
- **Арифметика, форматирование дат, `sum`/`join`** в шаблоне.
- **Dry-run (§55) кастомный ack не показывает** — предпросмотр живёт отдельной кнопкой.
- **Порядок ключей вложенных объектов** при подстановке `${ body.obj }` не сохраняется (map);
  невалидный UTF-8 в строках нормализуется до U+FFFD.
- **Версии спеки > 1**: `version` фиксирован единицей, иное — ошибка валидации.
