# 105. Клиент запроса в логах: фильтр по IP

Раздел заменяет фильтр «Хост клиента» (§67.3) на фильтр «Клиент». Фильтр выбирает по IP,
PTR-имя служит подписью, у каждого значения показано число записей за период. Заодно резолвер
перестаёт терять имя у записей после истечения кеша.

Развивает [§67](67-client-host-rdns.md) (колонка `client_host`, резолвер, фасет),
[§48](48-log-search-extended.md) (расширенные фильтры логов), [§72](72-logs-server-side-filter.md)
(серверные фильтры, единый набор параметров), [§78.6](78-node-url-and-log-counters.md) (единица счёта —
запись), [§79.4](79-failed-unit-node-tab-metrics.md) (панель фильтров на вкладке «Метрики»),
[§102.6](102-method-breakdown.md) (переход «метрики → журнал» с фильтрами).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций и новых
конфиг-ключей раздел не требует.**

---

## 105.1 Повод: разбор боевого узла

Жалоба: «в фильтре как будто только один хост». Разбор боя 20–21.09.2026 (только чтение, API
логов):

- `vika/yandex-delivery`: все 294 записи пришли с `192.168.86.246` = `SRV-P-1C-NODE3`. Для этого
  узла фильтр честный. Определение имён в целом работает: на соседних узлах видны
  `srv-p-1c-node1…4`, `SRV-P-1C-ITUPR`, `SRV-P-1C-GATE`, `PC78000`.
- **IP без PTR-записи в фильтр не попадают вовсе.** Фасет — `DISTINCT` непустых `client_host`.
  `messengers/mts/traffic`: 61 запрос из 100 пришёл с `192.168.2.5`, а в фильтре только NODE3.
  `vika/site/webhook_pp`: все запросы с `192.168.2.5`, фильтр пуст. То же у `192.168.3.28` и
  `192.168.6.167`.
- **Записи теряют имя.** У `yandex-delivery` 10 записей из 294 без `client_host`. L1-кеш
  резолвера живёт до 5 минут, и после истечения `Lookup` возвращает `""`, а не прежнее имя. Такую
  запись не находит ни один фильтр.
- **Фасет не знает периода.** Это `DISTINCT` по всей таблице узла, без числа записей: хост,
  приходивший полгода назад, стоит в списке наравне с сегодняшним.

## 105.2 Scope

**В scope:**

- фасет `GET /api/nodes/{id}/logs/clients`: пары «IP — имя» с числом записей за период;
- фильтр «Клиент» по IP (серверный фильтр `ip` уже есть, §72), имя — подпись;
- параметр `ip` в адресе вкладки и в переходе «метрики → журнал»;
- резолвер: stale-while-revalidate вместо «истёк — пусто».

**Вне scope:**

- клиент в строке или карточке записи лога — решение пользователя (§67.3 «колонки нет»
  остаётся в силе);
- приведение `client_host` к нижнему регистру: при группировке по IP регистр на фильтр не
  влияет;
- подпись «Nexus (повтор)» для `nexus-web-1.nexus_nexus_net` — так выглядит клиент повторов,
  которые шлёт Web;
- учёт в фасете остальных фильтров (метод, статус, полнотекст): фасет считает по узлу и периоду.

## 105.3 Фасет «Клиенты»

`GET /api/nodes/{id}/logs/clients?from=&to=` (scope `logs:read`, как `/logs/client-hosts`):

```json
{
  "items": [
    { "ip": "192.168.2.5",    "host": "",                               "count": 61 },
    { "ip": "192.168.86.246", "host": "SRV-P-1C-NODE3.vz78.vozovoz.ru", "count": 39 }
  ],
  "truncated": false,
  "logs_configured": true,
  "logs_available": true
}
```

```sql
SELECT IP,
       if(IP = '', client_host, '') AS k,
       argMaxIf(client_host, date_request, client_host != '') AS host,
       uniqExact(ID) AS n
FROM <table>
WHERE <nodeFilter> AND <date_create-окно> AND <date_request-окно>
GROUP BY IP, k
ORDER BY n DESC, IP, k
LIMIT 201            -- 201-я строка → truncated=true, отдаются 200
```

- **Период.** `from`/`to` — как у `/logs` (RFC3339 или UnixMilli). Без `from` окно — 24 часа
  до `to` (без `to` — до текущего момента), а не вся таблица: фасет читается на каждом раскрытии
  дропдауна. Окно и отсечение партиций по `date_create` (§72.4) — те же, что у списка:
  адаптер строит условия общим `searchConds` по запросу, урезанному до узла и периода.
- **Цена.** Потолок запроса — 10 секунд, как у `/logs/count`; превышение → `logs_available=false`.
- **Единица — запись** (`uniqExact(ID)`), та же, что у списка и `/logs/count` (§78.6).
- **Записи без имени засчитываются к своему IP.** Имя — самое свежее непустое за окно
  (`argMaxIf`). Поэтому 10 «потерявших имя» записей `yandex-delivery` учитываются вместе с
  остальными 284, и решение работает на уже записанной истории.
- **Пустой `IP`** бывает во внешних таблицах §64 (пишет посторонний сервис). Такие строки
  группируются по `client_host`. Значение без IP и без имени — одна строка с `ip=""`, `host=""`.
- **Pull-узлы** (§27.10) пишут в `IP` адрес брокера (`rabbitmq://…`). Он показывается как есть:
  API логов и так отдаёт его в поле `ip`.
- **Внешняя таблица без колонки `client_host`** (§67.5, до ручного `ALTER`) — не ошибка: тот же
  запрос без `client_host`, только IP, плюс Debug-строка.
- **Деградации** — как у `/logs/methods`: узел без таблицы → `200 + logs_configured=false`,
  ClickHouse недоступен → `200 + logs_available=false`.
- Старый `/logs/client-hosts` остаётся для API-токенов. UI его больше не вызывает.

## 105.4 Фильтр «Клиент»

- Значение с IP ставит параметр `ip=<ip>`: серверный `IP = ?` уже общий для списка, `/logs/count`,
  SSE-стрима, KPI и рейтинга методов (§72, §102). Значение без IP (только внешние таблицы) ставит
  `client_host=<host>`, как раньше. Одновременно действует только один из двух.
- Состояние фильтра логов получает `clientIp` рядом с `clientHost`; в адресе вкладки — параметр
  `ip`. Старые ссылки с `client_host` продолжают работать.
- Переход «метрики → журнал» (§102.6) переносит `ip` вместе с остальными фильтрами.
- Период фасета — период экрана: поля «Дата с/по» на вкладке «Логи», выбор периода на вкладке
  «Метрики». Без периода — последние 24 часа, и подпись под списком это говорит.

```
Логи узла → Фильтры → «Клиент» (вместо «Хост клиента»)
[SRV-P-1C-NODE3.vz78.vozovoz.ru  ⌄]      ← имя, если известно по фасету, иначе IP
┌────────────────────────────────────────────────┐
│ 🔍 Имя или IP…                                  │
│ Любой                                           │
│ SRV-P-1C-NODE3.vz78.vozovoz.ru              39  │
│   192.168.86.246                                │
│ имя не определено                           61  │
│   192.168.2.5                                   │
│ ─────────────────────────────────────────────── │
│ записей за выбранный период                     │  ← или «за последние 24 часа»
└────────────────────────────────────────────────┘
```

- Поиск в дропдауне — по имени и по IP.
- Список усечён (`truncated`) — строка «показаны первые 200».
- Фасет грузится при открытии дропдауна и перечитывается при каждом открытии, как раньше.
- Подпись окна: «за выбранный период», если у экрана есть начало периода; «за 24 часа до
  «Дата по»», если задан только конец; иначе «за последние 24 часа». ClickHouse недоступен или
  запрос упал — подпись «список клиентов сейчас недоступен» вместо чисел.
- Значение без IP и без имени (бывает только во внешних таблицах) видно с числом, но не
  выбирается: фильтра «IP пуст и имя пусто» у API нет, а пустой `client_host` означает «Любой».
  Причина написана в самой строке — у неактивного пункта всплывающая подсказка не появится.
- У вкладки «Метрики» границы пресета («последние N») берутся в момент запроса фасета, а ключ
  кеша — по периоду: иначе ключ менялся бы каждый рендер.

## 105.5 Резолвер: stale-while-revalidate

Было: запись L1 живёт до 5 минут (§67.2), после истечения `Lookup` возвращает `""` и планирует
фоновый резолв. Первая запись после каждого истечения — без имени, у активного клиента это
примерно одна запись из тридцати.

Стало: протухшая запись L1 **отдаёт прежнее имя** и планирует фоновое обновление (тот же
`pending`-guard: одно обновление на IP). Обновление перезаписывает значение, в том числе на
пустое, если PTR-запись исчезла. `""` остаётся только у первой записи **нового** IP на реплике.
Контракт «ноль I/O на пути доставки» сохраняется.

Кап L1 (10 000 записей) при переполнении по-прежнему выбрасывает протухшие записи первыми —
у них имя отдаётся «по старой памяти», и потерять их дешевле, чем свежие.

**Граница.** Резолвер не отличает «PTR-записи нет» от временного сбоя DNS (таймаут). Сбой во
время обновления перезаписывает имя пустым на `negative_ttl_sec` (по умолчанию 10 минут), как
было и до §105. Записи этого окна фасет §105.3 всё равно относит к их IP.

## 105.6 Неочевидности

- **Группировка по IP, а не по имени.** Имя — производное от IP и может отсутствовать (нет PTR,
  холодный кеш, запись до §67). Фильтр по имени терял бы и то и другое; фильтр по IP находит все
  записи клиента, а имя остаётся подписью.
- **`argMaxIf`, а не `any`.** Если у IP за окно встречались разные имена (PTR поменяли), подписью
  становится последнее.
- **Новых полей в ответе списка логов нет.** Поле `ip` запись уже отдаёт, а фильтр переиспользует
  существующий параметр `ip`. Клиент в самой записи не показывается (§105.2).

## 105.7 Проверка результата

- запросы с IP, у которого есть PTR, и с IP без PTR — в фильтре оба значения с числом записей;
- выбор IP без имени фильтрует журнал, «Показано N из M» и метрики под тем же фильтром;
- смена периода меняет список и числа фасета;
- у записей IP с именем, часть которых записана без `client_host`, одна строка фасета с полным
  числом;
- после выката на бою `192.168.2.5` появляется в фильтре `messengers/mts/traffic` и
  `vika/site/webhook_pp`.
