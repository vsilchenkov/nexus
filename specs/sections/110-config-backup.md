# 110. Резервная копия конфигурации: экспорт и импорт

Раздел добавляет администратору вкладку **«Настройки → Резервная копия»**. На ней два действия:

- **выгрузить** всю конфигурацию Nexus в один зашифрованный паролем файл;
- **восстановить** её из такого файла — только на **чистом** экземпляре, где нет узлов и нет
  команд, кроме сидированной Default. Вместе с конфигурацией создаются базы команд и таблицы логов
  узлов в ClickHouse, которых там ещё нет.

Развивает [§5](05-storage.md) (хранилища, шифрование кредов §5.5), [§18](18-multi-tenancy.md)
(команды и их базы ClickHouse), [§19](19-ch-templates.md) (шаблоны таблиц логов),
[§64](64-manual-external-table.md) (внешняя таблица), [§70](70-multi-instance-clickhouse.md) (владение
базами ClickHouse), [§90](90-external-services-security.md) (секреты настроек),
[§26](26-roles-access-control.md) (роли). Закрывает часть пункта «Bulk-операции и импорт/экспорт»
из [§16](16-out-of-scope.md).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций нет,** выкатывается
только Web.

## 110.1 Повод

Штатный архив — `pg_dump` (`scripts/deploy/pg_dump.sh`) — лежит на том же сервере, что и Nexus.
При потере сервера он пропадает вместе с ним. Но и уцелевший дамп не поднимает шину полностью:

- креды узлов и секреты настроек в нём зашифрованы `ENCRYPTION_KEY`. Без ключа дамп
  восстанавливается, но все эти значения приходится вводить заново;
- в дамп попадает `instance_identity` исходной ноды, а новая нода может иметь другой идентификатор
  (§70), и тогда имена баз ClickHouse не сходятся.

Нужен файл, который администратор скачивает к себе и хранит вне сервера, который не зависит от
ключа шифрования сервера и который поднимает на новом Nexus все узлы и команды одной операцией.

## 110.2 Что входит в файл

| Входит | Таблицы | Как переносится |
|---|---|---|
| Команды | `teams` | слаг, название, внешняя ссылка; имя базы ClickHouse пересчитывается на цели (110.6) |
| Узлы | `nodes` | все поля, креды открытым текстом внутри зашифрованного файла; UUID сохраняется |
| Связи узлов с хостами | `node_allowed_hosts` | по шаблону хоста |
| Группы узлов | `node_groups` | §99 |
| Каталоги | `host_allowlist`, `headers_catalog`, `request_fields_catalog` | §23, §24, §41; `usage_count` не переносится — его ведёт триггер |
| Шаблоны ClickHouse | `ch_templates` | §19, вместе с признаком «по умолчанию» |
| Маскирование логов | `log_mask_patterns` | §95, набор целиком |
| Глобальные настройки | `app_settings` | кроме секции `clickhouse` и `general.version_override` (110.7) |
| Пользователи | `users`, `user_teams` | с bcrypt-хешем пароля: вход со старым паролем |
| API-токены | `api_tokens` | не отозванные; хранится только SHA-256 — токены продолжают работать |
| Реестр инстансов | `peer_instances` | §73, без кеша проб (`last_*`) |
| Личные настройки | `user_team_favorites`, `user_preferences` | §49, §71 |

**Не входит** и не будет входить:

- логи обмена (ClickHouse) — объём и назначение другие; при уцелевшем ClickHouse они остаются
  на месте и снова становятся видны (110.6);
- журнал аудита, журнал отказов §94, история поиска §62 — это история, а не конфигурация;
- сессии (Redis), одноразовые токены §88;
- `instance_identity` — идентичность ноды задаётся её конфигом, а не файлом (§70.1);
- `config.yml`, `.env`, `ENCRYPTION_KEY`, настройки NetBIOS §106 (живут в YAML).

## 110.3 Файл и шифрование

Файл — JSON-конверт:

```json
{
  "format": "nexus-config-backup",
  "protected": "<base64 от JSON заголовка и параметров KDF>",
  "nonce": "…",
  "ciphertext": "…"
}
```

Внутри `protected`:

```json
{
  "format": "nexus-config-backup",
  "version": 1,
  "header": {
    "exported_at": "2026-09-29T17:30:00Z",
    "nexus_version": "v1.40.0",
    "schema_version": 43,
    "source_instance_id": "kz",
    "counts": {"teams": 6, "nodes": 142, "users": 18, "...": 0}
  },
  "kdf": {"name": "argon2id", "time": 3, "memory_kib": 65536, "threads": 4, "salt": "…"}
}
```

- **Шифрование.** Ключ выводится из пароля администратора через Argon2id и шифрует
  gzip-сжатый JSON снимка алгоритмом AES-256-GCM.
- **Защита заголовка.** Байты `protected` служат дополнительными данными (AAD): правка заголовка —
  счётчиков, версии, параметров KDF — ломает расшифровку. `protected` хранится base64-строкой,
  а не вложенным объектом: у JSON нет канонической формы, и если бы редактор переформатировал
  вложенный объект (пробелы, порядок), копия стала бы невосстановимой. Заголовок читается без
  пароля, чтобы предпросмотр мог показать «что за файл»; кто и откуда выгружал, лежит только
  внутри зашифрованной части.
- **Пароль** не короче 12 символов. Без него файл не восстановить — это явно пишется в интерфейсе.
- **Защита от вредного файла.** На разборе ограничены:
  - параметры KDF (память не больше 256 МиБ, число проходов и потоков — в разумных границах),
    иначе файл мог бы заставить сервер выделить гигабайты;
  - размер после распаковки (64 МиБ);
  - размер самого запроса импорта (64 МиБ).
- **Имя файла:** `nexus-backup-<id ноды или хост>-<ГГГГММДД-ччммсс>.json`.

**Версии.** `version` — версия формата конверта и снимка; неизвестная версия отклоняется.
`schema_version` — номер последней миграции источника:

- файл **новее** схемы цели → отказ «обновите Nexus до версии не ниже источника»;
- файл **старше** — принимается: поля, которых в старом файле нет, получают значения по умолчанию.

## 110.4 Экспорт

`POST /api/backup/export` с телом `{"passphrase": "…"}` → вложение с файлом. POST, а не GET,
потому что пароль не должен попасть в адресную строку, журнал доступа nginx и историю браузера.

- **Согласованный срез.** Всё читается в одной транзакции `REPEATABLE READ READ ONLY`: узел,
  созданный посреди выгрузки, либо попадёт в файл целиком со связями, либо не попадёт вовсе.
- **Секреты.** Креды узлов и секреты настроек расшифровываются тем же кодом репозиториев, что
  при обычном чтении (§4.1 IMPLEMENTATION): вне `adapter/out/postgres` шифр не появляется.
- **Аудит.** Действие `config.export` со счётчиками и без секретов.

## 110.5 Импорт: только на чистом экземпляре

**Чистый экземпляр** — в PostgreSQL нет ни одного узла и нет команд, кроме сидированной Default.
Это тот же признак, которым гейт первого запуска §70.5 отличает «ноду только что подняли». Он
вынесен в общую SQL-константу, чтобы стартовый гейт, вкладка и импорт не разошлись.

Защита боевого экземпляра многослойная:

1. **Интерфейс.** Карточка восстановления на нечистом экземпляре показывает, сколько там узлов
   и команд, и не даёт выбрать файл.
2. **Предпросмотр** проверяет признак и отвечает 409, не расшифровывая файл глубже заголовка.
3. **Применение** в той же транзакции, что пишет данные, берёт блокировку
   `LOCK TABLE teams, nodes IN SHARE ROW EXCLUSIVE MODE` и пересчитывает признак. Узел или
   команда, созданные параллельно, дождутся конца импорта или сделают его невозможным — но
   смешаться с ним не могут. Параллельный второй импорт получает «импорт уже идёт».
4. **Подтверждение.** В диалоге нужно ввести адрес сервера, на который идёт восстановление
   (`window.location.host`). Сервер сверяет его со своим `Host`.
5. **Сверка с предпросмотром.** Применение принимает `preview_digest` — хеш файла и опций из
   предпросмотра — и отклоняет запрос, если применяется не тот файл или не те опции, которые
   администратор видел.

Все эндпоинты — роль admin и только браузерная сессия (`RequireSessionOnly`), как у §108: API-токен
не может ни выгрузить секреты, ни перезаписать конфигурацию.

## 110.6 Импорт: сопоставление, ClickHouse, статусы

**Сопоставление с тем, что уже есть на чистом экземпляре.** Даже чистый экземпляр не пуст:
миграции создают команду Default, пользователя `admin`, шаблон «Standard logs» и два шаблона
маскирования. Правило: строка, совпавшая по естественному ключу, остаётся с id цели, а все
ссылки на неё из файла перенаправляются; новая строка получает id из файла.

| Сущность | Ключ | Совпала |
|---|---|---|
| Команда Default | слаг | строка не заменяется (её id Web кеширует на старте); обновляются название и внешняя ссылка |
| Пользователь | логин | учётная запись цели не меняется (пароль, роль); членство в командах из файла добавляется |
| Шаблон ClickHouse | точное имя | описание и спецификация — из файла; признак «по умолчанию» — как в файле |
| Группа, хост | имя / шаблон без учёта регистра | остаётся строка цели |
| Заголовок, поле запроса | имя без учёта регистра | остаётся строка цели (узлы ссылаются на них по имени) |
| API-токен | хеш | пропускается |
| Инстанс §73 | адрес | пропускается; адрес, равный собственному публичному адресу, не переносится |
| Маскирование логов | — | набор заменяется целиком: у шаблонов нет ключа, и дописывание дублировало бы сиды |

**UUID узлов сохраняются всегда.** Строки логов в ClickHouse привязаны к узлу по `node_id` (§61),
и при уцелевшем ClickHouse узел с новым id не увидел бы собственной истории.

**Базы и таблицы ClickHouse.**

- Имя базы команды вычисляется по идентификатору **целевой** ноды: `nexus_<slug>` или
  `nexus_<id>_<slug>` (§70.2). Слаг проверяется на бюджет длины для этого идентификатора.
  Исключение — **тот же** идентификатор у источника и цели (восстановление той же ноды): имена
  баз берутся из файла как есть. Команда, созданная до §70 на ноде, получившей идентификатор
  позже, живёт в `nexus_<slug>`, а не в вычисленной `nexus_<id>_<slug>`, и без исключения её
  уцелевшие логи стали бы невидимы.
- Таблица узла переносится по карте «база команды в источнике → база команды на цели». Внешняя
  таблица §64 не меняется никогда. Таблица в базе, которой нет в карте, остаётся как есть
  и даёт предупреждение.
- Базы и таблицы создаются **до** записи в PostgreSQL: все операции идемпотентны
  (`CREATE … IF NOT EXISTS`), поэтому сбой ClickHouse не оставляет в PostgreSQL полузагруженной
  конфигурации, а повтор импорта безопасен.
- Правила создания таблицы — те же, что при сохранении узла (§19.5): шаблон узла, иначе шаблон
  по умолчанию при включённом логировании, внешнюю таблицу не создавать. Отличие одно: ошибка
  создания таблицы прерывает импорт. При обычном сохранении узел без таблицы — мягкая деградация,
  а при восстановлении это сотня узлов, чьи логи Sender бесконечно ретраил бы в `nexus.logs.retry`.
- Уже существующие таблицы доводятся до текущей схемы теми же `ADD COLUMN IF NOT EXISTS`, что
  выполняются на старте сервисов, — иначе чтение логов падало бы до рестарта.
- Состояние базы по маркеру владения §70:

| База | Решение |
|---|---|
| нет | создать |
| наша (маркер с идентификатором этой ноды) | использовать; старые логи снова видны |
| без маркера, пустая | занять |
| без маркера, с таблицами | только по явной галочке «Занять существующие базы без маркера» |
| чужая, конфликт маркеров, состояние неизвестно | импорт невозможен |

Пустой идентификатор ноды совпадает с пустым идентификатором любого соседа (§70.1). Если у
источника и цели идентификатор пустой и ClickHouse общий, «наша» база может оказаться базой
живого источника — предпросмотр об этом предупреждает.

**Узлы, не проходящие нынешнюю проверку.** Правила валидации со временем ужесточаются, и узел
источника, сохранённый давно, может не пройти `Validate` на новой версии. Блокировать из-за этого
всё восстановление нельзя. Такой узел импортируется **выключенным**, с предупреждением и причиной.
Так же выключается узел, чей `target_url` ведёт на входной адрес самой цели (защита от петли
§32.2). Превышение лимита узлов на команду блокирует импорт.

**Статусы после импорта** (переключатель в предпросмотре):

- **как в файле, узлы RabbitMQAsync — на паузе** (по умолчанию). Pull-узел начинает забирать
  очередь через 15 с после появления. Если источник ещё жив (перенос, а не авария), два сервера
  разбирали бы одну очередь наперегонки;
- **всё как в файле** — полный автоматический подъём;
- **все узлы на паузе** — администратор включает узлы сам.

## 110.7 Глобальные настройки

Секции `general`, `security`, `sentry`, `notifications`, `logging`, `mail` переносятся с теми же
проверками, что при сохранении из интерфейса (`AppSettingsUsecase.Prepare`). Поле, не прошедшее
проверку на цели, пропускается с предупреждением, а не роняет импорт. Пример — рабочий лимит тела
выше потолка из конфига цели (§97).

**Никогда не переносятся:**

- **`clickhouse`.** Импорт создаёт базы и маркеры на текущем соединении ClickHouse. Адрес из файла
  после перезагрузки настроек увёл бы все сервисы на сервер, где этих баз нет, а на следующем
  старте туда же ушёл бы гейт владения. Предпросмотр показывает хост, порт, базу и пользователя
  из файла (без пароля) — подключение к ClickHouse администратор настраивает на новом сервере сам;
- **`general.version_override`** — на боевой ноде запрещён (§34.3).

После записи публикуются события перезагрузки импортированных секций и секции `masking`: Sender
перечитывает шаблоны маскирования без рестарта (§95). `SectionAll` не используется — он
переподключил бы ClickHouse во всех сервисах.

## 110.8 Предпросмотр и применение

**`POST /api/backup/import/preview`** — тело `{file, passphrase, options}`. Расшифровывает файл,
строит план и выполняет **всю** запись в PostgreSQL в транзакции с откатом (dry-run): нарушения
ограничений и внешних ключей видны до того, как администратор нажмёт «Восстановить». ClickHouse
только опрашивается. Ответ:

- заголовок файла;
- счётчики «создать / уже есть / заменить» по каждой сущности;
- решения по базам и таблицам ClickHouse;
- пропущенные пользователи и токены;
- предупреждения и блокирующие ошибки;
- `preview_digest`.

**`POST /api/backup/import/apply`** — тело `{file, passphrase, options, preview_digest, confirm_host}`.

1. Сверяет `confirm_host` с адресом, по которому пришёл запрос: имя хоста без порта и регистра
   (прокси перед Web может убрать порт из `Host`). Это подтверждение «вы на том сервере», а не
   аутентификация. Не совпало — 400 `backup.confirm_host_mismatch`.
2. Пересобирает план и сверяет `preview_digest` (409 `backup.digest_mismatch`). Если за время
   между предпросмотром и применением появились блокирующие проблемы — 409 `backup.import_blocked`.
3. Создаёт базы (с маркером владения §70) и таблицы ClickHouse; уже существующие таблицы
   доводит до текущей схемы — добавляет недостающие колонки, без backfill. Любой сбой здесь
   прерывает импорт до записи в PostgreSQL (500 `backup.clickhouse_failed`); все операции этого
   шага идемпотентны, повтор безопасен.
4. Одной транзакцией записывает PostgreSQL. Аудит `config.import` — в той же транзакции.
5. Публикует перезагрузку настроек.

Выполняется на контексте, отвязанном от соединения клиента, со своим таймаутом: закрытая вкладка
не должна оборвать импорт между ClickHouse и PostgreSQL.

**`GET /api/backup/status`** — признак чистоты, число узлов и команд, доступность ClickHouse,
идентификатор ноды и счётчики для карточки выгрузки.

Кеши узлов публиковать не нужно: Receiver не кеширует промахи, Sender читает узел из PostgreSQL
на каждое сообщение, puller RabbitMQ перечитывает список раз в 15 с.

## 110.9 Интерфейс

Вкладка «Резервная копия» в «Настройках», после «Инстансы», только для роли admin.

- **Карточка «Выгрузить конфигурацию»:**
  - что попадёт в файл (счётчики) и что не сохраняется;
  - пароль дважды;
  - предупреждение «без пароля файл не восстановить, храните файл вне сервера»;
  - кнопка «Скачать файл».
- **Карточка «Восстановить из файла»:**
  - на нечистом экземпляре — объяснение со счётчиками, кнопка выбора файла выключена;
  - на чистом — шаги в той же карточке: файл и пароль → «Проверить файл» → предпросмотр
    (счётчики, ClickHouse, предупреждения, переключатель статусов, галочка «занять» — только
    если такие базы найдены) → «Восстановить…» → диалог с вводом адреса сервера → результат
    со ссылкой на узлы.

## 110.10 Процедура аварийного восстановления

Пошагово — в DEPLOYMENT.md. Главное:

1. Поднять Nexus на новом сервере обычной установкой. `ENCRYPTION_KEY` может быть новым: файл
   от него не зависит.
2. **Если ClickHouse уцелел** (на бою он внешний) и логи нужны — задать ТОТ ЖЕ `instance.id`, что
   был у погибшей ноды, **до первого старта**. Тогда базы команд совпадут по имени и маркеру и
   будут подхвачены вместе с логами. Смена идентификатора после первого старта требует процедуры
   §70 (DEPLOYMENT §5А.5).
3. Настроить подключение к ClickHouse в `config.yml` или `.env` (из файла оно не переносится).
4. Войти администратором и восстановить конфигурацию из файла.

## 110.11 Вне рамок

- **Экспорт по расписанию и по API-токену** (автоматический бэкап с другой машины). Выгрузка
  всех секретов по токену — отдельное решение о безопасности.
- **Выборочный экспорт и импорт узлов между живыми экземплярами** (GitOps, перенос одной
  команды) — остаток пункта §16: импорт намеренно ограничен чистым экземпляром.
- **Перенос логов ClickHouse** — бэкап ClickHouse описан в DEPLOYMENT §5.4.
