# 64. Ручная (внешняя) таблица логов ClickHouse

Раздел вводит режим, в котором Nexus **не управляет** таблицей логов узла, а только читает из неё:
логи, счётчики дашборда, графики. Это позволяет использовать Nexus как фронт логирования над
таблицей, которую наполняет посторонний сервис. Развивает §19 (шаблоны CH-таблиц), §37 (`node_id`
в логах), §56 (синхронизация схемы) и §61 (атрибуция записей на общей таблице).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 64.1 Проблема

Узел с «ручной» таблицей (пустой `clickhouse_template_id`, §19) до этого раздела обслуживался
Nexus'ом как обычный, и таблица не была защищена ни от одной из четырёх операций:

| Операция | Что делала | Чем грозила чужой таблице |
|---|---|---|
| `provisionTable` при сохранении узла | `CREATE TABLE IF NOT EXISTS` по **дефолтному** шаблону, если включено логирование | Создание таблицы, которой оператор не просил |
| Стартовые ALTER'ы Web и Sender | `ADD COLUMN IF NOT EXISTS` (`node_id`, `http_method`, `request_size`, `response_size`) + backfill-мутации `ALTER … UPDATE` | Изменение схемы и данных постороннего писателя при каждом рестарте сервисов |
| Housekeeping Sender'а | `ALTER TABLE … DROP PARTITION` по `clickhouse_retention_days` (дефолт **90**) | **Удаление чужих данных**: дропается партиция ЦЕЛИКОМ, а не строки узла |
| §56 «Синхронизировать схему» | Диффил таблицу против дефолтного шаблона (`resolveTemplate` даёт его при пустом `template_id`) | Предложение ALTER'ов, которых оператор не задавал |

Сценарий, ради которого раздел и делается: **в CH-таблицу пишет другой сервис, а Nexus нужен как
интерфейс чтения**. Записи постороннего писателя имеют `node_id = ''` и по правилу §61 засчитываются
узлу, пока на таблицу ссылается ровно один узел Nexus, — то есть логи и счётчики работают уже
сейчас. Не хватало именно гарантии невмешательства.

## 64.2 Модель данных

Колонка `nodes.external_table` (миграция 0027) и поле `domain.Node.ExternalTable`:

```sql
ALTER TABLE nodes ADD COLUMN external_table BOOLEAN NOT NULL DEFAULT false;
```

- **`external_table = true`** — таблицей владеет оператор или посторонний сервис. Nexus её не
  создаёт, не переименовывает, не альтерит, не дропает её партиции и не даёт запустить §56.
  Чтение (логи, KPI, графики, `DeleteFailed` очереди) работает как обычно.
- **Несовместимо с `clickhouse_template_id`** (`ErrNodeExternalTableTemplateConflict`, i18n-код
  `node.validation.external_table_conflict`): шаблон означает ровно обратное — «таблицей управляет
  Nexus». Валидация доменная, зеркалится на фронте.
- **Флаг переживает копирование узла** (`clone := *src`): копия ссылается на ту же таблицу, значит
  остаётся внешней.
- Переключение флага попадает в `diffNodes` → аудит `node.update`: оно меняет, кто отвечает за схему
  и retention таблицы.

**Разовая миграция legacy-узлов.** Та же миграция 0027 проставляет дефолтный шаблон узлам, у которых
`clickhouse_template_id IS NULL` и непустой `clickhouse_table`:

```sql
UPDATE nodes SET clickhouse_template_id = (SELECT id FROM ch_templates WHERE is_default LIMIT 1)
WHERE clickhouse_template_id IS NULL AND clickhouse_table <> ''
  AND EXISTS (SELECT 1 FROM ch_templates WHERE is_default);
```

Без этого смена семантики выключила бы им housekeeping молча, и таблицы росли бы бесконечно.
Откат (`down`) удаляет только колонку: какие узлы были `NULL` до миграции, восстановить нельзя, а сам
шаблон безвреден — он фиксирует ровно то поведение, что у них было.

## 64.3 Гейты невмешательства

Четыре точки, симметрично таблице из §64.1:

1. **`provisionTable`** ([node.go](../../internal/web/usecase/node.go)) — ранний no-op с `Debug`.
   Одним гейтом покрыты `Create`, `Update`, `Copy` и `Move`.
2. **Перенос узла в другую команду не ребейзит имя таблицы.** Хелпер `targetCHTable` вместо
   `rebaseCHTable` в `Move` и `MovePreview`: внешняя таблица не обязана лежать в БД команды, и
   ребейз `nexus_<команда>.<имя>` увёл бы узел на несуществующее имя, а сама таблица осталась бы без
   читателя. `RENAME TABLE` для неё тоже не выполняется.
3. **`AND NOT external_table`** в трёх SQL: `ListClickHouseTables` Sender'а и Web'а (источник списка
   для стартовых ALTER'ов) и `ListForHousekeeping` (retention). Фильтр на уровне **узла**, а не
   таблицы: если на одно имя ссылаются внешний и обычный узел, таблица остаётся под управлением
   Nexus — ею всё равно распоряжается второй узел.
4. **§56 schema-sync** — `plan()` отвергает внешний узел с `domain.ErrNodeExternalTable` → HTTP 409 +
   i18n `ch_sync.external_table_forbidden`. Не 400: запрос корректен, недопустимо состояние узла.

Retention-поле у такого узла в UI скрыто; хранимое значение `clickhouse_retention_days` остаётся
(дефолт 90), но никем не применяется — housekeeping до узла не доходит.

**Чтение: единственное место, где пустой `node_id` засчитывается узлу.** Пятая точка, добавленная
после боевого инцидента. Гейт владения §70.4 опирается на маркер `__nexus_owner`, которого у чужой
БД нет и быть не может — «таблица не наша» здесь не признак соседней ноды Nexus, а нормальное
состояние. Поскольку весь поток внешнего писателя идёт с `node_id = ''`, включённая гейтом строгая
атрибуция прятала **всё** содержимое таблицы: узел показывал пустой журнал и нулевые KPI при
миллионах записей в ClickHouse.

С версии 1.22.5 правило перевёрнуто: атрибуция строгая **везде**, а внешняя таблица — единственное
исключение, где действует `(node_id = ? OR node_id = '')`. Владение на выбор фильтра не влияет
вовсе (правило целиком — §61.1). Границы послабления:

- **на разрушающие операции оно не распространяется**: `DeleteFailed` («Очистить неудачные»)
  по-прежнему упирается в `AssertOwnsTable` и на чужой таблице отказывает (409). Смягчена только
  видимость записей, не право их менять;
- **общая таблица остаётся строгой**: если на то же имя ссылаются ≥2 узла, счётчик §61 срабатывает
  раньше признака внешности. Смешанная таблица (внешний узел + обычный) попадает под это же правило;
- **признак берётся из своей PostgreSQL** — то есть послабление включает оператор, пометивший узел
  внешним, а не эвристика по состоянию ClickHouse.

## 64.4 Проверка структуры таблицы

Схему внешней таблицы Nexus не правит, поэтому её пригодность оператор проверяет явно — **до**
сохранения узла.

`POST /api/ch-tables/verify` (manager+, session-only), тело `{"table": "db.table"}`. Проверяется
**имя**, а не id узла: кнопка должна работать в форме ещё не сохранённого узла.

```json
{ "ok": false, "table": "external_db.audit_log", "table_missing": false,
  "missing": ["node_id"], "mismatched": [{"name": "status", "want": "Int32", "got": "String"}] }
```

- Эталон — `domain.RequiredLogColumns` (24 колонки, §4.3). Сверка — чистая
  `domain.VerifyLogTableColumns`.
- **Лишние колонки допускаются**: писатель вправе держать свои поля, а INSERT и SELECT Nexus'а
  перечисляют колонки явно.
- Нормализация типов: убираются пробелы; `DateTime('<tz>')` считается равным `DateTime` (таймзона —
  атрибут отображения, представление то же); **`Bool` считается равным `UInt8`** — в ClickHouse это
  алиас с тем же физическим представлением, а поле `LogRecord.Done` объявлено в Go как `bool`, так
  что драйвер принимает обе формы и на запись, и на чтение (таблицы с `done Bool` встречаются на
  стендах). `Nullable(...)`, `LowCardinality(...)`, `DateTime64` — честное расхождение с показом
  `want`/`got`.
- Отсутствие таблицы и любые расхождения — **HTTP 200 с `ok=false`**, это результат проверки, а не
  ошибка вызова. 400 — некорректное имя (до ClickHouse не доходит), 503 — ClickHouse не настроен.

## 64.5 UI формы узла

**Дефолты при создании** (подставляются асинхронно, каждый — один раз и только пока поле в исходном
значении, чтобы медленный ответ не затёр ввод оператора):

- **шаблон по умолчанию** (`is_default`), а не «(нет / ручная таблица)» — типовой узел должен
  получать таблицу под управлением Nexus;
- **редактируемый префикс** `<ch_database команды>.` в поле «Таблица логов» — оператору остаётся
  дописать имя; префикс можно стереть, если внешняя таблица лежит в другой БД;
- **включённый лимит тела** со значением `web.node_default_max_body_size` (см. §64.6).

**Поведение полей:**

- выбор шаблона снимает «Внешняя таблица», возврат к «(нет / ручная таблица)» ставит её обратно —
  ручную таблицу обычно и заводят под постороннего писателя;
- чекбокс «Внешняя таблица» виден только при пустом шаблоне;
- «Retention (дней)» скрыт при `external_table` — иначе поле обещало бы несуществующее поведение;
- кнопка «Синхронизировать схему» (§56) скрыта при `external_table`;
- кнопка «Проверить» — у поля таблицы при пустом шаблоне и непустом имени; результат сбрасывается
  при правке имени или шаблона, чтобы не относиться к прежнему значению.

## 64.6 Конфигурация

`web.node_default_max_body_size` (дефолт **50000**, границы 1..10 000 000 — те же, что у
`domain.Node.MaxBodySize`) — значение «Макс. размер тела», подставляемое формой при **создании**
узла. Существующие узлы и создание через API не затрагивает.

Значение отдаётся фронту в уже существующем `GET /api/settings/public` (поле
`node_default_max_body_size`): эндпоинт авторизованный и кэшируется под team-независимым ключом.
Берётся из конфига, а не из `app_settings`, — это параметр развёртывания, а не переключатель в UI.

## 64.7 Вне scope

- Автоматическое приведение внешней таблицы к схеме Nexus (в том числе «Проверить и исправить»):
  структуру ведёт владелец таблицы; при обновлении Nexus, меняющем схему логов, довести таблицу —
  его задача (проверка покажет, чего не хватает).
- Разделение записей Nexus'а и постороннего писателя в счётчиках: они смешиваются в одних KPI.
  Строгая изоляция по `node_id` включается лишь на таблице, которую делят ≥2 узла Nexus (§61).
- Запись Nexus'а во внешнюю таблицу не запрещается: узел с логированием пишет в неё как обычно —
  предполагается, что структура совпадает (это и проверяет §64.4).
- Ретеншен внешней таблицы: TTL/дроп партиций настраивает её владелец средствами ClickHouse.
