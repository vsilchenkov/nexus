## 15. Критерии приёмки

- `docker compose up` поднимает всю систему (Receiver, Sender, Web, Postgres, ClickHouse, Kafka, Prometheus) одной командой.
- Создание узла через UI → отправка `POST /api/v1/request/{path}` доходит до внешнего адреса, ответ возвращается клиенту, лог появляется в нужной таблице ClickHouse.
- При создании узла с несуществующей таблицей UI открывает диалог §7.6, после подтверждения таблица появляется в ClickHouse и узел готов принимать трафик.
- Overview работает в обоих режимах (таблица/карточки), выбор сохраняется между сессиями, переключение не теряет фильтры.
- Detail-страница узла показывает данные из ClickHouse и Prometheus, обновляется в реальном времени.
- Падение ClickHouse не ломает доставку: сообщения продолжают идти, метрики продолжают отдаваться, после восстановления ClickHouse буфер сливается.
- Падение Kafka останавливает только async-путь, синхронные запросы продолжают работать.
- Все методы видны в Prometheus, графики строятся в UI.
- Авторизация работает, `viewer` не может редактировать узлы (кнопки редактирования скрыты или disabled), не видит раздел `Пользователи`.
- На странице Settings → ClickHouse кнопка «Проверить соединение» работает без сохранения, кнопка «Сохранить и переподключить» делает graceful-переключение с откатом при ошибке.
- На странице Settings → Users админ может создать, отключить, удалить пользователя и сменить ему пароль; нельзя удалить или понизить последнего активного админа; нельзя удалить самого себя.
- При первом входе пользователя с флагом `must_change_password` редирект на смену пароля, остальной UI недоступен до смены.
- Все сервисы используют `github.com/vsilchenkov/logging`: уровень и режим вывода (stderr/файл) настраиваются через env, ошибки логируются через `ErrorWithOp` с полем `op`. Логгер инициализируется один раз в `main` и передаётся в подсистемы через конструкторы (DI); `logging.GetLogger()` в продакшн-коде не вызывается.
- При `SENTRY_USE=true` ошибки уровня error попадают в Sentry с указанным `Environment` и `Release` из `BuildConfig`; кнопка «Отправить тестовое событие» в Settings → Sentry успешно создаёт event.
- При `SENTRY_ENABLE_TRACING=true` входящие HTTP-запросы Receiver и обработка сообщений Sender создают транзакции с корректными тегами `service`, `node`, `root_method`.
- В Sentry не попадают тела запросов/ответов, заголовки авторизации и пароли (`BeforeSend` фильтрует чувствительные поля).
- Каждый бинарь принимает флаг `--config /path/to/file.yml`; при его отсутствии используется `config/config.yml`; флаг `--debug` загружает `config_debug.yml`.
- Файлы `config/config.yml` и `config/config_debug.yml` присутствуют в репозитории (первый — через `.example.yml` шаблон), `config.yml` не коммитится.
- `make build`, `make build-windows`, `make run-receiver`, `make test`, `make swagger`, `make docker-up` отрабатывают без ручных правок. На Windows-машине с установленным GNU Make цели `build-windows` и `test` проходят.
- Swagger UI доступен по `/swagger/index.html` для Receiver и Web в dev/staging; `make swagger` генерирует актуальную документацию, CI-проверка `swagger drift check` фейлит сборку при расхождении.
- `make test` запускает unit-тесты и завершается успехом; `make test-coverage` показывает покрытие ≥ 70% для пакетов `/internal/receiver`, `/internal/sender`, `/internal/storage`.
- `make test-integration` запускает Postgres, Redis, ClickHouse и Kafka через testcontainers и проходит end-to-end сценарии создания узла, отправки запроса и проверки лога в ClickHouse.
- `make loadtest TARGET_RPS=500 DURATION=10m NODES=50` создаёт 50 рандомных узлов с разными комбинациями `url_mode` и `auth_type`, гонит 500 rps смешанного трафика 10 минут и автоматически проверяет критерий в финальном отчёте: достигнутый rps ≥ 95% от target, p95 ≤ 200 мс, error rate < 0.1%, для async-сообщений число записей в ClickHouse = числу отправленных. При нарушении любого условия — exit code 1.
- Все настройки нагрузочного теста (RPS, длительность, число узлов, доли разных типов узлов, размер payload, задержка mock-сервера) настраиваются флагами без правки кода.
- В корне репозитория присутствуют `README.md` и `TESTING.md` с описанным в §13.4 содержимым; README содержит явную ссылку на TESTING.md.
- На вкладке «Логи» узла переключатель «Live» включает SSE-стрим: новые записи появляются в таблице в реальном времени (не более 2 сек от записи в ClickHouse до отображения в UI), фильтры в live-режиме отключены, лимит буфера UI — 500 записей.
- Действие «Replay» из меню записи в логах открывает диалог с редактируемым телом запроса и опциями `Куда отправить` / `Авторизация` / `Sync вместо async`. После отправки в ClickHouse появляется новая запись с маркером `__replay_of=<original_id>` в поле `parameters`, в audit log — запись `node.replay`. Rate limit 10 replay/мин на пользователя срабатывает корректно.
- Кнопка «Тестовый запрос (dry-run)» в форме редактирования узла открывает диалог; запрос проходит через шину согласно текущему (несохранённому) конфигу формы, не записывается в production-таблицу ClickHouse, результат показывается пошагово (auth, URL, headers, response, что было бы залогировано).
- В UI есть страница «Audit log» (видна только админам) с таблицей записей, фильтрами по периоду / пользователю / типу действия / target ID, модалкой с детальным diff'ом для `node.update`, экспортом в CSV. Записи в audit log нельзя изменить или удалить через UI/API.
- Записи audit log хранятся `web.audit_retention_days` дней (по умолчанию 365), housekeeping-job удаляет старые записи раз в сутки.
- Все миграции из `/migrations` применяются автоматически при первом старте каждого сервиса (через advisory lock без race condition между инстансами); упавшая миграция приводит к exit code 1 с записью ошибки через `ErrorWithOp` и в Sentry. Команда `make migrate-status` показывает текущую версию схемы. Команда `make migrate-down N=1` корректно откатывает последнюю миграцию.
- Login через UI создаёт серверную сессию в Redis под ключом `session:{token}` с TTL 24 часа; logout мгновенно удаляет ключ. При смене роли или отключении пользователя все его сессии удаляются через `SCAN MATCH session:*`. При недоступности Redis Web API отвечает 503 на эндпоинты, требующие авторизации.
- Поля `auth_credentials` и `incoming_auth_credentials` в БД хранятся в формате `v1:<nonce>:<ciphertext>:<auth_tag>` (AES-256-GCM). При старте сервиса невалидный `ENCRYPTION_KEY` (отсутствует, неверная длина или невозможность расшифровать существующие значения) приводит к exit code 1. В UI значения никогда не возвращаются в API-ответах в открытом виде — только флаг `*_set: true/false`.
- Утилита `make rotate-encryption-key OLD_KEY=... NEW_KEY=...` корректно перешифровывает все чувствительные поля; повторный запуск идемпотентен.
- Диалог удаления узла содержит чекбокс «Также удалить таблицу логов в ClickHouse» (по умолчанию выключен), требует ввода `path` узла для подтверждения. В audit log пишется запись `node.delete` с указанием, удалена ли таблица.
- В Settings → ClickHouse → блок «Таблицы в базе» с фильтром `Все` / `Привязанные` / `Осиротевшие`. Кнопка «Очистить осиротевшие» открывает batch-диалог удаления нескольких таблиц.
- При полной остановке PostgreSQL Receiver продолжает обслуживать запросы на основе данных в Redis; после восстановления БД новые узлы создаются без рестарта.
- При полной остановке Redis Receiver автоматически переключается на чтение конфига напрямую из PostgreSQL, сервисы не падают; после восстановления Redis кеш заполняется и нагрузка на PostgreSQL возвращается к норме.
- При одновременной недоступности PostgreSQL и Redis обслуживаются только узлы, лежащие в локальном LRU-кеше; остальные получают 503 «config unavailable» без падения процесса.
- При полной остановке ClickHouse сервисы не падают, логи буферизуются в памяти и при переполнении уходят в файл-фоллбек; после восстановления ClickHouse файл-фоллбек загружается обратно.
- При полной остановке Kafka синхронные запросы продолжают работать; async возвращает 503; Sender автоматически переподключается с экспоненциальным backoff без перезапуска.
- Узел в режиме `static` доставляет сообщения на `target_url` из конфига; узел в режиме `from_request` доставляет на URL из query-параметра `url_base` входящего запроса.
- В режиме `from_request` параметр `url_base` исключается из итоговой query string перед отправкой во внешний узел.
- В режиме `from_request` запрос без `url_base` возвращает 400 Bad Request с сообщением `{"error": "url_base query parameter is required"}` — никакого fallback на `target_url` нет.
- Невалидный URL в `url_base` возвращает 400; URL, не входящий в `url_allowed_hosts` (при непустом allowlist), возвращает 403. В обоих случаях сообщение в Kafka не кладётся (для async) и в Sender не уходит (для sync).
- В ClickHouse-логе поле `url` содержит фактический адрес доставки, а не `target_url` из конфига.
- При `auth_type = token_from_request` Receiver проставляет внешнему узлу заголовок `Authorization: Bearer <token>`, где `<token>` извлекается из источника `auth_dynamic_source` (query / header / body) по имени `auth_dynamic_field`.
- При `auth_type = basic_from_request` Receiver проверяет наличие во входящем запросе заголовка `Authorization: Basic <base64>` и пробрасывает его во внешний запрос без изменений — никакого декодирования или перекодирования.
- Для `token_from_request` с источником `header` префикс `auth_dynamic_strip_prefix` (по умолчанию `Bearer `) корректно отрезается перед использованием.
- Любой динамический режим без кредов возвращает 401 Unauthorized с описанием. Для `basic_from_request` отсутствие заголовка `Authorization`, неверный префикс (не `Basic `) или невалидная Base64-строка после префикса также дают 401.
- Креды исключаются из проксируемого запроса: для `token_from_request` — значение удаляется из query / header / body согласно настройкам; для `basic_from_request` — исходный заголовок шины не дублируется (даже если он в `forward_headers`).
- Значения кредов не попадают в ClickHouse-логи (заголовок `Authorization` и поле по имени `auth_dynamic_field` маскируются как `***`), в stdout-логи и в Sentry breadcrumbs.
- Комбинация `url_mode = from_request` + любой динамический `auth_type` работает: все служебные параметры принимаются в одном запросе и все исключаются из проксируемого запроса.
- При недоступности внешнего узла sync возвращает клиенту реальный код ответа, async уходит в DLQ после исчерпания retry с заголовками-метаданными.
- Эндпоинты `/health` и `/ready` отвечают согласно §9.6, контейнеры в `docker-compose.yml` имеют корректные healthcheck.
- Graceful shutdown по `SIGTERM` завершает все in-flight запросы, сливает ClickHouse-буфер и коммитит Kafka-offset'ы до выхода.
- Все секреты (пароли PostgreSQL, Redis, ClickHouse, Sentry DSN, ENCRYPTION_KEY) хранятся только в `.env` (или внешнем секрет-менеджере) — в `config.yml`, `config_debug.yml` и других файлах git'а их нет. Поиск `grep -r "PASSWORD\s*=" config/` не возвращает реальных значений.
- Swagger UI описывает только HTTP-эндпоинты Receiver и Web; контракт Sender (gRPC) описан в `.proto` и в Swagger не дублируется.
- При старте сервиса топики `nexus.async` и `nexus.async.dlq` автоматически создаются (если не существуют) с параметрами из конфига: 4 партиции, retention 30 дней (`retention.ms=2592000000`), `cleanup.policy=delete`, `compression.type=lz4`.
- Команда `kafka-topics --describe --topic nexus.async` показывает retention.ms=2592000000 и все остальные параметры согласно §5.3.
- При reset consumer offset на начало (`kafka-consumer-groups --reset-offsets --to-earliest`) Sender переобрабатывает все сообщения за последние 30 дней.
- Producer работает с `acks=all` и `enable.idempotence=true` — повторная отправка одного и того же сообщения при ретрае не создаёт дублей в топике.
- Consumer коммитит offset только после успешной доставки во внешний узел (`enable.auto.commit=false`); при рестарте Sender'а в середине обработки сообщения оно обрабатывается повторно, потерь нет.
- В Settings → Language выбор «Русский» переключает UI без перезагрузки, сохраняется в `users.lang` и подтягивается при следующем входе; язык по умолчанию для нового пользователя — English (либо определяется по `Accept-Language`, если содержит `ru`).
- Серверные ответы API учитывают заголовок `Accept-Language` и возвращают тексты ошибок на соответствующем языке; логи в ClickHouse, stderr и метрики Prometheus остаются на английском.
- Все эндпоинты Receiver доступны только с префиксом `/api/v1/` (`/api/v1/request/...`, `/api/v1/requestAsync/...`); запрос без префикса возвращает 404 с подсказкой использовать `/api/v1/`. Боевой трафик идёт через единый вход Web (`/api/v1/*` проксируется в Receiver). gRPC-сервис зарегистрирован с пакетом `nexus.sender.v1`.
- Валидация полей узла (см. таблицу лимитов в §3.3) отвергает превышение длины / неверный формат с 400 Bad Request и понятным сообщением; БД-constraint'ы дополнительно защищают от обхода API.
- При достижении `nodes_soft_limit` в UI появляется баннер на странице создания узла; при достижении `nodes_hard_limit` API возвращает 400 с сообщением о превышении лимита.
- В ClickHouse-таблице узла поля `attempts` и `attempts_details` заполняются корректно: `attempts >= 1` всегда, `attempts_details` пустая строка при успехе с первой попытки, JSON-массив со всеми деталями попыток при наличии ретраев или ошибке.
- Колонки `team_id` присутствуют в таблицах `nodes` и `users`, имеют default-значение `'default'`, NOT NULL. UI и API игнорируют это поле в v1 — все запросы работают со значением `'default'`.
- Узел в состоянии `paused` принимает входящие запросы (sync возвращает HTTP 202 с `queued: true`, async — обычное 200), сообщения копятся в Kafka; Sender-consumer пропускает их и переоткладывает с задержкой. При смене статуса на `enabled` Sender обрабатывает накопленные сообщения с обычной скоростью. Метрика `nexus_paused_messages_total{node}` корректно отражает накопление.
- UI Settings → API Tokens работает для всех ролей: пользователь видит только свои токены, может создать/отозвать/удалить. При создании секретное значение показывается ровно один раз. В БД хранится только `SHA-256(token)`.
- Запросы к Web API с заголовком `Authorization: Bearer db_...` проходят через middleware API-токенов: scope проверяется на каждом эндпоинте, недостаточный scope → 403; превышение `api_token_rate_limit_per_min` (100/мин по умолчанию) → 429. Невалидный / отозванный / истёкший токен → 401.
