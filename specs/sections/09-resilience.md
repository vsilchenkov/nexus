## 9. Высоконагруженность и отказоустойчивость

### 9.1 Целевые показатели

- **Целевой RPS** — 500 rps на одну пару Receiver+Sender при p95 ≤ 200 мс (без учёта времени ответа внешнего узла). Достижимо на скромном железе (2–4 vCPU, 4–8 GB RAM на ноду) при условии keep-alive на стороне клиентов и прогретого Redis-кеша. Большая нагрузка покрывается горизонтальным масштабированием — оба сервиса stateless по отношению к запросу.
- **Горизонтальное масштабирование** — оба сервиса stateless по отношению к запросу, можно запускать N инстансов за load balancer. Состояние — в PostgreSQL (конфиг, источник правды), Redis (горячий кеш), Kafka (очередь), ClickHouse (логи).
- **Целевой даунтайм** при штатном обновлении — 0 (rolling deploy, graceful shutdown).

### 9.2 Производительность Receiver

- **Redis-кеш конфига узлов** с TTL (`redis.node_ttl_sec`, по умолчанию 5 минут) — read path: Redis → PostgreSQL → fallback in-memory. См. §5.4 и §9.4. При попадании в Redis-кеш (target 99%+ на горячем кеше) запрос обслуживается за <1 мс — это держит p95 в норме под 500 rps.
- Локальный second-level cache в памяти процесса (LRU, 1–5 секунд TTL, ~1000 узлов) для самых горячих узлов — снимает нагрузку с Redis при пиковом RPS и спасает в момент кратковременного Redis-flutter'а.
- Парсинг JSON стримово, без полной загрузки тела в память (лимит `max_body_bytes`).
- Пул соединений к PostgreSQL (`pgxpool`, 25 connections под 500 rps) и к Redis (`go-redis`, 50 connections); параметры в YAML.
- Подготовленные запросы (`prepared statements`) для горячих SQL.
- Keep-alive для входящих HTTP-соединений (`idle_timeout_sec: 120`) — без keep-alive каждый запрос превращается в TCP handshake, латентность ухудшается, ресурсы тратятся впустую.

### 9.3 Производительность Sender

- Пул воркеров (`sender.workers`, 50 по умолчанию) для исходящих HTTP-вызовов — горутины потребляют задания из канала, ограничивая параллелизм. Размер пула рассчитан как `target_rps × p95_latency`: 500 rps × 100 мс = 50 одновременных в полёте.
- HTTP-клиент с пулом соединений (`keep-alive`, `max_idle_conns_per_host: 20`) — критично для производительности при работе с одним и тем же внешним узлом. Без keep-alive каждый запрос требует TCP+TLS handshake (50–200 мс), что убивает throughput.
- Параллельных Kafka-consumer-инстансов столько же, сколько партиций (`kafka.consumer.instances: 4`, см. §5.3). Можно распределить между несколькими процессами Sender'а в production.
- gRPC-сервер с `max_concurrent_streams: 1000` — лимит на одно соединение от Receiver. Receiver держит пул из 8 gRPC-соединений, что даёт суммарный потолок 8 × 1000 = 8000 одновременных RPC-вызовов (с большим запасом).
- Прогрев соединений к частым внешним узлам при старте (опционально).

### 9.4 Отказоустойчивость зависимостей

Никакой сбой во внешней зависимости не должен ронять сервис. Read path конфига устроен трёхуровневым: **Redis → PostgreSQL → локальный LRU-кеш в памяти**. На каждом уровне есть свой fallback.

**PostgreSQL недоступен:**
- Receiver продолжает работать на данных из Redis. Запись новых узлов через UI временно невозможна — Web возвращает ошибку с понятным сообщением.
- Web показывает баннер «БД недоступна, работаем в read-only».
- Sender не зависит от PostgreSQL напрямую (конфиг приходит в gRPC-запросе от Receiver или из Kafka-сообщения вместе с payload).
- Метрика `nexus_postgres_unavailable_total` инкрементится для алертинга.

**Redis недоступен:**
- Receiver автоматически переключается на чтение конфига **напрямую из PostgreSQL** на каждый запрос. p95 latency временно растёт (на горячих SQL остаётся приемлемой за счёт prepared statements).
- Локальный LRU-кеш в памяти процесса смягчает пик нагрузки на PostgreSQL в этот момент.
- Web API при недоступности Redis отвечает 503 на все эндпоинты, требующие авторизации (сессии хранятся в Redis — без него нельзя проверить токен). Это сознательное решение: лучше показать пользователю «временные проблемы, попробуйте через минуту», чем пускать без проверки роли. Login форма доступна и отвечает 503 с понятным сообщением.
- Rate limit и circuit breaker временно отключаются (они опираются на Redis).
- Метрика `nexus_redis_unavailable_total` инкрементится для алертинга.
- При восстановлении Redis сервисы автоматически возвращаются к кешированию без рестарта.

**Одновременная недоступность PostgreSQL и Redis** (крайний случай):
- Receiver обслуживает запросы только по конфигам, лежащим в локальном LRU-кеше памяти процесса.
- Узлы, для которых ни в LRU, ни где-либо ещё нет данных, получают ответ HTTP 503 «config unavailable».
- Sender продолжает работать (для sync — через gRPC, для async — из Kafka).

**ClickHouse недоступен:**
- Логи буферизуются в памяти (лимит `clickhouse.buffer_max_size`).
- При переполнении буфера — сброс в файл-фоллбек (NDJSON, каталог `logging.dir`).
- После восстановления ClickHouse файл-фоллбек загружается обратно background-воркером, in-memory буфер сливается батчами.
- Основной поток обработки запросов **не блокируется**: запись лога идёт через неблокирующий канал; если канал полон, лог отбрасывается с инкрементом метрики `nexus_clickhouse_dropped_total`, но запрос обрабатывается.

**Kafka недоступна:**
- `requestAsync` возвращает клиенту HTTP 503 с понятным телом `{"result": false, "error": "queue unavailable"}` (синхронный путь продолжает работать без изменений).
- Sender-consumer переходит в режим переподключения с экспоненциальным backoff (1s → 2s → 4s → … → 60s cap), без падения процесса.
- При восстановлении Kafka обработка продолжается с последнего закоммиченного offset — потерь сообщений нет.

**Внешний узел недоступен или возвращает ошибку:**
- Sync: возвращается клиенту реальный код ответа (5xx, timeout — 504), запрос фиксируется в ClickHouse с `done=false` и причиной.
- Async: retry по политике узла (`retry_count`, `retry_backoff_ms`). После исчерпания — сообщение уходит в `nexus.async.dlq` с заголовками: оригинальный topic, причина, число попыток, timestamp последней попытки.

**Sender недоступен:**
- Receiver: sync-запросы получают 503, async продолжают идти в Kafka. Метрика `nexus_sender_unavailable_total` инкрементится для алертинга.

### 9.5 Защита от перегрузки

- **Rate limit на узел** (`receiver.rate_limit_per_node`) — по умолчанию 0 (без лимита), включается для узлов с известной квотой внешнего API. Счётчики хранятся в Redis (`ratelimit:{node}:{minute}`) для согласованности между инстансами Receiver.
- **Circuit breaker** на внешние узлы — состояние (closed/open/half-open + счётчики) хранится в Redis (`circuit:{node}`), что даёт согласованное поведение между несколькими Sender'ами. После N последовательных ошибок Sender временно (на M секунд) возвращает клиенту 503 / кладёт в DLQ без попытки доставки. Параметры в конфиге узла.
- **Backpressure** — если очередь воркеров Sender заполнена, gRPC-вызовы от Receiver получают `ResourceExhausted` (которое Receiver транслирует как HTTP 503).
- **Graceful shutdown** — оба сервиса по `SIGTERM`:
  1. Перестают принимать новые запросы (HTTP/gRPC возвращают 503 на новые соединения).
  2. Дорабатывают активные in-flight запросы (с таймаутом 30 сек по умолчанию).
  3. Сливают ClickHouse-буфер.
  4. Коммитят Kafka-offset'ы.
  5. Завершают процесс.

### 9.6 Health-проверки

Каждый сервис экспонирует:

- **`GET /health`** — liveness, возвращает 200, если процесс жив (без проверки зависимостей). Используется Docker `HEALTHCHECK` и Kubernetes `livenessProbe`.
- **`GET /ready`** — readiness, возвращает 200, если зависимости в рабочем состоянии:
  - Receiver: (PostgreSQL pingable ИЛИ Redis pingable) И есть данные в одном из них.
  - Sender: gRPC-сервер слушает, Kafka producer готов.
  - Web: PostgreSQL pingable И Redis pingable.

Деградированный режим (например, Redis недоступен, но PostgreSQL работает) даёт ready=200, но статус возвращает с детальным телом `{"ready": true, "degraded": true, "checks": {...}}` — балансировщик не выкидывает узел из ротации, но мониторинг видит деградацию.

`/ready` используется балансировщиком: если ready=false, узел выводится из ротации, но процесс не убивается.
