## 32. Защита от зацикливания запросов (loop protection)

Шина проксирует входящий HTTP-запрос на произвольный `target_url`. Если оператор по ошибке укажет в
качестве цели **адрес самого Receiver-а** (`http(s)://<nexus>/v1/request/<path>` или
`/v1/requestAsync/<path>`), запрос вернётся во входной endpoint и породит **лавину вложенных
вызовов**: `Receiver → Sender → внешний HTTP → снова Receiver → …`. Цепочку гасят только таймауты и
лимиты сокетов, что приводит к исчерпанию file descriptors и деградации сервиса. Для async-варианта
петля идёт через Kafka `nexus.async` и особенно опасна — топик копит сообщения.

Раздел вводит **две независимые меры**: основную (hop-счётчик, обрывает петлю любой топологии во время
выполнения) и вспомогательную (проверка `target_url` при сохранении узла — быстрая обратная связь
оператору). Параметры по умолчанию: лимит переходов **5**, ответ при обнаружении петли — **508 Loop
Detected**.

### 32.1. Hop-счётчик `X-Nexus-Hops` (основной механизм)

Служебный заголовок `X-Nexus-Hops`, который Receiver **инкрементит на каждом проходе запроса через
шину**. Логика — в usecase Receiver-а (общая для sync и async, чтобы покрыть оба пути из одного места):

1. На входе (`Route` / `RouteAsync`) читается `X-Nexus-Hops` из заголовков запроса. Отсутствует или
   нечисловой → трактуется как `0`.
2. Если защита включена (`receiver.max_hops > 0`) и `incoming >= max_hops` → запрос отклоняется
   ошибкой `domain.ErrLoopDetected` (HTTP **508**), запрос **наружу не уходит**.
3. Иначе в исходящую карту заголовков кладётся `X-Nexus-Hops: incoming+1`.

Заголовок добавляется **в обход allowlist** узла (`forward_headers`): шина пробрасывает только
заголовки из списка узла, но hop-счётчик — служебный и форвардится всегда. В sync-пути он попадает в
`SendRequest.headers` (gRPC к Sender), в async — в `Envelope.Headers` (Kafka). Sender знать о
заголовке не обязан — он просто переносит карту заголовков в исходящий HTTP-запрос
(`hreq.Header.Set`). Таким образом каждый следующий виток петли видит увеличенный счётчик, и цепочка
гарантированно обрывается не позже `max_hops` проходов — **независимо от топологии** (прямая петля,
косвенная `Nexus → внешний прокси → Nexus`, режим `url_mode=from_request`).

**Конфиг:** `receiver.max_hops` (yaml) / `NEXUS_RECEIVER_MAX_HOPS` (env), дефолт `5`. Значение `< 0`
полностью выключает проверку (служебный заголовок при этом не добавляется и не читается).

**Наблюдаемость:** счётчик Prometheus `nexus_receiver_loop_detected_total` с меткой `mode` (`sync` /
`async`) инкрементится при каждом отклонении по петле. Событие пишется в лог уровня `warn`.

### 32.2. Self-reference валидация `target_url` (вспомогательный механизм)

Чтобы оператор узнал об ошибке **сразу при сохранении узла**, а не по факту лавины запросов,
Web-сервис при `Create`/`Update` узла проверяет `target_url`:

- Действует только для `url_mode=static` (у `from_request` статического URL нет — его покрывает
  hop-счётчик).
- Если `host:port` цели совпадает с одним из сконфигурированных «своих» authority **и** path
  начинается с `/v1/request` или `/api/v1/request` (входной префикс шины) — узел отклоняется ошибкой
  `domain.ErrNodeTargetURLSelfReference` (HTTP **400**, код `node.validation.target_url_self`, поле
  `target_url`).
- **Loopback (`localhost` / `127.0.0.1` / `::1`) намеренно НЕ блокируется безусловно** — это сломало
  бы локальный тест-стенд, где `target_url` легитимно указывает на локальный mock-сервис. Блокируется
  только точное совпадение с собственным ingress.

**Конфиг:** `web.self_ingress_hosts` (список authority вида `host` или `host:port`). По умолчанию
заполняется хостом из существующего `web.receiver_url` (публичный адрес Receiver-а). Если список пуст
(оператор не сообщил собственный адрес) — проверка пропускается; основной защитой остаётся
hop-счётчик §32.1.

Это намеренно **best-effort** UX-проверка: она ловит самую частую ошибку конфигурации, но не является
гарантией (косвенные петли и `from_request` она не видит). Полная гарантия — на hop-счётчике.

### 32.3. Поведение и совместимость

- Легитимные многозвенные цепочки `Nexus → Nexus → …` (до `max_hops` звеньев) продолжают работать;
  превышение лимита трактуется как петля.
- Существующие узлы и клиенты не затрагиваются: при отсутствии заголовка счётчик стартует с `0`.
- Заголовок `X-Nexus-Hops` — внутренний для шины; внешние клиенты его слать не должны (если пришлёт —
  это лишь уменьшит доступный бюджет переходов, петлю это не создаёт).

### 32.4. Out of scope

- `http.Client.CheckRedirect` / лимит HTTP-редиректов на стороне Sender (отдельная защита от
  redirect-петель внешнего узла — не относится к зацикливанию через шину).
- Глобальный rate-limit как средство против петель (уже есть per-node rate-limit §3; здесь решается
  именно структурная петля, а не флуд).
