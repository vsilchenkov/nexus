## 3. Receiver Service

### 3.1 Эндпоинты

Два корневых маршрута — `/api/api/v1/request` и `/api/api/v1/requestAsync`. К корню добавляется путь конкретного узла, настроенный через UI:

```
POST /api/api/v1/request/{node_path}        — синхронный
POST /api/api/v1/requestAsync/{node_path}   — асинхронный
```

Примеры: `/api/api/v1/request/webhook/send`, `/api/api/v1/requestAsync/geo/notify`.

Глубина `node_path` произвольная (один или несколько сегментов через `/`).

**Единый вход.** Боевой трафик идёт через тот же хост, что и админка (Web Service): Web реверс-проксирует `/api/api/v1/request|requestAsync|callback` в Receiver. Поэтому все публичные эндпоинты живут под общим префиксом `/api`, что позволяет ingress/SPA-fallback корректно разделять API и статику (без префикса `/api` запрос проваливался бы в SPA-fallback и возвращал `index.html`). Напрямую в Receiver те же пути тоже доступны.

**Версионирование API.** Сегмент версии `v1` (под `/api/`) — обязательная часть пути. Это публичный контракт для внешних клиентов, которые будут стучаться годами; любое breaking change ломает их. Стратегия:

- При совместимом изменении (новые опциональные поля в теле, новые header'ы) — оставляем `/api/v1/`.
- При несовместимом изменении (удалили поле, поменяли семантику, изменили формат ответа) — добавляем `/api/v2/` параллельно. Обе версии работают одновременно минимум 6 месяцев, после чего `/api/v1/` помечается как deprecated через заголовок ответа `Deprecation: true` и `Sunset: <дата>`.
- Старые версии живут до тех пор, пока есть значимый трафик. Метрика `nexus_requests_total{version="v1"}` позволяет видеть, кто ещё на старой версии.
- Запрос без префикса версии (например, `POST /request/...`) возвращает 404 с подсказкой `{"error": "API version required, use /api/v1/..."}`.

Web Service API админки (см. §11) живёт под `/api/*` без сегмента версии, поскольку UI обновляется одновременно с backend.

### 3.2 Семантика методов

**`/api/v1/request/*` — синхронный:**
1. Receiver принимает JSON-тело и заголовки.
2. По `node_path` находит конфиг узла (Redis → PostgreSQL).
3. Проверяет авторизацию входящего запроса согласно настройкам узла.
4. Определяет целевой URL согласно `url_mode` узла (см. §3.4); валидирует против allowlist. При невалидном URL — 400/403, в Sender не уходит.
5. По gRPC передаёт сообщение в Sender Service вместе с фактическим target URL и остальным конфигом.
6. Sender Service выполняет HTTP-запрос к внешнему узлу и возвращает ответ через gRPC.
7. Receiver проксирует ответ внешнего узла клиенту как есть (status code, тело, релевантные заголовки).

**`/api/v1/requestAsync/*` — асинхронный:**
1. Receiver принимает JSON, проверяет авторизацию.
2. Определяет целевой URL согласно `url_mode` узла (см. §3.4); валидирует. При невалидном URL — 400/403, в Kafka не кладётся.
3. Кладёт сообщение в Kafka (topic = `nexus.async`, ключ = `node_path`, тело = JSON envelope с метаданными, включая разрешённый target URL).
4. Сразу возвращает клиенту HTTP 200 и тело `{"result": true, "id": "<uuid>"}`. При ошибке постановки (узел не найден/выключен, неверный метод, невалидный URL и т.п.) — соответствующий HTTP-код и тело `{"result": false, "message": "<причина>"}` (#7).

> **RabbitMQAsync и `result`-ответ (#8).** Формат `{"result":…}` применим только к HTTP-эндпоинту `requestAsync`. Узел `RabbitMQAsync` — pull-модель: Receiver сам забирает сообщения из очереди, синхронного HTTP-клиента, которому возвращать `{"result":…}`, нет. Поэтому #8 неприменим; успех/ошибка обработки вытянутого сообщения отражаются в логах ClickHouse, метриках и ack/requeue очереди (§27).

### 3.3 Конфигурация узла

Каждый узел в БД хранит:

- `path` — путь после корня (`webhook/send`)
- `root_method` — `request` либо `requestAsync`
- `incoming_method` — HTTP-метод, который узел принимает на вход (`GET`/`POST`/`PUT`/`DELETE`, по умолчанию `POST`). Запрос другим методом отклоняется с `405 Method Not Allowed`. Для pull-узлов (RabbitMQAsync) неприменим, для callback-маршрута (webhook) не проверяется.
- `outgoing_method` — HTTP-метод, которым Sender вызывает получателя (`GET`/`POST`/`PUT`/`DELETE`, по умолчанию `POST`). Всегда диктует метод исходящего запроса независимо от метода входящего.
- `url_mode` — режим определения целевого URL (см. §3.4): `static` (по умолчанию) или `from_request`
- `target_url` — статичный адрес перенаправления (используется при `url_mode = static`; при `from_request` игнорируется)
- `url_param_name` — имя query-параметра, в котором клиент передаёт URL (по умолчанию `url_base`, можно переопределить)
- `url_allowed_hosts` — список разрешённых хостов (или wildcard-паттернов) для `url_mode = from_request`; пустой = разрешено всё (опасно в production)
- `auth_type` — `none` / `basic` / `token` / `token_from_request` / `basic_from_request`
- `auth_credentials` — логин/пароль или токен. Шифруется AES-256-GCM в БД (см. §5.5). Используется при `auth_type` = `basic` или `token`; в режимах `*_from_request` игнорируется.
- `auth_dynamic_source` — где брать токен для `token_from_request`: `query` (по умолчанию), `header` или `body`. Для `basic_from_request` игнорируется — источник всегда заголовок `Authorization` (см. §3.5).
- `auth_dynamic_field` — имя query-параметра / заголовка / JSON-поля для `token_from_request`. Дефолты: `token` для query/body, `Authorization` для header. Для `basic_from_request` игнорируется.
- `auth_dynamic_strip_prefix` — для `token_from_request` с `auth_dynamic_source = header`: префикс, который надо отрезать (по умолчанию `Bearer `, пустая строка — брать как есть). Для `basic_from_request` игнорируется.
- `incoming_auth_type` — `none` / `basic` / `token` (авторизация на входе)
- `incoming_auth_credentials` — креды для проверки входящих. Шифруется так же, как `auth_credentials` (см. §5.5).
- `forward_headers` — список имён заголовков из источника, которые нужно пробросить
- `timeout_ms`, `retry_count`, `retry_backoff_ms`
- `clickhouse_table` — имя таблицы для логов этого узла
- `status` — состояние узла: `enabled` (по умолчанию, нормальная работа), `disabled` (узел не активен, запросы получают 404), `paused` (запросы принимаются и складываются в Kafka, но не отправляются — см. §3.6). Заменяет старый булев флаг `enabled`.

#### Лимиты на поля узла

Жёсткие ограничения, валидируемые на уровне БД (constraints) и API (валидация на входе). Превышение — 400 Bad Request с понятным сообщением:

| Поле | Ограничение | Обоснование |
|---|---|---|
| `path` | 1–255 символов, regex `^[a-zA-Z0-9][a-zA-Z0-9/_-]*$` | URL-safe, без открывающих/закрывающих слешей |
| `target_url` | 1–2048 символов, валидный URL со схемой `http`/`https` | Лимит браузеров и большинства HTTP-серверов |
| `auth_credentials` | до 1024 символов открытого значения | Достаточно для длинных JWT и большинства токенов |
| `incoming_auth_credentials` | до 1024 символов открытого значения | Аналогично |
| `url_param_name`, `auth_dynamic_field`, `auth_token_param_name` | 1–64 символа, regex `^[a-zA-Z][a-zA-Z0-9_-]*$` | Валидное имя HTTP-параметра / заголовка |
| `url_allowed_hosts` | до 50 элементов, каждый до 253 символов (лимит DNS) | Не больше — лучше использовать wildcard-паттерн |
| `forward_headers` | до 30 элементов, каждый — валидное имя HTTP-заголовка до 100 символов | Защита от bloat |
| `clickhouse_table` | формат `db.table`, каждая часть 1–64 символа, regex ClickHouse-имени | Соответствует ограничениям ClickHouse |
| `timeout_ms` | 100 – 300000 (5 минут) | Нижняя граница — на случай быстрых API; верхняя — чтобы не залипали воркеры |
| `retry_count` | 0–10 | Больше — это патологический случай, ставится `0` и реализуется на стороне клиента |
| `retry_backoff_ms` | 0–60000 | Backoff между попытками |

**Общий лимит узлов на инсталляцию.** Мягкий лимит — **10 000 узлов**, UI показывает баннер при ≥80% («рассмотрите архитектурный пересмотр»). Хард-лимит — **50 000 узлов**, попытка создать ещё один отвергается с сообщением `{"error": "node limit reached, contact administrator"}`. Оба значения настраиваются в `web.nodes_soft_limit` и `web.nodes_hard_limit` в конфиге (см. §8.3).

### 3.4 Режимы определения целевого URL

Каждый узел работает в одном из двух режимов, задаётся полем `url_mode`:

**`static` (по умолчанию).** Классический режим — все запросы узла идут на адрес из `target_url`. Поля `url_param_name` и `url_allowed_hosts` игнорируются. Используется для большинства узлов с фиксированным внешним endpoint'ом.

**`from_request`.** Целевой URL берётся из query-параметра входящего запроса. Позволяет одному узлу проксировать сообщения на разные адреса в зависимости от того, что прислал клиент. Сценарии: интеграция с динамически создаваемыми webhook'ами, прокси-роутинг между несколькими внешними системами, multi-tenant API gateway.

Логика обработки при `url_mode = from_request`:

1. Receiver берёт имя параметра из `url_param_name` (по умолчанию `url_base`) и ищет его в query string входящего запроса.
2. **Параметр обязателен.** Если его нет в query — Receiver возвращает 400 Bad Request с телом `{"error": "url_base query parameter is required"}`. Никакого fallback на `target_url` нет — режим `from_request` подразумевает, что клиент сам контролирует адрес доставки.
3. Значение валидируется как корректный URL (схема `http`/`https`, валидный hostname). При невалидном — 400 Bad Request с описанием.
4. URL проверяется против allowlist (`url_allowed_hosts`). Если allowlist непустой и URL ни одному паттерну не матчит — 403 Forbidden.
5. После всех проверок URL используется как целевой адрес запроса.

Пример: `POST /api/v1/request/webhook/send?url_base=https://api.partner.com/hook` — Receiver валидирует `https://api.partner.com/hook`, проверяет против allowlist узла, и проксирует тело запроса по этому адресу.

**Параметр `url_base` исключается из итоговой query string** перед отправкой во внешний узел — служебный параметр шины не должен попадать к получателю. Остальные query-параметры (если есть) передаются как есть.

**Безопасность.** Принятие URL от клиента — потенциальная SSRF-уязвимость. Для каждого узла с `url_mode = from_request` обязательно настраивается allowlist хостов (`url_allowed_hosts` — список доменов или wildcard-паттернов вида `*.partner.com`). По умолчанию allowlist пустой, что означает «разрешено всё» — для production-узлов это надо настраивать в обязательном порядке. UI показывает красное предупреждение при пустом allowlist.

В ClickHouse-лог поле `url` записывается с **фактическим** адресом, по которому ушёл запрос (не с `target_url` из конфига).

### 3.5 Режимы исходящей авторизации

Поле `auth_type` определяет, как Receiver формирует заголовок `Authorization` для исходящего запроса к внешнему узлу:

**`none`.** Авторизация отключена — заголовок не добавляется.

**`basic`.** Базовая HTTP-авторизация со статичными учётными данными. Логин и пароль берутся из `auth_credentials`, кодируются Base64, проставляется заголовок `Authorization: Basic <encoded>`.

**`token`.** Статичный Bearer-токен. Берётся из `auth_credentials` и подставляется как `Authorization: Bearer <token>`. Один токен на весь узел.

**`token_from_request`.** Bearer-токен извлекается из самого входящего запроса. Шина пробрасывает его как `Authorization: Bearer <token>`.

**`basic_from_request`.** Прозрачный проброс заголовка Basic-auth. Шина берёт заголовок `Authorization` из входящего запроса (если он начинается с `Basic `) и передаёт его внешнему узлу без изменений. Никакого декодирования или перекодирования — то, что пришло, то и ушло. Полезно для прокси-сценариев, где клиент сам управляет своими кредами, а шина не должна их видеть в открытом виде.

#### Настройки

Только режим `token_from_request` использует группу настроек источника:

| Поле | Назначение | Дефолт |
|---|---|---|
| `auth_dynamic_source` | Где искать токен: `query` / `header` / `body` | `query` |
| `auth_dynamic_field` | Имя query-параметра / заголовка / JSON-поля | `token` (для header — `Authorization`) |
| `auth_dynamic_strip_prefix` | Для `source = header` — префикс, который отрезается | `Bearer ` |

`basic_from_request` ничего не настраивает — источник всегда заголовок `Authorization`, формат всегда `Basic <base64>`. Никаких полей и опций.

#### Логика обработки при `token_from_request`

1. Receiver извлекает значение из источника `auth_dynamic_source` по имени `auth_dynamic_field`. Для `header` снимает префикс `auth_dynamic_strip_prefix`.
2. **Значение обязательно.** Если его нет (или после снятия префикса осталась пустая строка) — 401 Unauthorized: `{"error": "auth token is required in <source> <field>"}`.
3. Значение проставляется в `Authorization: Bearer <token>` исходящего запроса.

#### Логика обработки при `basic_from_request`

1. Receiver читает заголовок `Authorization` входящего запроса.
2. **Заголовок обязателен и должен начинаться с `Basic `.** Если он отсутствует, пустой или с другим префиксом — 401 Unauthorized: `{"error": "Authorization: Basic header is required"}`.
3. Шина опционально проверяет, что после `Basic ` идёт валидная Base64-строка (декодирование выполняется только ради валидации; результат не используется). При невалидной строке — 401.
4. Заголовок проставляется во внешний запрос **без изменений** — ровно та же строка, что пришла от клиента.

#### Исключение из проксируемого запроса

После извлечения служебные данные удаляются из проксируемого запроса:
- Для `token_from_request`: значение удаляется из источника (`query` → параметр вырезается, `header` → заголовок не передаётся, `body` → поле удаляется из JSON).
- Для `basic_from_request`: исходный заголовок `Authorization` шины не дублируется (даже если он в `forward_headers`), на его место ставится тот же заголовок, но уже как часть исходящего запроса шины. Фактически это то же значение — внешний узел видит ровно то, что клиент отправил шине.

#### Маскирование в логах (оба режима)

Значения кредов не пишутся в открытом виде нигде:
- В ClickHouse-логе (поля `parameters`, `url`, `request`) значения по имени `auth_dynamic_field` (для Bearer) и заголовок `Authorization` (для Basic) заменяются на `***`.
- В stdout-логах сервиса — то же маскирование.
- В Sentry-breadcrumbs значения маскируются через `BeforeSend` / `BeforeBreadcrumb` (см. §14.2).

#### Примеры

**Bearer из query:**
`POST /api/v1/request/proxy/api?token=abc123` → шина проставляет `Authorization: Bearer abc123`, query пустая.

**Bearer прозрачный (header):**
`auth_dynamic_source = header`, `auth_dynamic_field = Authorization`, `auth_dynamic_strip_prefix = "Bearer "` →
клиент `Authorization: Bearer abc123` → шина забирает `abc123` → внешнему узлу `Authorization: Bearer abc123`.

**Bearer из X-Api-Key (трансформация):**
`auth_dynamic_source = header`, `auth_dynamic_field = X-Api-Key`, `auth_dynamic_strip_prefix = ""` →
клиент `X-Api-Key: abc123` → шина забирает `abc123` целиком → внешнему узлу `Authorization: Bearer abc123`.

**Basic прозрачный:**
`auth_type = basic_from_request` (других настроек нет) →
клиент `Authorization: Basic YWRtaW46c2VjcmV0` → внешнему узлу `Authorization: Basic YWRtaW46c2VjcmV0`. Шина не декодирует креды, только пробрасывает заголовок.

#### Комбинация с `url_mode = from_request`

Любой динамический `auth_type` совместим с динамическим URL. Пример:
`POST /api/v1/request/proxy/api?url_base=https://api.partner.com/hook` с заголовком `Authorization: Basic YWRtaW46c2VjcmV0` (узел в режиме `basic_from_request`)
→ шина проксирует тело на `https://api.partner.com/hook` с тем же `Authorization: Basic YWRtaW46c2VjcmV0`. Параметр `url_base` исключается из итоговой query.

#### Безопасность

Креды не логируются и не выводятся в UI в открытом виде. Маскирование выполняется по имени поля (для Bearer) или для всего заголовка `Authorization` (для Basic) во всех местах: ClickHouse-логи, stdout-логи, Sentry-breadcrumbs. В UI в полях логов и метрик вместо креды показывается `***`. Allowlist хостов из §3.4 защищает от сценария, когда злоумышленник одновременно подменит URL и подсунет в шину чужие креды для атаки на внутренний сервис.

#### Обновление §41 (универсальная динамическая авторизация)

Раздел §41 уточняет поведение §3.5 (детали — там):

- **`source` теперь только `header`/`query` в UI** (legacy `body` сохранён в БД/коде для существующих
  узлов). `basic_from_request` тоже honored `source`/`field` (раньше — хардкод заголовка
  `Authorization`); миграция `0021` пинит существующие строки на `header`/`Authorization`.
- **Умный дедуп схемы:** если извлечённое значение уже начинается с `Bearer `/`Basic `
  (регистронезависимо) — оно идёт как есть (исключает `Bearer Bearer <jwt>` для `?Bearer=Bearer+<jwt>`).
  Ручной `auth_dynamic_strip_prefix` стал необязательным (оставлен для back-compat).
- **Пустое/отсутствующее поле → запрос уходит БЕЗ `Authorization`** (а не `401`). Для **входящей**
  авторизации (см. §3.3, §41) пустое поле по-прежнему → `401` (гейт).
- **Входящая авторизация** (`token`/`basic`) получила симметричные `incoming_auth_dynamic_source`
  (`header`/`query`) и `incoming_auth_dynamic_field` — можно принимать креду клиента из query-параметра
  или кастомного заголовка. Дефолт `header`/`Authorization` сохраняет прежнее поведение.
- **Каталог «полей запроса»** (`request_fields_catalog`, `/api/request-fields`) — combobox-
  автодополнение имён полей; выбор поля обязателен для динамических режимов.

### 3.6 Состояния узла

Узел в каждый момент времени находится в одном из трёх состояний — поле `status` в БД:

| Состояние | Receiver принимает запросы | Sender отправляет во внешний узел | Когда использовать |
|---|---|---|---|
| `enabled` | Да | Да | Обычная работа |
| `disabled` | Нет (HTTP 404) | — | Узел больше не нужен, но удалять рано (логи, история) |
| `paused` | Да | Нет (копит в Kafka) | Плановые работы на внешнем узле |

**`paused` подробно.** Полезен для случаев, когда внешний узел планово недоступен (deployment, migration, maintenance window). Шина в этом режиме:

1. Принимает входящие запросы как обычно (валидирует, авторизует).
2. **Все запросы превращаются в async** независимо от `root_method`. Receiver кладёт сообщение в Kafka с тем же envelope, что для `requestAsync`. Sync-клиенты получают HTTP 202 Accepted с телом `{"result": true, "id": "<uuid>", "queued": true, "node_status": "paused"}` — необычный ответ, означающий «принято, но обработано позже».
3. Sender-consumer **не обрабатывает** сообщения для paused-узлов: при получении из Kafka проверяет статус узла, и если `paused` — переоткладывает обработку через delayed-redelivery (re-publish с задержкой 30 секунд) либо просто не коммитит offset и ждёт до следующего polling-цикла. Сообщения накапливаются в топике до снятия паузы.
4. **При снятии паузы** (переход в `enabled`) Sender начинает обрабатывать накопленные сообщения с обычной скоростью — порядок сохраняется, лимит размера = retention Kafka (30 дней, см. §5.3).

**Ограничения паузы:**
- Если узел провёл в `paused` более 7 дней — UI показывает баннер «Узел в паузе X дней, накоплено N сообщений. Проверьте, нужна ли пауза до сих пор».
- Sync-клиент, привыкший получать реальный ответ, при пересылке через paused-узел получит только id — нужно учитывать в интеграциях. Это сознательный trade-off.
- Метрика `nexus_paused_messages_total{node}` показывает, сколько накопилось.

**UI:** На странице узла и в форме настроек — переключатель состояния (radio из трёх вариантов с иконками: `▶ Active`, `⏸ Paused`, `⏹ Disabled`). Смена статуса требует подтверждения через диалог с описанием последствий каждого режима.
