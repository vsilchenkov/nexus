# 56. Синхронизация схемы ClickHouse существующей таблицы (ALTER)

Раздел закрывает ловушку §19/C.1: изменение шаблона или CH-настроек узла **не
применяется к уже существующей таблице**. Таблица создаётся один раз
(`CREATE TABLE IF NOT EXISTS`, §19.3), и новые кодеки/индексы/движок/native-TTL к
ней не приезжают — синхронизации схемы с шаблоном нет. §56 добавляет её через
`ALTER TABLE`. Развивает §19 (шаблоны), §4.3 (схема таблицы логов), §22
(logging_enabled), §26 (RBAC).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 56.1 Зачем

Оператор правит шаблон (добавляет `CODEC(ZSTD(3))`, индекс, включает native-TTL)
или переключает узел на другой шаблон — и ждёт, что таблица перестроится. Но
`provisionTable` выполняет `CREATE TABLE IF NOT EXISTS`, который по существующей
таблице **no-op**. Изменения молча не применяются (C.1 предупреждает об этом, но
не решает). §56 — реальное применение.

## 56.2 Модель: предпросмотр + явное применение

Автоматически ALTER'ить боевые таблицы при сохранении узла **опасно** (операции
CH тяжёлые, частично необратимые: `MODIFY COLUMN CODEC` переписывает парты при
мердже, `MODIFY TTL` пересчитывает, `MATERIALIZE INDEX` перечитывает историю).
Поэтому §56 — **явное действие оператора с предпросмотром DDL**, а не побочка
сохранения:

1. **Plan (read-only).** Сервер читает схему существующей таблицы из ClickHouse,
   диффит против целевого шаблона узла и возвращает список **ALTER-операторов** +
   список **неприменимого** (что ALTER'ом не изменить). ClickHouse при этом не
   меняется.
2. **Apply.** Оператор видит точный DDL и подтверждает — сервер исполняет
   ALTER'ы по порядку. Действие пишется в аудит (`node.ch_schema_sync`).

Диффит **чистый планировщик** [PlanSchemaSync](../../internal/domain/ch_schema_sync.go)
(без ClickHouse — юнит-тестируемо); интроспекцию и исполнение делает
adapter/usecase.

## 56.3 Что применяется ALTER'ом, а что нет

| Изменение | Как | Оператор |
|---|---|---|
| Сжатие (CODEC) обязательной колонки | применимо | `ALTER TABLE t MODIFY COLUMN <col> <Type> [CODEC(...)]` (без CODEC — сброс к дефолту) |
| Data-skipping индекс: добавить/убрать/изменить | применимо | `ADD INDEX` / `DROP INDEX` (изменение = DROP + ADD) |
| native-TTL (`ttl_mode`) | применимо | `MODIFY TTL date_create + INTERVAL <days> DAY DELETE` / `REMOVE TTL` |
| Движок (Engine) | **нельзя** | rejection: нужна пересоздача таблицы |
| `ORDER BY` | **нельзя** | rejection: ключ сортировки существующей таблицы неизменяем |
| `PARTITION BY` | **нельзя** | rejection: ключ партиционирования неизменяем |

Неприменимое не пытаемся ALTER'ить (сломались бы) — показываем как **rejection**
с причиной; для него остаётся путь «новое имя таблицы» (создастся свежая, старые
данные останутся в прежней).

**Порядок ALTER'ов:** CODEC → DROP INDEX → ADD INDEX → TTL. DROP до ADD, чтобы
пересоздать изменившийся индекс с тем же именем без коллизии.

## 56.4 Интроспекция существующей таблицы

Снимок [CurrentTableSchema](../../internal/domain/ch_schema_sync.go) читается из
ClickHouse:
- **CODEC** по колонкам — `system.columns.compression_codec`;
- **индексы** — `system.data_skipping_indices` (name/type/expr/granularity);
- **TTL / engine / order_by / partition_by** — `system.tables`
  (`engine`, `sorting_key`, `partition_key`) + разбор native-TTL.

Пустые поля снимка (Engine/OrderBy/PartitionBy) трактуются как «неизвестно» и
**не** порождают rejection — неполная интроспекция не должна блокировать
применимые ALTER'ы.

## 56.5 Неочевидности

- **Нормализация CODEC — best-effort.** `system.columns.compression_codec` отдаёт
  запись в обёртке `CODEC(...)` и может дополнять дефолтными параметрами
  (`ZSTD` → `ZSTD(1)`). Планировщик снимает обёртку и сравнивает регистро- и
  пробел-независимо; семантически равные, но текстово разные кодеки могут дать
  «ложный» `MODIFY` — ClickHouse исполнит его идемпотентно, а оператор видит DDL
  в предпросмотре. Для таблиц, созданных самим Nexus из шаблона, текстовое
  совпадение обычно держится.
- **ADD INDEX индексирует только новые парты.** Историю индекс покрывает лишь
  после `MATERIALIZE INDEX` (тяжёлая операция) или естественного мерджа. §56 (v1)
  делает `ADD INDEX` без авто-`MATERIALIZE`; материализацию исторических партов
  оператор при необходимости запускает вручную.
- **Retention остаётся двухконтурным.** native-TTL (`ttl_mode=ttl_days`) и
  partition-drop housekeeping'а (`clickhouse_retention_days`, §4.3) — разные
  механизмы; §56 синхронизирует только native-TTL шаблона, housekeeping работает
  как прежде.
- **Права.** Действие доступно роли **manager+** (как и правка узла); viewer его
  не видит. Пишется аудит.

## 56.6 API и UI

- `POST /api/nodes/{id}/ch-schema/plan` — предпросмотр (read-only): `{ table,
  statements[], rejections[], table_missing }`.
- `POST /api/nodes/{id}/ch-schema/apply` — исполнить ALTER'ы; аудит
  `node.ch_schema_sync`.
- UI: кнопка **«Синхронизировать схему»** в CH-секции формы узла (рядом с
  предупреждением C.1) → диалог со списком DDL и неприменимого → «Применить».
