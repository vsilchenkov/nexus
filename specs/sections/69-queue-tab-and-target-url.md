# 69. Вкладка «Очередь» для всех узлов, схема target_url, пересборка адреса доставки

Раздел закрывает три следствия одного боевого инцидента (2026-07-27, узел `telephony/lenobl/stat`
команды `vika`): узел в режиме `url_mode=static` сохранили с адресом `vozovoz.lenobl.com` — без
схемы. Валидация это пропустила, все доставки падали с `unsupported protocol scheme ""`, а после
исправления конфига застрявшие async-сообщения продолжали падать ещё сутки. Очистить их из
интерфейса было нельзя: у синхронного узла нет вкладки «Очередь».

Развивает §34 (управление async-очередью), §35 (вкладка узла), §36 (DLQ-репроцессор),
§3.3–3.4 (конфиг узла и резолв URL). Карта реализации —
[../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 69.1 Вкладка «Очередь» доступна для всех типов узлов

**Было:** вкладка показывалась только у `requestAsync`. У `request` и `RabbitMQAsync` её не было
вовсе, а вместе с ней — ни «Повторить все сейчас», ни «Очистить неудачные». Единственный способ
убрать накопившиеся записи `done=0` у синхронного узла — временно сменить тип узла на
`requestAsync`, очистить и вернуть обратно.

**Стало:** вкладка есть у всех узлов; её наполнение зависит от наличия очереди в Kafka.

| Секция | `request` (sync) | `requestAsync` | `RabbitMQAsync` (pull) |
|---|---|---|---|
| KPI «Ожидают отправки» | нет | да | да |
| «Ожидают отправки» (peek Kafka, purge, удаление сообщения) | нет | да | да |
| KPI «Неудачные доставки» | да | да | да |
| «Неудачные доставки» (список, replay, «Повторить все», «Очистить») | да | да | да |
| Баннер статуса + пауза/отключение | да | да | да |

Записи `done=0` у синхронного узла появляются так же, как у асинхронного: открытый circuit breaker,
сетевая ошибка, ответ больше лимита тела, не-2xx статус. Отличий в чтении и очистке нет — обе
операции работают с ClickHouse, а не с Kafka.

**Тексты отличаются по смыслу, а не косметически.** Для `request`:

- баннер паузы — «входящие запросы отклоняются сразу», а не «копятся в очереди ниже»;
- вместо подсказки про авто-повтор до DLQ TTL — «синхронные запросы не повторяются автоматически:
  ответ уже отдан вызывающему»;
- подтверждения очистки не обещают «авто-повтор прекратится» — прекращать нечего.

Для `RabbitMQAsync` отдельный текст паузы и пустой очереди: paused pull-узел исключается из
поллинга (`NodeLister` отдаёт только не-disabled, менеджер пропускает paused), поэтому новые
сообщения ждут **в брокере**, а не в очереди Nexus. Обещать «возобновите, чтобы их отправить, либо
очистите очередь» здесь нельзя: очистка тронет только то, что шина успела принять до паузы.

**Бэкенд не потребовал новых эндпоинтов:** маршруты `/nodes/:id/async-queue/*` уже были
node-scoped и не проверяли тип узла, а `purge-failed`/`replay-failed` изначально работают через
ClickHouse. Добавлены только ранние выходы (§69.4).

## 69.2 target_url обязан быть абсолютным http(s)-адресом

`Validate()` проверял `target_url` лишь на непустоту (для `static`) и длину ≤2048. Адрес без схемы
проходил сохранение и падал уже на доставке — то есть ошибка конфигурации обнаруживалась как
ошибка рантайма, на каждом вызове узла.

**Правило:** при `url_mode=static` (в него же нормализуются pull-узлы, §27.11) непустой
`target_url` обязан парситься как URL со схемой `http`/`https` и непустым хостом. Пробелы по краям
срезаются в `SetDefaults()`.

**Почему проверка привязана к режиму, а не к «любому непустому значению»:** при `from_request` поле
на форме скрыто и не используется (адрес приходит в запросе). Остаточное значение от переключения
режима иначе блокировало бы сохранение ошибкой на невидимом поле — тупик для оператора.

Ошибка: `ErrNodeTargetURLScheme` → HTTP 400 с `code = node.validation.target_url_scheme` и
`field = target_url` (стандартный механизм §21: подсветка поля на форме). Клиентская проверка
в `nodeValidation.ts` — зеркало доменной, ошибка ловится до запроса. Подсказка поля прямо
предупреждает, что адрес без схемы не сохранится.

Асимметрия закрыта: для `url_mode=from_request` требование `http(s)` действовало и раньше (на
рантайме, при резолве URL из запроса) — теперь та же проверка живёт в одном хелпере
`domain.AbsoluteHTTPURL` и переиспользуется резолвером Receiver'а и валидацией публичного адреса
приложения.

## 69.3 Адрес доставки static-узла пересобирается по свежему конфигу

Receiver резолвит целевой URL **один раз, на приёме**, и кладёт готовую строку в конверт Kafka.
Sender и DLQ-репроцессор отправляли ровно по ней, а конфиг узла перечитывали только ради TTL,
задержки, статуса и логирования. Следствие в инциденте: синхронные вызовы починились сразу после
правки `target_url`, а шесть уже принятых async-сообщений повторялись каждые
`dlq_retry_delay_seconds` (5 мин) по старому битому адресу и должны были долбиться до
`dlq_ttl_seconds` (24 ч).

**Стало:** при `url_mode=static` адрес собирается заново перед каждой отправкой —

```
база = target_url узла (актуальный, без своей query и fragment)
    + хвост path-passthrough (env.request_path, §39)
    + query из конверта
```

Точка внедрения — `buildSendInput`, поэтому правило действует сразу на трёх путях: основной
async-consumer, redelivery из delay-топика paused-узлов (§3.6) и DLQ-репроцессор (§36).

**Ограничения (осознанные):**

- **Query берётся из конверта, а не из свежего `target_url`** — в конверте она уже объединена с
  query входящего запроса, и брать обе значило бы дублировать параметры. Поэтому правка
  схемы/хоста/пути в `target_url` действует на застрявшие сообщения, а правка query внутри
  `target_url` — нет.
- **`url_mode=from_request` не пересобирается**: исходное значение url-параметра вырезано из query
  на приёме и существует только внутри самого `env.target_url`.
- **Любой сбой разбора — адрес из конверта** (как раньше). Тот же паттерн обратной совместимости,
  что и с `received_at`: нет данных — ведём себя как до изменения.

Факт расхождения адреса конверта и фактического пишется в debug-лог (§51.9), URL — без query.

## 69.4 Kafka-операции не трогают брокеры для sync-узлов

Раз вкладку теперь видит и синхронный узел, `List`/`purge` обязаны отсекать его сами: иначе каждое
открытие вкладки означало бы бесполезный скан обоих топиков до `peek_cap` (1000) сообщений.
`PurgeFailed` для sync-узла пропускает запись tombstone'ов в Redis — читать их некому, DLQ-репроцессора
у синхронного узла нет; удаление записей `done=0` из ClickHouse работает как обычно.

## 69.5 Scope

**В разделе:** видимость вкладки и её наполнение по типам узлов; валидация схемы `target_url`
(бэкенд + форма); пересборка адреса доставки для static-узлов; ранние выходы Kafka-операций.

**Вне раздела:**

- миграция существующих узлов с адресом без схемы — таких на бою нет (проверено по всем командам);
  строгая валидация начнёт отвергать сохранение/копирование/dry-run такого узла, лечится ручной
  правкой адреса;
- пересборка адреса для `from_request` (данных нет, см. §69.3);
- изменение самого контракта конверта (версионирование, вынос в общий пакет) — остаётся в планах.
