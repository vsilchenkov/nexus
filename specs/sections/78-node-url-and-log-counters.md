# 78. Адрес узла без сегмента метода, счётчик логов по записям, проброс параметров при смене метода

Раздел закрывает три замечания боевой эксплуатации команды `webhook` (узел `sbp-qr`,
`root_method=requestAsync`, `incoming_method=GET`, `outgoing_method=POST`), полученные 2026-08-04:

1. **Адрес узла содержит служебный сегмент** `request`/`requestAsync`. Партнёру, который
   интегрируется с шиной, это видно как деталь реализации Nexus: чтобы дать ему два метода одного
   API (синхронный и асинхронный), приходится публиковать два адреса, различающихся не именем
   метода, а внутренним признаком шины.
2. **Счётчик логов узла не сходится со списком** — «Показано 17 из 40», и остальные 23 записи
   недостижимы: скролл сообщает, что история кончилась.
3. **Не подтверждён проброс параметров при смене метода**: клиент шлёт `GET` с query, узел
   настроен отправлять `POST`.

Развивает [§3](03-receiver.md) (эндпоинты Receiver), [§18](18-multi-tenancy.md) (слоги команд),
[§32.2](32-loop-protection.md) (самоссылка), [§40](40-any-http-method.md) (методы узла),

## 78.1 Короткий адрес узла: `/api/v1/<команда>/<путь>`

**Проблема.** Публичный адрес узла сегодня обязан нести корневой метод:
`/api/v1/request/<team_slug>/<node_path>` или `/api/v1/requestAsync/<team_slug>/<node_path>`.
Корневой метод — свойство **узла** (колонка `nodes.root_method`), а не запроса: клиент не выбирает
синхронность, он лишь обращается по адресу, который ему выдали. Требование к адресам выглядит так:

```
https://nexus.vz78.vozovoz.ru/api/v1/webhook/sbp-qr         → узел sbp-qr        (request)
https://nexus.vz78.vozovoz.ru/api/v1/webhook/sbp-qr-async   → узел sbp-qr-async  (requestAsync)
```

Для клиента это два метода одного API с общим корнем `…/api/v1/webhook`; какой из них синхронный,
решает конфигурация узла в Nexus, а не URL.

**Решение.** Вводится короткая форма адреса — без сегмента метода:

```
/api/v1/<team_slug>/<node_path>      короткая форма
/api/v1/<node_path>                  короткая форма для команды default (как и у legacy-формы)
```

Синхронность определяется полем `node.RootMethod` **после** резолва узла — того самого резолва,
который уже выполняется для каждого запроса (`resolveNode`: точное совпадение `team+path` →
интерпретация «слога не было, это путь в default» → longest-prefix для §39 path-passthrough).
Дополнительных полей, миграций и обращений в БД не требуется.

| `root_method` узла | Поведение короткого адреса |
|---|---|
| `request` | синхронная маршрутизация; узел на паузе → 202 + `queued:true` (§3.6, та же развилка, что у legacy-формы) |
| `requestAsync` | асинхронная маршрутизация (Kafka), ответ `{result:true,id}` |
| `RabbitMQAsync` | **404** `node not found` — у pull-узла нет входящего HTTP; факт существования узла не раскрывается |
| узел не найден / отключён | 404 `node not found` (как у legacy-формы) |

**Совместимость — обязательное требование.** Формы `/api/v1/request/…`,
`/api/v1/requestAsync/…` и `/api/v1/callback/…` продолжают работать без ограничения срока: адреса
уже выданы внешним системам и меняться не должны. Обе формы ведут в один и тот же код
маршрутизации; различие только в способе выбора синхронности:

- legacy-форма: метод задан URL и **проверяется** — `/api/v1/request/<async-узел>` по-прежнему
  отвечает 404 (`route.go`: «node is requestAsync, not request»), а
  `/api/v1/requestAsync/<sync-узел>` по-прежнему принимается (на этом стоит §3.6);
- короткая форма: метод **берётся** из `root_method`, проверять нечего.

**Ограничение формата, о котором нужно знать.** Первый сегмент короткого адреса всегда трактуется
сначала как слог команды, и лишь затем — как начало пути узла в команде `default` (существующее
поведение резолвера). Поэтому узел `default`-команды с путём `webhook/sbp-qr` и узел `sbp-qr`
команды `webhook` по короткому адресу неразличимы: выиграет тот, что найдётся первым (команда).
Однозначность даёт полная форма со слогом — `/api/v1/default/webhook/sbp-qr`.

## 78.2 Маршрутизация: один catch-all вместо трёх маршрутов

**Ограничение gin, определяющее решение.** Зарегистрировать `/api/v1/*path` рядом с существующими
`/api/v1/request/*path` нельзя — роутер падает при старте (проверено на gin v1.12.0, дословно):

```
catch-all wildcard '*path' in new path '/api/v1/*path'
conflicts with existing path segment 'request' in existing prefix '/api/v1/request'
```

Два обходных пути отвергнуты:

- **разбор короткого адреса в `NoRoute`** — теряются middleware группы `/api/v1`: rate-limit
  (§9.4) вообще не применился бы, а `metrics.GinMiddleware` выходит досрочно при пустом
  `c.FullPath()`, то есть боевой трафик по новым адресам исчез бы из `nexus_requests_total`;
- **перепись пути обёрткой `http.Handler` вокруг всего движка** — единая точка на всём трафике
  сервиса ради одного маршрута; сложнее и опаснее того, что решает.

**Принятое решение.** Три маршрута Receiver заменяются одним catch-all в той же группе, а первый
сегмент разбирает handler:

```
v1.Any("/*path", h.handleIngress)      вместо /request/*path, /requestAsync/*path, /callback/*path
```

`handleIngress` смотрит на первый сегмент `c.Param("path")`:

| первый сегмент | ветка |
|---|---|
| `request` | синхронная (прежний `handleSync`, включая paused → async) |
| `requestAsync` | асинхронная (прежний `handleAsync`) |
| `callback` | webhook-callback (прежний `handleCallback`, требование `webhook_signature`) |
| любой другой | короткая форма §78.1 — диспетчеризация по `root_method` |

Проверено на gin v1.12.0: одиночный `/api/v1/*path` регистрируется без паники, соседние ветки
дерева (`/api/nodes`, `/api/nodes/:id`, `/api/settings/*`) продолжают матчиться, а
`c.Param("path")` отдаёт полный хвост вместе с сегментом метода.

**Что обязано остаться неизменным (и как это обеспечивается):**

- **Ключ rate-limit.** Сегодня ключ — хвост *после* сегмента метода (`webhook/sbp-qr`); с
  catch-all в параметр приходит `/request/webhook/sbp-qr`. Middleware обязан срезать сегмент
  метода тем же хелпером, что и handler, иначе (а) legacy- и короткая формы попадут в разные
  корзины и клиент удвоит квоту простой сменой формы адреса, (б) сменятся ключи Redis у всех узлов.
- **Метки метрик.** `c.FullPath()` теперь одинаков для всего боевого трафика, поэтому метка
  `method` больше не может выводиться из него. Handler кладёт её в контекст явно (новый ключ
  рядом с `metrics.NodeLabelKey`), значения прежние — `request` / `requestAsync`; короткая форма
  даёт ту же метку, что и legacy-форма того же узла, то есть ряды не разъезжаются и трафик по
  новым адресам виден в существующих панелях. Это обязательное требование: на
  `method="requestAsync"` стоит дашборд Kafka (`deploy/grafana/nexus-kafka.json`), на
  `method="request"` — алерт латентности (`deploy/prometheus.alerts.yml`). Запрос, у которого узел
  не разрезолвился (404 по короткому адресу), метится `route` — отдельным рядом, чтобы мусорные
  обращения не подмешивались в боевые. Webhook-callback'и получают метку `callback` вместо прежней
  строки-имени маршрута (`POST /api/v1/callback/*path`); в дашбордах и алертах она не используется.
  Метку ставит вызывающий, а не общий async-код: sync-узел на паузе уходит в async-ветку (§3.6), но
  остаётся `request` — ровно как метился по имени маршрута до §78.
- **Метка `node`** по-прежнему ставится handler'ом равной пути узла без слога команды (совпадение
  с меткой Sender, §21).
- **404-подсказки.** Ответ на запрос без префикса `/api/v1/` («API version required, use
  /api/v1/…») остаётся в `NoRoute` без изменений. Граничные пути (проверено): `/api/v1/` → 400
  `empty node path`, `/api/v1` без слеша → 307 на `/api/v1/` (штатный редирект gin), путь вне
  `/api/v1/` → прежний 404.

**Изменение поведения, которое нужно зафиксировать явно:** сегодня `callback` зарегистрирован как
`POST`-only, и запрос другим методом падает в `NoRoute` → `404 not found`. После объединения
маршрутов handler обязан отвечать **405 Method Not Allowed** — это честнее и различимо в логах, но
формально это смена кода ответа для не-POST обращений к `/api/v1/callback/…`.

**Web как единый вход.** Боевой трафик приходит в Web (:8000), который реверс-проксирует
`/api/v1/*` в Receiver. Под `/api/v1/` в Web нет ничего, кроме этого прокси (весь админский REST
живёт на `/api/…` без `v1`), поэтому три proxy-маршрута тоже заменяются одним
`r.Any("/api/v1/*path", …)`: путь уходит в Receiver дословно, диспетчеризацией занимается только
Receiver. Прокси, как и сейчас, регистрируется на движке, а не в группе `/api` — CSRF-проверка
Origin на боевой трафик не вешается. Побочное следствие: неизвестный путь `/api/v1/…` теперь
получает 404 от Receiver (`{"error":"node not found"}`) вместо 404 от SPA-фолбэка Web
(`{"error":"not found"}`).

## 78.3 Резерв слогов команд

Первый сегмент короткого адреса — слог команды, поэтому слоги, совпадающие с сегментами методов,
делают короткую форму неоднозначной. Запрещаются при создании и переименовании команды:
`request`, `requestasync`, `callback`. Формат слога (`^[a-z][a-z0-9_]{0,31}$`) сам по себе не
допускает `requestAsync` в каноническом написании, но нижний регистр запрещается ради читаемости
адресов.

Проверка стоит **на создании команды** (`TeamUsecase.Create`) и отвечает 400 с локализованным
текстом и кодом `team.slug_reserved`. Внутрь `Team.Validate()` она намеренно не попадает: та же
функция вызывается при **переименовании**, и запрет в ней сломал бы правку уже существующей команды
с таким слагом — ровно то, чего раздел обещает не делать. Локализация — серверная
(`platform/i18n`, en+ru): форма команд показывает текст ошибки как есть, отдельных ключей во
фронте не требуется.

**Миграции и CHECK-constraint'а нет**: уже существующие команды не ломаются. Если такая команда где-то
создана до релиза, её узлы остаются доступны по legacy-форме (`/api/v1/request/request/<path>`), а
короткая форма для них недоступна — это состояние выявляется проверкой при выкате
(`SELECT slug FROM teams WHERE slug IN (…)`, в описании релиза).

## 78.4 Самоссылка, replay и dry-run

**Защита от зацикливания (§32.2) обязана понимать новую форму.** Сегодня самоссылкой считается
`target_url`, чей путь начинается с `/v1/request` или `/api/v1/request` на одном из «своих»
authority. Узел, чей `target_url` указывает на собственный короткий адрес
(`https://<свой хост>/api/v1/webhook/sbp-qr`), под это правило не подпадает и был бы сохранён —
защита молча ослабла бы ровно в момент появления новой формы. Признак «входной путь шины»
расширяется до любого пути под `/api/v1/` (и `/v1/`) на своём authority. Хоп-счётчик §32.1
остаётся второй линией обороны и не меняется.

**Служебные вызовы шины (replay §7.4, dry-run §55) продолжают строить legacy-форму** со слогом
команды. Менять их не требуется: форма адреса — публичный контракт для внешних клиентов, а не
внутренний транспорт; переключение служебных путей на короткую форму дало бы риск без выгоды.

## 78.5 Адрес узла в интерфейсе

Карточка «Конфиг» узла показывает **короткий адрес основным**, классический — свёрнутой строкой
(утверждено заказчиком):

```
┌ Адрес узла ─────────────────────────────────────────────────┐
│ https://nexus.vz78.vozovoz.ru/api/v1/webhook/sbp-qr  [копировать] │
│ ▸ классический: https://…/api/v1/requestAsync/webhook/sbp-qr      │
└─────────────────────────────────────────────────────────────┘
```

Правила сборки короткого адреса на фронте:

- команда узла известна → `<public_base_url>/api/v1/<slug>/<path>`;
- команда `default` → `<public_base_url>/api/v1/<path>`, **кроме** случая, когда первый сегмент
  пути узла совпадает с зарезервированным словом §78.3 — тогда показывается форма со слогом
  (`/api/v1/default/<path>`), иначе показанный адрес уехал бы в legacy-ветку;
- узлы `RabbitMQAsync` адрес не показывают (как и сейчас — входящего HTTP у них нет).

## 78.6 Счётчик логов: единица счёта — запись, а не строка

**Симптом.** Шапка вкладки «Логи» узла: «Показано 17 из 40» при размере страницы 50; скролл
подгрузки не даёт — внизу «записей больше нет». Оставшиеся 23 записи недостижимы никаким способом.

**Причина.** Список и счётчик считают разные единицы:

- `GET /api/nodes/{id}/logs/count` выполняет `SELECT count()` — это **строки** таблицы ClickHouse;
- список после дедупа по `id` на фронте показывает **записи** (уникальные `ID`).

В таблице логов одна запись живёт несколькими строками: каждый повторный **прогон доставки** пишет
свою строку с тем же `ID` (redelivery Kafka, DLQ-репроцессор §36, `ttl_expired`, replay, дренаж
retry-топика §38). Внутренние ретраи одного прогона, наоборот, схлопнуты в одну строку — их
описывают колонки `attempts`/`attempts_details`. Модель «запись = `ID`, строка = прогон доставки»
уже зафиксирована в коде: `NodeKPI` §44 считает `countDistinct(ID)`, `FailedIDs` — `DISTINCT ID`,
`GetByID` берёт свежайшую строку записи. Из общего ряда выпадали только `Count` и `CountFailed`.

Подтверждение с боя: аудит очистки неудачных доставок отдал `cancelled=5, deleted=10` — те же
данные в двух единицах (5 записей = 10 строк).

**Решение — единица счёта одна во всём read-path: запись.**

- `Count` (счётчик «из M») → `uniqExact(ID)` под теми же фильтрами, что и список;
- `Search` (страница списка) → `LIMIT 1 BY ID` поверх существующей сортировки: страница из `limit`
  строк становится страницей из `limit` **разных записей**, каждая — свежайшей попыткой, той же
  строкой, что раскроет `GetByID`;
- `CountFailed` (KPI «неудачные доставки» вкладки «Очередь») → `uniqExact(ID)`. Неудачная запись =
  запись, у которой в окне есть хотя бы одна строка `done=0`, — ровно то множество, которое
  отменяет и удаляет очистка (`FailedIDs`/`DeleteFailed`). Как следствие, видимое «очищено N» и
  число отменённых сообщений перестают расходиться;
- `ListSince` (live-tail) дедупу **не** подвергается: там повтор `ID` — это новое событие по уже
  показанной записи, а не дубль;
- `CountErrors` (§20.3, Telegram-уведомления) остаётся на строках — это счётчик событий доставки,
  он не стоит парой ни к одному списку. Решение фиксируется явно, чтобы следующий читатель не счёл
  его забытым.

**Что это меняет для пользователя:** «Показано N из M» сходится; скролл доходит до конца истории;
KPI неудачных доставок совпадает со списком под ним.

**Границы и известные следствия:**

- дедуп на фронте (`useInfiniteLogs`) **остаётся**. Keyset-курсор строится по свежайшей попытке
  последней записи страницы, поэтому старые попытки уже показанной записи лежат ниже курсора и
  могут прийти повторно на следующей странице; это стоит лишних строк, но не ложного конца
  истории — контракт §72.2 (`items.length < pageSize` = история кончилась) сохраняется;
- автоокно §77.2 автоматически начинает мерить наполнение страницы записями, кода это не требует;
  счётчик, как и раньше, автоокном не сужается;
- **внешние таблицы §64** (пишет посторонний сервис): колонка `ID` для них обязательна
  (`RequiredLogColumns`, проверяется `POST /api/ch-tables/verify`), поэтому счёт по записям работает
  так же. Но если чужой писатель заполняет `ID` неуникально (или оставляет пустым), все такие
  строки схлопнутся в одну запись. Это не регресс §78: список и раньше схлопывал их дедупом по
  `id` на фронте — менялся только счётчик, который показывал «1 из N». Теперь обе цифры сходятся;
  чтобы видеть строки по отдельности, писатель обязан заполнять `ID` уникально;
- стоимость `uniqExact` на больших таблицах выше, чем у `count()`. Действующий потолок §67
  (таймаут 10 с → мягкая деградация «Показано N» без «из M») остаётся страховкой; если замер на
  боевых объёмах покажет систематические таймауты, план «Б» — переиспользовать существующий флаг
  `app_settings.general.metrics_approx_counts` (§44), как это уже сделано в `NodeKPI`
  (`uniq` вместо `uniqExact`, HyperLogLog, ошибка ~0.3 %). В рамках этого раздела флаг **не**
  вводится.

**Правки формулировок в действующих разделах** (контракт обязан читаться однозначно): §67.4
(счётчик «Всего»), §72.2 («N и M считают одно множество»), §77.2 (границы автоокна) дополняются
единицей счёта — «запись (уникальный `ID`)», со ссылкой сюда.

## 78.7 Проброс параметров при смене метода (GET → POST)

**Проверено на боевом узле, изменений в коде не требует.** Клиент шлёт
`GET /api/v1/requestAsync/webhook/sbp-qr?mdOrder=…&operation=deposited&orderNumber=…&status=1`,
узел настроен `incoming_method=GET`, `outgoing_method=POST` — наружу уходит
`POST https://vika-webservices…/hs/webhook/request/sbp-qr?mdOrder=…&operation=deposited&…`,
ответ 200. Параметры доезжают.

Контракт фиксируется в ТЗ явно, потому что вопрос возникает повторно:

- **query входящего запроса всегда переносится в URL исходящего**, независимо от пары методов
  (`ResolveURL` → `appendQuery`); параметры узла из `target_url` и параметры клиента
  складываются, повторяющиеся ключи сохраняются;
- вырезаются только служебные параметры: имя `url_param_name` при `url_mode=from_request` (§3.4) и
  поле динамической авторизации при `auth_dynamic_source=query` (§41);
- **тело исходящего запроса = тело входящего**. У `GET` оно, как правило, пустое, значит наружу
  уйдёт `POST` с пустым телом. Конверсии «query → тело» в шине нет и в рамках раздела не вводится:
  формат тела (JSON? form-urlencoded? какие имена полей?) — это контракт принимающей системы, а не
  шины, и молча синтезировать его нельзя;
- зеркалирование метода (наружу уходит тот же метод, что пришёл) — это `outgoing_method=ANY` §40,
  отдельный режим;
- **известное ограничение, оставленное вне рамок:** заголовок `Content-Type` берётся из входящего
  запроса, поэтому «голый» GET без `Content-Type` даёт исходящий POST без `Content-Type`. Задать
  его на узле сейчас нечем (`forward_headers` только пробрасывает пришедшее). Строгий приёмник
  ответит на такой POST 400/415. Если понадобится — это отдельный раздел (статические заголовки
  узла), а не правка этого.

Раздел закрывается **приёмочным тестом** на связку «входящий GET с непустой query +
`outgoing_method=POST`»: сегодня такой сценарий не покрыт (тесты подмены метода идут с пустой
query, тесты query — с методом POST), то есть работающее поведение ничем не защищено от регресса.

## 78.8 Вне рамок

- Свой сегмент метода в адресе для каждого узла (произвольный алиас) — адрес остаётся
  `<команда>/<путь>`.
- Перевод служебных путей (replay, dry-run) на короткую форму.
- Статические заголовки исходящего запроса (см. ограничение `Content-Type` в §78.7).
- Флаг приблизительного счёта записей в логах (план «Б» §78.6).
- Изменение единицы счёта `CountErrors` §20.3.

## 78.9 Приёмка

**Короткий адрес.** Integration-сценарии на реальных PostgreSQL/Kafka/CH (образцы —
`receiver_anymethod_test.go`, `receiver_async_test.go`): sync-узел по короткому адресу отвечает
телом получателя; async-узел по короткому адресу кладёт сообщение в Kafka; `RabbitMQAsync` →
404; sync-узел на паузе → 202 `queued`; **обе legacy-формы продолжают работать**, включая
`/api/v1/request/<async-узел>` → 404 и `/api/v1/callback/…` с подписью; путь без слога резолвится в
команду `default`; rate-limit считает legacy- и короткую форму одной корзиной; не-POST на
`callback` → 405. Unit: разбор первого сегмента (таблица), метка метрик из контекста, валидация
зарезервированных слогов, самоссылка на короткий адрес отклоняется.

**Счётчик логов.** Integration-тест с посевом **дублей `ID`** (несколько строк на запись, разные
`date_request`) — сегодня ни один тест логов дублей не сеет, через эту дыру дефект и прошёл:
`Count` = число записей; страница = `limit` разных записей, каждая свежайшей попыткой; keyset-скролл
доходит до конца истории; `CountFailed` = число записей с неудачными попытками и совпадает с
`FailedIDs`. Тест обязан быть красным на коде до раздела.

**Параметры при смене метода.** Integration-тест GET+query → POST на mock-получателе: проверяется
итоговый URL со всеми параметрами и метод запроса.

**Живой прогон на стенде** (браузером): карточка узла показывает короткий адрес, копирование
работает, вызов по нему проходит; на узле с повторными доставками «Показано N из N», скролл доходит
до конца.
