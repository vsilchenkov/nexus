# 107. Потоковые подписки и медленные ответы: SSE на GET и таймауты вне breaker

Раздел добавляет узлу две настройки для получателей, чьи ответы не укладываются в модель «запрос —
ответ целиком»:

- **«Не открывать поток (SSE) на GET»** — Receiver сам отвечает `405` на подписку
  `text/event-stream`, не обращаясь к получателю;
- **«Не считать таймаут отказом защиты»** — таймаут при уже установленном соединении не
  засчитывается в circuit breaker узла.

Развивает [§40](40-any-http-method.md) (методы узла), [§55](55-dry-run-real-call.md) (dry-run
повторяет шаги Receiver), [§80.5](80-async-throughput.md) (закрывает п. 2 — «вклад таймаута в
счётчик брейкера настраиваемый вплоть до нуля»), [§81](81-breaker-manual-reset.md) (трёхзначный
вердикт брейкера), [§94](94-rejected-requests.md) (журнал отказов), [§83](83-async-ack-template.md)
(прецедент «статус задаёт настройка узла, а не отказ»).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграция `0043`** — две
булевы колонки узла, аддитивно (§74.2). **Proto:** поле `SendRequest.breaker_ignore_timeouts = 34`.

## 107.1 Повод: MCP-серверы за шиной

Разбор команды `mcp` 23.09.2026. Шесть узлов (`mcp-1c-*`, `onec-rest-*`) проксируют MCP-серверы
(протокол Model Context Protocol, транспорт Streamable HTTP) на `192.168.3.115`. Клиент — Claude
Code.

**Что делает клиент.** После подключения MCP-клиент открывает GET-запросом с
`Accept: text/event-stream` отдельный канал (SSE), по которому сервер мог бы сам присылать
уведомления. Канал бесконечен: он живёт, пока клиент подключён. Сервер `:8172` держит его,
присылая `: ping` раз в 15 секунд. Вызовы инструментов идут отдельными POST-запросами.

**Что делает шина.** Синхронный путь устроен как «запрос — ответ целиком»: Sender дочитывает тело
до конца (`io.ReadAll` в `httpclient`), а до Receiver ответ доходит одним сообщением unary-вызова
gRPC `Send`. Бесконечный поток поэтому не отдаётся клиенту ни байтом (даже заголовки) и
обрывается по `timeout_ms` узла: `status 0`, `upstream_timeout`, клиенту `504`. Уже полученный
статус `200` и пинги при этом выбрасываются.

**Последствия, замеренные на бою** (журнал с 20–21.09 по 23.09, на каждый из шести узлов):

| Что | Сколько |
|---|---|
| `GET … upstream_timeout` — по одной строке на каждое подключение клиента | 195–231 |
| `POST 400` — проба `server/discover` новой версии протокола (`2026-07-28`), сервер отвечает `Missing session ID`, клиент переходит на `initialize` | 177–226 |
| **`POST … circuit_breaker_open` — вызовы инструментов получили 503** | **8–10** |

Последняя строка — главный вред. Таймаут узла засчитывается брейкеру отказом (§81.2), счёт идёт
подряд, успех его обнуляет. Несколько сессий, подключившихся за пару минут без вызовов между ними,
складывают таймауты своих GET-каналов — и брейкер открывается. Живой пример, `mcp-1c-vika_dev5`,
21.09:

```
15:13:38 … 15:13:58   GET  0  upstream_timeout ×5 подряд   ← брейкер открылся (порог 5)
15:14:02, 15:14:25    POST 0  circuit_breaker_open        ← вызовы инструментов получили 503
```

Подъём `timeout_ms` (190 → 300 с) не помогает: GET всё равно не получит ответа, соединение просто
висит дольше, а брейкер открывается позже.

**Почему не «входящий метод = POST».** Receiver тогда отвечает на GET `405` — но как **отказ**:
запрос попадает в журнал отказов §94. Группы там агрегируются (одна на узел), однако отметка
«просмотрено» снимается новым отказом (§94.6), и бейдж «Логи» горел бы постоянно — на каждое
подключение сессии. Вдобавок отрезаются DELETE (закрытие сессии) и OPTIONS (CORS-проверка
браузерных инструментов вроде MCP Inspector).

Протокол MCP прямо разрешает серверу ответить `405` на GET: «потока у меня нет». Клиент тогда
канал не открывает и не переспрашивает. Раздел даёт шине сказать это самой — и не как отказ.

## 107.2 Настройка «Не открывать поток (SSE) на GET»

**Модель.** `nodes.sse_decline BOOLEAN NOT NULL DEFAULT false`; `domain.Node.SSEDecline`.
Применяется только к синхронному узлу (`root_method = request`), **принимающему GET** — входящий
метод `ANY` или `GET` (`Node.sseDeclineApplies`). У остальных `NormalizeForRootMethod` сбрасывает
флаг и записывает поле в `cleared_incompatible_fields` аудита (как `path_passthrough`):

- `requestAsync` отвечает клиенту сам, не дожидаясь получателя, — подписка на входе не висит;
- у `RabbitMQAsync` входа нет вовсе;
- узел с входящим `POST`, `PUT`, `DELETE` (пустой метод — это `POST`) отвечает на GET отказом
  метода §40 и без флага. Скрытый в форме флаг подменял бы этот отказ своим 405 молча — вне
  журнала отказов. Правило добавлено по замечанию со стенда: переключатель у такого узла
  показывался, хотя смысла не имел.

`DeclineStream` проверяет то же условие — страховка от ручной правки БД.

**Что считается подпиской.** `domain.IsSSESubscribe(method, header)`: метод `GET` **и** в `Accept`
есть медиатип `text/event-stream` (без учёта регистра, параметры допустимы) с `q ≠ 0`. `Accept`
разбирается по элементам списка через `mime.ParseMediaType`; битый элемент пропускается, а не
роняет разбор. POST с тем же `Accept` подпиской не считается: MCP-клиент шлёт так вызовы
инструментов, и сервер вправе ответить на них коротким SSE — у такого ответа есть конец, шина
отдаёт его целиком, как и сейчас.

**Где проверяется.** `checkNodeAcceptsSync` (Receiver):

1. `Disabled` → `404` (как прежде: выключенный узел наружу не раскрывается);
2. **новое:** `SSEDecline && IsSSESubscribe` → `domain.ErrStreamDeclined`;
3. `Paused` → переключение в async (§3.6);
4. тип узла, входящий метод (§40), входящая авторизация (§41).

Проверка стоит **до паузы**: подписка на поставленном на паузу узле не превращается в сообщение
очереди (Sender потом повис бы на ней в async-пути). И **до метода и авторизации**: ответ `405`
не зовёт получателя и ничего не раскрывает сверх того, что раскрыл бы `401` включённого узла.
Цена — клиент без токена получит `405`, а не `401`, и в журнал отказов не попадёт. Это граница,
названная явно.

**Ответ.** `405 Method Not Allowed`, тело `{"error":"event stream is not supported by this node"}`,
заголовок `Allow` (RFC 9110 требует его в 405):

- `incoming_method = ANY` → `POST, PUT, PATCH, DELETE, HEAD, OPTIONS`;
- `incoming_method = GET` → пустой: другого метода узел не принимает.

**Это не отказ.** Ответ помечается `MarkProxiedResponse` — тем же механизмом, которым §94.2
исключает статусы получателя и шаблона ответа приёма §83: статус задала настройка узла, шина
отработала штатно. Поэтому:

| Куда | Попадает? |
|---|---|
| Журнал отказов §94 и `nexus_ingress_rejected_total` | нет |
| Лог узла в ClickHouse (пишет Sender) | нет — Sender не вызывается |
| Circuit breaker, статус узла, gauge исхода (всё в Sender) | нет |
| `nexus_requests_total{service="receiver",method="request",status="405"}` | **да** — так ответы видны в метриках по узлу |
| Служебный лог | `Debug` «sse subscription declined by node setting» (узел, команда, метод) |

**Охват.** Полная (`/api/v1/request/…`) и короткая (§78, `/api/v1/<команда>/<путь>`) формы адреса
идут через один `handleSync`. Async-входы не затрагиваются: у async-узлов флаг сброшен
нормализацией.

**Dry-run (§55.9).** Отчёт получает шаг `stream.declined` перед `method.incoming`: при флаге и
подзапросе-подписке (GET + `Accept: text/event-stream` в заголовках подзапроса) шаг помечен
проваленным с пояснением, реальный вызов не выполняется — как на бою.

## 107.3 Настройка «Не считать таймаут отказом защиты»

**Модель.** `nodes.breaker_ignore_timeouts BOOLEAN NOT NULL DEFAULT false`;
`domain.Node.BreakerIgnoreTimeouts`. Применяется ко всем типам узлов: брейкер общий для sync,
async, повторов из DLQ и pull-узлов (§81).

**Какой таймаут не считается.** Только **таймаут при установленном соединении**: получатель
принял запрос, но не ответил (или не дочитался ответ) за `timeout_ms`. Признак —
`httptrace.ClientTrace.GotConn` сработал до ошибки, а ошибка — `context.DeadlineExceeded` (в том
числе при чтении тела). `httpclient` оборачивает такую ошибку sentinel'ом
`port.ErrResponseTimeout`, сохраняя цепочку (`%w: %w`) — `failureReason`, `504` клиенту и
`out.Timeout` не меняются.

**Какие отказы по-прежнему считаются** — ровно то, что §80.5 п. 2 требует оставить быстрым
сигналом «получателя нет»: отказ соединения, DNS, TLS и **таймаут установки соединения**
(`Dialer.Timeout` в Go тоже даёт `DeadlineExceeded`, но `GotConn` при нём не срабатывает), а также
ответы 5xx.

**Вердикт.** `classifyUpstream` получает флаг узла. После проверки смерти родительского контекста
(§81.2 — она остаётся первой): `errors.Is(err, port.ErrResponseTimeout) && флаг` →
**воздержание** (`voteAbstain`): ни `RecordFailure`, ни `RecordSuccess`. Успехом таймаут не
считается намеренно — иначе он обнулял бы счёт настоящих отказов соединения. `Debug` в
`voteBreaker` фиксирует, что таймаут не учтён по настройке узла.

**Чего флаг не меняет** (решение заказчика): статус узла на рабочем столе (бейдж §52, gauge §41),
строку лога (`upstream_timeout`), ответ клиенту (`504`), повторы по `retry_count`, DLQ для
async. Медленный получатель остаётся виден как медленный — флаг лишь не даёт медленности закрыть
доставку остальным запросам.

**Доставка флага.**

- sync: Receiver кладёт `node.BreakerIgnoreTimeouts` в `SendRequest.breaker_ignore_timeouts = 34`,
  gRPC-адаптер Sender'а — в `SendInput`;
- async, DLQ, отложенный топик, pull: Sender читает узел из БД на каждое сообщение (`nodepg`).

Двухзначный флаг, а не «вес» 0…1 из формулировки §80.5: реальные случаи — «медленность — норма
для этого узла» и «нет». Промежуточный вес ни один разбор не потребовал.

## 107.4 Интерфейс

Форма узла, карточка «Маршрут» — переключатель после «Входящего метода», только у `request` с
входящим `ANY` или `GET`. Смена типа или метода скрывает переключатель, и в сохранение флаг уходит
выключенным, без записи «сброшено несовместимое поле» в аудите:

```
┌ Маршрут ───────────────────────────────────────────────┐
│ Тип метода   (•) request ( ) requestAsync ( ) RabbitMQ │
│ Путь узла    [mcp-1c-vika_dev5                ]        │
│ Входящий метод  [ANY ▾]                          (i)   │
│ [━◯] Не открывать поток (SSE) на GET             (i)   │ ← §107
│      Подписка GET с Accept: text/event-stream сразу    │
│      получает 405 «потока нет». Нужно MCP-серверам:    │
│      nexus не передаёт бесконечные потоки.             │
│ Состояние    [▶ | ⏸ | ⏹]                               │
└────────────────────────────────────────────────────────┘
```

Карточка «Куда перенаправить» — переключатель у всех типов, под полями защиты:

```
│ Таймаут, мс [300000]          Повторы [0]              │
│ Порог отказов защиты [ ]      Пауза до пробы, с [ ]    │
│ [━◯] Не считать таймаут отказом защиты           (i)   │ ← §107
│      Получатель принял запрос, но не ответил за        │
│      таймаут — защита не открывается. Отказ            │
│      соединения, DNS и TLS по-прежнему считаются.      │
```

Вкладка «Настройки» узла (просмотр) — строки только при включённом флаге:

```
Входящий метод        [ANY]
Поток SSE на GET      отклоняется (405)              ← §107
Исходящий метод       [ANY]
Таймаут / повторы     300000 мс / 0
Таймаут и защита      не открывает защиту            ← §107
```

## 107.5 Выкат и откат

- **Порядок: Receiver → Sender → Web.** Миграцию `0043` применяют Receiver и Web на старте, Sender
  не мигрирует сам — а новый Sender читает колонку `breaker_ignore_timeouts` в async-пути и упал бы
  на старой схеме. Старый Sender поле `34` игнорирует: флаг не действует, пока Sender не обновлён.
- Кеш узлов Redis хранит `domain.Node` целиком (JSON без тегов). Записи без новых полей читаются
  как `false` — хук `UnmarshalJSON` не нужен (оба флага по умолчанию выключены).
- **Откат:** 1 миграция; `down` удаляет обе колонки — значения флагов теряются, поведение
  возвращается к прежнему (подписка висит до таймаута, таймаут открывает брейкер).
- **После выката на бою:** включить SSE-флаг на шести MCP-узлах команды `mcp` и вернуть порог
  брейкера к значению по умолчанию (временная мера 23.09 — порог 100).

## 107.6 Попутно: кеш узла в Receiver терял поля входящей авторизации

Выборка узла из PostgreSQL в Receiver (`nodecache/reader.go`, промах Redis) не читала
`incoming_auth_dynamic_source` и `incoming_auth_dynamic_field`. Промах случается после каждого
сохранения узла: Receiver по событию инвалидации удаляет ключ Redis, следующий запрос читает
PostgreSQL. Узел с входящей авторизацией по query-параметру после этого искал токен в заголовке
`Authorization` (значения по умолчанию), а write-back закреплял урезанный узел в Redis — истечение
TTL не лечило, следующий промах давал то же самое. Это второй случай того
же класса: в §81.9 так же забыли колонки брейкера, и sync-путь слал нули.

Исправлено вместе с тестом-сторожем: узел со всеми полями не по умолчанию пишется через Web-репозиторий
и читается выборкой Receiver; сравниваются все поля `domain.Node`, кроме явного списка
исключений с причинами (поля, которые Receiver не использует). Новая колонка, забытая в выборке
Receiver, валит тест.

## 107.7 Вне рамок

- Несколько входящих/исходящих методов на узле — рассмотрено и снято: не покрывает подстановку
  GET→POST без усложнения до таблицы соответствий.
- Потоковая передача SSE без накопления (server-streaming gRPC, запись частями, таймаут простоя,
  `proxy_buffering off`) — отдельное большое ТЗ, только если появится получатель, реально
  присылающий уведомления.
- Вес таймаута 0…1 и глобальный уровень флага в «Настройки → Общие» (§98.5) — только флаг узла.
- Влияние флага таймаута на статус узла (бейдж, gauge).
- `POST 400` на пробе `server/discover` — честный ответ получателя, уходит обновлением MCP-серверов.
