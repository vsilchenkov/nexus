## 44. Счётчики дашборда: согласование, настройки периода/автообновления, диагностика

Раздел вводит согласование счётчиков рабочего стола (Overview) и смежные UX-доработки. Поводом стал
боевой баг: KPI в **шапке** не сходились с суммой по **таблице узлов** даже при одном периоде (24ч),
потому что считались из разных источников разными единицами.

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). Анализ боевого инстанса по этим
счётчикам — скил `.claude/skills/nexus-prod`.

### 44.A Унификация счётчиков шапки (главный фикс)

**Проблема.** Шапка считала **попытки** из Prometheus (`increase(nexus_requests_total[86400s])`,
жёстко 24ч): ретраи async раздували исходящие, поэтому возможно `outgoing > incoming`. Таблица
считала **уникальные запросы** из ClickHouse (`In=countDistinct(ID)`, `Out=uniqExactIf(ID,done=1)`,
`Errors=In−Out`, всегда `Out ≤ In`). Знак отношения был обратным → две несопоставимые системы.

**Решение.** Шапка = **Σ строк таблицы** за **выбранный** период, из того же источника (ClickHouse,
уникальные запросы). `error_rate = errors/incoming` (доля недоставленных от входящих). Очередь Kafka
остаётся из Prometheus (мгновенный lag — только там).

- `MetricsUsecase.NodesOverview` возвращает `Totals` (Incoming/Outgoing/Errors/ErrorRate) = сумма
  `Items`; считается и в CH-, и в Prometheus-fallback-ветке → инвариант «шапка = Σ таблицы»
  выполняется в любом режиме и за любой период.
- `MetricsUsecase.Overview` урезан до `kafka_queue` + `prometheus_available`.
- `GET /api/metrics/nodes` отдаёт `totals`; фронт берёт incoming/outgoing/errors оттуда (период в
  ярлыке карточек), Kafka — из `/api/metrics/overview`.

### 44.B Дефолтный период 24ч + настройка «под себя»

`defaultPeriod` = 24ч (было 1ч). На рабочем столе пользователь сохраняет любой пресет как свой
дефолт (кнопка «По умолчанию»), активный дефолт подсвечен. Произвольный календарный диапазон
дефолтом не сохраняется.

> **Изменено в §71.** Дефолт переехал из `localStorage` (`nexus.overview.period`, один ключ на
> браузер) на сервер и стал **своим у каждой команды**: при переключении команды применяется её
> дефолт. Прежнее значение разово мигрирует в глобальный преф пользователя. См.
> [71-user-preferences.md](71-user-preferences.md).

### 44.C Автообновление: тоггл паузы + интервал в конфиг

Рабочий стол автообновлялся (12с хардкод). Добавлены: кнопка play/pause (персист
`nexus.overview.autorefresh`), и интервал вынесен в `app_settings.general.metrics_refetch_ms`
(1..120с, дефолт 12с), отдаётся всем авторизованным в `/api/settings/public`, настраивается в
`Settings → General`. Дашборд и страницы узлов берут его (`useMetricsRefetchMs`).

### 44.D Процент ошибок по каждому узлу

Рядом со счётчиком «Ошибки» в таблице и карточках узлов — доля `errors/in` (как в шапке). Если
ошибок нет (или нет входящих) — процент не выводится.

> **Отменено в §47.3.** Per-node процент ошибок (`nodeErrPct`) убран из карточек и таблицы узлов
> Overview («сливается» с числом ошибок). Общий процент ошибок в шапке дашборда (§44.A,
> `error_rate`) сохранён. См. [47-logs-filter-refinements.md](47-logs-filter-refinements.md).

### 44.E Диагностический reconciliation API

`GET /api/metrics/diagnostics?range=…|from/to` (scope `metrics:read`) отдаёт обе стороны рядом —
Prometheus (попытки) и ClickHouse (уникальные) + per-node-сверку (включая узлы, видимые только в
Prometheus). Объясняет расхождения: ретраи (`outgoing>incoming` у Prometheus), занижение `increase`,
разное определение ошибки (CH «не доставлено» включает 3xx/висящие). Используется скилом
`nexus-prod`.

### 44.J Дата к времени в логах и «последних запросах»

В таблице логов и блоке «последние запросы» узла время дополнено датой: компактный формат
`DD.MM.YY HH:MM:SS` (24ч, год двузначный) одной строкой, `whitespace-nowrap` — разметка колонок не
едет (URL по-прежнему truncate). Хелпер `fmtLogTs` (детерминированный, фиксированная ширина).

### 44.K Производительность и стабильность UI

- **Потолок бесконечного скролла логов.** Без виртуализации неограниченный append вешал вкладку на
  узлах с сотнями тысяч логов. Введён потолок накапливаемых строк (`MAX_INFINITE_ROWS=1000`,
  `LogsTab.tsx`): по достижении подгрузка вниз останавливается, показывается подсказка
  `logs.cap_reached` (сузить период/фильтр).
- **Список логов не читает тела из ClickHouse.** `Search`/`ListSince` используют `listCols`
  (`'' AS request/response`) вместо `selectCols` — тела в списке не показываются (ленивы, §42), и
  CH больше не читает/не гоняет body-колонки для каждой строки страницы (на бою с большими телами
  это и тормозило пагинацию). Контентный поиск (`q`) по-прежнему фильтрует по реальным телам в WHERE;
  тело строки тянется при разворачивании через `GetByIDPreview`.
- **Постоянная высота KPI-счётчиков шапки.** Строка `delta` (процент) в `Kpi` резервируется всегда
  (nbsp-плейсхолдер) — карточка не подрастает при дозагрузке цифр, интерфейс не прыгает.

### 44.G Колонка «Команды» в списке пользователей

В `Settings → Users` — колонка с чипами команд каждого пользователя: дефолтная помечена; если
`default_team_id` не входит в членства — warn-чип «⚠ default» (подсвечивает рассинхрон, ту же
ситуацию, что чинит §18.9). Членства тянутся батч-запросом `TeamRepo.ListTeamsByUsers` (без N+1).

### 44.H / Sentry-фикс — смежные правки в составе ТЗ

- **Скоупинг команды при входе** (боевой баг p.nikonov): `current_team_id` сессии резолвится по
  фактическому членству, а не слепо из `default_team_id`. Подробности — §18.9.
- **Невалидный UUID в `:id` → 404, не 500** (Sentry `NEXUS-7`): репозитории трактуют pg `22P02`
  (не-UUID в `$1::uuid`) как not-found. Касается `/api/nodes/{id}/…`, `/api/users/{id}`,
  `/api/teams/{id}`.

### 44.L Режим подсчёта уникальных: точно / приблизительно (перф дашборда)

**Проблема.** Счётчики (§44.A) и KPI узлов считают уникальные запросы точным `countDistinct(ID)`
(= `uniqExact`, полный хэш-сет ID). `NodesOverview` гоняет `NodeKPI` **на каждый узел команды**; за
большой период (30д) на узлах/командах с большим объёмом точный distinct упирает ClickHouse в 100% CPU
и рабочий стол грузится секунды (на стенде: 171 узел, 30д ≈ 7с). Лишнего из CH при этом не тянется
(только агрегаты, без тел) — дорог сам точный distinct по всем строкам окна.

**Решение.** Настройка `app_settings.general.metrics_approx_counts` (bool, **дефолт false = точно**):

- `false` — `countDistinct`/`uniqExactIf` (точно, как было);
- `true` — `uniq`/`uniqIf` (HyperLogLog: **приблизительно**, ошибка ~0.3%, но в ~3× дешевле по CPU;
  на стенде 30д 7с → 2.5с). Инвариант «шапка = Σ строк таблицы» сохраняется в обоих режимах (обе
  стороны из одной агрегации); guard `delivered ≤ total` остаётся (HLL может слегка превысить).

Переключатель — в `Settings → General` (admin), применяется на лету (hot-reload app_settings, читается
per-request в `MetricsUsecase`). Оператор включает приблизительный режим, когда узлов/данных много.
Режим — общий для дашборда и страницы узла (KPI). Прокинут параметром `approx` в
`NodeLogMetrics.NodeKPI` (адаптер выбирает функцию агрегации), usecase читает настройку и передаёт.
