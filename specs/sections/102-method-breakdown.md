# 102. Запросы по методам: рейтинг подпутей на вкладке «Метрики»

Раздел отвечает на вопрос, который сегодня на странице узла не задать: **сколько запросов пришло на
каждый метод**. У passthrough-узла ([§39](39-path-passthrough.md)) один узел обслуживает десятки
подпутей и пишет их все в одну ClickHouse-таблицу, а вкладка «Метрики» показывает одно суммарное
«Всего» и один график.

Развивает [§21](21-node-detail.md) (вкладка «Метрики»), [§39](39-path-passthrough.md) (колонка
`method` = подпуть), [§33.4](33-chart-tooltips.md) (клик по графику → журнал),
[§48](48-logs-advanced-filters.md) (фильтр по методу), [§79.4/§79.5](79-failed-unit-node-tab-metrics.md)
(фильтры и единица счёта столбцов), [§84.5](84-node-observability.md) (второй график под трафиком),
[§100](100-click-targets.md) (природа навигационных элементов). Карта реализации —
[../IMPLEMENTATION.md](../IMPLEMENTATION.md).

**Миграций раздел не требует** — используется существующая колонка ClickHouse `method`.

## 102.1 Диагноз: разбивки нет ни на одном экране

`method` заполняется хвостом пути при `path_passthrough` (§39.4): один узел `dadata` принимает и
`suggestions/api/4_1/rs/suggest/address`, и `api/v2/clean/address`, и ещё десяток подпутей. Для шины
это один узел — одна конфигурация, один target, одна таблица логов. Для человека это разные
интеграции с разной нагрузкой и разным здоровьем.

Что есть сегодня:

| Экран | Что отвечает | Чего не отвечает |
|---|---|---|
| «Метрики», KPI | сколько всего запросов у узла | сколько у каждого метода |
| «Метрики», график «Запросы» | когда шёл трафик | какой метод его дал |
| «Логи», фильтр «Метод» (§48.4) | сколько у ОДНОГО метода (счётчик «из M») | сравнить методы между собой |

Единственный способ получить картину — открыть журнал и перебрать методы комбобоксом по одному,
выписывая счётчики на бумажку. Список значений для комбобокса при этом уже считается
(`GET /nodes/{id}/logs/methods`, `DISTINCT method` до 200 значений), то есть данные для рейтинга в
системе есть — не хватает только агрегата.

## 102.2 Форма: рейтинг, а не стопка по времени

Рассматривались три формы. Выбран **горизонтальный рейтинг** — строка на метод, длина полосы
пропорциональна числу запросов, сортировка по убыванию:

| Форма | Почему не она |
|---|---|
| Стопка по времени (те же столбцы, что у «Запросы», сегменты — методы) | Отвечает на «когда какой метод шёл», а спрошено «сколько какого». Восемь цветов в легенде с именами по 40–120 символов нечитаемы, а запрос дорожает до `GROUP BY (интервал, метод)` со взрывом кардинальности |
| Кольцо (donut) с легендой | Не даёт сравнить близкие доли и не показывает абсолютные числа без чтения легенды; длинные имена всё равно уезжают в легенду |
| **Горизонтальный рейтинг** | Сравнение — длиной полосы (единственное кодирование, которое глаз читает точно); имя метода получает целую строку, а не подпись оси; один дешёвый `GROUP BY method` |

Рейтинг устроен как график трафика: синий сегмент — доставлено, красный — ошибки (те же токены
`accent`/`err`, та же пара «доставлено/ошибки», что в KPI и тултипе §33).

**Показывается топ-8**, остальные свёрнуты в строку **«Остальные»**; кнопка «Показать ещё»
раскрывает до 20 строк, она же в раскрытом виде становится «Свернуть» (двадцать строк вытесняют
латентность и ёмкость за край экрана, и вернуться к восьми должно быть чем, кроме перезагрузки
страницы; «Свернуть» не предлагается, когда сворачивать нечего). Числа выбраны так: 8 строк +
«Остальные» ≈ 240 px — сопоставимо с высотой графика «Запросы» (180 px), карточка не оттесняет
латентность и ёмкость за пределы экрана. Если свернуть осталось РОВНО один метод, он показывается
сам, а не строкой «Остальные · 1 метод» — свёртка одного элемента только прячет имя, ничего не
экономя.

## 102.3 Единица счёта и арифметика «Остальных»

**Единица — ЗАПИСЬ**, а не строка таблицы: та же единица, что у KPI «Всего» и у графика трафика
(§79.5). Доля метода считается от `kpi.total`.

Разбивка — одна одностадийная агрегация тем же выражением, что считает KPI
(`uniqueExprs`: `countDistinct(ID)` / `uniqExactIf(ID, done = 1)`, либо HLL-пара в приблизительном
режиме §44-perf), с тем же `WHERE` (общий `searchConds`, то есть те же фильтры §79.4):

```sql
SELECT method, <total>, <delivered>
FROM <таблица> WHERE <фильтры>
GROUP BY method ORDER BY total DESC, method ASC LIMIT <20+1>
```

**Двухстадийная свёртка `GROUP BY ID` (как у графика трафика в точном режиме) здесь не нужна.** Она
существует, чтобы привязать запись к интервалу её ПЕРВОГО прогона; у рейтинга интервалов нет,
привязывать не к чему. Отсюда прямое следствие, которое надо знать при чтении экрана: **деградация
§79.5.1 (`chart_unit=attempts`) на рейтинг не распространяется** — соседний график может перейти на
счёт по прогонам, рейтинг остаётся по записям. Расхождение единиц на одной карточке названо в
подсказке.

Стоимость разбивки равна стоимости уже безусловно выполняемого `NodeKPI`: то же множество строк, те
же выражения, разложенные по группам. (Соблазнительный аргумент «`method` — третья компонента
`ORDER BY` таблицы, значит агрегация идёт по порядку ключа» неверен: это не префикс ключа, а у
внешней таблицы §64 ключ вообще чужой.)

**Строку «Остальные» считает клиент** из того же снимка ответа:

```
Остальные.total     = kpi.total     − Σ(показанных методов)
Остальные.delivered = kpi.delivered − Σ(показанных)
свёрнуто методов    = methods.length − показано   (+ «+», если список усечён)
```

Это возможно ровно потому, что `Σ(по всем методам) == kpi.total`: одно и то же выражение, разбитое
по `method`. Инвариант держится, пока у каждой записи (`ID`) одно значение `method`, а так и есть:
`method` фиксируется при построении записи один раз, повторы и финализация DLQ переиспользуют тот же
конверт, а replay создаёт НОВУЮ запись с новым `ID`.

Где инвариант всё-таки может дать перекос — и что тогда видно на экране:

| Случай | Эффект | Поведение |
|---|---|---|
| Внешняя таблица §64: пишет чужой сервис, гарантий «один `ID` — один `method`» нет | Σ может превысить `kpi.total` | «Остальные» ≤ 0 → строка **не рисуется** |
| Приблизительный счёт (HLL): сумма оценок по группам ≠ оценке по всему множеству, ±0,3 % в любую сторону | то же | то же, плюс кламп «доставлено ≤ всего» в каждой строке |
| Батч-писатель долил строки между запросом KPI и запросом разбивки | то же | то же |
| Правила маскирования §95 поменялись внутри окна | один логический метод расщеплён на две строки рейтинга | не лечится кодом, названо здесь |

Нулевая строка «Остальные» рядом с пометкой «есть ещё методы» была бы прямой ложью на экране —
поэтому при неположительном остатке строки нет вовсе.

## 102.4 Контракт API

Разбивка живёт в **существующем** `GET /api/metrics/nodes/{id}` и включается флагом
`with_methods=1`. Не отдельный эндпоинт — по двум причинам:

1. арифметика «Остальных» вычитает из `kpi.total`, то есть рейтинг и KPI обязаны быть **одним
   снимком**; два запроса дали бы два окна и «Остальные» с плавающим знаком;
2. клиент держит последний удачный снимок целиком (`useStableData`), и «залипшая» карточка остаётся
   внутренне согласованной.

Флаг, а не безусловный расчёт, — потому что тот же эндпоинт обслуживает вкладку «Обзор», которой
разбивка не нужна, и внешних потребителей со scope `metrics:read`.

Новые поля ответа:

| Поле | Смысл |
|---|---|
| `methods` | `[{method, total, delivered}]`, до 20 строк, по убыванию `total`; всегда массив, не `null` |
| `methods_available` | источник ответил; `false` — карточка сообщает о недоступности, остальная вкладка живёт |
| `methods_truncated` | методов больше, чем помещается в ответ (см. ниже) |

`methods_truncated` определяется запросом `LIMIT limit+1` и отбрасыванием лишней строки. Признак
«вернулось ровно `limit` строк» не годится: при РОВНО двадцати методах он объявил бы несуществующий
хвост, и на экране появилось бы «Остальные · 12+ методов» при полностью показанном списке.

Размер выдачи — константа сервера (20), а не параметр запроса: иначе потребитель с
`metrics:read` попросит сто тысяч групп.

## 102.5 UI карточки

Карточка «Запросы по методам» стоит **под графиком «Запросы»**, над ёмкостью и латентностью.

```
┌ Запросы по методам ─────────────────────────────── ⓘ ┐
│ suggestions/…/rs/suggest/address                     │
│ ███████████████████████████████▌            12 480   │
│ suggestions/…/rs/findById/party                      │
│ ██████████▏                                  4 213   │
│ api/4_1/rs/geolocate/address                         │
│ ████▊                                        1 902   │
│ …                                                    │
│ Остальные · 27 методов                               │
│ ▓▓▏                                            940   │
│                  [ Показать ещё ] / [ Свернуть ]     │
└──────────────────────────────────────────────────────┘
```

**Сокращение имени — в СЕРЕДИНЕ.** Методы одного узла различаются хвостом
(`…/findById/address` против `…/findById/party`), поэтому обрезание конца прячет ровно то, что
отличает строки друг от друга. Сокращение считается посимвольно в моноширинном шрифте, а не
CSS-классом `truncate`: у символьного правила есть тест, у раскладки в jsdom тестов быть не может
(урок §100).

**При наведении** — тултип §33 с ПОЛНЫМ именем (переносится, не обрезается), числом запросов, долей
от всех, разбивкой «доставлено/ошибок» и подсказкой действия «Открыть журнал по методу».

**Строка с пустым `method`** (обычный узел, записи до §39) подписана «(без подпути)» и
**ссылкой не является** — см. 102.6.

**Нечего ранжировать — карточки нет вовсе**, ни пустой, ни с объяснением. Подсказка на месте
рейтинга («разбивки нет», «узел не проксирует подпути») сообщала бы только о самом себе и занимала
место ровно там, где у passthrough-узла стоят данные, — а на обычном узле висела бы всегда.

| Состояние | Что показано |
|---|---|
| У узла нет ClickHouse-таблицы (`chart_available=false`) | карточки нет — сверху уже висит общая подсказка «логирование не настроено» |
| Меньше двух групп: один метод на весь период либо метод пуст у всех записей (обычный узел) | карточки нет — сравнивать не с чем |
| Активен фильтр «Метод» на этой же вкладке | карточки нет — под фильтром рейтинг вырождается в одну строку со 100 % |
| `methods_available=false` (внешняя таблица §64 без колонки `method`, отказ разбивки) | карточки нет; KPI, график трафика и латентность остаются, причина уходит в лог (DBG, см. 102.7) |
| Две группы и больше | рейтинг |
| График выше деградировал до попыток (`chart_unit=attempts`, §79.5.1) | рейтинг рисуется как обычно (он всегда по записям) + предупреждение о расхождении единиц: суммы полос сойдутся с «Всего», но не с высотами столбцов |

## 102.6 Клик по строке: журнал за тот же период и по тому же методу

Строка — **настоящая ссылка** (`<a href>`), а не кнопка с обработчиком: у неё есть адрес, значит
работают контекстное меню «Открыть в новой вкладке», Ctrl+клик и средняя кнопка мыши (§100.2).
Кнопка «Показать ещё» / «Свернуть» адреса не имеет и остаётся кнопкой — и стоит ВНЕ строк-ссылок
(интерактив не вкладывается в интерактив).

Ссылка ведёт на вкладку «Логи» этого узла с окном текущего периода метрик и фильтром по методу.

**Для этого расширяется контракт дип-линка журнала.** Сегодня при переходе «график → журнал»
переносятся только `from/to/status/done`, а расширенные фильтры вкладки «Метрики» (§79.4:
полнотекстовый запрос с его режимами и хост клиента) — нет. Тултип посчитан ПОД ними, поэтому
ссылка, ведущая в журнал без них, обещает одно число, а показывает другое. Контракт дополняется
ключами `method`, `q`, `q_case`, `q_word`, `q_regex`, `client_host`; вкладка «Логи» подставляет их в
форму и раскрывает панель расширенных фильтров. Побочно это закрывает ту же дыру у клика по столбцу
графика (§33.4), где она существует с самого начала.

Обратная сторона: новые ключи обязаны **явно вычищаться** переходами, которые их не задают
(«Очередь → Логи» §35), иначе пересланный адрес утащит в журнал чужой фильтр.

**Строка «(без подпути)» ссылкой не делается**: пустое значение фильтра в параметры не попадает, и
такая ссылка открыла бы журнал вообще без фильтра — то есть показала бы ВСЕ записи под видом
«записей без подпути». Отдельный серверный фильтр «метод пуст» в раздел не входит (см. 102.8).

## 102.7 Цена и деградации

Карточка добавляет **третий** конкурентный запрос к ClickHouse на вкладке «Метрики» (после
§84.5 их было два: трафик и латентность) и уходит на каждом цикле авто-обновления (~12 с).
Защита от того, чтобы разбивка утянула за собой всю вкладку:

- у запроса разбивки **свой под-таймаут** внутри общего бюджета вкладки: медленная разбивка не
  съедает время графика трафика, без которого вкладка бесполезна;
- её ошибка **не каскадит** — гасится только карточка (`methods_available=false`);
- `approx` (точный/приблизительный счёт) читается **один раз на запрос**: KPI и разбивка обязаны
  считаться одним и тем же выражением, иначе «Остальные» поедут на переключении настройки.

**Штатные деградации, а не «не должно случиться»:**

- **кардинальность `method` не ограничена.** В подпуть попадают идентификаторы
  (`.../orders/12345`), поэтому на окне 30 суток групп могут быть миллионы, и запрос имеет право
  упереться в лимит памяти ClickHouse. Результат — `methods_available=false` и подсказка; вкладка
  продолжает работать;
- **у внешней таблицы §64 может не быть колонки `method`.** Это не авария инсталляции, а чужая
  схема: событие логируется на уровне debug (как уже сделано для `client_host`), а не предупреждением
  на каждый двенадцатисекундный поллинг.

**Границы защиты — чего раздел НЕ делает:** не нормализует пути (два адреса, различающиеся
идентификатором, остаются разными методами); не чинит расщепление метода сменой правил маскирования
§95; не даёт разбивку за пределами выбранного периода; не показывает методы, у которых в окне нет
ни одной записи.

## 102.8 Вне рамок раздела

- **p95/p99 по методам.** Единица перцентилей — ПОПЫТКА (§79.5), у рейтинга — ЗАПИСЬ; смешивать их
  в одной карточке нельзя, а отдельный проход по строкам — ещё один запрос.
- **Методы во времени** (стопка или линии по интервалам) — `GROUP BY (интервал, метод)` с отбором
  top-N внутри каждого интервала, отдельный разговор про кардинальность.
- **Разбивка по `http_method`** (GET/POST/…) — другая колонка и другой вопрос.
- **Нормализация путей** (`/orders/12345` → `/orders/{id}`) — лечит кардинальность, но требует
  правил на узел.
- **Серверный фильтр «метод пуст»** — нужен, чтобы строка «(без подпути)» стала ссылкой.
- **Кросс-узловой топ методов** на рабочем столе, экспорт рейтинга, сортировка по ошибкам вместо
  числа запросов, запоминание «Показать ещё» в персональных настройках (§71).
