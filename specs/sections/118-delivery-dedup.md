# 118. Дедупликация доставки: анализ, сквозной `X-Nexus-Id`, мягкая остановка Sender

Раздел отвечает на вопрос «можно ли дедуплицировать на уровне Nexus без доработок 1С и стоит ли».
Он фиксирует, где шина сама порождает повторную доставку, как ту же задачу решают другие системы,
какие есть варианты, и реализует два из них:

- **Д1** — сквозной заголовок `X-Nexus-Id` к получателю;
- **Д2** — мягкая остановка Sender: деплой больше не обрывает доставку посреди запроса.

Остальные варианты (Д3–Д5) описаны как предложение. Их делать после замера на бою (118.11).

Развивает [§3.6](03-receiver.md) (обещание «стабильного `id` в конверте»),
[§27.4/§27.14](27-rabbitmq-async.md) (at-least-once RabbitMQAsync), [§16](16-out-of-scope.md)
(exactly-once вне рамок), [§30](30-logging-panic-recovery.md) (`request_id`), [§36](36-dlq-reprocessor.md)
(DLQ-репроцессор), [§83](83-async-ack-template.md) (`X-Nexus-Id` в ответе клиенту),
[§85](85-replay-from-logs.md) (повторы из логов), [§93](93-ha-replicas.md) (две реплики),
[§109](109-sender-restart-resilience.md) (рестарт Sender, sync), [§113](113-paused-sweep-honest-queue.md)
и [§114](114-kafka-commit-stuck-and-monitor.md) (передоставка после сбоев commit).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций нет, ключей
`config.yml` нет.** Выкатываются Sender (Д1, Д2) и Receiver (исправление `msgID` у RabbitMQAsync).

## 118.1 Повод

Асинхронная доставка — at-least-once. ТЗ перекладывает идемпотентность на получателя: §3.6 —
«дедупликации в шине нет — идемпотентность на стороне приёмника, для этого в конверте есть
стабильный `id`». Но **конверт до получателя не доходит.** Sender отправлял только пробрасываемые
заголовки клиента, `Content-Type`, `X-Nexus-Hops` и `Authorization`. Получатель (как правило, 1С)
не получал ни одного идентификатора Nexus, поэтому дедуплицировать ему было нечем, даже если бы
он захотел. Обещание ТЗ не выполнялось.

## 118.2 Где рождаются повторы — по коду

«ID стабилен» — у повторной доставки тот же ID записи лога (ID конверта).

| Источник | Механизм (до §118) | ID стабилен? |
|---|---|---|
| **Остановка или деплой Sender** | runner отменял контекст приложения ДО `App.Stop`; контекст consumer'а производный — HTTP-запрос к получателю рвался посреди отправки, offset не коммитился, после старта сообщение уходило снова. Получатель (1С) оборванный вызов обычно дорабатывает до конца. Sync при этом получал до `shutdown.timeout_sec` (`GracefulStop`), async — ноль | да |
| Падение процесса между 2xx и commit | перечитывание с последнего committed offset | да |
| Ребаланс двух реплик (§93), пересоздание reader'а, сбой commit (§113.6, §114) | то же | да |
| Таймаут ПОСЛЕ отправки | считается «не доставлено»: ретрай `retry_count` и DLQ. Репроцессор повторяет через ≤ 60 с, затем каждые `dlq_retry_delay_seconds` (5 мин) до `dlq_ttl_seconds` (24 ч). В DLQ уходит **любой** не-2xx, включая 409 «уже обработано» | да |
| Копия до commit (DLQ, топик паузы, republish репроцессора) | падение между копией и commit — две живые копии | да |
| Продюсер Kafka | **не идемпотентен** (118.10): `segmentio/kafka-go` идемпотентного producer'а не умеет, а Writer сам повторяет батч до 10 раз — запись, сохранённая брокером без подтверждения, ложится второй раз | да |
| RabbitMQAsync: `basic.ack` не прошёл | requeue → повторный pull. Без AMQP `message_id` каждый pull — новый UUID | только с `message_id` |
| Клиент переотправил (потерян ответ, 502/504) | новый запрос → новый UUID. 1С копит неотправленное в **растущий** пакет — тело каждый раз другое | нет |
| Повторы из логов (§85, §96, §36.11) | намеренно: новый ID + `__replay_of=<исходный>` в query | — |

## 118.3 Принципиальная граница

Гарантировать «ровно один раз» внешнему HTTP-получателю **только со стороны отправителя нельзя**.
Если связь оборвалась после отправки, отправитель не знает, обработан ли запрос: повторит — может
задвоить, не повторит — может потерять. Отраслевой ответ — at-least-once плюс идемпотентный
получатель («effectively-once»). Exactly-once Kafka (транзакции) работает только для цепочек
«Kafka → обработка → Kafka» и на внешний HTTP не распространяется.

Поэтому шина может:

- не плодить **собственных** повторов (Д2, Д3);
- дать получателю **стабильный ключ** (Д1);
- для исхода «неизвестно» выбрать между повтором и ручным разбором (Д4);
- отсеивать повторы **клиента**, если у них есть ключ (Д5).

## 118.4 Как это делают другие

| Система | Механизм | Ключ, окно |
|---|---|---|
| AWS SQS FIFO | дедупликация при приёме в очередь | `MessageDeduplicationId` или SHA-256 тела; 5 мин |
| Azure Service Bus | duplicate detection | `MessageId`; от 20 с до 7 сут (по умолчанию 10 мин) |
| NATS JetStream | дедупликация при публикации | заголовок `Nats-Msg-Id`; окно потока (минуты) |
| Kafka | идемпотентный producer — только повторы самого producer'а; транзакции — только внутри Kafka | PID + sequence |
| Apache Camel, Spring Integration, MuleSoft | Idempotent Consumer: репозиторий ID (память, JDBC, Redis), выражение ключа, «до или после обработки» (`eager`, `removeOnFailure`) | выражение; TTL репозитория |
| microservices.io — Idempotent Consumer / Inbox | таблица обработанных ID в транзакции потребителя | ID сообщения |
| Standard Webhooks (Svix, Zapier, Twilio), GitHub, Shopify | отправитель шлёт ID доставки (`webhook-id`), одинаковый на всех повторах; дедуплицирует получатель | ID доставки |
| Stripe, ЮKassa, IETF draft `Idempotency-Key` | ключ в заголовке, сервер помнит результат и отдаёт его на повтор | ключ; 24 ч |
| Envoy, gRPC | автоповтор только если запрос гарантированно не ушёл (`reset-before-request`, transparent retry) | — |

Для шины, доставляющей по HTTP (по сути — вебхуки), мейнстрим такой: **стабильный ID доставки в
заголовке + не порождать собственных повторов**. Дедупликация на входе по содержимому — нишевая и
включается точечно.

## 118.5 Варианты без доработок 1С

| # | Что | Цена | Что закрывает |
|---|---|---|---|
| **Д1** | **сквозной `X-Nexus-Id`** — ID записи лога в заголовке каждого исходящего запроса | малая | сам по себе 1С не меняет, но даёт ей ключ; API с ключом идемпотентности дедуплицируют сразу (с опцией псевдонима, см. Д1+); обещание §3.6 выполняется |
| **Д2** | **мягкая остановка Sender** — доставки в полёте доигрываются до потолка | средняя | самый частый системный источник — повторы на каждом деплое и рестарте, у всех узлов |
| Д3 | журнал доставленных (Idempotent Consumer): Redis `delivered:<node>:<id>` после 2xx, проверка перед доставкой в основном consumer'е, sweeper'е паузы и DLQ-репроцессоре | средняя | ребаланс, сбой commit, падение после 2xx, копии до commit, повторы producer'а; не закрывает таймаут и повтор клиента |
| Д4 | флаг узла «получатель не идемпотентен»: без автоповтора, если запрос ушёл, а исход неизвестен (таймаут после соединения — признак `ErrResponseTimeout` уже есть); такое сообщение — в «Неудачные доставки» с пометкой «исход неизвестен», решение за оператором (повтор §85 есть); 4xx (кроме 408/429) — без повторов по DLQ | средняя | таймауты и бессмысленные повторы 4xx — ценой ручного разбора |
| Д5 | дедупликация на входе по SHA-256 тела или бизнес-ключу (язык путей §83 `${ body.… }`), окно 5 мин – 24 ч; повтор получает тот же ack без постановки в очередь; только opt-in | средняя | только точные повторы; растущие пакеты 1С не ловит; риск ложного срабатывания на законно одинаковых сообщениях |
| Д1+ | опция узла: дублировать `X-Nexus-Id` под именем `Idempotency-Key` или своим (`Idempotence-Key` у ЮKassa) | малая | идемпотентность у API, которые понимают ключ |

## 118.6 Решение

- **Делаем сейчас: Д1 и Д2.** Дёшево, без новых настроек, убирают системный источник повторов и
  выполняют обещание §3.6.
- **Д3 + Д4 — после замера (118.11) и только одним флагом узла** («защита от повторной доставки»)
  у 1С-получателей, где повтор дорог (пример — 15 повторов в `acc_kz`, §79).
- **Д5 — не рекомендуется**: 1С шлёт растущие пакеты, хеш тела их не склеит. Кэш ответов в стиле
  Stripe для sync — тяжело и не нужно.
- **Д1+** — по запросу, когда появится получатель с поддержкой ключа идемпотентности.

## 118.7 Д1 — сквозной `X-Nexus-Id`

**Контракт.** Каждый исходящий запрос Sender'а к получателю несёт заголовок `X-Nexus-Id`:

- значение — ID записи лога ClickHouse (колонка `ID`) этой доставки: по нему получатель находит
  запись в «Логах» узла, а оператор — запрос в журнале получателя;
- async: ID конверта; **одинаков** на всех in-process повторах (`retry_count`), на повторах
  DLQ-репроцессора, после передоставки Kafka (рестарт, ребаланс) и после снятия паузы;
- sync: ID вызова; одинаков на in-process повторах. Повтор клиента — новый вызов и новый ID;
- RabbitMQAsync: AMQP `message_id`, если его задал издатель, иначе UUID на каждый pull. До §118
  `msgID()` вызывался дважды, и ID в заголовке Kafka не совпадал с ID конверта — исправлено;
- повтор из логов (§85, §96, §36.11) — новая доставка с **новым** `X-Nexus-Id` (иначе получатель,
  дедуплицирующий по ключу, проглотил бы намеренный повтор); связь с исходной — `__replay_of` в query;
- одноимённый заголовок клиента (если узел его пробрасывает) **перезаписывается** значением шины.

То же имя Nexus уже отдаёт клиенту в ответе по шаблону §83 — один ID проходит путь «клиент →
шина → получатель».

**Почему не `Idempotency-Key`.** С заголовком `Idempotency-Key` или `X-Idempotency-Key` `net/http`
считает POST повторяемым (тело собрано из `bytes.Reader`, есть `GetBody`). Транспорт тогда сам
переотправляет запрос на переиспользованном соединении, если ошибка чтения случилась до первого
байта ответа, то есть **уже после** отправки. Для получателя, который ключ не понимает (1С), это
добавочный источник повторов. Псевдоним под этим именем — только по опции узла (Д1+), для
получателей, которые ключ понимают.

**Как 1С может этим воспользоваться** (вне рамок Nexus, для справки команде 1С). Регистр сведений
«Обработанные сообщения шины» с измерением «ИдентификаторСообщения» (строка 36). В HTTP-сервисе
нужно прочитать заголовок `X-Nexus-Id`, в той же транзакции, что и обработка документа, проверить
и записать ключ. Если запись есть — ответить 200 без повторной обработки. Чистка — регламентным
заданием старше `dlq_ttl` + запас.

## 118.8 Д2 — мягкая остановка Sender

«Перестать брать новое» и «оборвать начатое» — разные сигналы:

- **чтение** (FetchMessage, пауза retry-in-place, тики проходов DLQ-репроцессора и sweeper'а
  паузы) привязано к контексту приложения — runner отменяет его первым, новые сообщения не берутся;
- **доставка** (обработка сообщения, HTTP к получателю, публикация в DLQ или топик паузы, commit
  offset'а) идёт на отвязанном контексте доставки (`context.WithoutCancel` + собственная отмена).
  Его отменяет только `App.Stop` по истечении потолка.

Порядок остановки:

1. `drain`: gRPC-health → NOT_SERVING, пауза `shutdown.drain_sec` (как раньше, §93.5);
2. **одновременно** под одним потолком `shutdown.timeout_sec`: доигрывание async-доставок (основной
   consumer, DLQ-репроцессор, sweeper паузы) и `GracefulStop` gRPC. Параллельно, а не друг за
   другом — общее время остановки не растёт против прежнего (кроме шага 3: до 5 с, только при
   достигнутом потолке);
3. потолок истёк, а доставка ещё идёт → Warn с числом оборванных, отмена контекста доставки
   (прежнее поведение), короткое ожидание выхода;
4. закрытие reader'ов Kafka — **после** выхода горутин: раньше reader закрывался до ожидания, и
   commit доставленного сообщения упал бы;
5. retry-consumer логов CH, фоновые задачи, flush логов в ClickHouse, закрытие producer'а.

Нового ключа конфига нет: потолок — существующий `shutdown.timeout_sec` («потолок ожидания уже
принятых запросов», 30 с). Docker обязан ждать дольше: `stop_grace_period` ≥ `drain_sec` +
`timeout_sec` + 5 с ожидания оборванных доставок + время flush логов (до 15 с). В HA-файле это 45 с; в одиночных compose-файлах ключа не было (дефолт
Docker — 10 с), с §118 он задан всем трём сервисам приложения.

## 118.9 Границы (что НЕ закрыто)

- Доставка дольше потолка (медленный получатель, `timeout_ms` до 600 с) обрывается, как раньше, и
  после старта уходит снова. Получатель должен быть идемпотентным — для этого и есть Д1.
- Ребаланс группы во время дренажа может отклонить commit — сообщение перечитает другая реплика.
- SIGKILL, OOM, падение машины — без изменений (at-least-once).
- Пока реплика дренирует, сообщения её партиций ждут: партиции переходят к другой реплике только
  после выхода из группы. Это не дольше потолка. Reader'ы слотов, уже закончивших доставку, тоже
  держатся до конца самой долгой: закрытие любого из них — ребаланс группы, и commit доставок в
  полёте был бы отклонён (повтор, ради устранения которого дренаж и сделан). Цена — всплеск lag на
  выкате пар §93 до потолка.
- Бюджет `stop_grace_period: 45s` покрывает обычную остановку, но не худший случай: потолок
  достигнут (5 + 30 + 5 с) и ClickHouse медленно принимает сброс логов (до 15 с) — SIGKILL оборвёт
  сброс. Где бывают доставки дольше `timeout_sec`, значение поднимается в локальном override
  (DEPLOYMENT §9.1.12). До §118 одиночный стек в этом месте убивался через 10 с.
- Таймаут после отправки, повтор DLQ по любому не-2xx, повтор клиента, повтор producer'а Kafka — не
  закрыты (Д3–Д5, 118.10).
- Windows-сервис (SCM) ждёт остановки по своим правилам; рабочий путь — Docker.
- `X-Nexus-Id` уходит **всем** получателям, включая сторонние API (Telegram, платёжные шлюзы,
  §39 passthrough). Это случайный UUID v4: сведений о шине, клиенте или теле он не несёт, а по нему
  можно сопоставить запрос с записью лога. Отключения заголовка нет.
- Мягкая остановка опирается на порядок runner'а: контекст приложения (чтение) отменяется до
  `App.Stop`. Если бы `App.Stop` вызвали без этой отмены, DLQ-репроцессор и sweeper паузы читали бы
  дальше до обрыва по потолку — так было и до §118.

## 118.10 Producer Kafka не идемпотентен

Комментарий `NewProducer`, ключи `config.yml` (`retries`, `enable_idempotence`,
`max_in_flight_requests`, `delivery_timeout_ms`) и §5.3/§8/§15 утверждали обратное:
«идемпотентный producer, exactly-once на ретраях». `segmentio/kafka-go` идемпотентного producer'а
не поддерживает, а эти ключи разбираются, но нигде не читаются. Фактически работают
`RequiredAcks=all` и встроенный повтор Writer'а — до 10 попыток. Запись, которую брокер сохранил,
но подтверждение потерялось, ложится второй раз с тем же ID конверта (Д1 и Д3 это покрывают).
С §118 комментарии и ТЗ говорят правду; поведение не меняется. Переход на клиент с идемпотентным
producer'ом (например, franz-go) — отдельное решение, вне рамок.

## 118.11 Замер на бою (до решения по Д3–Д5)

Запросы — к таблице логов узла в ClickHouse (`<db>.<table>`), за 30 дней:

```sql
-- 1. Собственные повторы шины: сообщение доставлено (2xx) больше одного раза.
SELECT node_id, count() AS delivered_more_than_once
FROM (SELECT node_id, ID, countIf(done = 1) AS ok
      FROM <db>.<table> WHERE date_create >= today() - 30
      GROUP BY node_id, ID HAVING ok > 1)
GROUP BY node_id ORDER BY delivered_more_than_once DESC;

-- 2. Повторы клиента: одинаковое тело под разными ID в окне 10 минут
--    (пустое тело исключено — у всех GET одинаковый хеш).
SELECT node_id, sum(n - 1) AS extra_copies
FROM (SELECT node_id, checksum_request, toStartOfTenMinutes(date_request) AS w,
             uniqExact(ID) AS n
      FROM <db>.<table>
      WHERE date_create >= today() - 30 AND done = 1 AND request_size > 0
        AND parameters NOT LIKE '%__replay_of=%'
      GROUP BY node_id, checksum_request, w HAVING n > 1)
GROUP BY node_id ORDER BY extra_copies DESC;

-- 3. Повторы из логов (намеренные).
SELECT node_id, count() FROM <db>.<table>
WHERE date_create >= today() - 30 AND parameters LIKE '%__replay_of=%'
GROUP BY node_id;
```

Если запрос 1 после выката §118 почти пуст, Д3 не нужен. Если велик запрос 2 — смотреть, что шлёт
клиент (Д5 по бизнес-ключу или правка клиента). Таймауты (Д4) видны в «Неудачных доставках».

## 118.12 Проверка

- Unit (Sender): `X-Nexus-Id` = ID на всех in-process попытках, перекрывает клиентский заголовок,
  есть в sync. Остановка во время доставки: доставка доходит до конца и коммитится (регрессия:
  красный на коде до §118); доставка дольше потолка обрывается, остановка укладывается в потолок.
- Unit (Receiver): у RabbitMQAsync без `message_id` ID в заголовке Kafka = ID конверта.
- Integration: медленный получатель, остановка Sender'а во время запроса → у получателя ровно один
  запрос, после рестарта повтора нет; у передоставленного сообщения тот же `X-Nexus-Id`.
- Стенд: эхо-получатель видит `X-Nexus-Id`, равный ID записи лога; рестарт sender посреди медленной
  доставки → один запрос у получателя, в логе Sender'а — дренаж.
