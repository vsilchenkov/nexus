# 60. Перенос узла между командами не должен утаскивать общую таблицу логов

Раздел закрывает дефект переноса узла (§18): таблица логов переезжала в целевую команду
безусловно, хотя её могут делить несколько узлов. Развивает §18 (multi-tenancy, Move),
§19 (шаблоны CH-таблиц), §10.C.2 (нормализация имени таблицы до `<ch_database>.<table>`).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 60.1 Дефект

`Move` выполнял `RENAME TABLE <old> TO <new>` всегда, когда имя таблицы менялось. Логика написана
в предположении «одна таблица — один узел», но `clickhouse_table` — обычное поле конфигурации, и
семейство узлов одного сервиса штатно делит общую таблицу.

Последствие: перенос ОДНОГО узла уносил общую таблицу в БД целевой команды, и все остальные узлы
оставались со ссылкой на несуществующую таблицу. Логирование у них ломалось молча — ошибка
всплывала только в фоне: `code: 60, Unknown table expression identifier 'nexus_default.<table>'`.

Поймано на тестовом стенде: перенос одного узла из 176, делящих `nexus_default.loadtest`,
обезглавил остальные 175.

Второй, менее заметный дефект: если в целевой БД уже есть таблица с таким именем, `RENAME` падает
(«Table already exists»), и перенос завершался с предупреждением, хотя ситуация штатная.

## 60.2 Правило переноса таблицы

При переносе узла считается число ДРУГИХ узлов с тем же `clickhouse_table` — по всем командам, без
team-scope: «соседи» после переносов закономерно оказываются в разных командах.

| Ситуация | Что происходит с таблицей |
|---|---|
| Таблица только у переносимого узла | `RENAME` в БД целевой команды — логи следуют за узлом (прежнее поведение) |
| Таблицу делят другие узлы | Исходная таблица **не трогается**; переехавшему узлу создаётся своя в БД целевой команды по его шаблону |
| Исходной таблицы нет в ClickHouse | Перенос без CH-операции (таблица появится при первом логе) |
| Имя занято в целевой БД | `RENAME` пропускается, узел пишет в существующую таблицу |

История логов при общей таблице остаётся у прежней команды — это корректно: её наполняли все узлы
семейства, а не один переехавший.

## 60.3 Гарантии и деградация

- **PG-запись авторитетна.** Узел и его `clickhouse_table` переносятся в транзакции; всё
  ClickHouse-взаимодействие — best-effort после commit'а. Сбой CH не отменяет перенос.
- **Создание новой таблицы — мягкое.** Не удалось создать (CH недоступен) → предупреждение в лог,
  узел уже перенесён; таблицу дотянет обычный provisioning при следующем сохранении узла.
- **Неизвестно, общая ли таблица** (порт подсчёта не подключён или запрос упал) → поведение
  прежнее, `RENAME`. Обоснование: оставить узел без таблицы хуже, чем перенести её.

## 60.4 UI

Подсказка в диалоге переноса раньше обещала переезд таблицы безусловно. Теперь она описывает
фактическое правило: таблица последует за узлом, только если принадлежит ему одному; общая
останется у текущей команды вместе с историей, а узлу будет создана новая.

## 60.5 Вне scope

- Слияние истории логов между таблицами (перелив данных) не делается — при необходимости это
  ручная операция администратора.
- Таблица, на которую после переносов не ссылается ни один узел, становится orphan'ом; для них уже
  есть отдельный раздел UI («Orphans»).
