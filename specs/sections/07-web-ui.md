## 7. Веб-интерфейс

### 7.1 Аутентификация

- Логин на основе username/password.
- **Серверные сессии в Redis.** При успешном логине Web Service генерирует случайный opaque-токен (32 байта в base64), сохраняет в Redis под ключом `session:{token}` со значением `{user_id, role, lang, created_at, last_seen_at}` и TTL `redis.session_ttl_sec` (по умолчанию 24 часа). Токен возвращается клиенту в HttpOnly Secure SameSite=Strict cookie с именем `nexus_session`.
- На каждый запрос Web API middleware читает cookie, ищет ключ в Redis, продлевает TTL, добавляет в контекст `user_id` и `role`. Отсутствующий или просроченный ключ → 401 Unauthorized.
- **Logout** — удаление ключа `session:{token}` из Redis и cookie с пустым значением и `Max-Age=0`. Действует мгновенно: после следующего запроса пользователь невалиден.
- **Принудительный logout всех сессий пользователя** (при смене роли, отключении или смене пароля) — выполняется через `SCAN MATCH session:*` с проверкой `user_id` в значении и удалением подходящих ключей. Не самая дешёвая операция (O(n) от числа активных сессий), но выполняется редко.
- **Почему сессии, а не JWT.** Шина уже зависит от Redis для кеша конфига, rate-limit и circuit-breaker (см. §5.4). Сессии переиспользуют этот же Redis, что даёт: мгновенный logout, мгновенную блокировку пользователя при изменении роли/отключении, отсутствие необходимости в blocklist'ах. JWT решал бы только проблему stateless-аутентификации, которая в нашем сценарии не актуальна.
- Дефолтный пользователь: `admin` / `admin` (с принудительной сменой пароля при первом входе — флаг `must_change_password = true`).
- Роли: `admin` (полный доступ), `manager` (управление узлами), `viewer` (только просмотр).
  Иерархия прав: `viewer` < `manager` < `admin`. Полная матрица доступа и описание
  роли `manager` — в [§26](26-roles-access-control.md).
- Управление пользователями только из роли `admin`.

### 7.3 Overview (головной экран)

Список всех узлов с агрегированными счётчиками. Поддерживает два режима отображения с переключателем в шапке:

- **Таблица** (по умолчанию) — узел, метод, вход, выход, ошибки, статус. Сортировка кликом по заголовку колонки.
- **Карточки** — карточка на узел с micro-chart за последний период, крупным счётчиком и индикатором статуса.

Выбор режима сохраняется в `localStorage` пользователя и применяется при следующем входе.

В шапке экрана:
- 4 KPI-блока: входящие за 24ч, исходящие за 24ч, текущий размер очереди Kafka, ошибки за 24ч.
- Поиск по имени узла и URL.
- Фильтр по корневому методу (`request` / `requestAsync` / все).
- Переключатель «Таблица / Карточки».
- Кнопка «Новый узел» → §7.5.

Параметры фильтра, поиска и сортировки сохраняются при переключении режима отображения. Клик по строке таблицы или по карточке открывает §7.4.

Статусы узла: `OK` (зелёный), `Очередь` (жёлтый, есть лаг по Kafka или растёт latency), `Down` (красный, недавние запросы заканчиваются ошибкой). Карточка узла со статусом `Down` получает дополнительную красную рамку.

### 7.4 Node detail (детальная страница узла)

Открывается кликом на узел из overview. Содержит:

**Шапка:**
- Хлебные крошки (`Узлы / {root_method} / {path}`).
- Имя узла, badge с типом метода (`request` / `requestAsync`), индикатор статуса, отметка времени последнего обновления.
- Кнопки: «Тест» (отправить тестовый запрос), «Изменить» → §7.5, меню «⋮» (удалить, выгрузить логи, посмотреть в Prometheus).

**Вкладки:** `Обзор` (по умолчанию), `Логи`, `Конфигурация`, `Метрики`.

**Вкладка «Обзор»:**

1. Четыре KPI-блока с метриками за выбранный период (по умолчанию 1ч):
   - Вход — общее число запросов + дельта к среднему.
   - Доставлено — число успешных + процент.
   - p95 latency — с подписью p99.
   - Ошибки — число + процент + краткая разбивка по причинам (timeout / 5xx / 4xx).

2. График трафика (запросы/мин + точки ошибок) с переключателем диапазона: `15м`, `1ч`, `24ч`, `7д`.

3. Таблица последних запросов из ClickHouse:
   - Колонки: время, статус-код, длительность, HTTP-метод, checksum_request / checksum_response.
   - Имя таблицы (`nexus_default.{table}`) показано рядом с заголовком блока.
   - Кнопки «Фильтр» и «Все логи» (переход на вкладку Логи).
   - Строки с ошибками подсвечены фоновой заливкой.
   - Клик по строке раскрывает её и показывает полное тело запроса, тело ответа, заголовки и причину ошибки.

**Вкладка «Логи»:**
- *Список записей* — таблица с колонками: время (`date_request`), статус (`status` с цветной плашкой), длительность (`duration`), URL (фактический), checksum запроса (короткий, 8 символов с tooltip полного), кнопка «⋮» для действий над записью.
- *Фильтры в шапке* — статус (`OK` / `Ошибки` / `Все`), период (последние 5 мин / час / день / произвольный диапазон), фильтр по IP, по Host (имя инстанса), полнотекстовый поиск по `request` / `response` / `reason` (через ClickHouse `hasToken` или `LIKE`), фильтр по `done = true/false`.
- *Пагинация* — bottom-pagination на 50 записей с возможностью изменить размер страницы (50/100/200).
- *Режим Live-tail* — переключатель в шапке («⏸ Pause» / «▶ Live»). При включённом live-режиме фильтры/поиск временно отключаются (греются), таблица показывает новые записи по мере их появления (через SSE-стрим от Web Service). Новая запись подсвечивается на 1 секунду фоном. Авто-прокрутка к новой записи, если пользователь не скроллил вручную (если скроллил — баннер «N новых записей» внизу, клик возвращает к live). Лимит буфера в UI — 500 последних записей в памяти, старые выпадают. По умолчанию в detail узла открывается обычный режим; live включается явно. Полезно при разборе текущего инцидента — то же ощущение, что `tail -f` в терминале.
- *Действия над записью* (меню «⋮»):
  - **Открыть детали** — модальное окно со всеми 18 полями таблицы, в том числе телом запроса/ответа в pretty-JSON viewer'е с подсветкой синтаксиса. Поля с маскированными значениями (`***`) явно помечены — нельзя «развернуть» обратно.
  - **Скопировать как curl** — кнопка генерирует и копирует в буфер `curl`-команду, воспроизводящую исходный запрос к шине (с URL, headers, body). Чувствительные значения в команде заменены на `<token>` / `<password>` с пояснительной подсказкой, что их нужно подставить вручную перед отправкой.
  - **Replay** — повторная отправка запроса через шину; подробно описано в §7.4.1.

**Вкладка «Конфигурация»:** read-only представление настроек узла (то же, что в §7.5, но без возможности редактирования).

**Вкладка «Метрики»:** ссылка на соответствующий dashboard в Prometheus + список метрик с текущими значениями.

#### 7.4.1 Replay запроса

Действие «Replay» из меню «⋮» в логах позволяет повторно отправить тот же запрос через шину. Сценарии: внешний узел временно лежал, нужно пересоздать конкретные сообщения; разработчик дебажит, почему именно этот запрос упал; проверка изменений в конфиге узла на реальных данных.

**Диалог Replay** открывается над таблицей логов:
- Шапка: ID исходного запроса, время оригинального запроса, краткая информация о узле.
- Pretty-JSON viewer оригинального тела запроса с возможностью **редактирования** (например, поправить одно поле перед повторной отправкой).
- Список заголовков (read-only — заголовки берутся из оригинала; редактирование headers — out of scope).
- Селект «Куда отправить» — `На тот же URL` (по умолчанию, использует `url` из лога) или `По текущему конфигу узла` (резолвится заново согласно `url_mode`).
- Селект «Авторизация» — `Использовать текущий конфиг узла` (по умолчанию) или `Без авторизации` (для отладки 401-ошибок). Чувствительные данные оригинального запроса (`token`, `Authorization: Basic ...`) **не восстанавливаются из лога** — там они уже маскированы. Если нужны конкретные креды — пользователь вводит их вручную в специальное поле (только для replay, никуда не сохраняется).
- Чекбокс **«Sync вместо async»** — если оригинал был `requestAsync`, replay можно отправить как `request`, чтобы дождаться ответа прямо в диалоге (удобно для отладки).
- Кнопки «Отмена» / «Отправить replay».

**Поведение после отправки:**
- Replay-запрос проходит через ту же шину что обычный запрос (Receiver → Sender → внешний узел). Не bypass — реальный путь, чтобы воспроизвести реальное поведение.
- В лог ClickHouse записывается новая запись с новым `ID`. **В поле `parameters` добавляется служебный маркер `__replay_of=<original_id>`** — это единственный способ связать replay с оригиналом в логах, поле `parameters` уже маскирует чувствительные значения, так что добавление туда служебной метки безопасно.
- Результат replay показывается прямо в диалоге: HTTP-статус, длительность, тело ответа, ссылка на новую запись в логах.
- Action записывается в audit log (см. §7.13): кто и когда выполнил replay какого запроса.

**Ограничения и безопасность:**
- Replay доступен только админам и операторам с правом на узел; `viewer` видит кнопку как disabled с tooltip «нет прав».
- Rate limit: не более 10 replay в минуту с одного аккаунта (защита от случайного флуда).
- Replay узла, который сейчас в режиме `Не активен` — отклоняется с сообщением «узел отключён, включите его перед replay».
- Replay не доступен для записей с `done = false` старше 7 дней (защита от воспроизведения устаревших проблем).

#### 7.4.2 Ленивая подгрузка тел запроса/ответа

Тела `request`/`response` могут быть крупными JSON (десятки–сотни КБ каждое). Если
snapshot-список из 50–200 строк тянет тела для всех записей сразу, браузер получает
многомегабайтный ответ, парсит его и **подвисает** — особенно на узлах с большим
объёмом трафика и большими payload'ами.

Поэтому тела грузятся **лениво, только по раскрытию конкретной строки**:

- **Списки и стрим отдают только метаданные.** `GET /api/nodes/{id}/logs` (snapshot) и
  `GET /api/nodes/{id}/logs/stream` (SSE) возвращают `LogRecordDTO` **без** полей
  `request`/`response`/`parameters` (они `omitempty` и не заполняются). Колонки в
  ClickHouse-`SELECT` остаются (full-text-фильтр `q` по `request`/`response` работает
  на стороне БД), но наружу тела не отдаются.
- **Полная запись — по отдельному эндпоинту.** `GET /api/nodes/{id}/log/{logId}`
  (путь `log`, не `logs`, чтобы не конфликтовать со статическим сегментом
  `.../logs/stream` в gin-роутере) возвращает запись целиком, включая тела. Scope —
  `logs:read`.
- **UI.** Клик по строке таблицы логов раскрывает её; только в этот момент монтируется
  запрос за телом (`react-query` ключ `["log", nodeId, logId]`). Request/Response
  показываются в pretty-JSON-блоках с собственным скроллом (`max-h`), не «съедая»
  страницу. Несколько строк раскрываются независимо; данные кешируются.

То же правило применяется к **журналу аудита** (§7.13): JSON в колонке `details`
сериализуется и попадает в DOM **только при раскрытии** строки (`<details>` рендерит
`<pre>` по `onToggle`), а не эагерно для всех строк сразу.

### 7.5 Node settings (создание и редактирование узла)

Двухколоночная форма. Левая колонка — поля настроек, разбитые на 5 секций. Правая колонка — предпросмотр маршрута и контекстная подсказка.

**Секция «Маршрут»:**
- *Тип метода* — выбор между двумя визуальными карточками: `request` (sync, ждём ответ узла) и `requestAsync` (в Kafka, 200 сразу). Это первое и самое важное решение — оно определяет всё дальнейшее поведение.
- *Путь узла* — поле с префиксом `/request/` или `/requestAsync/` (зависит от выбранного типа). Под полем — полный итоговый URL.
- *Состояние* — radio из трёх вариантов: `▶ Активен` (нормальная работа), `⏸ Пауза` (запросы принимаются и копятся в Kafka, не отправляются), `⏹ Отключён` (запросы получают 404). Подробно — §3.6.

**Секция «Куда перенаправить»:**
- *Режим URL* — выбор между двумя визуальными карточками:
  - `Статичный` — все запросы идут на адрес из поля `Target URL` (по умолчанию).
  - `Из запроса` — URL берётся из query-параметра входящего запроса (см. §3.4).
- *Target URL* — статичный адрес. Показывается и обязателен только в режиме `Статичный`; при переключении на `Из запроса` поле скрывается.
- При выборе режима `Из запроса` появляется блок настроек:
  - *Имя параметра* — текстовое поле, по умолчанию `url_base`. Под полем — пример: `?url_base=https://api.partner.com/hook` (превью с актуальным значением имени).
  - *Allowlist хостов* — список chips. Целевой URL должен матчить хотя бы один элемент, иначе 403. Пустой список — разрешено всё (UI показывает красное предупреждение «небезопасно для production»).
  - Информационная подсказка под блоком: «Параметр обязателен. Запросы без `url_base` получают 400 Bad Request».
- *Timeout* — таймаут ответа в мс.
- *Retry policy* — селект `3 retry` / `5 retry` / `Без retry`.

**Секция «Авторизация»:**
- *Входящая* — авторизация запросов к шине: `Basic auth` / `Bearer token` / `Без авторизации`, с соответствующими полями (login + password или token).
- *Исходящая* — авторизация шины при стуке к внешнему узлу. Селект с пятью вариантами:
  - `Без авторизации`
  - `Basic auth` — статичные login + password
  - `Bearer token` — статичный токен (одно значение на узел)
  - `Bearer из запроса` — токен извлекается из входящего запроса и пробрасывается как `Authorization: Bearer ...` (см. §3.5). Появляется блок настроек:
    - *Источник* — селект `Query string` (по умолчанию) / `HTTP-заголовок` / `JSON-тело`.
    - *Имя* — текстовое поле; placeholder зависит от источника: `token` для query/body, `Authorization` для header.
    - *Префикс для отрезания* — только при источнике `HTTP-заголовок`. Дефолт `Bearer `. Подсказка: «Эта часть значения заголовка отрезается перед использованием. Пустое поле — брать значение как есть.»
    - *Превью* — динамический пример преобразования.
    - Подсказка: «Токен обязателен. Запросы без токена в указанном источнике получают 401 Unauthorized».
  - `Basic из запроса` — прозрачный проброс заголовка `Authorization: Basic ...` из входящего запроса во внешний без изменений (см. §3.5). Никаких настроек у этого варианта нет — только информационный блок:
    - Превью: клиент шлёт `Authorization: Basic YWRtaW46c2VjcmV0` → внешнему узлу уходит `Authorization: Basic YWRtaW46c2VjcmV0` (то же значение).
    - Подсказка: «Шина не декодирует и не модифицирует креды — просто пробрасывает заголовок как есть. Запрос без заголовка `Authorization: Basic ...` получает 401 Unauthorized».

Разделение на входящую и исходящую обязательно — это две разные сущности с разными секретами.

**Секция «Заголовки для проброса»:**
- Список заголовков как chips с возможностью удаления.
- Поле ввода + кнопка «Добавить» для нового заголовка.
- Значения берутся из входящего запроса и передаются как есть внешнему узлу.

**Секция «Логирование в ClickHouse»:**
- *Таблица* — поле с именем таблицы (формат `db.table`) + кнопка «Проверить» рядом.
- Под полем — статус проверки:
  - `✓ Таблица существует, схема соответствует` (зелёный).
  - `⚠ Таблица существует, схема не совпадает` (жёлтый) → ссылка на просмотр diff и предложение пересоздать.
  - `✗ Таблицы не существует` (красный) → кнопка «Создать таблицу» открывает диалог §7.6.
  - `✗ Нет подключения к ClickHouse` (красный) → ссылка на Settings → ClickHouse.
- Чекбоксы: логировать тело запроса / тело ответа / заголовки.

**Правая колонка:**
- *Предпросмотр маршрута* — текстовое представление пути сообщения от клиента до ответа (HTTP-метод, путь шины, Receiver, gRPC sync или Kafka, Sender, внешний URL, ответ клиенту). Обновляется при изменении полей формы. В режиме `Из запроса` целевой адрес показывается как `{url_base из запроса}` с подсказкой про fallback и allowlist.
- *Контекстная подсказка* — меняется в зависимости от ситуации. Например, при смене типа на `requestAsync` показывается предупреждение, что ответ внешнего узла больше не передаётся клиенту. При выборе режима `Из запроса` с пустым allowlist — красное предупреждение про SSRF-риск.
- *Кнопка «Удалить узел»* (только в режиме редактирования, не при создании) — открывает диалог подтверждения, подробно описанный ниже.

**Диалог удаления узла:**
- Заголовок: «Удалить узел `{path}`?»
- Информационная плашка: «За всё время работы этого узла было обработано **N запросов**. Логи хранятся в таблице `{clickhouse_table}`.»
- Чекбокс **«Также удалить таблицу логов в ClickHouse»**, по умолчанию **выключен**. Только для роли `admin` — для `viewer` чекбокс задизейблен с tooltip «удалять таблицы может только admin» (но `viewer` всё равно не доходит до этого диалога — кнопка удаления узла ему недоступна).
- Под чекбоксом — пояснение в двух режимах:
  - Если **выключен**: «Узел будет удалён из конфигурации. Таблица `{clickhouse_table}` останется в ClickHouse — её можно удалить позже из Settings → ClickHouse → Orphaned tables (см. §7.8).»
  - Если **включён** (загорается жёлтым предупреждением): «Таблица `{clickhouse_table}` будет **навсегда удалена** вместе со всеми N записями. Действие необратимо.»
- Поле «Подтверждение». Чтобы кнопка «Удалить» стала активной, пользователь должен ввести `path` узла в текстовое поле (типовая защита от случайного нажатия).
- Кнопки «Отмена» и «Удалить навсегда».

**Поведение по умолчанию (чекбокс выключен):** удаляется только запись из PostgreSQL и связанные `node_headers`. ClickHouse-таблица остаётся как «осиротевшая» — она доступна напрямую через ClickHouse, но не через UI шины. Это сознательное решение: логи могут быть нужны для аудита, расследования инцидентов, отчётности. Лучше накапливать осиротевшие таблицы и периодически чистить, чем терять данные вместе с конфигом.

**Действие в audit log** (см. §7.13): запись `node.delete` с `details: {"path": "...", "clickhouse_table": "...", "table_dropped": true|false, "logs_count": N}`.

**Шапка формы:** хлебные крошки, заголовок, кнопки «Отмена», «Тестовый запрос (dry-run)» и «Сохранить».

Все изменения применяются только после нажатия «Сохранить». До этого новые запросы идут по старому конфигу.

#### 7.5.1 Dry-run — тестовый запрос перед сохранением

Кнопка **«Тестовый запрос (dry-run)»** в шапке формы позволяет проверить конфигурацию узла на реальном запросе **до** её сохранения. Это страхует от ошибок типа «настроил динамический URL не из того query-параметра» или «забыл добавить хост в allowlist» — без dry-run первая отправка реального трафика всегда нервная.

**Диалог dry-run** открывается поверх формы и содержит:
- *HTTP-метод* — селект `POST` (по умолчанию) / `GET` / `PUT` / `DELETE` / `PATCH`.
- *Query-параметры* — список chips «key=value». Если форма настроена на `url_mode = from_request`, в подсказке отдельным цветом показано, что параметр `url_base` обязателен. Аналогично для `auth_type = token_from_request` с источником `query`.
- *Заголовки* — список chips «Header: value». Если узел в режиме `basic_from_request` или `token_from_request` с источником `header`, подсказка указывает, какой именно заголовок ожидается.
- *Тело запроса* — JSON-редактор с подсветкой синтаксиса. Кнопка «Заполнить примером» подставляет минимальный валидный JSON `{"test": true}`.
- *Чекбокс «Использовать mock-сервер вместо реального узла»* — по умолчанию **включён**. Когда включён, запрос всё равно проходит через шину (Receiver → авторизация → резолв URL → проверки → Sender), но вместо реального HTTP-вызова Sender вызывает встроенный mock, который возвращает HTTP 200 со случайной задержкой 50–100 мс. Это позволяет проверить корректность конфига узла без побочных эффектов во внешней системе. Когда выключен — запрос реально уходит на внешний узел (нужно для отладки специфичных ответов или авторизаций).

**Результат dry-run** показывается в нижней части диалога в виде структурированного отчёта по шагам:

1. **Auth (incoming)** — статус проверки входящей авторизации: `OK` или `Failed` с причиной.
2. **URL resolution** — какой URL получился, через какой `url_mode`, прошёл ли allowlist. Полный resolved URL.
3. **Auth (outgoing)** — какой `Authorization` заголовок сформирован. Креды показаны как `***` с длиной (например, `Bearer *** (32 chars)`).
4. **Headers forwarded** — список заголовков, которые ушли бы во внешний узел.
5. **Body sent** — тело, которое ушло бы (после исключения служебных полей типа `token`, `auth_token` и т.п.).
6. **Response** — статус, заголовки и тело ответа (от mock-сервера или реального узла).
7. **Would log to ClickHouse** — превью записи, которая попала бы в таблицу логов (все 20 полей с реальными значениями и маскированием).

**Ограничения и поведение:**
- Dry-run **не сохраняет конфиг узла** и не пишет в production-таблицу ClickHouse — никаких побочных эффектов.
- Используется текущее значение формы, включая несохранённые изменения. Сохранение через «Сохранить» — отдельный шаг.
- При создании нового узла (`path` ещё не существует в БД) dry-run работает с тем `path`, который пользователь ввёл в форме — если он ещё не сохранён, для проверки используется временный путь `__drytun_<random>` под капотом.
- Запись в audit log: кто и когда сделал dry-run какого узла (без тела запроса/ответа).
- Доступно только админам — `viewer` видит кнопку как disabled.

### 7.6 Диалог создания таблицы в ClickHouse

Открывается из §7.5 (кнопка «Создать таблицу») или из Settings → ClickHouse. Модальный диалог содержит:

- Заголовок с именем создаваемой таблицы.
- Выбор шаблона схемы:
  - *Стандартный* — полная схема из §4.3 (по умолчанию).
  - *Минимальный* — только метаданные без полей `request` / `response` (для узлов с большим телом).
- Текстовая область с SQL-запросом, заполненным по выбранному шаблону. Подсветка синтаксиса, разрешено редактирование.
- Подсказка с информацией о базе данных (существует или будет создана).
- Кнопки: «Открыть в редакторе» (полноэкранный режим для сложных правок), «Отмена», «Создать таблицу».

После успешного выполнения CREATE TABLE диалог закрывается, форма §7.5 автоматически обновляет статус таблицы на «существует».

### 7.8 Settings → ClickHouse

Двухблочная страница: форма подключения сверху, список таблиц снизу.

**Блок «Подключение к ClickHouse»:**

В правом верхнем углу блока — статус соединения: `Подключено` (зелёный), `Ошибка` (красный с tooltip с текстом ошибки), `Не проверено` (серый).

Поля:
- *Host* + *Port* (одна строка, port справа).
- *База данных* — имя БД, в которой будут создаваться таблицы узлов.
- *Пользователь* + *Пароль* (одна строка).
- *Протокол* — radio: `Native TCP` / `HTTP`; чекбокс `TLS`.
- *Буферизация* — два поля: размер пачки (записей) и интервал flush (секунд).

Кнопки:
- **«Проверить соединение»** — ping по значениям из формы без сохранения. Результат показывается inline (текст под кнопкой или у индикатора статуса). Позволяет валидировать новые креды до их применения к production.
- **«Сохранить и переподключить»** — graceful-переключение: новые логи идут на новый сервер только после успешного ping, иначе откат на старые настройки и сообщение об ошибке. Буфер несохранённых логов мигрирует на новое соединение.
- **«Отмена»** — сброс полей к текущим сохранённым значениям.

**Блок «Таблицы в базе»:**

Список таблиц из выбранной БД, обновляется при загрузке страницы и по кнопке «Обновить». Сверху — фильтр в виде сегментированного контрола: `Все` / `Привязанные` / `Осиротевшие` (по умолчанию `Все`).

Колонки:
- Имя таблицы (`db.table`, моноширинный шрифт).
- Количество записей.
- Размер на диске.
- Привязка — chip с именем узла, который пишет в эту таблицу, или красный chip `осиротевшая` (если таблица существует, но ни один узел в неё не пишет — например, узел был удалён, а таблицу не удалили).
- Дата последней записи (полезно, чтобы понимать, сколько таблица уже не используется).
- Меню действий «⋮»:
  - **Открыть в логах** — переход в просмотр содержимого таблицы (доступно только для привязанных, иначе grey-out).
  - **DROP таблицу** — диалог подтверждения как в §7.5 (с вводом имени таблицы для подтверждения и плашкой «Действие необратимо»). Только для админа. Для осиротевших — без предупреждения «возможно, нужно для аудита»; для привязанных — красная плашка «**Внимание:** к этой таблице привязан активный узел `{node_path}`. После удаления узел перестанет работать. Сначала перепривяжите узел к другой таблице, или удалите узел.»

Кнопка «Создать таблицу» открывает диалог §7.6 с произвольным именем.

**Регулярная чистка осиротевших таблиц.** В правом верхнем углу блока — кнопка «Очистить осиротевшие» (только для админа). Открывает диалог со списком всех осиротевших таблиц, рассортированных по дате последней записи. У каждой строки чекбокс. Внизу — кнопка «Удалить выбранные» с подтверждением и плашкой о необратимости. Полезно для разовой чистки после крупных рефакторингов или для compliance-процедур.

В audit log пишется отдельная запись `clickhouse.table.drop` с полями `table_name`, `was_orphaned`, `dropped_by`.

### 7.9 Settings → Users

Управление пользователями UI. Доступно только админам.

**Шапка блока:**
- Счётчики: всего пользователей, активных, отключённых.
- Поиск по логину и email.
- Кнопка «Добавить» → диалог §7.10.

**Информационный баннер** появляется сверху, когда пользователь `admin` всё ещё использует пароль по умолчанию: «Пользователь `admin` использует пароль по умолчанию. Рекомендуем сменить его».

**Таблица пользователей.** Колонки:
- *Пользователь* — аватар (инициалы или цветной кружок с первой буквой), логин, email, метка «это вы» для текущего пользователя.
- *Роль* — chip с иконкой:
  - `Полный доступ` (синий, `ti-shield`) — может всё.
  - `Только просмотр` (серый, `ti-eye`) — может только просматривать.
- *Статус* — `Активен` (зелёная точка) или `Отключён` (серая точка). Отключённая строка отображается с opacity 0.55.

- *Действия* — иконки-кнопки:
  - `ti-key` — компактный диалог смены пароля.
  - `ti-edit` — открывает диалог §7.10 в режиме редактирования.
  - `ti-trash` — удаление с подтверждением.
  - `ti-player-play` — только у отключённых, включает пользователя обратно.

**Правила безопасности:**
- Текущий пользователь не может удалить или отключить сам себя.
- Текущий пользователь не может сменить собственную роль на `Только просмотр`.
- Удалить или отключить последнего активного админа нельзя — соответствующие кнопки скрыты или disabled с tooltip «Должен остаться хотя бы один администратор».
- Логин нельзя изменить после создания — это упрощает аудит-логи.

### 7.10 Диалог пользователя (создание / редактирование)

Модальный диалог, обслуживает оба сценария. Заголовок и текст кнопки меняются: «Новый пользователь» / «Создать пользователя» при создании, «Редактирование `{login}`» / «Сохранить» при редактировании.

Поля:

- *Логин* — текстовое поле, латиница, цифры, точки, подчёркивания. Под полем подсказка: «Нельзя изменить позже». В режиме редактирования поле read-only.
- *Email* — опционально.
- *Пароль* — поле с кнопкой «Сгенерировать» (выдаёт сильный пароль 12 символов: разный регистр, цифры, символы). Под полем — индикатор силы пароля (4 сегмента) и текстовое описание (`Слабый` / `Средний` / `Сильный`). В режиме редактирования поле скрыто; смена пароля — отдельный компактный диалог через `ti-key`.
- *Роль* — выбор между двумя визуальными карточками: `Полный доступ` и `Только просмотр`, каждая с иконкой и кратким описанием прав.
- *Активен* (только в режиме редактирования) — toggle для отключения / включения пользователя.
- *Требовать смену пароля при первом входе* — чекбокс, по умолчанию включён при создании.

**Шапка:** заголовок, подзаголовок с контекстом, кнопка закрытия.

**Подвал:** кнопки «Отмена» и «Создать пользователя» / «Сохранить».

**Компактный диалог смены пароля** (вызывается из `ti-key`):
- Текущий пароль (только если пользователь меняет собственный пароль).
- Новый пароль + кнопка «Сгенерировать» + индикатор силы.
- Чекбокс «Требовать смену при следующем входе».
- Кнопки «Отмена» / «Сменить пароль».

### 7.11 Settings → Language

Выбор языка интерфейса. Доступен всем ролям (включая `viewer`) — это персональная настройка.

**Поддерживаемые языки:**
- **English** — язык по умолчанию.
- **Русский** — переключение через UI.

**Дизайн страницы:**
- Две карточки в один ряд: флаг страны + название языка + описание + галочка-индикатор выбранного варианта.
- Под карточками — информационный блок с пояснением, что выбор применяется только к текущему пользователю, а логи и метрики остаются на английском.

**Поведение:**
- Изменение применяется сразу, без перезагрузки страницы — все элементы UI перерисовываются с новыми переводами.
- Выбор сохраняется в профиле пользователя (поле `users.lang` в PostgreSQL) и подтягивается при следующем входе.
- При первом входе пользователя (новый аккаунт или гость) язык определяется по заголовку `Accept-Language` браузера: если содержит `ru` — Русский, иначе English.
- В шапке любой страницы есть быстрый переключатель языка (компактный, рядом с кнопкой темы).

**Технические требования:**
- Переводы хранятся в JSON-файлах `/web-ui/locales/en.json` и `/web-ui/locales/ru.json`, ключи структурированы по экранам (`overview.title`, `node.detail.tabs.logs` и т.п.).
- Используется библиотека i18n (`react-i18next` для React, `vue-i18n` для Vue или аналог — на выбор реализации).
- Серверные ответы API (тексты ошибок, валидации) тоже локализуются: клиент передаёт заголовок `Accept-Language: ru` или `en`, сервер отвечает на соответствующем языке.
- Логи самих сервисов (stderr/файлы), записи в ClickHouse и метрики Prometheus сохраняются **только на английском** независимо от языка интерфейса. Это нужно для машинной обработки и интернационального сопровождения.
- Числа, даты и проценты форматируются согласно локали (`Intl.NumberFormat`, `Intl.DateTimeFormat`): «1,234.56» для en, «1 234,56» для ru; даты в формате `MM/DD/YYYY` для en, `DD.MM.YYYY` для ru.

### 7.12 UX-требования

- Переключение темы светлая/тёмная без перезагрузки, выбор сохраняется в `localStorage`.
- Все счётчики и статусы обновляются в реальном времени (SSE) или периодическим polling каждые 5–10 сек как fallback.
- Все деструктивные действия (удаление узла, отключение, пересоздание таблицы) требуют подтверждения.
- Все long-running операции (проверка ClickHouse, тестовый запрос, создание таблицы) показывают состояние загрузки и не блокируют UI.
- Форма §7.5 поддерживает клавиатурную навигацию и сохранение по `Ctrl/Cmd+S`.
- Все формы валидируются на клиенте до отправки; ошибки показываются inline рядом с полем.

### 7.13 Audit log (журнал действий)

Отдельная страница для просмотра журнала действий пользователей в UI. Помогает разбирать инциденты «у нас перестало работать в 14:32 — кто-то менял конфиг?» и обеспечивает прозрачность для аудита и compliance.

**Доступ.** Видна только админам. В шапке навигации — пункт «Audit» рядом с «Settings», или внутри настроек как отдельный раздел `Settings → Audit log`.

**Что записывается** (таблица `user_audit` из §5.1):
- Действия с пользователями: вход / выход / неуспешный логин, создание, изменение роли, отключение, удаление, смена пароля.
- Действия с узлами: создание, изменение конфига (с diff'ом полей), отключение/включение, удаление.
- Действия с ClickHouse-таблицами: создание, изменение настроек подключения, проверка соединения.
- Действия с настройками приложения: изменение Sentry, изменение языка пользователя (только сам факт, без значения).
- Replay-запросы: см. §7.4.1.
- Dry-run: см. §7.5.1.

**Что НЕ записывается** в audit:
- Просмотр (read-only действия) — view списка узлов, чтение логов, открытие detail-страницы. Иначе журнал замусоривается.
- Содержимое запросов/ответов в replay (только факт операции и target узла).
- Значения паролей и токенов (только факт изменения).

**Поля записи журнала:**
- `id` — UUID.
- `user_id` / `user_login` — кто (если действие выполнено не пользователем, а системой — `system`).
- `action` — машинно-читаемый код: `node.create`, `node.update`, `node.delete`, `user.login.success`, `user.login.failed`, `node.replay`, `node.dry_run` и т.п.
- `target_type` / `target_id` — что было задействовано (например, `node` / `id-узла`).
- `details` — JSON с дополнительными полями: для `node.update` — diff изменённых полей (старое → новое, чувствительные значения маскированы); для `user.login.failed` — IP, User-Agent.
- `ip_address` — IP клиента.
- `created_at` — таймстемп с миллисекундами.

**UI страницы:**
- *Таблица* — колонки: время, пользователь (с аватаром-инициалом), действие (с иконкой по категории), target (кликабельный — переход на сущность, если она ещё существует), краткое описание из `details`, IP.
- *Фильтры* — период, конкретный пользователь, тип действия (мультиселект с группировкой `user.*`, `node.*`, `settings.*`), фильтр по `target_id` (например, увидеть всю историю одного узла).
- *Поиск* — по логину пользователя, по target ID, по содержимому `details`.
- *Кнопка «Открыть детали»* в каждой строке — модальное окно с полным JSON `details`, в том числе с раскрытым diff для `node.update` (две колонки: до и после, изменённые поля подсвечены).
- *Пагинация* — 50/100/200 записей на страницу, infinite scroll или классическая.
- *Экспорт* — кнопка «Скачать CSV» с применёнными фильтрами (для отчётов compliance).

**Retention.** По умолчанию записи audit log хранятся **365 дней** в PostgreSQL. Старые записи удаляются housekeeping-job'ом раз в сутки. Срок настраивается в `web.audit_retention_days` в конфиге (см. §8.3).

**Безопасность.** Удалить или изменить запись audit log нельзя ни через UI, ни через API (даже админу). Это append-only журнал. Прямое изменение записей возможно только на уровне БД и считается компрометацией — должно быть невозможно по политикам доступа к Postgres.

### 7.14 API-токены для интеграций

Read-only токены для скриптов, custom-дашбордов, BI-выгрузок, интеграции с Grafana. В отличие от session-токенов (см. §7.1), которые живут в Redis и привязаны к браузерной сессии, API-токены хранятся в PostgreSQL, имеют long-lived TTL, не привязаны к cookie и используются через заголовок `Authorization: Bearer <token>`.

**Кто может создать.** Любой пользователь UI, включая `viewer`. Это сознательное решение: чтобы аналитик с ролью `viewer` мог выгружать логи в свой BI без обращения к админу.

**Ограничения по правам.** API-токен не может расширять права своего владельца — токен `viewer`'а не получит доступ к админским эндпоинтам. По сути scopes — это подмножество прав пользователя, не расширение.

**Доступные scopes** (выбираются при создании токена):
- `logs:read` — чтение ClickHouse-логов любого узла команды владельца через эндпоинт `/api/nodes/{id}/logs` (и его потоковый вариант `/logs/stream` — нет, только snapshot-чтение, SSE доступен только для UI-сессий).
- `nodes:read` — чтение списка и конфигов узлов (без чувствительных полей — `auth_credentials` всегда возвращается как `***`).
- `metrics:read` — чтение агрегированных метрик через `/api/metrics/*` (если будет добавлено в будущем).
- `audit:read` — чтение audit log (только для админов).

Mutating scopes (`*:write`, `*:delete`) **не предусмотрены в v1**. API-токены — строго read-only. Если нужно автоматизировать управление узлами — это делается через CI с обычными админ-сессиями (или через отдельный механизм в v2).

**Страница «Settings → API Tokens»:**
- Видна всем ролям. Каждый пользователь видит только свои токены.
- Таблица токенов: имя, prefix (`db_xxxxxxxx`, первые 8 символов — для идентификации без раскрытия), scopes (chips), дата создания, последнее использование, истечение (или `пожизненный`), статус (активен / отозван / истёк).
- Кнопка «Создать токен» → диалог:
  - *Имя* (`grafana-export`, `bi-daily-sync`) — обязательно.
  - *Scopes* — мультиселект.
  - *Истечение* — `Без истечения` / `30 дней` / `90 дней` / `365 дней` / `Произвольная дата`.
  - Кнопка «Создать» — генерируется токен формата `db_<base64-32-байт>` (например, `db_3xK9mPq7vR2nL8wT5sF4hY6jB1aZ0cE`). **Показывается один раз** в модальном окне с большой кнопкой «Скопировать в буфер». После закрытия диалога — никогда больше не показывается. Если потеряли — создайте новый, старый отзовите.
  - В БД хранится только `SHA-256(token)`, само значение не сохраняется. Это значит, что админ не может «подсмотреть» чужой токен в БД.
- Меню действий «⋮» в каждой строке: **Отозвать** (с подтверждением, мгновенно делает токен невалидным) и **Удалить** (только для отозванных или истёкших — для аудита).

**Использование клиентом:**

```
curl https://nexus.example.com/api/nodes/abc/logs \
  -H "Authorization: Bearer db_3xK9mPq7vR2nL8wT5sF4hY6jB1aZ0cE"
```

Middleware Web API при получении заголовка `Authorization: Bearer db_...` (префикс `db_` — маркер API-токена, чтобы не путать с прокси-bearer'ами):
1. Считает `SHA-256` от значения.
2. Ищет в таблице `api_tokens` запись с этим хешем, `revoked_at IS NULL`, `expires_at IS NULL OR expires_at > now()`.
3. Если найдена — обновляет `last_used_at`, добавляет в request context `user_id`, `scopes`. Если запрашиваемый эндпоинт требует scope, которого нет — 403 Forbidden.
4. Если не найдена — 401 Unauthorized.

**Аудит.** Создание, отзыв, удаление токена пишутся в `user_audit` (`api_token.create`, `api_token.revoke`, `api_token.delete`). Использование токена в `audit` не пишется (иначе журнал переполнится) — для статистики служит поле `last_used_at`.

**Rate limit.** Запросы с API-токеном идут под отдельным rate limit: 100 запросов в минуту на токен. Превышение — 429 Too Many Requests с заголовком `Retry-After`. Лимит настраивается в `web.api_token_rate_limit_per_min` (см. §8.3).
