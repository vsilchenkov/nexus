## 34. Операбельность: навигация, сессия, версия, управление async-очередью Kafka, фикс replay

Раздел объединяет пять эксплуатационных доработок, дающих оператору контроль над тем, что сейчас
зашито в код/конфиг или работает неверно: положение пункта «Настройки» в навигации, настраиваемая
длительность сессии, видимая и (в dev) настраиваемая версия приложения, управление накопившейся
async-очередью Kafka прямо на странице узла, и устранение бага повторной отправки запросов без тела.

Каждый пункт самодостаточен. Общая тема — **операбельность**: уменьшить число вещей, ради которых
сейчас нужен рестарт, пересборка или ручной доступ к Kafka/БД.

### 34.1. Навигация: «Настройки» вниз сайдбара

Пункт «Настройки» в левом сайдбаре (`web-ui/src/components/Sidebar.tsx`) сейчас стоит в одном ряду с
основными разделами (Nodes, Audit, Kafka). Настройки — вспомогательный, редко используемый функционал,
поэтому ссылка **опускается в подвал сайдбара**, к блоку с пользователем и версией: основная
навигация остаётся вверху, «Настройки» прижимаются к низу (`mt-auto`), визуально отделённые от
оперативных разделов. Поведение ссылки (роуты `/settings/*`, активное состояние) не меняется — только
положение. Стиль `NavLink` переиспользуется (общий рендер-хелпер, без дублирования классов).

### 34.2. Настраиваемая длительность сессии

Сейчас TTL пользовательской сессии (Redis) жёстко берётся из `cfg.Redis.SessionTTLSec` (дефолт
86400 с = 24 ч) и применяется в `AuthUsecase` (Login / Check-sliding-Touch / SwitchTeam). Изменить
его можно только правкой конфига и рестартом Web-сервиса.

Вводится **настройка длительности сессии в UI** (раздел настроек, доступ admin), хранимая в
динамической части настроек `app_settings` (singleton `id=1`, JSONB), как Sentry/ClickHouse:

- Новый блок `security` в `domain.AppSettings`: `SecuritySettings{ SessionTTLSeconds *int }`. `nil` =
  использовать значение из env-конфига (`cfg.Redis.SessionTTLSec`) — обратная совместимость.
- **Валидация диапазона:** `[300 c (5 мин), 30 сут]`. Вне диапазона — доменная ошибка
  `ErrSessionTTLInvalid` → handler `Update` отвечает 4xx, значение не сохраняется.
- **Применение без рестарта.** `AuthUsecase` берёт TTL не как фиксированное число, а через провайдер
  `func() time.Duration` (атомарный держатель `SessionTTLProvider` на базе `atomic.Int64`, секунды +
  fallback из env). Новые сессии и sliding-`Touch` читают актуальное значение. Обновление значения —
  через существующий hot-reload (Redis pub/sub, новая секция `security`): на старте провайдер
  сидится из `app_settings`, при изменении настроек — пересеивается callback'ом без рестарта.
- **Семантика смены.** Уменьшение TTL действует на активные сессии при следующем их `Touch`
  (sliding-окно становится короче); увеличение — продлевает. Это приемлемо и ожидаемо для
  sliding-сессий.

Только Web-сервис выдаёт сессии; Receiver/Sender провайдер не нужен.

### 34.3. Версия: видимость + dev-override

`GET /api/version` сейчас отдаёт только `{version}` — git-версию, вшитую в бинарь ldflags'ом
(`git describe --tags --always --dirty`, см. §30 и `internal/platform/build`). В dev без тега это
`dev` / короткий хеш / суффикс `-dirty`, и поменять отображаемую версию вручную нельзя.

**Доработка двусоставная.**

1. **Обогащение endpoint'а (всегда).** `GET /api/version` отдаёт
   `{ version, commit, build_date, override_allowed }` (`commit`/`build_date` уже есть в
   `build.Commit`/`build.BuildDate`). Футер SPA показывает `v{version}`, а в tooltip (`title`) —
   `commit` и `build_date`. Endpoint остаётся публичным (без авторизации).

2. **Ручной override — только в dev.** Отображаемую версию можно переопределить вручную, но это
   разрешено исключительно в dev-окружении; в проде версия всегда автоподставляется из git, и менять
   её запрещено. Реализуется серверным гейтом:
   - Конфиг-флаг `web.allow_version_override` (bool, **дефолт `false`** = прод-безопасно; в dev-конфиге
     ставится `true`). Значение отражается в ответе как `override_allowed`.
   - Хранение override — поле `version_override *string` в `app_settings.general`.
   - **Приоритет:** если `allow_version_override=true` и override непуст → отдаётся override; иначе —
     git-версия из ldflags (override игнорируется).
   - **Гейт записи:** `AppSettingsUsecase.Update` отклоняет изменение `version_override`, если флаг
     выключен (доменная ошибка → handler 403). В UI поле настройки версии **скрыто/недоступно**, когда
     `override_allowed=false`.

Это даёт dev-сборкам осмысленную, настраиваемую версию, не открывая возможность подменять версию в
проде.

### 34.4. Управление async-очередью Kafka на узле requestAsync

**Проблема.** Async-запрос (`POST /v1/requestAsync/{path}`) сразу кладётся в Kafka-топик `nexus.async`
(envelope, key=`node.Path`) и обрабатывается Sender-consumer'ом. Если внешний адрес получателя
перестал работать или узел переведён в `paused` (Sender не коммитит offset → сообщения копятся),
очередь растёт и накопленные запросы становятся неактуальными. Сейчас нет способа из UI увидеть
очередь узла и почистить её — нужен ручной доступ к Kafka.

Вводится **раздел управления очередью прямо на странице узла `requestAsync`** (новая вкладка
«Очередь» в `NodeDetail`, рядом с Overview/Logs/Config/Metrics; видна только для `root_method ==
requestAsync`). Возможности:

1. **Размер очереди** — сколько сейчас неконсюмированных сообщений узла, **напрямую из Kafka**.
2. **Список запросов** — первые 50 (как в логах): id, метод, target URL, время приёма, размер тела;
   с **ленивой подгрузкой тела** выбранного запроса по клику (паттерн раскрытия строки из логов).
3. **Удалить выбранный запрос.**
4. **Очистить очередь за выбранный период** — с тем же `PeriodPicker` (1ч/3ч/24ч/7д/14д/30д/
   произвольный), что и на других экранах.
5. **Очистить всю очередь** узла.

**Ограничение Kafka и механизм удаления (неочевидность).** Kafka — append-only лог: физически удалить
одно сообщение в середине или вырезать произвольный временной диапазон **нельзя** (а используемый
high-level клиент `segmentio/kafka-go` не предоставляет даже `DeleteRecords`). Поэтому «удаление»
реализуется **логически, через tombstones**:

- Множество отменённых `Envelope.ID` хранится в Redis (ключи `qcancel:<id>` с TTL = retention топика
  `nexus.async`; per-ID-ключи самоистекают вместе с физическим устареванием сообщений — без
  неограниченного роста).
- **Sender-consumer** перед отправкой во внешний адрес проверяет cancel-set: если `Envelope.ID`
  отменён → коммитит offset и **пропускает** отправку (без внешнего HTTP и без DLQ). Проверка
  ставится после десериализации envelope и **до** обработки `paused`-статуса — чтобы можно было
  чистить бэклог именно paused-узла (основной сценарий). При недоступности Redis — **fail-open**
  (доставляем, не блокируем; §9.4).
- Тогда все три операции — единый механизм: «удалить выбранный» = добавить 1 id; «очистить период» =
  отобрать id с `ReceivedAt ∈ [from, to]` и добавить; «очистить всё» = отобрать все id узла и добавить.

Физически сообщения остаются в Kafka до retention, но во внешний адрес уже не уходят — что и требуется.

**Чтение очереди (peek).** Размер и список читаются транзиентным `kafka.Reader` **без GroupID**:
от committed-offset группы Sender (через `OffsetFetch`) до high-watermark (`ListOffsets`), с фильтром
по key=`node.Path` и десериализацией envelope. Чтение ограничено по времени (bounded ctx) и по
объёму (cap, напр. 5000 сообщений) — при переполнении возвращается флаг `capped` (UI показывает
«показаны первые N, очередь больше»; lag/глубина — нижняя оценка). Транзиентный reader не входит в
consumer-группу Sender, ничего не коммитит и не мешает доставке.

**API (node-scoped, под `/api/`, admin; мутации — CSRF + rate-limit; мягкая деградация
`kafka_available=false` при недоступном кластере):**

```
GET    /api/nodes/:id/async-queue/depth                       → { count, capped, kafka_available }
GET    /api/nodes/:id/async-queue/messages                    → первые 50 метаданных
GET    /api/nodes/:id/async-queue/messages/body?partition=&offset=  → тело одного сообщения
DELETE /api/nodes/:id/async-queue/messages/:msgId             → отменить один (tombstone)
POST   /api/nodes/:id/async-queue/purge   body { from?, to? } → очистить период; пусто = всё
```

Период `from`/`to` парсится тем же контрактом, что у Kafka-монитора. Все мутации пишут запись в audit
log (новое действие `async_queue.purge`).

**Тесты.** Пропуск отменённого сообщения в Sender (cancelled → HandleAck, внешний HTTP не вызван,
DLQ не записан; ошибка проверки → доставка/fail-open); Redis cancel-set (Cancel→IsCancelled, TTL,
неизвестный id); usecase (peek/purge с моками, деградация при отсутствии peeker, проброс окна периода
в ScanIDs, audit); парсер метаданных сообщения (совпадение/несовпадение key, битый JSON, границы
периода); HTTP-хендлер (роуты, RBAC 403, CSRF, 400 на плохом периоде).

### 34.5. Фикс: повторная отправка (replay) запроса без тела даёт 405

**Симптом.** Повтор запроса из логов (`POST /api/logs/{id}/replay`) падает с
`405 {"error":"http method not allowed for this node"}`, если у исходного запроса не было тела.

**Причина.** В лог ClickHouse пишется **исходящий** метод узла: и sync (`route.go`), и async
(`route_async.go`) кладут в запрос к Sender `string(node.OutgoingMethod)`, а Sender логирует его как
`method`. Replay читает `orig.Method` (= исходящий метод) и отправляет его как **входящий** метод
обратно в Receiver, где он валидируется против `node.IncomingMethod`. Когда `OutgoingMethod !=
IncomingMethod` — типичный случай «узел принимает POST, а во внешний API ходит GET (без тела)» —
replay получает 405. «Нет тела» здесь коррелирует с исходящим GET и потому проявляется именно так.

**Исправление.** Replay переинъецирует запрос через входной endpoint Receiver'а, поэтому должен
использовать **входящий** метод узла (`node.IncomingMethod`), а не залогированный исходящий
(`orig.Method`). Пустой `IncomingMethod` трактуется как `POST` (так же, как `methodMatches` в
Receiver). Тело берётся как прежде (с проверкой «тело не логировалось → 422 ErrReplayBodyUnavailable»).

**Тесты.** Узел `IncomingMethod=POST, OutgoingMethod=GET`, лог `method=GET` → replay диспатчит `POST`
(а не GET), регресс на 405; пустой `IncomingMethod` → `POST`; сохранить существующие сценарии
недоступного/явно-пустого тела.

### 34.6. Scope / Out of scope

**В scope:** перенос пункта «Настройки» вниз; настройка длительности сессии (app_settings + динамический
провайдер + hot-reload + валидация); обогащённый `/api/version` + dev-only override версии (гейт
`allow_version_override`); вкладка «Очередь» на узле requestAsync (глубина, список первых 50 + тело,
удаление одного/период/всё через cancel-set, проверка в Sender); фикс replay-метода; тесты по всем
пунктам; синхронизация бандла SPA и i18n.

**Out of scope:**

- **Физическое удаление сообщений из Kafka** (truncate середины/диапазона) — невозможно в append-only
  логе и не предоставляется `segmentio/kafka-go`. Используется логический tombstone-механизм; сообщения
  истекают по retention.
- **Точный счётчик очереди при очень больших объёмах** — peek ограничен cap'ом; сверх cap'а возвращается
  нижняя оценка с флагом `capped`.
- **Управление очередью для узлов RabbitMQAsync** — у них своя семантика источника (pull из RMQ);
  вкладка «Очередь» вводится только для `requestAsync`.
- **Override версии в проде** — намеренно запрещён гейтом; прод всегда показывает git-версию.
