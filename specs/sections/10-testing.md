## 10. Тестирование

### 10.1 Уровни тестирования

Кодовая база покрывается тестами на трёх уровнях:

**Unit-тесты.** Покрывают всю бизнес-логику: маршрутизация запросов, валидация URL, резолв динамической авторизации (Bearer/Basic из запроса), формирование заголовков, маскирование чувствительных полей, retry-логика, circuit breaker, парсинг конфигов. Запускаются командой `make test`, не требуют внешних зависимостей (Docker, Postgres, Kafka). Используется стандартный `testing` + `testify/assert`/`require`. Mock'и для интерфейсов — через `mockery` или ручные стабы.

**Покрытие.** Минимальная планка покрытия unit-тестами — **70%** для пакетов `/internal/receiver`, `/internal/sender`, `/internal/storage`. Метрика снимается через `go test -coverprofile`, отчёт публикуется в CI. Падение покрытия ниже планки фейлит сборку.

**Integration-тесты.** Запускают реальные зависимости в Docker (через `testcontainers-go`): Postgres, Redis, ClickHouse, Kafka. Проверяют end-to-end сценарии: создание узла через API → отправка запроса → доставка во внешний mock-сервер → запись лога в ClickHouse. Запускаются `make test-integration`, требуют запущенного Docker daemon.

**Performance / сценарный тест.** Отдельный исполняемый сценарий нагрузки — см. §10.2.

### 10.2 Сценарный тест производительности

Цель — проверить, что система держит заявленные показатели (500 rps, p95 ≤ 200 мс, см. §9.1) на реалистичной смеси трафика, а не на синтетическом потоке одинаковых запросов.

**Поведение:**
- Генератор создаёт **рандомные узлы** при старте (через Web API): N узлов с случайными `path`, разными `root_method` (часть `request`, часть `requestAsync`), разными комбинациями `url_mode` (static / from_request) и `auth_type` (none / token / token_from_request / basic / basic_from_request). Доли распределения настраиваются.
- Поднимает **mock-сервер внешних узлов**: HTTP-сервер, принимающий запросы по любому пути, отвечающий 200 с настраиваемой задержкой (по умолчанию 50 мс с jitter ±30 мс). Имитирует реальный внешний API без зависимости от внешнего интернета.
- Генерирует **рандомные запросы**: рандомный выбор узла из созданных, рандомный JSON-payload (от 100 байт до 5 KB), рандомные значения query-параметров (включая `url_base` и `token` для динамических узлов), рандомные заголовки.
- Запускает нагрузку с настраиваемым RPS в течение настраиваемого времени.
- В конце выводит отчёт: фактический rps, p50/p95/p99 latency, error rate, размер ClickHouse-буфера, Kafka-lag.

**Настройки через флаги/env:**

```
--target-rps=500              # целевой RPS (по умолчанию 500)
--duration=10m                # длительность нагрузки
--nodes=50                    # количество создаваемых узлов
--ratio-async=0.3             # доля requestAsync (0.0–1.0)
--ratio-dynamic-url=0.2       # доля узлов с url_mode=from_request
--ratio-auth-token=0.4        # доля узлов с auth_type=token_from_request
--ratio-auth-basic=0.2        # доля узлов с auth_type=basic_from_request
--payload-min=100             # минимальный размер payload в байтах
--payload-max=5120            # максимальный размер payload
--mock-latency-ms=50          # средняя задержка mock-сервера
--mock-latency-jitter-ms=30   # jitter задержки
--cleanup=true                # удалять созданные узлы после теста
--report=report.json          # путь для итогового отчёта
```

**Расположение:** `/cmd/loadtest/main.go` — отдельный исполняемый файл. Не часть основных бинарей. Запускается командой `make loadtest` (см. §13.1).

**Где он живёт в CI/CD.** В CI запускается короткая версия (1 минута на 100 rps) на каждом PR — smoke-test, чтобы убедиться что система собралась и не падает под нагрузкой. Полный 10-минутный тест на 500 rps запускается nightly или вручную перед релизом — он не подходит для каждого PR из-за длительности.

**Критерий «прошёл/не прошёл».** Тест автоматически проверяет в финальном отчёте:
- Достигнутый rps ≥ 95% от target.
- p95 latency ≤ 200 мс (без учёта `--mock-latency-ms`).
- Error rate < 0.1%.
- Нет потерь сообщений (для async: число сообщений в ClickHouse-логе = числу отправленных).
- При нарушении любого условия — exit code 1, CI-сборка фейлится.

### 10.3 Где описана процедура запуска

Все команды запуска тестов, требования к окружению, переменные окружения и примеры вызова сценарного теста с разными параметрами описаны в **TESTING.md** в корне репозитория (см. §13.4). README.md содержит ссылку на этот файл.
