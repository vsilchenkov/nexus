## 22. Контроль логирования узла, раскладка карточками, Telegram-алерты через Prometheus

Раздел вводит три связанных улучшения: гранулярный контроль логирования на уровне узла,
полноценный карточный вид головного экрана и унификацию источника данных для Telegram-алертов
(перевод с ClickHouse на Prometheus, тот же источник, что и графики панели).

### 22.1. Поля контроля логирования узла

К `domain.Node` (и таблице `nodes`) добавлены три поля:

| Поле | Тип | Дефолт | Назначение |
|---|---|---|---|
| `logging_enabled` | bool | `true` | Мастер-тумблер. При `false` узел **не пишет лог в ClickHouse вообще** (ни sync, ни async, ни запись при открытом circuit breaker). |
| `max_body_size_enabled` | bool | `false` | Включает ограничение размера сохраняемых тел. |
| `max_body_size` | int32 | `0` | Максимальное число **символов** (рун) в сохраняемых полях `request`/`response`. Диапазон 0..10 000 000; при включённом тумблере обязано быть `> 0`. |

Дефолты сохраняют прежнее поведение (логирование включено, лимита нет). В API
`logging_enabled` передаётся как nullable: отсутствие поля трактуется как `true` (обратная
совместимость со старыми клиентами).

Миграция — `migrations/0010_node_logging_controls.up.sql` (с `CHECK` на диапазон).

### 22.2. Обрезка тел (`max_body_size`)

> **⚠️ Superseded в §43.** Поведение «тихого усечения» ниже заменено на **reject + лог**: при
> превышении лимита sync-запрос/ответ отклоняется (413/502), async не доставляется, во всех случаях
> пишется запись `done=0` с reason, тело не сохраняется, checksum — по полному телу. Актуальное
> поведение — [43-body-size-hard-limit.md](43-body-size-hard-limit.md). Текст ниже сохранён исторически.

При `max_body_size_enabled = true` сохраняемые в ClickHouse поля `request` и `response` режутся
до `max_body_size` **символов** (рун, не байт — чтобы не разорвать многобайтовый UTF-8 и не
получить битую запись). При срабатывании в конец дописывается маркер `…(truncated)`.

**Контрольные суммы `checksum_request` / `checksum_response` считаются по ПОЛНОМУ телу** (до
обрезки) — целостность исходного payload сохраняется и видна в логе, даже если само тело урезано.

Обрезка применяется только к сохраняемой копии лога; на тело, отправляемое во внешний узел, она
не влияет.

### 22.3. Сценарные требования к логированию

Запись в ClickHouse не должна ломаться на «сложных» телах. Покрыто тестами (unit + integration на
реальном контейнере ClickHouse):

- большое тело (сотни КБ) — сохраняется и читается байт-в-байт;
- спецсимволы (кавычки, переводы строк, табы, `NUL`, `<`, `&`, `;`), JSON с экранированием,
  unicode/кириллица/emoji — драйвер `clickhouse-go/v2` экранирует сам, ручное экранирование не
  нужно;
- обрезка по рунам даёт валидный UTF-8;
- при `logging_enabled = false` в таблице узла **нет ни одной записи** (`count == 0`).

### 22.4. Telegram-алерты через Prometheus

Раньше планировщик уведомлений (§20) считал ошибки запросами `CountErrors` к ClickHouse — по одному
запросу на узел за тик. Теперь источник — **Prometheus**, единый с графиками панели (§21).

- Введена метрика Sender `nexus_request_incomplete_total{method, node}` — счётчик «незавершённых»
  исходящих вызовов (любой не-2xx: сетевой сбой `status=0`, 3xx, 4xx, 5xx, circuit-breaker).
  Математически это точный эквивалент прежнего ClickHouse-условия
  `status>=400 OR status=0 OR done=0`, поскольку `status>=400` и `status=0` — подмножества
  `done=0`, то есть всё условие сводится к `done=0` ⟺ `!rec.Done`.
- `PromMetrics.NodeErrors(window)` делает **один** запрос
  `sum by (node)(increase(nexus_request_incomplete_total{service="sender"}[window]))`; планировщик
  раскладывает результат по командам, сопоставляя метку `node` с `path` узла.
- **Зависимость:** уведомления теперь требуют настроенного Prometheus. Без него планировщик не
  запускается (warn в лог), как и графики панели. Это сознательная унификация источника.

### 22.5. Раскладка карточками (Overview)

Карточный вид головного экрана приведён к эталону `specs/ui_cards.html`:

- цветная **полоса-акцент** слева по статусу: OK (зелёный), Очередь/Медленно (жёлтый), Down
  (красный), Пауза (синий), Отключён (серый);
- шапка: имя узла (моноширинный, обрезка с многоточием), chip метода, pill статуса с точкой;
- три метрики с разделителями: вход за окно, **p95** латентности, ошибки (красный при `>0`);
- **спарклайн** входящего трафика (12 точек за окно);
- подвал: target URL (или `{URL из запроса}` для динамического режима);
- в тулбаре — фильтр **«Все статусы»**; сортировка по умолчанию `err → warn → paused → ok →
  disabled`, внутри статуса — по убыванию трафика.

**Нагрузка:** спарклайн — один Prometheus `query_range` с `by (node)` на весь список (не зависит от
числа узлов); p95 — один instant-запрос `histogram_quantile` по уже существующей гистограмме
`nexus_request_duration_seconds{service="sender"}` (Sender пишет её и для sync, и для async — новой
метрики не потребовалось).

### 22.6. Форма узла: разделение «Заголовки» и «Логирование»

Прежний единый блок «Заголовки и логирование» разделён на две карточки:

- **«Заголовки»** — управление `forward_headers` (какие заголовки пробрасывать на целевой узел):
  chip-теги с удалением, поле ввода + кнопка «Добавить».
- **«Логирование»** — мастер-тумблер `logging_enabled` вверху (при выключении весь блок
  деактивируется); ClickHouse-шаблон/таблица/retention; чекбоксы `log_request_body` /
  `log_response_body` / `log_headers`; тумблер `max_body_size_enabled` + поле `max_body_size`.
