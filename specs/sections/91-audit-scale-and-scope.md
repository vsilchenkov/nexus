# 91. Журнал аудита: объём выдачи, видимость записей, состав событий

Раздел развивает §7.13 (audit log), §18.1 (глобальные действия), §26/§87 (доступ к журналу),
§86.7 (сквозной скоуп), §72/§77 (механика подгрузки списков).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 91.1 Почему журнал выглядел полупустым

Жалоба звучала как «в аудите мало строк». Записей в БД при этом много: retention 365 дней
(§7.13), housekeeping удаляет только то, что старше. Мало их было **на экране**, и причин
оказалось три независимых.

**Первая: пагинации не существовало.** Страница просила `limit: 200` одним запросом, `offset`
не передавала никогда, кнопки «ещё» не имела. Сервер отдавал `{items}` без общего числа,
поэтому обрезка выдачи ничем не показывалась: 201-я запись просто не существовала для
пользователя. Оставался только CSV-экспорт, но чтобы понять, что чего-то не хватает, надо было
сначала догадаться о самом факте обрезки.

**Вторая: половина событий не попадала ни в один режим просмотра.** Выдача скоупится командой
сессии, а записи о входах, неудачных логинах, восстановлении пароля и действиях над
пользователями пишутся с `team_id IS NULL` (§18.1 — они глобальные, к команде не относятся).
Условие `team_id = $1` такие строки отсекает всегда. Обойти это можно было только вручную
адресом `?team_id=*`, о котором знает разве что автор кода.

**Третья: журнал забивался переключениями команды** — см. §91.2.

Retention к жалобе отношения не имел, но при проверке на стенде это стоит помнить:
`config_debug.yml` держит `audit_retention_days: 30`, то есть на дев-стенде старое действительно
вычищено.

### Что сделано

**Keyset-пагинация вместо offset.** Курсор — пара `(created_at, id)` последней показанной
записи, параметры `before_ts` + `before_id` (работают только вместе: половина курсора означала
бы молча другую выборку, а не «страницу дальше»). Offset остаётся поддержанным для CSV-выгрузки
и совместимости API.

Сортировка стала `ORDER BY created_at DESC, id DESC`. Одного `created_at` мало: метки не
уникальны, порядок среди равных не определён, и записи на границе страницы либо дублировались
бы, либо терялись. По этой же причине курсор сравнивает кортеж, а не отдельные поля. Миграция
0038 добавляет индексы под реальный запрос — `(team_id, created_at DESC, id DESC)` для
командного скоупа и частичный `(created_at DESC, id DESC) WHERE team_id IS NULL` для глобальных
записей: без ведущего `team_id` страница «редкой» команды на инстансе с десятком команд
просматривала бы и отбрасывала чужие строки. Оба индекса обслуживают и `count(*)` счётчика —
он идёт по тем же условиям. Аддитивно: старый индекс по `created_at` остаётся (его используют
выборки по периоду и housekeeping).

**Счётчик «показано N из M».** Новый `GET /api/audit/count` с тем же набором фильтров, но без
`limit` и курсора: он отвечает на вопрос «из скольких», а не «сколько на странице». Условия
`WHERE` для списка и счётчика собирает один общий код — разъехавшись, они дали бы счётчик,
считающий не то, что показано на экране.

**Подгрузка по скроллу** — та же механика, что у логов узла (§72.3/§77): накопление страниц с
дедупом по `id`, подгрузка при приближении к низу, догрузка когда страница короче контейнера,
схлопывание кеша при возврате к верху, потолок накопленных строк. Общая часть вынесена в
переиспользуемое ядро; журнал логов остался его обёрткой и не менялся по поведению.

## 91.2 Состав событий: что журнал перестал и начал записывать

**`team.switch` больше не пишется.** Переключение команды — обычная навигация, а не подотчётное
действие: его выполняет и переход по ссылке на узел или команду (§76/§89.3), то есть записи
появлялись без всякого участия пользователя. При двенадцати командах на бою они вытесняли
содержательные события из видимого окна выдачи — то есть прямо усиливали проблему §91.1.

Вдобавок запись была ещё и бесполезной: `actor` вычисляется до смены команды, поэтому строка
уходила со **старым** `team_id`, и в журнале новой команды (куда пользователь только что
переключился) она не показывалась. Константа удалена, накопленные записи вычищает миграция
0039. Миграция **необратима** — down не восстанавливает удалённое, это фиксируется строкой
«Откат» в CHANGELOG (§74.6). Внимание при выпуске: `scripts/release/rollback_info.py` эту потерю
НЕ пометит — он ищет `DROP TABLE`/`DROP COLUMN`/`DELETE FROM` в `*.down.sql`, а здесь удаление
стоит в `up`. Строку про потерю записей пишем руками (тот же случай, что §87.4).

**`user.logout` начал писаться.** §7.13 требует фиксировать «вход / выход / неуспешный логин»,
константа была объявлена с самого начала, но не использовалась нигде: выходы не попадали в
журнал вовсе. Запись создаётся только после успешного удаления сессии — запись о выходе,
которого не произошло, хуже её отсутствия.

**Глобальные записи видны администратору.** Флаг фильтра добавляет к скоупу строки с
`team_id IS NULL`, и handler ставит его, когда роль сессии `admin`. Для `operator` и `manager`
поведение не меняется — журнал остаётся строго командным. Ручной `?team_id=*` (весь инстанс)
сохраняется как был.

Выбор именно «только админу» осознанный: глобальные записи — это входы и неудачные логины всех
пользователей инстанса, включая тех, кто в команду просматривающего не входит. Показывать их
любому оператору значило бы расширить видимость за пределы членств, чего избегают и §62.3, и
§76.5, и §86.2.

Роль берётся из сессии, а для API-токена её подставляет та же псевдо-сессия, что и для
остальных проверок. Значит токен с ролью admin тоже начнёт получать глобальные записи — это
поведенческое изменение для существующих интеграций, читающих `/api/audit`: выдача станет
шире, но никогда не уже.

CSV-выгрузка использует тот же разбор фильтра, что и экран, поэтому глобальные записи
попадают и в неё — ровно для тех, кто видит их в интерфейсе. Это намеренно: выгрузка,
отдающая другое множество, чем показано в таблице, — источник неверных выводов при разборе
инцидента (то же правило уже действует для сквозного скоупа §86.7).

## 91.3 Интерфейс

Список получает вертикальный скролл-контейнер (до 70 % высоты окна) с подгрузкой по мере
прокрутки. Под таблицей — состояние: «загрузка», «больше записей нет», «показан предел записей»
при достижении потолка накопления. Над таблицей — счётчик «показано N из M».

Карточка со списком рендерится всегда, а не по приходу данных: иначе структура страницы прыгает
при первой загрузке, а сам скролл-контейнер (к нему привязан обработчик) появляется позже первой
страницы.

Попутно исправлено пустое состояние: `colSpan` был жёстко равен 6, тогда как в сквозном режиме
(§86.7) появляется седьмая колонка «Команда» — строка «Нет записей» не растягивалась на всю
ширину таблицы.

## 91.4 Вне рамок

- **Фильтры по периоду, пользователю и цели**, мультиселект действий, поиск по `details` — §7.13
  их описывает, но реализован по-прежнему только фильтр по одному действию (12 значений из 47
  существующих). Отдельная задача: без keyset-пагинации она всё равно не имела бы смысла, а
  теперь имеет.
- **Автообновление журнала** (tail-poll, как у логов узла §77.1). Аудит читают постфактум, при
  разборе инцидента, поэтому живая лента здесь не нужна; механика в общем ядре есть, включить
  можно в любой момент.
- **Виртуализация списка.** Пока действует потолок накопленных строк — тот же подход, что в
  журнале логов.
- **Запись `user.logout` для истёкших сессий.** Пишется только явный выход; сессия, умершая по
  TTL, события не порождает (её никто не «закрывает»).
