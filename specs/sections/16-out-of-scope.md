## 16. Out of scope в v1 / планы на v2

Фичи, сознательно не вошедшие в первую версию ТЗ — зафиксированы здесь, чтобы не возвращаться к ним в каждом обсуждении. При реализации v2 этот список — отправная точка для нового ТЗ.

### Multi-tenancy — ✅ реализовано в v2 (см. §18)

Перенесено в полноценный раздел [§18 Multi-tenancy](18-multi-tenancy.md)
(фазы Phase 10 + Phase 11). Команды (`teams`) с изоляцией узлов, логов,
API-токенов и аудита; своя БД ClickHouse `nexus_<slug>` на команду;
team-switcher в UI; Receiver URL `/v1/request/<team_slug>/<path>`; перенос
узла между командами. Роль `team_admin` (RBAC по `user_teams.role`) и
SaaS-onboarding остаются возможными расширениями — см. §18.8.

Исторический контекст: в v1 колонки `team_id` были закладкой с дефолтом
`'default'`; в v2 (миграция 0008) они стали реальными UUID FK на `teams`.

### Webhook signature verification

В v1 шина только пересылает запросы во внешние узлы; обратных callback'ов от внешних узлов нет.

В v2 предполагается добавить:
- Эндпоинт `/v1/callback/{node_path}` для приёма callback-вебхуков от внешних систем (например, статусы async-доставки, асинхронные ответы на отложенные операции).
- Проверка подписи `X-Signature: hmac-sha256=<hex>` или `X-Hub-Signature-256: sha256=<hex>` (GitHub-style) — алгоритм и формат заголовка выбираются в настройках узла.
- Поле `callback_secret` в `nodes` (зашифрованное, как `auth_credentials`).
- Поведение при невалидной подписи: 401 + запись в audit, метрика `nexus_callback_signature_invalid_total{node}`.
- Маршрутизация валидированных callback'ов: либо записываются как отдельный лог в ClickHouse-таблицу узла, либо пробрасываются в Kafka-топик `nexus.callback`, откуда их забирает интегратор.

### Webhook / уведомления для операторов

В v1 уведомления только в Sentry (для разработчиков). Операторские оповещения о статусе шины — out of scope.

В v2 — отдельный раздел Settings → Notifications с подключениями к Slack, Telegram, generic webhook. Триггеры: узел упал, success rate < N% за M минут, ClickHouse-буфер переполнен, Kafka lag > N, paused-узел в паузе > 7 дней, и т.п. С шаблонами сообщений на двух языках.

### Шаблоны узлов

В v1 каждый узел создаётся с нуля. В v2 — возможность создавать «templates» с предзаполненными значениями (типовая авторизация, retry-policy, набор forward headers) и при создании нового узла применять шаблон.

### Версионирование конфигов узла + откат

В v1 каждое изменение узла перезаписывает старое значение, история — только в audit log как diff. В v2 — отдельная таблица `node_versions` с N последних версий, вкладка «История» в detail-странице узла, кнопка «Откатить к версии». Закроет сценарий «вчера ещё работало, что-то поменяли».

### Bulk-операции и импорт/экспорт

В v1 узлы создаются по одному через UI. В v2 — чекбоксы на Overview с массовыми действиями (включить, отключить, удалить, экспорт), JSON/YAML-экспорт всех или выбранных узлов, импорт с предпросмотром изменений (для миграции между окружениями и GitOps-сценариев).

### Mutating API tokens

В v1 API-токены строго read-only (см. §7.14). В v2 — токены с write-scopes (`nodes:write`, `nodes:delete`) для автоматизации управления узлами из CI/CD. Это требует дополнительной защиты: audit для каждого изменения через токен, требование подтверждения для деструктивных операций, опционально — двухфакторная авторизация при создании write-токена.

### Интеграция с KMS / Vault

В v1 ключ шифрования `ENCRYPTION_KEY` берётся из env (см. §5.5). Архитектура с версионированием `v1:<nonce>:<ciphertext>:<auth_tag>` оставляет место под v2 — интеграция с AWS KMS, HashiCorp Vault или другим внешним секрет-менеджером для управления ключами без рестарта сервиса.

### OpenTelemetry

В v1 трейсинг через Sentry (`EnableTracing`). В v2 — экспорт трасс и метрик через OTLP в Tempo/Jaeger/Grafana. Sentry останется для отлова ошибок и Performance-сэмпла.

### Тег для группировки узлов на Overview

В v1 узлы фильтруются по статусу/имени. В v2 — добавить поле `tags []string` на узле, чтобы помечать `production`, `staging`, `partner-X`, `legacy` и фильтровать по ним. Помогает наводить порядок в 100+ узлах.
