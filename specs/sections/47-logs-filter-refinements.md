# 47. Доработка фильтра логов узла и деталей лога

Раздел уточняет поведение вкладок узла и деталей лога по трём наблюдениям с боя
(nexus.vz78.vozovoz.ru). Развивает §33.4 (клик по графику → логи за момент), §7.4.1/§42 (ленивая
подгрузка тел лога) и §44 (счётчики дашборда, per-node процент ошибок).

## 47.1 Клик по столбцу графика — по сегментам (баг-фикс §33.4)

**Проблема.** Столбец `TrafficChart` показывает суммарное число запросов бакета (высота ∝ `count`),
красной долей снизу — ошибки. По §33.4 клик по столбцу открывает вкладку «Логи» за окно бакета
`[from, to)`. Клик передавал `onlyErrors: d.errors > 0`
([TrafficChart.tsx](../../web-ui/src/components/ui/TrafficChart.tsx)), а
[NodeDetail.tsx](../../web-ui/src/pages/NodeDetail.tsx) `openLogsAt` маппит это в
`status: "err" | "all"`. Итог: если в бакете есть **хоть одна** ошибка, весь столбец открывался с
фильтром «только ошибки» → из, например, 19 запросов пользователь видел лишь 4 (ошибочные).

**Решение.** Сегменты столбца делаются **раздельно кликабельными**:

- клик по **красному** сегменту (ошибки) → логи бакета с `status=err`;
- клик по **синему** сегменту (успешные) → логи бакета со `status=all` (все запросы окна).

Окно `[from, to)` у обоих сегментов одинаковое (границы бакета). При малой доле ошибок красный
сегмент получает минимальную высоту (кликабелен даже при 1–2 ошибках из сотен). Маппинг
`openLogsAt` (`status = onlyErrors ? "err" : "all"`) не меняется — корректность даёт правильный
`onlyErrors` от конкретного сегмента.

**Кавеат (не предмет фикса).** Число на столбце (`count`) берётся из серии метрик узла
(`/api/metrics/nodes/:id`), а строки логов — из ClickHouse по времени. При расхождении источников
(Prometheus считает попытки, ClickHouse — уникальные записи; §44.A) счётчик столбца и число открытых
строк могут отличаться на единицы. Это существующая особенность подсчёта, а не эффект данного фикса.

## 47.2 Поле «Параметры» в детали лога (§7.4.1/§42)

При разворачивании строки лога (`LogBodies` в
[LogsTab.tsx](../../web-ui/src/components/node/LogsTab.tsx)) показываются тело запроса и ответ. Нужно
дополнительно показывать **параметры запроса** (query) записи:

- новый блок «Параметры» располагается **над** сеткой тел request/response;
- заполняется лениво при разворачивании — из того же detail-ответа
  `GET /api/nodes/:id/log/:logId`, поле `parameters` (бэкенд уже отдаёт его в
  `toLogDTO(..., includeBodies=true)` — [logs_handler.go](../../internal/web/adapter/in/http/logs_handler.go);
  тип `LogDetail` уже содержит `parameters?: string`);
- блок **показывается только если параметры непусты**; при пустом значении поле скрыто и не занимает
  места;
- рендер по образцу тела (лейбл + копирование + `<pre>` с `prettyMaybe`). Параметры приходят в
  detail-ответе целиком (обычно короткая query-строка), поэтому чанки/скачивание (§42) не нужны —
  достаточно компактного inline-блока.

Изменение чисто фронтендовое: модель данных, ClickHouse-колонка `parameters` и API уже существуют
(поле используется, например, в replay — [replay.go](../../internal/web/usecase/replay.go)
`url.ParseQuery(orig.Parameters)`).

## 47.3 Убрать per-node процент ошибок из Overview (частичный реверс §44)

§44 добавил «Процент ошибок по каждому узлу» — `nodeErrPct(errors/in)` в
[Overview.tsx](../../web-ui/src/pages/Overview.tsx), выводимый в карточках и строках таблицы узлов.
На практике он «сливается» с числом ошибок и мешает восприятию. Per-node процент и его расчёт
удаляются.

**Общий** процент ошибок в шапке дашборда (`errPct` из `tot.error_rate`, §44.A) **сохраняется** — это
единственное место, где процент ошибок остаётся.

## 47.4 Кликабельный спарклайн на дашборде — дип-линк в логи узла

Мини-график (`Sparkline`) на карточке узла дашборда (рабочий стол, вид «Карточки») делается активным:
клик по столбцу открывает **логи этого узла** за окно соответствующего бакета — так же, как клик по
графику на странице самого узла (§33.4/§47.1).

- **Sparkline** получает опциональный `onOpenLogs(range)`; при заданном обработчике столбцы
  кликабельны (`cursor-pointer`) и передают окно бакета `[start, start+bucketW)` (границы уже
  считаются из `periodWindow(period)` для тултипа).
- **Карточка** навигирует на `/nodes/:id?tab=logs&from=<ms>&to=<ms>` (`useNavigate`). Обработчик
  задаётся только для узлов с таблицей логов (`clickhouse_table`) — иначе бары некликабельны.
- **NodeDetail** читает `tab`/`from`/`to` из query (`useSearchParams`) при монтировании: `tab=logs`
  → стартовая вкладка «Логи», `from`/`to` (мс) → стартовый `LogsInitialFilter` (`status=all`, границы
  через `msToDatetimeLocal`). Переиспользуется существующая машинерия `initialFilter` `LogsTab` —
  отдельного кода фильтрации не добавляется.
- Спарклайн не несёт per-bucket ошибок (окрашен по статусу узла), поэтому деления на «ошибки/успех»
  (как у сегментов §47.1) нет — открываются все запросы бакета (`status=all`). Дип-линк по URL
  переживает перезагрузку и шарится.

## 47.x Scope / неочевидности

- Ни миграций, ни изменений Go-кода: §47.2 использует уже отдаваемое поле `parameters`, §47.1 и §47.3
  — правки React/i18n. Требуется пересборка встроенного SPA-бандла (`internal/web/static/`).
- §47.3 частично отменяет §44 (per-node процент). Общий `error_rate` шапки не затрагивается.
- §47.1 не меняет источник счётчика столбца — расхождение Prometheus↔ClickHouse (§44) остаётся
  диагностируемым через `GET /api/metrics/diagnostics`.
