## 5. Хранилища

### 5.1 PostgreSQL (конфигурация)

Таблицы (минимум):

- `methods` — корневые методы (`request`, `requestAsync`)
- `nodes` — узлы перенаправления (см. §3.3). Дополнительное поле `team_id` (varchar, NOT NULL, default `'default'`) — закладка для будущей multi-tenancy (out of scope в v1, см. §15).
- `node_headers` — заголовки для проброса (FK на `nodes`)
- `users` — пользователи UI (см. §7.9), поля: `id`, `login` (unique, immutable), `email`, `password_hash` (bcrypt/argon2), `role` (`admin` / `viewer`), `active` (bool), `must_change_password` (bool), `lang` (`en` / `ru`, default `en` — см. §7.11), `team_id` (varchar, NOT NULL, default `'default'` — out of scope в v1, см. §15), `created_at`, `last_login_at`
- `user_audit` — append-only журнал действий пользователей (см. §7.13). Поля: `id` (UUID), `user_id` (FK на `users`, nullable для `system`), `user_login`, `action` (string-код), `target_type`, `target_id`, `details` (JSONB), `ip_address` (inet), `created_at` (timestamptz). Индексы по `created_at`, `user_id`, `(target_type, target_id)`, `action`. Retention по умолчанию 365 дней (поле в конфиге `web.audit_retention_days`).
- `clickhouse_settings` — параметры подключения (см. §5.2)
- `app_settings` — singleton-таблица настроек приложения (Sentry, динамические параметры ClickHouse), см. §14.5
- `api_tokens` — read-only API-токены для интеграций (см. §7.15). Поля: `id` (UUID), `user_id` (FK на `users`), `name` (string, человекочитаемое имя — `"grafana-integration"`, `"bi-export"`), `token_hash` (varchar — SHA-256 от секретного значения, само значение в БД не хранится), `prefix` (varchar(8) — первые 8 символов токена, для идентификации в UI), `scopes` (text[] — список scope-кодов: `logs:read`, `nodes:read`, `metrics:read`), `created_at` (timestamptz), `last_used_at` (timestamptz, nullable), `expires_at` (timestamptz, nullable — пожизненный токен или с истечением), `revoked_at` (timestamptz, nullable). Индекс по `token_hash`.

#### Миграции

Все изменения схемы оформляются как файловые миграции в каталоге `/migrations` репозитория. Используется `golang-migrate` (`golang-migrate/migrate`). Имена файлов: `NNNN_short_description.up.sql` и `NNNN_short_description.down.sql`, где `NNNN` — порядковый номер с ведущими нулями.

**Процесс применения:**
- **Автоматически при старте.** Каждый сервис (Receiver, Sender, Web) при старте подключается к PostgreSQL и вызывает `migrate.Up()`. Если есть непримененные миграции — они выполняются последовательно в одной транзакции на миграцию.
- **Concurrency-safe.** `golang-migrate` использует таблицу `schema_migrations` с блокировкой через advisory lock PostgreSQL — несколько одновременно стартующих инстансов не пытаются накатить миграции параллельно. Лидер накатывает, остальные ждут и продолжают старт.
- **Падение миграции — это падение старта сервиса.** Если миграция не прошла (синтаксическая ошибка, конфликт констрейнта, недоступность БД) — сервис пишет ошибку через `ErrorWithOp` в логи и в Sentry, и завершает работу с exit code 1. Перезапуск не помогает — нужно человеческое вмешательство. Это сознательное решение: лучше пустой ответ от балансировщика, чем работа на старой схеме с новым кодом.
- **Откат миграций.** `down`-миграции пишутся для каждой `up` (это требование code review). Применяются вручную через `make migrate-down N=1` — отдельная команда, никогда не автоматически. Откат версии в production — это всегда ручная операция с участием DBA.
- **Совместимость нового кода со старой схемой.** В одной транзакции применяется одна миграция, поэтому во время rolling deploy на коротком окне могут одновременно работать инстансы со старым и новым кодом. Правило: новая миграция должна быть совместима со старым кодом (для DDL — это означает только additive-изменения: добавление nullable-колонок, новых таблиц, индексов CONCURRENTLY). Деструктивные изменения (удаление колонок, переименования) разбиваются на минимум 2 релиза: 1) добавили новое и пишем в оба места; 2) переключили чтение на новое; 3) удалили старое.

**Команды:**
- `make migrate-up` — применить все непримененные миграции (для локальной разработки).
- `make migrate-down N=1` — откатить N последних миграций.
- `make migrate-status` — показать текущую версию схемы и непримененные миграции.
- `make migrate-create NAME=add_node_tags` — создать пару пустых файлов `0042_add_node_tags.up.sql` и `0042_add_node_tags.down.sql`.

**Где смотреть состояние:** запрос `SELECT * FROM schema_migrations ORDER BY version DESC` показывает текущую версию и есть ли «грязные» (dirty) миграции — миграции, начавшие применяться, но упавшие посередине. Dirty-миграции требуют ручного исправления (по сценарию golang-migrate: исправить SQL, пометить версию как `force`).

### 5.2 ClickHouse

Подключение настраивается через UI (см. §7.8). Параметры:
- `host`, `port`
- `database` — имя БД, в которой создаются таблицы узлов
- `user`, `password`
- `protocol` — `native` (TCP, по умолчанию) или `http`
- `tls` — флаг включения TLS
- `batch_size` — размер пачки insert (по умолчанию 500 записей)
- `flush_interval_sec` — максимальный интервал между flush (по умолчанию 5 сек)

UI умеет:
- **Проверять соединение** — ping выполняется по значениям из формы без сохранения. Это позволяет валидировать новые креды до их применения.
- **Сохранить и переподключить** — graceful-переключение: новые логи идут на новый сервер только после успешного ping, иначе откат на старые настройки и сообщение об ошибке.
- **Создавать таблицу для узла** с предложением шаблона `CREATE TABLE` (см. §4.3) и возможностью отредактировать SQL перед выполнением (см. §7.6).
- **Показывать существующие таблицы** в выбранной БД с количеством записей, размером на диске и привязкой к узлу. Таблицы без привязки помечаются как `не привязана`.

### 5.3 Kafka

Брокер очередей для асинхронной доставки сообщений (`/requestAsync`).

#### Топики

| Топик | Назначение | Retention |
|---|---|---|
| `nexus.async` | Основная очередь async-сообщений | 30 дней |
| `nexus.async.dlq` | Dead letter queue (исчерпан retry) | 30 дней |
| `nexus.async.paused` | Delay-очередь сообщений узлов на паузе (§3.6): их переносят сюда, чтобы бэклог одного узла не задерживал соседей по партиции основного топика | 30 дней |
| `nexus.config.events` | Pub/sub для оповещения инстансов о смене настроек (см. §8.4) | 1 час |

**Retention 30 дней** означает, что сообщения хранятся в Kafka месяц с момента записи независимо от того, обработаны они или нет. Это даёт:
- возможность переобработать сообщения за прошедший период при ошибке логики (reset consumer offset),
- защиту от потери данных при длительном простое consumer'а (до 30 дней),
- аудит async-трафика без отдельного хранилища.

Размер диска под Kafka рассчитывается от: `пиковый RPS × средний размер сообщения × 30 дней × replication_factor`. При 500 rps async-трафика и среднем сообщении 2 KB: `500 × 2048 × 86400 × 30 × 3 ≈ 7.7 TB`. На практике async-трафик обычно составляет 10–30% от общего, то есть реальный пик в 50–150 rps async даёт 0.8–2.3 TB. С учётом сжатия lz4 (коэффициент 3–5× на JSON) — реально 0.2–0.5 TB при production-нагрузке. Мониторинг свободного места и алертинг обязательны.

#### Параметры топика

Каждый топик создаётся при старте сервиса (если не существует), параметры — в `kafka.topic` секции конфига:

| Параметр Kafka | Значение | Обоснование |
|---|---|---|
| `partitions` | 4 | Под параллелизм consumer'ов; запас по параллелизму даже для нагрузки выше 500 rps |
| `replication.factor` | 3 (prod) / 1 (compose) | Отказоустойчивость; 3 копии переживут падение одного broker'а |
| `min.insync.replicas` | 2 | Producer с `acks=all` ждёт подтверждения от 2 ISR, что гарантирует durability при падении одного broker'а |
| `retention.ms` | 2592000000 (30 дней) | Требование заказчика |
| `retention.bytes` | -1 | Без лимита по объёму — управляем только временем |
| `segment.ms` | 86400000 (1 день) | Сегменты ротируются раз в сутки — оптимально для retention 30 дней |
| `cleanup.policy` | delete | Удаление сегментов по истечении retention (не log compaction) |
| `compression.type` | lz4 | Хороший баланс CPU/коэффициента сжатия для JSON-payload |
| `max.message.bytes` | 10485760 (10 MB) | Под крупные payload'ы; согласовано с `producer.max_request_size` |
| `unclean.leader.election.enable` | false | Запрещаем выборы лидера из не-ISR реплики (защита от потери данных) |

#### Параметры брокера

Применяются при запуске Kafka-кластера (в production — через Ansible/Helm; в compose — через env-переменные контейнера):

| Параметр | Значение | Обоснование |
|---|---|---|
| `num.network.threads` | 3 | Дефолт Kafka, достаточен для 500 rps |
| `num.io.threads` | 8 | I/O через 8 потоков параллельно |
| `socket.send.buffer.bytes` | 1048576 (1 MB) | Сетевой буфер на отправку |
| `socket.receive.buffer.bytes` | 1048576 (1 MB) | Сетевой буфер на приём |
| `socket.request.max.bytes` | 104857600 (100 MB) | Лимит размера запроса |
| `log.retention.hours` | 720 (30 дней) | Дефолт retention, если на топике не задано |
| `log.segment.bytes` | 1073741824 (1 GB) | Размер сегмента |
| `log.retention.check.interval.ms` | 300000 (5 минут) | Период проверки на удаление просроченных сегментов |
| `num.partitions` | 4 | Дефолт для автосоздаваемых топиков |
| `default.replication.factor` | 3 | Дефолт |
| `min.insync.replicas` | 2 | Дефолт на уровне брокера |
| `auto.create.topics.enable` | false | Топики создаёт приложение явно, со своими параметрами |
| `delete.topic.enable` | true | Разрешить удаление через API (для DevOps-процедур) |
| `transaction.state.log.replication.factor` | 3 | Для exactly-once семантики producer'а |
| `transaction.state.log.min.isr` | 2 | То же |
| `group.initial.rebalance.delay.ms` | 3000 | Задержка перед ребалансировкой при подъёме новых consumer'ов |
| `compression.type` | producer | Использовать сжатие, переданное producer'ом |

#### Параметры Producer (Receiver)

В секции `kafka.producer` конфига. Полный список и обоснование выбора:
- `acks: all` — самая надёжная настройка, ждём подтверждения от всех ISR. С `min.insync.replicas=2` это значит подтверждение от 2 broker'ов.
- `enable.idempotence: true` — гарантирует exactly-once на стороне producer'а в рамках одной сессии (дубликаты не создаются при retry).
- `compression.type: lz4` — сжатие на стороне producer'а, broker сохраняет как есть.
- `linger.ms: 5` — микро-батчинг: producer ждёт до 5 мс, чтобы набрать батч сообщений. Снижает overhead per-message в 5–10 раз при высоком RPS.
- `batch.size: 65536` (64 KB) — размер батча в байтах.
- `buffer.memory: 67108864` (64 MB) — буфер producer'а в памяти.
- `delivery.timeout.ms: 120000` (2 минуты) — общий лимит на доставку одного сообщения с учётом всех retry. По истечении — ошибка, async-обработчик кладёт сообщение в локальный disk-fallback и возвращает клиенту 503.
- `max.in.flight.requests.per.connection: 5` — параллельных запросов от producer'а к одному broker'у. Совместимо с `enable.idempotence=true`.

#### Параметры Consumer (Sender)

В секции `kafka.consumer` конфига:
- `enable.auto.commit: false` — критично: коммитим offset **только после успешной доставки** во внешний узел (см. §4.2). Это гарантирует, что необработанное сообщение не считается «прочитанным».
- `auto.offset.reset: earliest` — при подъёме нового consumer'а с пустым offset (или сброшенным) читаем с начала топика. Поскольку retention 30 дней — есть шанс переобработать всё за месяц.
- `max.poll.records: 500` — за один poll забираем до 500 сообщений; обрабатываем параллельно через пул воркеров (`sender.workers`).
- `max.poll.interval.ms: 300000` (5 минут) — если consumer не вернулся за poll'ом дольше 5 минут, его исключают из группы и партиции переразвешиваются. 5 минут с большим запасом покрывают самый медленный внешний узел.
- `session.timeout.ms: 30000`, `heartbeat.interval.ms: 10000` — стандартные значения для определения зависших consumer'ов.
- `isolation.level: read_committed` — читаем только committed-сообщения (нужно для transactional producer'а, если включим в будущем).
- `instances: 4` — равно числу партиций, максимальный параллелизм. Запускается как 4 consumer-горутины в одном процессе Sender или распределяется между несколькими инстансами Sender'а.

#### Развёртывание

В docker-compose: один broker в KRaft-режиме (без Zookeeper), `replication_factor=1`. Подходит только для разработки.

В production: кластер из 3 broker'ов (KRaft или с Zookeeper-ансамблем), отдельные машины с быстрыми дисками (NVMe SSD рекомендуется), 10 GbE сеть между broker'ами. Конкретное развёртывание production-кластера — за рамками этого ТЗ.

### 5.4 Redis

Redis используется как горячий кеш и быстрое key-value хранилище для оперативных данных. PostgreSQL остаётся источником правды; Redis содержит только производные и временные данные, которые можно полностью пересобрать из PostgreSQL.

**Что хранится в Redis:**

| Префикс ключа | Содержимое | TTL |
|---|---|---|
| `node:{path}` | Конфиг узла (URL, auth, заголовки, ClickHouse-таблица), сериализованный в JSON | 5 минут, продлевается на каждом чтении |
| `node:index` | Set всех известных `node_path` | без TTL, обновляется при изменении конфига |
| `app_settings` | Текущие настройки приложения (Sentry, ClickHouse) | без TTL |
| `session:{token}` | Сессия пользователя UI (user_id, role, lang) | 24 часа (`redis.session_ttl_sec`) |
| `ratelimit:{node}:{minute}` | Счётчик rate-limit на узел | 60 секунд |
| `circuit:{node}` | Состояние circuit breaker (closed/open/half-open + счётчики) | без TTL, управляется логикой |
| `kafka:processing:{msg_id}` | Идемпотентность обработки Kafka-сообщений | 1 час |

**Стратегия записи (write-through):**
- При изменении узла через Web UI запись сначала идёт в PostgreSQL, затем в Redis (или инвалидация ключа `node:{path}`).
- При изменении настроек приложения через UI — то же: PostgreSQL → Redis.

**Стратегия чтения (cache-aside):**
- Receiver при обработке запроса сначала смотрит в Redis по ключу `node:{path}`.
- Если cache miss — читает из PostgreSQL, кладёт в Redis, возвращает.
- При недоступности Redis Receiver автоматически переключается на чтение напрямую из PostgreSQL (с метрикой `nexus_redis_unavailable_total`).

**Что в Redis НЕ хранится:**
- Тела HTTP-запросов и ответов (они уходят прямо в ClickHouse).
- Пароли пользователей (только хеши, и только в PostgreSQL).
- Долгосрочные бизнес-данные.

Redis работает в режиме одиночного инстанса для compose-окружения; в production может быть кластером Redis Sentinel или Redis Cluster (отдельная задача за рамками этого ТЗ).

### 5.5 Шифрование чувствительных полей в БД

Поля `auth_credentials` и `incoming_auth_credentials` в таблице `nodes` (см. §3.3) шифруются перед записью в PostgreSQL и расшифровываются при чтении. Это защищает креды на случай: дампа БД, утечки бэкапов, неавторизованного доступа к Postgres-инстансу. Креды никогда не лежат в БД в открытом виде.

**Алгоритм: AES-256-GCM.** Симметричное шифрование с аутентификацией. Outdated-варианты (AES-CBC, AES-ECB, чистый Base64) не используются.

**Ключ шифрования.** 32 байта (256 бит) случайных данных, base64-кодированные, лежат в env-переменной `ENCRYPTION_KEY`. Никогда в YAML, никогда в git, только в `.env` или внешнем секрет-менеджере (см. §8.3). Генерация ключа разработчиком: `openssl rand -base64 32`.

**Валидация на старте.** При запуске каждый сервис, работающий с шифрованными полями (Receiver, Web), декодирует ключ из base64 и проверяет:
- значение не пустое,
- декодированная длина ровно 32 байта,
- при попытке расшифровать тестовое значение из БД ошибки нет (для миграций — пропускается).

Если хоть одно условие не выполнено — сервис **не стартует**, пишет ошибку через `ErrorWithOp` в логи и Sentry, exit code 1. Лучше не подняться, чем работать со сломанным шифрованием.

**Формат хранимого значения.** В колонке хранится строка вида `<version>:<nonce_base64>:<ciphertext_base64>:<auth_tag_base64>`, где `<version>` — версия формата (сейчас `v1`), `<nonce>` — 12 случайных байтов, уникальные для каждого шифрования, `<auth_tag>` — 16 байтов GCM-тега. Версионирование нужно для будущей ротации алгоритма без миграции данных.

**Что делать с открытыми значениями в коде.**
- Расшифровка происходит только в момент использования — Receiver декрипует перед формированием `Authorization` заголовка, Web — перед отображением в форме редактирования узла (только для админа; маска `***` со скрытым превью).
- В UI значения никогда не возвращаются в API-ответах в открытом виде. На фронтенд приходит `{"auth_credentials_set": true, "auth_type": "token"}` — флаг присутствия, но не сам токен. Редактирование — только через "перезапись" (поле в форме пустое; если пользователь ввёл — заменяем, если нет — оставляем).
- В логах (stdout, ClickHouse, Sentry) значения маскируются как `***` (см. §3.5).

**Ротация ключа** (нечастая операция при подозрении на компрометацию):
1. Сгенерировать новый ключ.
2. Запустить отдельную утилиту `make rotate-encryption-key OLD_KEY=... NEW_KEY=...` — она читает все шифрованные поля старым ключом, перешифровывает новым, записывает обратно. Идемпотентно (можно перезапускать).
3. Подменить `ENCRYPTION_KEY` в `.env` и перезапустить сервисы.
4. После успешного перезапуска старый ключ удаляется из всех мест хранения.

В первой версии используется один ключ — `ENCRYPTION_KEY`. Архитектура совместима с переходом на множественные версии ключей (через `<version>` в формате значения) без миграции — это резерв на будущее. Интеграция с KMS (AWS KMS, HashiCorp Vault) — out of scope в v1.
