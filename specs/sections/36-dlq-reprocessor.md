## 36. Авто-репроцессор DLQ (повторная доставка неудачных async-сообщений до TTL)

> Развивает §34.4/§35 (async-очередь и вкладка «Очередь»). Отвечает на вопрос: «приёмник был
> недоступен, сообщения попали в "Неудачные доставки"; что если адрес снова поднимется — они уже не
> уйдут?». До §36 — не уходят: после исчерпания короткого per-message retry Sender логирует `done=false`,
> публикует копию в `nexus.async.dlq` и коммитит offset. Переотправка — только вручную (replay) или
> проактивной паузой узла. §36 добавляет **автоматическую** повторную доставку из DLQ с ограничением по
> времени жизни (TTL).

### 36.1 Мотивация и принципы

- **Терминальность неудач — осознанный выбор §35** (короткий retry → DLQ, без бесконечной очереди и
  долбёжки мёртвого адреса; один мёртвый узел не должен стопорить общий consumer). §36 НЕ меняет этот
  путь — он добавляет ОТДЕЛЬНЫЙ фоновый процесс, который аккуратно дочищает DLQ.
- **TTL вместо бесконечного retry.** У каждого сообщения есть предельный срок жизни: `received_at +
  node.dlq_ttl_seconds`. По истечении — терминальный отказ (больше не пытаемся). По умолчанию **24 часа**.
- **Никакого head-of-line блокирования.** Репроцессор — самостоятельный фоновый sweeper в Sender
  (отдельная consumer-группа на DLQ), не мешает основному async-consumer'у.
- **Уважение к circuit breaker и tombstones.** Не пытаемся слать, если breaker узла открыт (адрес ещё
  мёртв) или сообщение отменено оператором (§34.4 qcancel).

### 36.2 Модель: периодический sweeper над DLQ

Репроцессор — **периодический** проход (а не непрерывный consumer), по образцу `ch_housekeeping`:
запускается в `sender/app.go` через `safego.Go`, тикает раз в `reprocess_interval` (глобальный конфиг,
дефолт 5 минут). Тик интервала = базовый backoff: повторно опубликованное сообщение естественно ждёт до
следующего прохода, без per-message планировщика и без busy-loop.

Источник — `nexus.async.dlq`, читается отдельной consumer-группой (`<group>-dlq-reprocess`), коммитит по
ходу. Каждое сообщение — сырой envelope (есть `received_at`, `id`, `node_path`, тело) + headers (§34.6:
`reason`, `last_attempt_at`); §36 добавляет header `attempts` (счётчик проходов репроцессора).

### 36.3 Логика обработки одного DLQ-сообщения

Порядок проверок (любая «терминальная» ветка — commit без republish, сообщение покидает цикл):

1. **Парс + резолв узла** по `node_path`. Узел удалён → drop (commit).
2. **Tombstone** (`qcancel:<id>` в Redis, §34.4) → drop: оператор уже отменил сообщение.
3. **TTL**: `now - received_at > node.dlq_ttl_seconds` → терминальный отказ. Логируем финальную запись в
   ClickHouse (`done=false`, `reason="ttl_expired"`), drop. Метрика `dlq_reprocess_ttl_dropped`.
4. **Статус узла**:
   - `disabled` → drop (узел выключен, доставлять некуда).
   - `paused` → republish в хвост DLQ без попытки (вернёмся, когда узел снова активен).
   - `enabled` → дальше.
5. **Retry-backoff** (§36.4): если в header'е есть `next_attempt_at` и `now < next_attempt_at` →
   рано: republish без попытки, сохраняя `next_attempt_at` (attempts не растёт). Метрика `skipped`.
6. **Circuit breaker узла открыт** (адрес ещё мёртв) → не пытаемся (иначе fast-fail-churn); republish в
   хвост (attempts+1). Backoff = интервал прохода. Проверка read-only (`Breaker.IsOpen`: open И cooldown
   не истёк) — не расходует half-open-пробу, в отличие от `Allow`.
7. **Попытка доставки** через переиспользуемый `SendUsecase.Send` (тот же путь, что у основного
   consumer'а: retry/breaker/логирование в CH):
   - `2xx` (`done=true`) → **успех**: commit, без republish. В CH появляется запись `done=true` →
     сообщение «восстановлено», счётчик «Неудачные доставки» за период падает. Метрика
     `dlq_reprocess_succeeded`.
   - не-`2xx` → republish в хвост DLQ (attempts+1, обновить `last_attempt_at`,
     `next_attempt_at = now + dlq_retry_delay_seconds`) + commit. Повтор после задержки. Метрика
     `dlq_reprocess_failed`.

Republish-в-хвост: физически сообщение дублируется в топике со временем, но «живая» копия одна (старую
закоммитили, читаем новую). На успех/TTL republish прекращается — циркуляция останавливается. DLQ
ограничен retention (30д) — самоистекает.

### 36.4 Backoff

Два уровня:

1. **Интервал прохода** (`reprocess_interval`, глобально, дефолт 5 мин) — базовый темп sweeper'а.
2. **Per-message задержка повторной доставки** (`dlq_retry_delay_seconds`, per-node, дефолт **5 мин =
   300 с**, совпадает с интервалом прохода) — при неудачной доставке (не-2xx) сообщение переотправляется
   в хвост DLQ с header `next_attempt_at = now + dlq_retry_delay_seconds`. На последующих проходах, пока
   `now < next_attempt_at`, доставку **не пытаемся**: republish без попытки, сохраняя `next_attempt_at`
   и не инкрементируя `attempts` (метрика `skipped`, reason `retry_backoff`). Это минимальный «пол»
   паузы между повторами одной ошибочной отправки, независимый от общего темпа прохода.

**Эффективная пауза между повторами = `max(reprocess_interval, dlq_retry_delay_seconds)`.** По умолчанию
`reprocess_interval` = 1 мин (sweeper тикает раз в минуту), `dlq_retry_delay_seconds` = 5 мин → повтор
раз в ~5 мин. `dlq_retry_delay_seconds` «прижимает» паузу снизу: чтобы повтор шёл реже/чаще для конкретного
узла — крутят per-node задержку (вплоть до ~1 мин — ниже глобального интервала смысла нет). Общий темп
прохода — глобальный `reprocess_interval`; держите его ≤ минимального per-node delay, который хотите задавать.

Экспоненциальный backoff (`min(2^attempts, cap)`) — out of scope v1; механика `next_attempt_at` уже
заложена и наращивается тем же header'ом при желании.

### 36.5 Настройки

**Per-node (требование пользователя):**
- `dlq_ttl_seconds` `INTEGER NOT NULL DEFAULT 86400` (24 ч), диапазон `[60, 2592000]` (1 мин .. 30 сут).
  Сколько держать сообщение в DLQ и пытаться переотправить, прежде чем сдаться. Миграция `0017`,
  `domain.Node` (+`SetDefaults`/`Validate`/`ErrNodeDLQTTLRange`), PG-маппер, DTO, UI-форма, i18n.
- `dlq_retry_delay_seconds` `INTEGER NOT NULL DEFAULT 300` (5 мин), диапазон `[1, 86400]` (1 с .. 24 ч).
  Минимальная задержка перед повторной доставкой ошибочной отправки (header `next_attempt_at`, §36.4).
  Дефолт совпадает с `reprocess_interval` (5 мин). Миграция `0018` (`NOT NULL DEFAULT 300` атомарно
  заполняет существующие узлы), `domain.Node` (+`SetDefaults`/`Validate`/`ErrNodeDLQRetryDelayRange`),
  PG-маппер (новый столбец последним), DTO, UI-форма, i18n.

**Global (config.yml, секция `sender.reprocessor`):**
- `disabled` `bool` (дефолт `false` → включён, как `receiver.puller.disabled`) — рубильник sweeper'а.
- `interval_sec` `int` (дефолт `60` = раз в минуту) — период прохода sweeper'а; держите ≤ минимального
  per-node `dlq_retry_delay_seconds` (эффективная пауза = `max(interval_sec, dlq_retry_delay_seconds)`).
- `max_scan` `int` (дефолт `1000`) — cap сообщений за один проход (защита брокеров).

«Ещё настройки по TTL по необходимости» — заложено: при желании per-node `dlq_reprocess_enabled bool`
(включить/выключить авто-повтор для конкретного узла) добавляется тем же паттерном.

### 36.6 UI

- **Форма узла**: поле «TTL неудачных доставок» (`dlq_ttl_seconds`), в часах для удобства (хранение в
  секундах), дефолт 24 ч, подсказка «сколько пытаться переотправить, прежде чем сдаться».
- **Вкладка «Очередь» → «Неудачные доставки»**: подсказка «повторяется автоматически до TTL (<N> ч)»;
  опционально колонка «попыток» (header `attempts`). Кнопка ручного «Повторить» остаётся (форс-повтор
  сейчас, не дожидаясь прохода).

### 36.7 Метрики (Prometheus)

`nexus_dlq_reprocess_total{node,result=succeeded|failed|ttl_dropped|skipped|dropped}` +
`nexus_dlq_reprocess_duration_seconds` (длительность одного прохода). Метки `result`:
`succeeded` (доставлено 2xx), `failed` (не-2xx → republish), `ttl_dropped` (истёк TTL),
`skipped` (paused / breaker-open / retry-backoff → republish без попытки),
`dropped` (узел удалён / disabled / отменён оператором — терминальный drop).

### 36.8 Scope

**В scope:** периодический sweeper в Sender; per-node `dlq_ttl_seconds`; глобальные конфиг-флаги;
republish-в-хвост с фиксированным backoff; уважение breaker/tombstone/status; финальный лог `ttl_expired`;
метрики; UI-поле TTL + подсказка.

**Out of scope (v2):** экспоненциальный per-message backoff; отдельный delay-топик; UI-дашборд
репроцессинга; ручной bulk-replay (отдельная мелкая фича поверх существующего replay).

### 36.9 Неочевидности

- **DLQ нельзя физически чистить** (нет DeleteRecords, общая партиция — §35) → «удаление» успешно
  доставленного = просто commit без republish (сообщение перестаёт циркулировать).
- **TTL считается от `received_at`** (исходный приём), а не от попадания в DLQ — чтобы суммарный срок
  жизни был предсказуем независимо от числа проходов.
- **Дубли в CH — норма**: каждый проход логирует попытку (`done=false`), успех — `done=true`. Это
  history/observability, не баг. Счётчик «Неудачные доставки» (`done=0` за период) естественно падает
  при восстановлении (или принудительно — см. §36.10).
- **Отдельная consumer-группа** на DLQ — репроцессор не конкурирует с §35-peek (тот без группы) и с
  основным async-consumer'ом.

### 36.10 Ручная очистка «Неудачных доставок»

Оператор может принудительно очистить неудачные доставки узла (вкладка «Очередь» → секция «Неудачные
доставки» → «Очистить неудачные за период» / «Очистить все неудачные»). Очистка делает **две вещи**:

1. **Останавливает авто-повтор**: ID неудачных сообщений (`done=0` за окно, из CH-логов узла)
   отменяются тем же tombstone-механизмом, что и §34.4 (`QueueCancelWriter.Cancel`). DLQ-репроцессор на
   следующем проходе видит tombstone и **дропает** эти сообщения (`result=dropped`) — больше не
   повторяет. Это и есть «удаление» из DLQ (физически чистить DLQ нельзя — §36.9).
2. **Убирает из вида**: записи `done=0` за окно удаляются из CH-таблицы узла **lightweight DELETE**
   (`DELETE FROM <table> WHERE done=0 AND date_request ∈ окно`). Счётчик/список «Неудачные доставки»
   обнуляются сразу, не дожидаясь, пока старые записи выпадут из периода.

**Эндпоинт:** `POST /api/nodes/{id}/async-queue/purge-failed` (admin/manager, под CSRF), тело
`{from?, to?}` (пусто = всё). Возвращает `{cancelled}` — число удалённых записей. Реализация:
`AsyncQueueUsecase.PurgeFailed` → `FailedLogsPurger` (`LogReaderCH.FailedIDs` + `DeleteFailed`) +
`QueueCancelWriter`. Без ClickHouse/таблицы узла — no-op. Действие пишется в аудит
(`op=purge_failed_period|purge_failed_all`).

**Очистка pending** (`POST .../purge`, §34.4) теперь доступна **всегда** (раньше UI прятал кнопки на
не-paused узле; на активном узле очередь обычно пуста — кнопки безвредны, а на паузе/при лежащем
Sender чистят накопленный backlog).

### 36.11 «Повторить все сейчас»

Кнопка «Повторить все сейчас» (вкладка «Очередь» → «Неудачные доставки») форсирует повтор всех
неудачных доставок узла за период, не дожидаясь следующего прохода авто-репроцессора. Для каждого
неудачного (`done=0`) сообщения за окно:

1. **Re-send**: запрос пере-инжектируется через Receiver (как построчный «Повторить», §7.4.1) — новый
   `id`, маркер `__replay_of`, маскирование/auth узла применяются заново. Для async — снова в
   `nexus.async`.
2. **Отмена оригинала**: при успешном re-send оригинал в DLQ отменяется (qcancel, как §34.4) — иначе
   при восстановлении адреса сообщение доставилось бы **дважды** (replay-копия + авто-повтор оригинала
   репроцессором). Если re-send упал — оригинал НЕ отменяется (остаётся авто-репроцессору).

**Эндпоинт:** `POST /api/nodes/{id}/async-queue/replay-failed` (admin-only, `{from?,to?}`). Реализация:
`ReplayUsecase.ReplayFailed` (общий примитив `LogReader.FailedIDs` с §36.10) + `replayOne` +
`QueueCancelWriter`. Один rate-limit на всю операцию; cap `replayAllCap`=500 за вызов (превышение →
`capped`); при отмене контекста — частичный результат с ошибкой. Возвращает `{total, replayed, failed,
capped}`. Аудит `op=replay_all`. Без CH-таблицы/cancel-writer'а — деградирует (no-op / без отмены).

**Роли.** Все мутации async-очереди (`purge`, `purge-failed`, `replay-failed`) — admin-only
(`authedAdmin`), как и весь экран управления очередью. Построчный «Повторить» (`/logs/:id/replay`)
остаётся доступнее (сессия) — это точечная отладка, а не массовая операция.
