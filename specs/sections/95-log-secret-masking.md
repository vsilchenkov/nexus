## 95. Маскирование секретов в логах узлов по шаблонам

Развивает §22 (маскирование по именам полей), §39 (кросс-маппинг `method`/`http_method`),
§48 (RE2-поиск), §51 (debug-логи и hot-reload), §64/§70 (ClickHouse-таблицы узлов),
§94 (маскирование пути в access-логе nginx — другой сток, см. §95.9).

### 95.1 Проблема

При `path_passthrough` (§39) секрет приходит от клиента **в пути** и оседает открытым текстом в
логе узла (ClickHouse): колонка `url` = `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, колонка
`method` (§39, `RequestPath`) = `bot<ТОКЕН>/getUpdates`. То же у green-api (`waInstance<id>/<метод>/<токен>`).
Существующие механизмы этот случай **не закрывают**:

- `platform/sensitive` маскирует по **именам полей** (заголовки/поля тела), а не по содержимому пути;
- `redactURL` вырезает только **query**, тогда как секрет здесь — в самом пути;
- маскирование nginx (§94/1.31.6) чинит **access-лог балансировщика**, а не лог узла в ClickHouse.

Найдено на бою `nexus-kz` (узлы `telegram`, `green-whatsapp`): живые токены Telegram-ботов и ключи
green-api лежали в логе узла как есть.

### 95.2 Решение

Справочник **regex-шаблонов** в PostgreSQL, по которым Sender маскирует значения **ПЕРЕД записью**
лога в ClickHouse. Управление — в панели (admin-only); применение — в Sender.

- Маскируются колонки **`url`, `method`, `parameters`**. Тела (`request`/`response`) — вне рамок v1
  (§95.8).
- Замена поддерживает **группы** Go regexp (`$1..$9`, `${name}`), чтобы не терять смысл лога:
  `(bot[0-9]+):[A-Za-z0-9_-]+` → `$1:***` оставляет `bot123456:***` (виден бот и id, скрыт токен).
- Шаблоны **глобальные на инсталляцию** (без team-скоупа): маскирование — свойство всего лога.
- Порядок применения — **`sort_order` по возрастанию**, затем `created_at` (детерминизм). Замены
  накладываются последовательно (одно правило может подготовить вход другому).
- Синтаксис — **RE2 (Go `regexp`)**: без backreferences и lookaround.

### 95.3 Модель данных

Миграция `0041_log_mask_patterns` (аддитивная), одна таблица:

| колонка       | тип             | смысл                                                        |
|---------------|-----------------|-------------------------------------------------------------|
| `id`          | UUID PK         | `uuid_generate_v4()` (PG12, §74)                             |
| `pattern`     | TEXT            | RE2-регэксп; компилируемость проверяется на create/update    |
| `replacement` | TEXT DEFAULT '***' | строка замены (поддерживает `$1..$9`, `${name}`)          |
| `description` | TEXT            | назначение (напр. «Telegram bot token»)                      |
| `enabled`     | BOOLEAN DEFAULT true | выключенный остаётся в справочнике, но не применяется   |
| `sort_order`  | INTEGER DEFAULT 0 | порядок применения (по возрастанию)                        |
| `created_by` / `updated_by` | VARCHAR(255) | §63 (Actor.UserLogin)                            |
| `created_at` / `updated_at` | TIMESTAMPTZ  |                                                       |

CHECK: `pattern` 1..500, `replacement` ≤ 200, `description` ≤ 500, `sort_order ≥ 0`. Индекс
`(enabled, sort_order, created_at)` под чтение активных в порядке применения.

**Сиды** (закрывают известные утечки, оператор правит под свои узлы):
`(bot[0-9]{6,}):[A-Za-z0-9_-]{20,}` → `$1:***` (Telegram);
`(waInstance[0-9]+/[A-Za-z]+/)[A-Za-z0-9._-]{20,}` → `$1***` (green-api).

### 95.4 Применение (Sender)

Маскирование — в **единой точке** `chlog.Writer.Write`, до попадания записи в буфер. Это закрывает
разом все три продьюсера (`send.go` sync/breaker-fail-fast, `dlq_reprocess.go` ttl-expired) и не
даёт сырому токену осесть ни в буфере, ни в retry-топике Kafka `nexus.logs.retry` (§38): записи
уходят туда уже замаскированными. Маскировать в `insertBatch` нельзя — это оставило бы вектор утечки
через retry-топик.

Набор шаблонов держит атомарный `LogMaskProvider`: сидится чтением из PG на старте (до первого лога),
обновляется **hot-reload** секции `masking` без рестарта. Некомпилируемый шаблон при сборке набора
пропускается (в БД валидируется на записи; в рантайме — вторая линия защиты, чтобы один битый
шаблон не отключил всё маскирование). Провайдер живёт в `WriterManager` и переживает пересоздание
`Writer`'а при hot-reload ClickHouse (§8.4).

### 95.5 Управление (Web)

CRUD `/api/log-masks` (List / Create / Update / Delete) + `/api/log-masks/preview` — **целиком
admin-only** (шаблоны описывают, как выглядят секреты; operator'ам их не показываем). После каждой
мутации usecase публикует reload секции `masking` — Sender'ы перечитывают справочник. Валидация
(длины + компиляция RE2) выполняется на сервере, не только в UI. Превью применяет тот же
`regexp.ReplaceAllString` к образцу и возвращает результат; недописанный/битый regex — ответ
`valid:false` (200), а не 400, чтобы живой ввод не сыпал ошибки в консоль (образец — превью §23).

### 95.6 Интерфейс (§21.5.2)

Новый пункт «Настройки → **Маскирование логов**» (admin-only), рядом со справочниками §23/§24.
Вкладка логов узла (`LogsTab`) **не меняется** — там отображается уже замаскированное значение.

```
Маскирование логов узлов                              [ + Добавить шаблон ]
Секреты в логах узлов (url · метод · параметры) скрываются по regex-шаблонам.

[ 🔍 поиск по описанию/шаблону ]

 # │ Шаблон (RE2)                    │ Замена │ Описание           │ Вкл │
 ──┼─────────────────────────────────┼────────┼────────────────────┼─────┼──────
  1 │ (bot[0-9]{6,}):[A-Za-z0-9_-]{20,}│ $1:*** │ Telegram bot token │ [✓] │ ✎  🗑
  2 │ (waInstance[0-9]+/[A-Za-z]+/)…  │ $1***  │ green-api token    │ [✓] │ ✎  🗑
```

Диалог add/edit — поля `pattern` / `replacement` / `description` / `sort_order` / `enabled` и **живое
превью** (образец с примером → результат замены). Тумблер «Вкл» в строке переключает `enabled`
(PATCH) без открытия модалки. Удаление — через подтверждение.

### 95.7 Наблюдаемость

- Sender на старте и при reload логирует `applied`/`skipped` (сколько шаблонов принято/пропущено).
- Debug-след §51.9 при тихом сбое чтения (маскирование остаётся no-op, логи пишутся).

### 95.8 Границы (что НЕ входит в v1)

- **Тела `request`/`response` не маскируются** (перфоманс: regex по телам до десятков КБ на каждую
  запись; для тел есть per-node «Ограничить размер тела» §22.2). План на v2.
- Маскирование применяется только к **новым** записям; исторические логи остаются как есть (чистятся
  retention узла §4.3 или вручную).
- RE2, не PCRE: без backreferences/lookaround.
- Слишком широкий шаблон может исказить полезные данные лога — для проверки есть превью.

### 95.9 Соотношение с маскированием nginx (§94/1.31.6) — не дубль

§95 и nginx-маскировка закрывают **два разных стока** одного секрета:

- **§95** — лог узла в **ClickHouse**, который пишет **Sender**;
- **nginx** — **access-лог балансировщика** (stdout контейнера, `docker logs`), который пишет nginx
  **до** того, как запрос дойдёт до Sender.

§95 до логов nginx не дотягивается (другой процесс), nginx-маскировка не влияет на ClickHouse. Токен
проходит оба стока, поэтому нужны оба механизма. Свести к одному нельзя: nginx не читает PG и
маскирует своим `map` в `nginx.conf`.
