# 106. Имя клиента без PTR: NetBIOS-опрос и дозаполнение client_host

Раздел добавляет резолверу имени клиента второй этап — опрос NetBIOS Node Status (UDP/137) для
IPv4-хостов, у которых нет PTR-записи, — и фоновую задачу Sender'а, которая дописывает имена в
уже записанные строки логов с пустым `client_host`. Расписание задачи — cron-выражение в
«Настройки → Общие», применяется без перезапуска.

Развивает [§67](67-client-host-rdns.md) (колонка `client_host`, резолвер `platform/rdns`),
[§105](105-log-client-filter.md) (фасет «Клиент», stale-while-revalidate),
[§94](94-rejected-requests.md) (журнал отказов пользуется тем же резолвером),
[§42.10](42-log-body-streaming.md) (образец дозаполнения мутацией), [§20](20-notifications.md)
(образец cron-планировщика с hot-reload), [§70.4](70-multi-instance-clickhouse.md) (владение
таблицами).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций нет.** Новые ключи
конфига — только блок `sender.rdns.netbios` (§106.5); расписание живёт в `app_settings`.

## 106.1 Повод: разбор боевого узла

Разбор 22.09.2026, узел `vika/dadata_suggestions`, фасет «Клиент» за 60 дней: 7 % записей без
имени клиента.

| IP | Имя (NetBIOS) | Записей за 60 дней |
|---|---|---|
| 192.168.2.5 | SRV-D-1C (dev-сервер 1С) | 21 616 |
| 192.168.6.167 | SRV-D-SQLDEV-HQ (dev SQL) | 5 746 |
| 192.168.3.15 | PC7821518 (рабочая станция) | 3 |

Причина — в корпоративном DNS, а не в резолвере §67. Контроллеры домена VZ78 авторитетно держат
одну обратную зону `168.192.in-addr.arpa` на все подсети 192.168.x. Для серверной подсети
192.168.86 PTR-записи заведены, для 2/3/6 — нет (авторитетный NXDOMAIN), хотя прямые A-записи
`<имя>.vz78.vozovoz.ru` есть у всех трёх. Хосты — Windows-машины домена и отвечают на NetBIOS
Node Status (`nbtstat -A`, `nmblookup -A`) именем `<00>`.

**Проба с боевого сервера шины** (`nmblookup -A` из сетевого пространства контейнера `sender`):

| IP | Ответ серверу шины | Ответ рабочей станции 192.168.8.x |
|---|---|---|
| 192.168.2.5 | нет (и `nmblookup -r` с хоста — нет) | да |
| 192.168.6.167 | да (`SRV-D-SQLDEV-HQ <00>`) | да |
| 192.168.3.15 | нет | да |
| 192.168.86.113 (контроль) | нет | — |

**Граница этого раздела.** UDP/137 из контейнера проходит (6.167 ответил), а большинство хостов
не отвечают именно серверу шины: скорее всего, область правила Windows Firewall «NB-Name-In»
ограничена подсетями рабочих станций, либо межвлановый ACL режет UDP/137 из серверного
сегмента. Этап NetBIOS закрывает тех клиентов, которые серверу шины отвечают (на момент разбора —
6.167). Главный объём (2.5) закрывается только на стороне инфраструктуры: регистрацией PTR в зоне
`168.192.in-addr.arpa` (правильно) или расширением области правила NB-Name-In. Реализация от
этого не зависит: этап выключен по умолчанию и включается, когда хосты отвечают.

## 106.2 Второй этап резолва

Цепочка фонового резолва `resolveOnce` (§67.2) становится такой:

1. Redis `GET nexus:rdns:<ip>` — как прежде; пустая строка — негативный хит.
2. PTR-lookup с `timeout_ms` — как прежде.
3. **Новое.** PTR ничего не дал (NXDOMAIN, пустой ответ, ошибка DNS), этап включён и адрес —
   IPv4: запрос NetBIOS Node Status (RFC 1002 §4.2.17–18) на `<ip>:137`.
4. Результат (позитивный или негативный) — в Redis и L1 с теми же `cache_ttl_sec` /
   `negative_ttl_sec`. Отдельного TTL у имён NetBIOS нет.

**Выбор имени.** Из таблицы имён ответа берётся первое уникальное имя (флаг группы снят) с
суффиксом `<00>` (служба рабочей станции). Имя обрезается от завершающих пробелов/NUL, длина
≤ 15, символы только `[A-Za-z0-9_-]`; имя с любым другим байтом (OEM-кодировка, пунктуация)
пропускается и берётся следующее подходящее. Групповое имя домена (`VZ78 <00> GROUP`) и имя
службы файлов `<20>` не подходят. К короткому имени дописывается DNS-суффикс из
`sender.rdns.netbios.suffix` через точку (`SRV-D-1C` → `SRV-D-1C.vz78.vozovoz.ru`), чтобы имена
NetBIOS в фильтре выглядели так же, как PTR-имена; пустой суффикс — короткое имя как есть.

**Контракт `Lookup` не меняется** — ноль I/O на пути доставки: этап работает только внутри
фонового резолва. IPv6 и не-IP значения этап не трогает. Отмена контекста (остановка сервиса)
посреди цепочки больше не кешируется как негативный ответ — раньше остановка посреди PTR-запроса
оставляла в кеше пустое имя на `negative_ttl_sec`.

**Debug-инструментация §51.9.** Атрибут `source` исхода резолва: `redis`, `dns`, `dns_negative`,
`netbios`, `netbios_negative`. Клиент NetBIOS пишет Debug на каждый запрос: `ip`, `port`, число
имён, `duration_ms`, ошибка. Молчащий хост — норма, Warn не пишется.

**Реализация.** Кодек и UDP-клиент — отдельный пакет `internal/platform/netbios` (парсер внешних
байт покрыт фаззингом); резолвер видит только функцию `func(ctx, ip) (string, error)`
(`rdns.WithNetBIOS`). Сокет «подключённый» (`DialContext("udp4")`): датаграммы от других адресов
отбрасывает ядро, ICMP port unreachable приходит быстрой ошибкой, а не таймаутом. Отмена ctx
снимает блокировку чтения через `context.AfterFunc` — своих горутин у клиента нет.

Резолвер общий для Sender (колонка `client_host`) и Receiver (журнал отказов §94), обе стороны
собирают его одной функцией `bootstrap.NewHostResolver` из секции `sender.rdns`.

## 106.3 Дозаполнение пустых client_host

Имя, которого не было в момент записи (первая запись нового IP, окно негативного кеша, этап
NetBIOS включён позже, PTR завели позже), в самой строке лога уже не появится. Задача Sender'а
дописывает его по расписанию (§106.4).

**Один цикл:**

1. Список управляемых таблиц — `ListClickHouseTables` (внешние таблицы §64 исключены на уровне
   SQL), затем мягкий гейт владения §70.4 `FilterManagedTables` — тот же, что у стартовых
   `ALTER` и `BackfillBodySizes`. Имя таблицы перед подстановкой в SQL проверяется
   `domain.IsValidCHTableName`.
2. По таблице: `SELECT DISTINCT IP FROM <t> WHERE client_host = '' AND IP != '' LIMIT 1000`
   (таймаут 2 минуты).
3. Каждый IP — синхронным резолвом полной цепочкой `Resolver.ResolveNow` (свежий L1 → без I/O;
   иначе Redis → PTR → NetBIOS, кеши заполняются, дедуп с фоновыми резолвами через singleflight),
   до 8 одновременно.
4. Если нашлось хотя бы одно имя — **одна** асинхронная мутация на таблицу:

   ```sql
   ALTER TABLE <t> UPDATE client_host = transform(IP, ['192.168.2.5', …], ['SRV-D-1C.vz78.vozovoz.ru', …], client_host)
   WHERE client_host = '' AND IP IN ('192.168.2.5', …)
   ```

   IP попадает в литерал, только если разбирается `net.ParseIP`; имя — только если проходит
   `^[A-Za-z0-9._-]{1,253}$`. Кавычек и обратных слешей в литералах поэтому быть не может.

**Идемпотентность.** Мутация трогает только строки с пустым `client_host` и только IP с найденным
именем; непустые имена не перезаписываются никогда. Повторный цикл после выполнения мутации
этих строк уже не видит. IP, для которых имя не нашлось, переспрашиваются каждый цикл — дёшево:
их негатив лежит в кеше `negative_ttl_sec`.

**Деплой-окно.** Таблица без колонки `client_host` (коды ClickHouse 10/16/47, как в §67.5) —
Debug и пропуск, не ошибка.

**Несколько реплик Sender.** Цикл берёт Redis-лок `sender-client-host-backfill` (TTL 15 минут);
реплика, не взявшая лок, пропускает цикл. Без Redis задача не запускается вовсе: нет ни
hot-reload расписания, ни лока (так же устроена политика защиты узла §98.5).

У Receiver'а задачи нет: журнал отказов §94 хранит имя в PostgreSQL-агрегатах и пересчитывает
его при сбросе.

## 106.4 Расписание в «Настройки → Общие»

Поле `general.client_host_backfill_cron` в `app_settings` (JSONB, миграция не нужна).

| Значение | Поведение |
|---|---|
| не задано (`null`) | расписание по умолчанию `0 * * * *` — раз в час, в начале часа |
| `""` | дозаполнение выключено |
| cron-выражение | стандартный 5-полевой cron (`cron.ParseStandard`, как у Telegram §20), время — часовой пояс контейнера Sender'а (`TZ`) |

**Почему раз в час.** Дефолт выбран так, чтобы имя появлялось в логах в пределах часа после
того, как его стало можно узнать (завели PTR, открыли UDP/137, истёк негативный кеш). Цена —
цикл каждый час читает колонки `IP` и `client_host` каждой управляемой таблицы целиком
(`SELECT DISTINCT … WHERE client_host = ''`). Обе колонки узкие и хорошо сжимаются, но на
очень больших таблицах интервал разумно увеличить в настройках. Лок цикла живёт 15 минут и
досрочно не снимается: при часовом интервале следующий тик его уже застаёт свободным, а
расписание чаще 15 минут фактически выполняется не чаще раза в 15 минут.

**Hot-reload.** Сохранение публикует событие `general` в `nexus:config:reload`; Sender перечитывает
поле из `app_settings` и пересобирает планировщик сразу (у `robfig/cron` расписание записи не
меняется — только полная пересборка, как в `NotificationScheduler.Reschedule`). То же выражение —
no-op. Невалидное выражение из БД (правка в обход API) оставляет прежнее расписание и пишет
ошибку; через API его не сохранить — 400 `domain: invalid client_host backfill cron expression`.

**UI.** Поле после «Срока хранения журнала отказов», с подсказкой, что делает задача, и строкой
«Изменения применяются на всех инстансах без перезапуска». Интерфейс отправляет поле, только
если оно изменилось, в том числе пустую строку: иначе выключить задачу было бы нельзя
(у числовых полей пустое значение значит «не трогать»).

## 106.5 Конфиг `sender.rdns.netbios`

```yaml
sender:
  rdns:
    netbios:
      enabled: false      # этап выключен по умолчанию
      port: 137
      timeout_ms: 1000    # таймаут одного запроса
      suffix: ""          # DNS-суффикс к короткому имени; "" = как есть
```

Валидация: `port` 1…65535, `timeout_ms` 1…60000, `suffix` пустой или DNS-имя
(`^[A-Za-z0-9-]+(\.[A-Za-z0-9-]+)*$`, ≤ 237 — полное имя из 15 символов NetBIOS-имени, точки и
суффикса обязано уложиться в 253 символа DNS-имени, иначе дозаполнение его молча отбросило бы).
Точки по краям (`vz78.vozovoz.ru.`) допустимы и обрезаются. Заодно отрицательные `timeout_ms`,
`cache_ttl_sec`, `negative_ttl_sec` самой секции `rdns` отклоняются на старте.

**Секция не перечитывается на лету** — после правки перезапустить `sender` и `receiver`. Этап
зависит от сети, а не от оператора, поэтому живёт в конфиге, а не в настройках интерфейса.

## 106.6 Инфраструктура

- UDP/137 из контейнеров `sender` **и** `receiver` до клиентских подсетей.
- На клиентских хостах — включённый NetBIOS over TCP/IP и входящее правило «NB-Name-In» с
  областью, включающей адрес сервера шины.

Проба до включения этапа (Sender на HA-оверлее — `sender-1`):

```sh
docker run --rm --network container:$(docker compose ps -q sender) alpine:3.20 sh -c \
  'apk add -q --no-cache samba-client && for ip in 192.168.2.5 192.168.6.167; do nmblookup -A $ip; done'
```

Ответ — таблица имён (`SRV-D-SQLDEV-HQ <00> - B <ACTIVE>`); `No reply from …` — хост серверу
шины не отвечает.

## 106.7 Границы защиты и неочевидности

- **Подмена ответа в LAN.** UDP без аутентификации: узел той же сети может ответить за чужой
  адрес. Подключённый сокет отбрасывает датаграммы с других адресов, ответ сверяется по номеру
  транзакции, имя проходит строгий фильтр символов. `client_host` — информационная подпись, на
  доступ и маршрутизацию она не влияет.
- **Выключенный хост.** Хост, который обычно отвечает, но был выключен в момент обновления кеша,
  получает пустое имя на `negative_ttl_sec` — та же граница, что у временного сбоя DNS (§105.5).
  Строки, записанные в это окно, дозаполнит следующий цикл.
- **Кап DISTINCT.** 1000 IP на таблицу за цикл без упорядочивания: если в таблице больше 1000
  разных IP без имени, часть разрешимых может ждать следующих циклов. Неразрешимые IP стоят
  дёшево (негативный кеш).
- **Объём мутации.** Одна мутация на таблицу за цикл, условие по лёгким колонкам. Незавершённые
  видны в `system.mutations WHERE is_done = 0`, зависшую можно снять `KILL MUTATION`.
- **Время срабатывания.** Cron считает время контейнера Sender'а; при `TZ` не задан — UTC.

## 106.8 Вне рамок

- Дозаполнение имён в агрегатах журнала отказов §94.
- Внешние таблицы §64 — владельцы при желании выполняют ту же мутацию вручную.
- Статический словарь «IP → имя», NetBIOS по IPv6, WINS, LLMNR/mDNS.
- Приведение имён к одному регистру (как в §105).
- Prometheus-метрики этапа и задачи — только логи, как в §67.
- Перечитывание блока `netbios` на лету.
- Кнопка «запустить сейчас» и человекочитаемая расшифровка cron в интерфейсе.

## 106.9 Проверка результата

- `internal/platform/netbios`: golden-запрос, разбор ответа (включая усечённые, чужой номер
  транзакции, ошибку RCODE, сжатое имя), фаззинг парсера, клиент против UDP-сервера на
  `127.0.0.1`.
- Резолвер: NetBIOS не вызывается при успешном PTR, вызывается при пустом, суффикс, IPv6,
  негативный кеш, `ResolveNow` на холодном кеше, отмена не кешируется.
- Задача: SQL мутации (golden, отбраковка IP и имён), фильтр владения, лок, `SetSchedule`
  (выключение, та же строка, смена, плохое выражение); integration — мутация в настоящем
  ClickHouse, непустые имена не тронуты, повторный цикл мутаций не добавляет, таблица без колонки.
- Настройки: валидация cron (400), публикация `general`, поле доходит до Sender'а через узкий
  overlay `bootstrap`; UI — гидратация, отправка изменённого значения и пустой строки.
- Стенд: `X-Forwarded-For` с адреса NetBIOS-хоста → `source=netbios` в Debug; cron на ближайшую
  минуту → `client_host backfill armed` без рестарта → мутация → имя в фасете «Клиент».
