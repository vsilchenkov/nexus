# 88. Почта (SMTP) и восстановление пароля

Раздел вводит в шину исходящую почту и построенное на ней самостоятельное восстановление
пароля пользователем. Две части связаны: восстановление без почты не работает, а иной
потребности в почте у шины пока нет. Развивает §7.1 (аутентификация), §7.9/§7.10
(управление пользователями), §20 (уведомления — образец секции настроек с тестовой
отправкой), §26.4 (self-service смена пароля), §28 (публичный адрес приложения),
§9.4 (rate limit).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 88.1 Проблема

Забытый пароль сегодня чинится только руками администратора. Сменить пароль можно двумя
способами, и оба требуют чего-то, чего у забывшего человека нет:

- `POST /api/users/:id/password` — нужна роль `admin`;
- `POST /api/me/password` (§26.4) — нужен **текущий** пароль.

Пользователь, который пароль не помнит, обязан дойти до администратора. На боевой установке
это десятки человек в двенадцати командах, и каждый такой случай — ручная операция с выдачей
временного пароля в мессенджере.

Почтового канала у шины при этом нет вовсе: единственный внешний канал уведомлений — Telegram
(§20). Колонка `users.email` существует с первых миграций и заполняется администратором в
`Настройки → Пользователи`, но не используется нигде, кроме поиска по списку.

## 88.2 Модель настроек

Настройки почты — новая секция `mail` в singleton-конфиге `app_settings` (JSONB), как
`sentry`, `clickhouse` и `notifications`. Отдельной таблицы не заводится. Все поля —
указатели: `nil` означает «не задано, взять дефолт».

Имя секции — `mail`, а не `smtp`: SMTP здесь деталь транспорта (появится отправка через
HTTP API провайдера — переименовывать секцию будет нельзя, имя уже лежит в сохранённом
JSONB и в шине reload-событий), и внутрь секции входит не только транспорт, но и параметры
самого восстановления.

| Поле | Тип | Дефолт | Валидация |
|---|---|---|---|
| `enabled` | bool | `false` | — |
| `host` | string | `""` | непустой при `enabled`, без схемы и пробелов |
| `port` | int | `587` | 1…65535 |
| `encryption` | string | `starttls` | `none` \| `starttls` \| `tls` |
| `auth_type` | string | `plain` | `none` \| `plain` \| `login` \| `cram-md5` |
| `username` | string | `""` | ≤ 255 |
| `password` | string | `""` | ≤ 255, **маскируется** при чтении |
| `from_address` | string | `""` | синтаксис адреса; обязателен при `enabled` |
| `from_name` | string | `Nexus` | ≤ 128, **без `\r\n`** |
| `helo_host` | string | `""` | ≤ 255, без пробелов |
| `timeout_sec` | int | `10` | 1…120 |
| `skip_tls_verify` | bool | `false` | — |
| `password_reset_enabled` | bool | `false` | требует `enabled` |
| `password_reset_ttl_min` | int | `60` | 5…1440 |

Дефолт `enabled = false` — fail-closed: незаполненная секция не должна означать «шлём почту
непонятно куда».

`helo_host` заведён не для полноты: в контейнере имя хоста — случайный hex, и часть
корпоративных релеев такое `EHLO` отвергает. Поле снимает целый класс инцидентов ценой одной
строки в форме.

Запрет `\r\n` в `from_name` — защита от инъекции заголовка письма: перевод строки в этом поле
позволил бы дописать произвольные MIME-заголовки. По той же причине имя пользователя **не
подставляется в тему** письма (§88.6).

**Пароль SMTP хранится в JSONB открытым текстом** — ровно как DSN Sentry и пароль ClickHouse;
шифрование `app_settings` в шине не реализовано вообще (AES-256-GCM применяется только к
кредам узлов). Защита — маскирование при чтении через API и admin-only доступ к разделу.
Это расхождение с §5 фиксируется здесь явно и отдельным разделом не лечится.

Изменение секции публикует reload-событие `mail`. Перезагружать сам транспорт не нужно —
соединение с релеем живёт одну отправку и создаётся из свежепрочитанных настроек. Событие
обслуживает другое: признак «восстановление доступно», который отдаётся форме входа
(§88.4.5) и держится в памяти процесса, а не читается из БД на каждый запрос.

## 88.3 Транспорт

Отправка вынесена в отдельный пакет платформы с узким контрактом: конфигурация, сообщение
(тема, текстовая часть, HTML-часть, получатель) и единственный метод отправки. Потребители —
usecase тестовой отправки и usecase восстановления — работают с интерфейсом, объявленным на
своей стороне, и типов почтовой библиотеки не видят.

Используется **`github.com/wneessen/go-mail`** (MIT) — единственная новая прямая зависимость
раздела. Транзитивных модулей она не добавляет: `golang.org/x/crypto` и `golang.org/x/text`
уже в графе зависимостей.

Решение принято сравнением двух написанных реализаций. Стандартная библиотека `net/smtp`
закрывает только сам диалог, и в объёме этого раздела требует ~250 строк собственного кода
против ~90, причём ~145 из них — протокол и кодировки:

- **implicit TLS (порт 465)** `smtp.SendMail` не умеет — нужен ручной TLS-handshake до
  создания клиента;
- **PLAIN поверх нешифрованного канала** стандартная библиотека намеренно запрещает, а
  внутренние релеи на порту 25 настроены именно так — нужна своя реализация механизма
  аутентификации;
- **`AUTH LOGIN` в стандартной библиотеке отсутствует полностью**, а Exchange часто предлагает
  только его; строки-вызовы сервера при этом не стандартизированы (`Username:`, `User Name`, …);
- **MIME** (RFC 2047 в теме, `multipart/alternative`, quoted-printable) собирается руками;
- **таймаут и контекст** навешиваются вручную — дедлайном на сокет и сторожевой горутиной.

Существенно, что все перечисленные места ломаются **молча**: ни компилятор, ни линтеры, ни
`go vet` не видят ни неверной кодировки темы, ни перепутанного порядка `boundary`. Симптом —
нечитаемое письмо у получателя. Репозиторий действительно предпочитает писать своё
(`ackspec` §83, `logsearch` §48), но там доменные мини-языки без stdlib-аналога и без
совместимости по проводу; здесь — чужой формат и чужой сервер.

Режим `starttls` требует шифрования **обязательно**: если сервер не предлагает `STARTTLS`,
отправка завершается ошибкой. Молчаливый откат в открытый канал для письма со сбросом пароля
недопустим.

`skip_tls_verify` отключает проверку сертификата сервера — режим для самоподписанных
внутренних релеев. Интерфейс предупреждает о небезопасности, но не запрещает.

## 88.4 Восстановление пароля

### 88.4.1 Хранение токена

Токен восстановления хранится в PostgreSQL, а не в Redis. Redis дал бы TTL из коробки и
обошёлся без миграции, но проигрывает на трёх требованиях раздела: подсчёт активных запросов
на пользователя, гашение всех выданных ссылок при смене пароля (в Redis — обход ключей на
**каждую** смену пароля) и различение «ссылка истекла» против «ссылка уже использована».
Плюс прецедент: API-токены (§7.14) хранятся ровно в такой форме.

**Таблица `one_time_tokens` (миграция 0036) — общая, а не под один сценарий.** Восстановление
пароля лишь первый её потребитель: §88.12 уже называет следующих — подтверждение email при
его смене и приглашение пользователя. Все такие механизмы отличаются только назначением и
полезной нагрузкой, а инварианты у них общие: случайный токен, хранение хеша, одноразовость,
срок жизни, привязка к пользователю, предел числа активных ссылок. Разводит их колонка
`purpose` (`VARCHAR(32)` под `CHECK`-ограничением — образец `users.role`, миграции 0013/0035:
опечатка в назначении иначе выдавала бы токены, которые молча никогда не найдутся; цена —
новое назначение требует миграции).

Состав записи: идентификатор пользователя, назначение, **SHA-256-хеш токена** (сам токен в БД
не попадает — дамп базы не даёт возможности войти), полезная нагрузка назначения (`JSONB`,
для восстановления пароля всегда пустая), момент создания, момент истечения, момент
использования, IP запросившего. Токен — 32 байта из криптографического генератора в
URL-safe base64.

Одноразовость обеспечивается атомарной операцией «пометить использованным, если ещё не
использован и не истёк» — гонка двух одновременных подтверждений невозможна на уровне СУБД.

**Погашение обязано фильтровать по `purpose`, и это граница безопасности, а не аккуратность.**
Как только в таблице лежат токены разных назначений, запрос без фильтра позволяет обменять
ссылку, выданную на слабое действие (подтверждение адреса), на сильное (смена пароля).
Требование закрепляется тестом: токен чужого назначения на эндпоинте подтверждения
восстановления обязан быть отвергнут как недействительный.

Просроченные записи удаляются лениво, при создании очередного токена, с хвостом в 7 дней:
отдельный фоновый процесс ради этого не заводится, а хвост оставлен для расследований.

Число одновременно действующих ссылок **одного назначения** на пользователя — **не более 3**.
Превышение не создаёт токен и не шлёт письмо, но ответ клиенту не меняется (§88.4.3).

### 88.4.2 Эндпоинты

Три публичных маршрута, объявленных рядом с входом и вне групп, требующих аутентификации:

| Маршрут | Запрос | Ответ |
|---|---|---|
| `POST /api/auth/password-reset/request` | `{login}` — логин **или** email | `202 {"ok":true}` во всех содержательных исходах; `400` — негодное тело; `429` — лимит |
| `GET /api/auth/password-reset/validate?token=…` | — | `200 {"valid": true\|false}` |
| `POST /api/auth/password-reset/confirm` | `{token, new_password}` | `204`; `400` с локализованной ошибкой; `429` |

Код `202`, а не `200`: письмо уходит фоном, «принято к обработке» — честная семантика.

Проверка CSRF, висящая на всей группе `/api`, эти маршруты **не обходит и обходить не должна**:
запросы методом GET проходят всегда, POST с пустым `Origin` проходит (внешние инструменты и
интеграционные тесты), POST с `Origin` того же хоста проходит (SPA). Сторонний сайт,
пытающийся инициировать сброс от имени открывшего его пользователя, получает отказ до
обработчика.

Резолв пользователя: сначала точное совпадение по логину (он уникален), при промахе — по
email без учёта регистра. Колонка `email` уникальности не имеет, поэтому **несколько
совпадений трактуются как «не найден»**: письмо не уходит, чтобы владелец одного из адресов
не получил ссылку на чужую учётную запись.

### 88.4.3 Единый ответ без утечки

Форма восстановления публична, поэтому различающиеся ответы превратили бы её в справочник
существующих логинов и почтовых адресов. Ответ `202` возвращается **одинаковым** во всех
исходах: письмо отправлено, пользователя нет, у него не указан email, он отключён, email
неоднозначен, превышено число активных ссылок, почта выключена.

Настоящая причина уходит в аудит (поле `reason` записи) и в служебный лог. Администратор
видит её в разделе «Аудит» — просто не через публичную форму.

Постоянное время ответа искусственно **не выравнивается**, и это осознанно:

- обработчик всегда делает одинаковую работу — проверку лимита и один индексный поиск, — и
  отвечает, не дожидаясь SMTP; разница «есть/нет пользователя» составляет попадание против
  промаха по индексу и неразличима на фоне сетевой задержки;
- искусственная задержка разницу не устраняет, а маскирует, зато даёт способ удерживать
  соединения на публичном эндпоинте;
- существующая форма входа течёт по времени сильнее: проверка пароля выполняется только для
  найденного пользователя. Раздел эту планку не опускает, но и не поднимает.

### 88.4.4 Ограничение частоты

Действует существующий механизм лимитов (окно в минуту, общий Redis, деградация в пропуск при
недоступности Redis). Три независимых ключа, все с одним лимитом
`web.password_reset_rate_limit_per_min` (дефолт **5**, `-1` — выключить):

- по IP запрашивающего — против массовой рассылки с одного адреса;
- по **введённой строке** — против точечного заваливания ящика конкретного человека;
  считается независимо от того, существует такой пользователь или нет, иначе сам лимит стал
  бы способом узнать ответ;
- по IP на подтверждении — против перебора токенов.

### 88.4.5 Видимость функции на форме входа

Ссылка «Забыли пароль?» показывается, только если восстановление действительно работоспособно:
почта включена и настроена (хост, адрес отправителя), восстановление разрешено и **задан
публичный адрес приложения** (§28). Последнее условие обязательно: без публичного адреса
ссылка в письме получится без хоста — письмо уйдёт, а перейти по нему будет некуда.

Признак отдаётся полем `password_reset_enabled` в уже существующем публичном ответе
`GET /api/version`, который форма входа и так запрашивает — дополнительного обращения к
серверу не появляется. Значение держится в памяти процесса и обновляется по reload-событию
`mail` (§88.2): этот эндпоинт опрашивают в том числе соседние инстансы (§73), и чтение БД на
каждый его вызов недопустимо. Ошибка чтения — признак `false`, ссылки нет (fail-closed).

Обработчик `request` при выключенной функции отвечает **тем же** `202`: контракт эндпоинта не
должен зависеть от того, узнал ли клиент признак, и второго способа выяснить конфигурацию
появляться не должно.

### 88.4.6 Проверка ссылки не расходует токен

Проверка при открытии страницы (`validate`) токен **не гасит**; гасит только подтверждение
(`confirm`).

Помимо очевидного удобства (человек узнаёт о протухшей ссылке сразу, а не после того, как
дважды ввёл новый пароль), здесь есть практическая причина: корпоративные почтовые шлюзы с
защитой от вредоносных ссылок **сами открывают** адреса из писем. Гасись токен на открытии,
сканер убивал бы ссылку раньше адресата.

Окно между проверкой и подтверждением может истечь, поэтому интерфейс обязан показывать
состояние «ссылка недействительна» и по ошибке подтверждения тоже.

## 88.5 Отправка письма выполняется фоном

Синхронно выполняются резолв пользователя, все проверки, создание токена и запись в аудит.
Ответ отдаётся сразу после этого. Само письмо отправляется в отдельной горутине с
собственным таймаутом.

Причины две:

- **тайминг**: синхронная отправка сделала бы время ответа оракулом («доли секунды — такого
  пользователя нет, три секунды — есть»), обесценив §88.4.3;
- **отзывчивость**: диалог с релеем занимает секунды, а при его недоступности — до таймаута;
  публичный неаутентифицированный эндпоинт, висящий десять секунд, — готовый усилитель
  отказа в обслуживании.

Токен записывается **до** запуска отправки: письмо, доехавшее раньше записи, дало бы мёртвую
ссылку.

Цена решения признаётся явно: **пользователь не узнает из ответа, что письмо не ушло**.
Поэтому кнопка «Отправить тестовое письмо» в настройках обязательна — она и есть синхронная
диагностика с внятной ошибкой. Сбой фоновой отправки виден администратору в аудите
(`reason: send_failed`), в служебном логе уровня `error` (то есть и в Sentry) и в метриках.
Перезапуск сервиса между ответом и отправкой теряет письмо; очередь и повторы не вводятся,
пользователь повторяет запрос.

## 88.6 Шаблон письма

Язык письма — **язык получателя** из его карточки (`users.lang`), с откатом на английский.
Не язык запрашивающего: письмо читает владелец ящика, а запрос мог прийти от постороннего.

Шаблоны хранятся файлами рядом с кодом отправки и встраиваются в бинарь. Текстовая часть и
HTML-часть — раздельные шаблоны; HTML-часть проходит контекстное экранирование, поэтому имя
пользователя в ней безопасно.

Подстановки: имя пользователя, адрес ссылки, срок действия в минутах, момент истечения (UTC),
IP запросившего (пустой — блок не выводится), код инстанса (§70, пустой — не выводится),
название системы.

**Тема (ru):** `Nexus: восстановление пароля`
**Тема (en):** `Nexus: password reset`

При заданном коде инстанса он добавляется в тему в квадратных скобках: `Nexus [kz]:
восстановление пароля`. Имя пользователя в тему не подставляется (§88.2).

Текстовая часть, русская:

```
Здравствуйте, {{имя}}!

Для вашей учётной записи Nexus запрошено восстановление пароля.

Чтобы задать новый пароль, откройте ссылку:
{{ссылка}}

Ссылка действует {{минут}} мин. (до {{момент}}) и срабатывает один раз.
Запрос отправлен с адреса {{ip}}.

Если вы не запрашивали восстановление — просто проигнорируйте это письмо.
Пароль останется прежним, делать ничего не нужно.

--
Письмо отправлено автоматически, отвечать на него не нужно.
```

Текстовая часть, английская:

```
Hello, {{name}}!

A password reset was requested for your Nexus account.

To set a new password, open this link:
{{link}}

The link is valid for {{minutes}} min (until {{moment}}) and works only once.
The request came from {{ip}}.

If you did not request a password reset, simply ignore this email.
Your password stays unchanged, no action is needed.

--

```

**встроенными** стилями (почтовые клиенты игнорируют блок стилей в шапке) и **без внешних
картинок и трекинг-пикселей**:

```

│                                          │
│  Здравствуйте, Иван Иванов!              │
│  Для вашей учётной записи запрошено      │
│  восстановление пароля.                  │

│                                          │
│  Или скопируйте адрес:                   │  ← дубль текстом: часть клиентов
│  https://nexus.…/reset-password?token=…  │    режет кнопки
│                                          │
```

Адрес ссылки собирается из публичного адреса приложения (§28), пути `/reset-password` и

**Тестовое письмо** — отдельный короткий шаблон. Тема: `Nexus: проверка почтовых настроек` /
`Nexus: mail settings check`. Тело: «Это тестовое письмо от Nexus. Если вы его получили,
отправка почты настроена верно» плюс строка с хостом релея и временем отправки.

## 88.7 Смена пароля по ссылке

Подтверждение переиспользует существующий механизм смены пароля целиком — тот, которым
пользуются админская смена и self-service §26.4. Это важно: он **гасит все живые сессии
пользователя**, что для сценария «пароль мог утечь» обязательно.

Порядок операций значим:

1. Пароль проверяется на соответствие политике (минимум 8 символов) **до** гашения токена —
   иначе опечатка в длине убивала бы ссылку безвозвратно.
2. Токен гасится атомарно.
3. Проверяется, что пользователь активен. Проверка обязана быть **и здесь**, а не только при
   запросе: между письмом и переходом может пройти до суток, за которые администратор мог
   отключить учётную запись.
4. Пароль меняется, все сессии пользователя завершаются.
5. Пишется запись аудита.

Флаг «требовать смену пароля при следующем входе» **снимается**: человек только что задал
пароль сам. Побочный корректный эффект — если администратор выдал временный пароль, а
пользователь вместо входа воспользовался восстановлением, флаг больше не мешает.

Пользователь **без пароля** восстановление проходит: это ровно тот сценарий, ради которого
функция и нужна.

Остальные выданные ссылки этого пользователя гасятся автоматически — гашение встроено в
общий механизм смены пароля, поэтому срабатывает на всех путях: восстановление по почте,
самостоятельная смена, смена администратором. Без этого старая ссылка из почты позволяла бы
перебить только что установленный пароль.

Подтверждение пароля («повтор») проверяется в интерфейсе; на сервер уходит одно поле. Сервер
не в состоянии отличить опечатку от намеренного решения клиента, дублировать проверку
бессмысленно.

### 88.8.7 Журнал аудита

В список действий фильтра добавляются `user.password_reset.request` и
`user.password_reset.confirm`.

## 88.9 Наблюдаемость

Аудит:

| Действие | Когда | Подробности |
|---|---|---|
| `user.password_reset.request` | на каждый запрос, после попытки отправки | `{input, reason, error?}`, `reason` ∈ `sent`, `user_not_found`, `no_email`, `inactive`, `email_ambiguous`, `too_many_active`, `mail_disabled`, `send_failed` |
| `user.password_reset.confirm` | успешное подтверждение | `{via: "email"}` |

Существующая запись `user.password.change` при сбросе пишется дополнительно — это не дубль, а
два разных факта: кто инициировал и что пароль сменился.

Метрики: число запросов восстановления по исходу, число отправок письма по назначению и
исходу, длительность отправки. Без них фоновая отправка (§88.5) невидима вовсе.

Отладочные записи (§51.9) — на каждом тихом ветвлении запроса: пользователь не найден, нет
email, неактивен, неоднозначный email, почта выключена, сработал лимит, письмо ушло или не
ушло.

## 88.10 Границы защиты — чего раздел НЕ закрывает

1. **Определение существования учётной записи другими путями.** Единый ответ убирает оракул из
   формы восстановления, но форма входа уже различает пользователей по времени ответа.
   Раздел эту планку не меняет.
2. **Письма-раздражители на чужой ящик.** Зная чужой логин, можно инициировать письма на его
   адрес. Ограничено частотой и числом активных ссылок; полностью не закрывается — для этого
   нужна капча, которой в шине нет.
3. **Отключение лимита при недоступном Redis.** Механизм лимитов деградирует в пропуск
   (§9.4): пока Redis лежит, ограничений на рассылку нет вовсе. Сигнал — счётчик ошибок
   проверки лимита.
4. **Принадлежность релея.** Шина не проверяет, что указанный сервер принадлежит организации.
   `skip_tls_verify` отключает проверку сертификата — интерфейс предупреждает, но не запрещает.
5. **Подпись и репутация домена (DKIM/SPF/DMARC).** Настройка почтового домена, а не шины.
   Письма могут попадать в спам, а адрес отправителя — подделываться третьими лицами.
6. **Смена email администратором не подтверждается письмом.** Владелец админской учётной
   записи может вписать свой адрес в чужую карточку и получить сброс; след — только запись
   аудита `user.update`. Планку доверия к администраторам это не меняет: администратор и так
   задаёт пароль любому напрямую.
7. **Неуникальный и неподтверждённый email.** Дубликаты приводят к отказу, а не к письму;
   такие пользователи восстанавливаются только по логину.
8. **Учётная запись без пароля с указанным email** может быть занята владельцем этого ящика.
   Поведение оставлено разрешающим намеренно (§88.7).
9. **Канал доставки.** Ящик, промежуточные релеи, антивирусные сканеры вне контроля шины.
   Один частный случай учтён — открытие ссылок защитными шлюзами (§88.4.6).
10. **Токен в параметре запроса.** Заголовок `Referrer-Policy: same-origin` установлен
    глобально, внешних ссылок на странице нет. Передача во фрагменте адреса была бы строже, но
    хуже совместима с почтовыми клиентами — сознательный компромисс.
11. **Капчи нет** — только ограничение частоты.
12. **Письма «ваш пароль изменён» нет** — вне рамок раздела, возможное развитие.
13. **Потеря письма при перезапуске сервиса** между ответом и фоновой отправкой (§88.5).
14. **Пароль SMTP хранится открытым текстом** в конфиге приложения (§88.2).
15. **IP запросившего попадает в письмо** — персональные данные третьего лица. Осознанный
    компромисс ради сигнала «это не я» (общепринятая практика).
16. **Введённая строка попадает в аудит** — возможно, чужой email. Прецедент: неудачные
    попытки входа пишутся так же. Журнал доступен ролям от `operator`.
17. **Режимы шифрования покрыты автотестами частично** — проверяется отображение настроек в
    параметры соединения и полный диалог без шифрования; STARTTLS и implicit TLS проверяются
    на стенде.

## 88.11 Конфигурация

В файле конфигурации — **один** новый ключ:

```yaml
web:
  # §88: лимит запросов восстановления пароля на IP и на введённый логин
  # (и отдельно на подтверждение). -1 = выключить.
  password_reset_rate_limit_per_min: 5
```

Все лимиты шины живут в файле конфигурации, а не в БД: это параметр развёртывания, и
администратор не должен снимать собственную защиту от перебора кликом в интерфейсе.

Всё остальное — в БД (`app_settings.mail`): адрес релея, учётные данные, режим шифрования,
отправитель, срок действия ссылки, флаги включения. Меняется через интерфейс без перезапуска,
как настройки Telegram, Sentry и ClickHouse.

## 88.12 Scope (вне раздела)

- **Подтверждение email** при его задании или смене — отдельная задача. Хранилище для неё
  готово: назначение `email_change` в `one_time_tokens` (§88.4.1), новый адрес ложится в
  `payload`; нужны миграция расширения `CHECK`, шаблон письма и экран.
- **Приглашение пользователя** (админ заводит учётку, пароль задаёт сам приглашённый) —
  туда же, назначением `user_invite`.
- **Уведомление «ваш пароль изменён»** — отдельная задача.
- **Очередь писем с повторами** — не вводится; единственный потребитель почты шлёт одно
  письмо на действие пользователя.
- **Почтовые уведомления вместо/вместе с Telegram (§20)** — раздел даёт транспорт, но
  переводить на него планировщик уведомлений не берётся.
- **Вход через внешнего провайдера (SSO/OIDC)** — не рассматривается.
- **Капча на публичных формах** — не вводится.
- **Шифрование `app_settings`** — существующее свойство конфига, лечится отдельно и для всех
  секций сразу.
