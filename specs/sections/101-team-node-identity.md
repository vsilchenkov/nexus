# 101. Команда в идентичности узла

Раздел фиксирует, **чем узел отличается от другого узла** в метриках, Grafana, алертах и рантайме
шины. До него идентичностью везде служил путь, хотя путь уникален лишь внутри команды.

Развивает [§6](06-metrics.md) (метрики), [§18](18-multi-tenancy.md) (`UNIQUE (team_id, path)`),
[§22](22-logging-controls-cards.md) (уведомления), [§27](27-rabbitmq-async.md) (pull-узлы),
[§44.E](44-dashboard-counters.md) (диагностика счётчиков), [§46](46-node-status-redis.md) и
[§52](52-node-degraded-status.md) (статус узла), [§69](69-queue-tab-and-target-url.md) (вкладка
«Очередь»), [§78](78-node-url-and-log-counters.md) (метки Receiver'а),
[§81](81-universal-breaker-and-body-limit.md) (circuit breaker), [§94.8](94-rejected-requests.md)
(метка `<unresolved>`), [§98.2](98-ui-usability-and-node-protection.md) (ссылки в топах Kafka).
Закрывает follow-up [§86.8](86-all-teams-scope.md).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 101.1 Повод

На бою в «Мониторинг Kafka → Top failures» строка `telegram` не была ссылкой, хотя узел никто не
удалял. Разбор показал: путь `telegram` занят узлами двух команд — `messengers` (исходящие вызовы
API Telegram, 1 747 ошибок за сутки по ClickHouse) и `webhook` (входящие вебхуки, 8 ошибок). Метрики
Prometheus несли только `node="telegram"`, поэтому ряды двух узлов складывались (1 753 в Prometheus),
а резолвер §98.2 честно отказывался строить ссылку на неоднозначный путь. Та же склейка — в
дашбордах Grafana и алертах.

Проверка кода и боя нашла, что «узел = путь» заложено не только в метках:

| Место | Что происходило |
|---|---|
| Sender, async и DLQ: узел ищется `WHERE path = $1` | сообщение одноимённого узла могло уйти с адресом, авторизацией и CH-таблицей узла **другой команды** |
| Redis `nexus:node:last_error:<path>`, `fail_streak:<path>`, `circuit:<path>` | бейдж статуса и circuit breaker общие: отказы узла одной команды открывали breaker узлу другой |
| Вкладка «Очередь»: фильтр `key == path`; чтение тела по координатам без проверки | очистка очереди отменяла чужие сообщения; тело любого сообщения читалось по `(partition, offset)` |
| RMQ pull: воркеры и `rmq:health` по пути | одноимённые pull-узлы двух команд вытесняли друг друга |
| Receiver ставил метку `node` из адреса ДО резолва | у passthrough-узлов метка несла хвост адреса — **на бою 31 ряд с токенами Telegram-ботов** (`telegram/bot…:…/getUpdates`) |
| `GET /api/metrics/diagnostics` | «узлы только в Prometheus» — 393 пути ВСЕХ команд, включая ряды с токенами, любому токену `metrics:read` |
| Telegram-уведомления об ошибках | сумма одноимённых узлов уходила в обе команды |

## 101.2 Модель идентичности

Путь, совпадающий у двух команд, — штатная ситуация (§18), а не ошибка данных. Узел идентифицирует
одно из двух представлений, в зависимости от того, кто его читает:

| Кто читает | Идентичность | Почему |
|---|---|---|
| Люди, PromQL, Grafana, алерты | пара **(слог команды, путь)** | читается глазами, фильтруется в дашборде; слог неизменяем (§18, изменение запрещено в `TeamUsecase`) |
| Рантайм шины: доставка, ключи Redis, pull-воркеры, «Очередь» | **`node_id`** (UUID) | переживает переименование узла и перенос в другую команду (`NodeUsecase.Move` меняет команду при том же пути) |

Пара «слог + путь» в рантайме не годится именно из-за переноса: сообщения в полёте и в DLQ несли бы
слог прежней команды и после переноса считались бы «узлом, которого нет». С `node_id` они
доставляются перенесённому узлу.

## 101.3 Метрики

Во все per-node метрики добавлена метка **`team`** — слог команды узла:

`nexus_requests_total`, `nexus_request_incomplete_total`, `nexus_request_duration_seconds`,
`nexus_node_last_request_error`, `nexus_async_ingress_rejected_total`,
`nexus_async_ack_render_failed_total`, `nexus_rmq_messages_pulled_total`,
`nexus_rmq_pull_duration_seconds`, `nexus_rmq_connection_state`, `nexus_rmq_queue_depth`,
`nexus_rmq_consumer_count`, `nexus_node_degraded`, `nexus_dlq_reprocess_total`,
`nexus_replay_body_source_total`.

Кардинальность не растёт: число рядов по-прежнему равно числу узлов — одноимённые узлы просто
перестают делить ряд.

**Откуда берутся значения:**

| Ситуация | `team` | `node` |
|---|---|---|
| Узел найден | слог команды НАЙДЕННОГО узла | `node.Path` найденного узла |
| 404: узла нет (§94.8) | `""` | `<unresolved>` |
| Выход до резолва: пустой путь (400), не-POST callback (405), тело больше лимита (413), rate-limit (429), петля (508) | `""` | `""` |
| Маршруты, не относящиеся к узлам (служебные API, прокси Web `/api/v1/*path`) | `""` | `""` |

Правила:

- **Метки ставятся только из резолвнутого узла, никогда из адреса.** Слог и хвост адреса задаёт
  клиент — это неограниченная кардинальность (урок `nexus_ingress_rejected_total`, IMPLEMENTATION
  §94: метку команды из URL уже приходилось убирать). Разбивку мусорных обращений по путям даёт
  журнал отказов §94.
- **`node` — путь узла, а не хвост адреса.** У passthrough-узла (§39) адрес
  `/api/v1/request/messengers/telegram/bot<токен>/sendMessage` метится `node="telegram"`. До §101
  хвост попадал в метку целиком — это и была утечка токенов ботов в Prometheus (срок хранения 90
  суток) и дальше в диагностику Web. Заодно исправлен legacy-адрес без слога: `/request/a/b`,
  разрешившийся в узел `a/b` команды default, метился `node="b"`.
- **Метки ставятся после резолва, но без переноса резолва в начало обработчика.** Резолв до
  чтения тела невозможен: ответ 404 на непрочитанном теле рвёт соединение (см. `drainCap` в
  handler'е Receiver'а), а за прокси это превращается в 502. Поэтому usecase сообщает найденный
  узел наблюдателю (`RouteInput.OnNodeResolved`) сразу после резолва, и handler кладёт обе метки в
  контекст запроса. Наблюдатель покрывает все ветки после резолва — авторизацию, отказ по методу,
  disabled, paused, ack-шаблон, not-async.
- **Запасного значения из `c.Param("path")` больше нет.** Метрики-middleware берёт `node` и `team`
  только из контекста; без них — пустые строки. Это же убирает сырые пути из метрик прокси Web.
- Запись меток идёт через типизированные методы `metrics.Metrics` с `NodeLabels{Team, Node}`:
  позиционный `WithLabelValues` с неверным числом значений паникует в рантайме, а не на сборке.
- Порядок в объявлении — `{method, team, node, status}`; в выводе `/metrics` Prometheus всё равно
  сортирует метки по алфавиту.
- **Внешний Prometheus.** Если оператор сам навешивает на цель метку `team`, без
  `honor_labels: true` метка приложения станет `exported_team`. В поставляемых
  `deploy/prometheus*.yml` таких меток нет.

## 101.4 Контракт Receiver → Sender

| Канал | Добавлено |
|---|---|
| gRPC `SendRequest` | `team_slug = 33` (`node_id = 28` уже был) |
| Конверт `nexus.async` (три копии: Receiver — канон, Sender — полная, Web — проекция «Очереди») | `node_id`, `team` (оба `omitempty`) |
| Заголовки Kafka async/DLQ/paused | `node_id`, `team` |

Копии конверта сверяет контрактный тест (`tests/contract`); проекция Web проверяется как
подмножество канона.

**Ключ партиции остаётся `node.Path`.** Его смена переставила бы сообщения узла между партициями
на выкате и нарушила бы порядок доставки внутри узла. Одноимённые узлы двух команд делят партицию —
это вопрос пропускной способности, а не корректности.

## 101.5 Какой узел исполняет async-сообщение

| Конверт | Поведение Sender'а |
|---|---|
| Есть `node_id` | узел по id (с командой из БД); метка `team` — текущий слог узла |
| `node_id` не UUID | «узла нет» — сообщение отбрасывается, как для удалённого узла (иначе ошибка PostgreSQL `invalid input syntax for type uuid` дала бы вечный повтор) |
| Нет `node_id` (записан до обновления) | узел по пути: нет узлов — отброс (как раньше); один — доставка; **несколько** — см. ниже |

**Неоднозначный старый конверт** (путь занят узлами нескольких команд) не доставляется никому:

- основной consumer отправляет его в DLQ с причиной `node_ambiguous` и пишет warn;
- репроцессор DLQ такой конверт сбрасывает с warn и `result="dropped"` — срабатывает алерт
  `NexusDLQMessagesLost`, потеря видна оператору.

До §101 такое сообщение доставлялось случайному из узлов (`QueryRow` без `ORDER BY`), то есть
почти всегда с чужими адресом, авторизацией и CH-таблицей. Множество таких конвертов конечно: это
то, что лежало в очередях и DLQ на момент обновления.

Sync-запросы узел в Sender не ищут: адрес, авторизацию и id приносит Receiver, `team_slug` нужен
только меткам.

## 101.6 Рантайм-ключи Redis

| Назначение | Было | Стало |
|---|---|---|
| Исход последнего вызова (§46/§52) | `nexus:node:last_error:<path>` | `nexus:node:last_error:id:<node_id>` |
| Серия отказов (§52-доп) | `nexus:node:fail_streak:<path>` | `nexus:node:fail_streak:id:<node_id>` |
| Circuit breaker (§81) | `circuit:<path>` | `circuit:id:<node_id>` |
| Здоровье pull-узла (§27) | поле `<path>` хеша `rmq:health` | поле `<node_id>` |

Префикс `id:` исключает совпадение нового ключа со старым: двоеточие запрещено и в пути узла, и в
слоге команды.

- **Пустой `node_id`** (sync-запрос от Receiver'а старой версии на выкате): breaker работает по
  старому ключу пути — защита не выключается; исход узла не пишется (debug-строка).
- **Переход `last_error`.** Web при старте один раз переносит старые ключи в новые: `SET NX` с
  сохранением оставшегося TTL, только для путей, однозначных во всём инстансе. Без переноса
  простаивающие узлы после обновления показывали бы «нет данных» — ровно то, что закрывал §46.
  Перенос идемпотентен, две реплики Web (§93) друг другу не мешают. Старые ключи не удаляются —
  их читает прежний Web после отката. Выполненный перенос отмечается ключом
  `nexus:node:status_migration:101` (срок 30 суток): повтор на каждом рестарте вернул бы узлу
  «Down», снятый ручным сбросом защиты (§81.4.2), а узлу, созданному с путём удалённого, — чужой
  исход.
- **`fail_streak` и `circuit` не переносятся.** TTL ключа breaker'а — 10 минут: открытый breaker
  на обновлении закрывается и при продолжающихся отказах откроется снова; серия отказов начинается
  заново. Это фиксируется в DEPLOYMENT.

## 101.7 Pull-узлы RabbitMQ

Менеджер pull-воркеров ведёт узлы по `node_id` (lease уже был по id — совпадали только карты
воркеров), список pull-узлов отдаёт слог команды для меток, `rmq:health` пишется и читается по
`node_id`.

## 101.8 Вкладка «Очередь»

Сообщение принадлежит узлу, если `key == path` И (`node_id` конверта равен id узла ИЛИ `node_id`
пуст и путь однозначен во всём инстансе). Правило действует в списке, в поиске сообщений для
очистки (по периоду и целиком) и в чтении тела.

- **Однозначность пути** Web проверяет по узлам всех команд (`IDsByPaths`) на каждой операции.
  Ошибка PostgreSQL на этой проверке **скрывает** старые конверты, а не показывает их: отменить
  чужое сообщение хуже, чем оставить неочищенный остаток переходного периода.
- **Тело сообщения читается только у своего узла.** Раньше `GET …/async-queue/messages/body`
  проверял доступ к узлу из адреса, а сообщение брал по координатам `(topic, partition, offset)` из
  запроса — без проверки, что оно этому узлу принадлежит. Теперь чужое сообщение отдаёт 404
  (`error.not_found`).
- Проекция конверта у Web получает `node_id`. Её сверку с каноном держит `tests/contract`.
- В delay-топик паузы Sender перекладывает конверт байт в байт, поэтому `node_id` сохраняется и у
  отложенных сообщений.

## 101.9 Web: чтение метрик

- Запросы к Prometheus группируют `by (team, node)` (p95 — `by (team, node, le)`), результаты
  ключуются парой `NodeKey{Team, Path}`. Слог узла Web берёт по `team_id` из справочника команд.
- **Ряды, собранные до обновления** (`team=""`), в окнах, захватывающих выкат, приписываются узлу
  только если путь однозначен во всём инстансе и только для счётчиков. p95, гаудж и спарклайн не
  складываются: смешать перцентили нельзя, старый гаудж гаснет с процессом, а точки спарклайна идут
  без меток времени и при сложении сдвинулись бы. Однозначность проверяется по всем узлам инстанса;
  если проверить её нельзя (сбой PostgreSQL, неполный список узлов), ряд не приписывается никому.
- Узел, слог команды которого не удалось получить, получает нули, а не ряды без команды.
- **Статус узла:** Redis по `node_id`, запасной источник — гаудж Prometheus по паре.
  Клиентское правило §86.8 «при совпадении путей показывать неизвестно» снимается.
- **Уведомления (§22):** ошибки считаются по паре, одноимённый узел соседней команды в сумму не
  попадает.
- **Диагностика (§44.E)** показывает только ряды текущей команды: «узлы только в Prometheus» — это
  пути её переименованных и удалённых узлов, а не чужие команды, `""` или `<unresolved>`.
  Глобальные итоги Prometheus тоже берутся по слогу команды — иначе они сравнивались бы с
  ClickHouse одной команды. Если слог текущей команды неизвестен, Prometheus-сторона не
  заполняется (`prometheus_available=false`).
- **Топы Kafka (§98.2):** строка на пару (команда, путь), ссылка строится по точному ключу. Ряды до
  обновления сворачиваются в строку узла до отбора топа; ряд неоднозначного пути остаётся строкой
  без команды.
- Методы `NodeKPI` / `NodeChart` Prometheus-клиента не вызывались с §44 (KPI и график узла давно
  считает ClickHouse) и удалены.

## 101.10 Интерфейс

Топы на экране Kafka:

```
┌ Top failures ────────────────────────────────────────────────┐
│ УЗЕЛ                          ОШИБОК    ERROR RATE           │
│ telegram  ‹messengers›         1 747    19.5%   ← ссылка     │
│ telegram  ‹webhook›                8     3.5%   ← ссылка     │
│ telegram  ‹без команды›          412     2.1%   ← текст      │
└──────────────────────────────────────────────────────────────┘
```

- Приглушённый чип со слогом команды — справа от пути в той же ячейке; «Top producers» — так же.
- Слог приходит с сервера: экран админский, а админ может не состоять в команде узла, так что
  клиентский резолв по членствам (§62, §86) дал бы пустоту.
- Ссылка ведёт на `/nodes/<id>` без `?team=` — команду переключает `useEnsureNodeTeam` (§58).
- Строка без ссылки называет свою причину, их три:
  - заглушка `<unresolved>` (§94.8) — узел не найден (404), путь из адреса в метрики не пишется;
    чипа нет, команды у заглушки не бывает;
  - ряды до обновления (`team=""`), которые сервер не приписал узлу, — чип «без команды» и
    подсказка, что ряды собраны до разделения по командам и узел по ним однозначно не определить;
  - пара (команда, путь) без узла — чип команды и подсказка «переименован, удалён или перенесён в
    другую команду».
- Доступное имя ссылки включает слог («telegram messengers»): иначе скринридер читал бы две
  одинаковые ссылки «telegram».
- React-ключ строки — `team/path`: иначе две строки с одним путём конфликтуют.
- Бейдж исхода на «Узлах» в сквозном режиме показывает исход каждого узла: подмена на «неизвестно»
  при совпадении путей (§86.8) снята.

## 101.11 Grafana и алерты

**Дашборды** (`deploy/grafana/nexus-nodes.json`, `nexus-kafka.json`):

- переменная `team` — `label_values(nexus_requests_total{service="sender"}, team)`, «All» с
  `allValue: ".*"`: значение по умолчанию `(a|b)` спрятало бы ряды до обновления с `team=""`;
- переменная `node` зависит от `team`;
- выражения — `by (team, node)` с фильтром `team=~"$team"`, легенды `{{team}}/{{node}}`;
- стат-панели DOWN/DEGRADED/OK считают `count(max by (team, node)(…))`: одноимённые узлы — два узла;
- сводная таблица узлов склеивается по двум меткам (трансформация `merge` вместо `joinByField` по
  одному полю `node`).

**Алерты** (`deploy/prometheus.alerts.yml`, группа `nexus.nodes`) агрегируют `by (team, node…)`,
в summary — `{{ $labels.team }}/{{ $labels.node }}`.

**Проверка правил** — `make check-alerts` (`promtool check rules` + `promtool test rules` в
docker-образе Prometheus) и job в CI. Юнит-тест правил: один `node`, разные `team` → два алерта.

## 101.12 Выкат и смешанные версии

Миграций схемы нет. Порядок — **Sender → Receiver → Web**:

| Сочетание на выкате | Поведение |
|---|---|
| Новый Sender, старый Receiver | sync: `team_slug` пуст → метки `team=""`, breaker по пути; async: конверты без `node_id` → правило §101.5 |
| Новый Receiver, старый Sender | неизвестные поля proto и JSON игнорируются; поиск узла по пути — прежний дефект, поэтому Sender обновляется первым |
| Старый Web, новые Receiver/Sender | Web читает старые ключи Redis и группирует без `team` — обновлять сразу следом |

После обновления:

- ряды метрик меняют идентичность — графики за период выката разрываются на «до» (без `team`) и
  «после»; алерты по узлам разрешаются и загораются заново после своего `for`;
- `docker compose restart prometheus` — перечитать правила (`up -d` файл не перечитывает);
- дашборды переимпортируются (uid прежние — импорт перезаписывает);
- открытые breaker'ы закрываются, серии отказов начинаются заново;
- неоднозначные старые сообщения DLQ сбрасываются с алертом `NexusDLQMessagesLost`.

**Откат** кода без отката схемы: старые версии не знают новых полей и ключей и возвращаются к
поиску по пути; бейджи узлов до первого вызова показывают данные старых ключей.

## 101.13 Границы защиты

Раздел закрывает:

- попадание токенов и прочих хвостов passthrough-адреса в метки Prometheus;
- выдачу путей чужих команд и таких рядов через `/api/metrics/diagnostics`;
- доставку сообщения узлом чужой команды;
- общие breaker, статус и pull-воркер у одноимённых узлов;
- очистку и чтение чужих сообщений через вкладку «Очередь».

Раздел **не** закрывает:

- **уже собранные ряды с токенами** — они лежат в TSDB до истечения срока хранения (90 суток по
  умолчанию) или до удаления через admin API Prometheus (процедура — в DEPLOYMENT). Токены, которые
  уже могли увидеть держатели `metrics:read`, перевыпускают владельцы ботов — кодом это не лечится;
- ключ rate-limit — он по-прежнему строится из хвоста адреса;
- свободный текст в метке `reason` у `nexus_node_degraded` (сообщение ошибки RabbitMQ);
- отсутствие фильтра `method="requestAsync"` в топах Kafka (в них попадает и sync-трафик);
- ключ партиции Kafka (см. §101.4);
- видимость в «Очереди» сообщений, поставленных до переименования узла: их ключ — старый путь,
  доставляются они по `node_id`, но в список нового пути не попадают;
- **удаление одного сообщения по идентификатору** (`DELETE …/async-queue/messages/{msgId}`): отмена
  пишется в Redis по id сообщения без чтения Kafka, владелец не проверяется. Id знают клиент,
  отправивший сообщение, и команда узла (список «Очереди», журнал логов). Проверка владельца
  стоила бы скана обоих топиков на каждое удаление и ложно отказывала бы сообщениям глубже
  потолка скана.
