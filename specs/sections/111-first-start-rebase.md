# 111. Устойчивый первый старт ноды с `instance.id`

Раздел закрывает хрупкость стартового гейта §70.5, найденную стендом §110: **пустая** нода с
непустым `instance.id` могла навсегда перестать подниматься — Web завершался с
`team "default" is already bound to "nexus_default" on a used database`, хотя ни узлов, ни данных на
ноде ещё не было. Лечилось это только пересозданием базы PostgreSQL.

Развивает [§70.5](70-multi-instance-clickhouse.md) (первый запуск и ребейз сидированной команды),
[§93](93-ha-replicas.md) (реплики Web), [§110](110-config-backup.md) (восстановление на новом
сервере — там первый старт проходит каждый раз).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md). **Миграций нет, ключей конфига и
флагов запуска нет, интерфейс не меняется.**

---

## 111.1 Повод

Миграция §18 создаёт команду `default` с базой `nexus_default`. Нода с непустым `instance.id` обязана
один раз переписать это имя на `nexus_<id>_default` (§70.5, «ребейз сидированной команды»). До §111
право на переименование давал факт **«строку `instance_identity` вставил именно этот процесс»**.
Факт одноразовый: он достаётся тому, кто первым дошёл до заявки идентификатора, и больше никогда не
повторяется. Если этот «первый» не был стартом Web, дошедшим до переименования, — условие не
выполнялось уже никогда, и гейт трактовал пустую ноду как действующую.

## 111.2 Как в это попадали

| # | Сценарий | Что происходило |
|---|---|---|
| S1 | Первый старт Web оборвался между заявкой идентификатора и гейтом ClickHouse | между ними — расшифровка настроек, подключение к Redis и к ClickHouse. На стенде §110 упал тайм-аут Redis: идентификатор заявлен, база не переименована |
| S2 | Идентификатор первым заявил Receiver или Sender | шаг сверки выполняют все три сервиса (§70.5), а Receiver ещё и сам накатывает миграции. При порядке запуска «Receiver → Sender → Web» Web гарантированно не заявитель; при одновременном старте в compose — гонка |
| S3 | Первый старт Web без ClickHouse | гейт владения пропускался целиком, вместе с переименованием: база оставалась `nexus_default` |
| S4 | Две реплики Web (§93) стартуют одновременно на свежей ноде | вторая реплика падала и поднималась только рестартом — по двум причинам. В PostgreSQL: заявитель идентификатора один. В ClickHouse: вторая заставала базу, которую первая ещё захватывает (таблица-маркер создана, строки в ней нет), и получала отказ гейта первого запуска на собственной базе — `database already exists on first run of this instance … (verdict=unknown)` |

Во всех четырёх случаях PostgreSQL ноды пустая, в ClickHouse она ничего не захватывала — то есть
переименование по-прежнему безопасно. Отказ был следствием формулировки условия, а не состояния.

Вторая причина S4 найдена уже при реализации: тест двух реплик после правки переименования падал
примерно в одном прогоне из двенадцати. Замер на общем ClickHouse (две реплики одной ноды, разнос
старта 0–20 мс, 240 стартов): отказ второй реплике в 51 случае — окно между созданием базы и
записью строки маркера занимает десятки миллисекунд.

## 111.3 Правило

Право на переименование определяется **состоянием ноды, а не тем, кто вставил строку**. Условие —
составной признак «ноду только что подняли», уже введённый §70.5 для гейта первого запуска:

- в PostgreSQL нет ни узлов, ни команд, кроме сидированной («свежий PostgreSQL»);
- нода ещё ни разу не захватывала свои базы в ClickHouse (`instance_identity.ch_claimed = false`).

Оба признака перепроверяются на каждом старте, поэтому обрыв, повтор и порядок сервисов на исход
не влияют. Факт «строку вставили мы» в решениях больше не участвует.

Решение для команды, чья база всё ещё носит сидированное имя, при непустом `instance.id`:

| Свежий PostgreSQL | Базы уже захватывались | ClickHouse доступен | Решение |
|---|---|---|---|
| да | нет | да | **переименовать** |
| да | нет | нет | **переименовать** — операция только в PostgreSQL, ClickHouse для неё не нужен |
| да | да | да | отказ: нода держит базу под старым именем, переезд вручную |
| нет | любое | да | отказ: есть узлы или команды, переезд вручную |
| не выполнено хотя бы одно | — | нет | предупреждение в лог, старт продолжается |

Остальное — как в §70.5:

- имя уже равно `nexus_<id>_<slug>` — ничего не делать;
- имя не сидированное и не ожидаемое — отказ (рассинхрон, ручная правка `teams.ch_database`);
- `instance.id` пустой — шаг пропускается.

**Почему при недоступном ClickHouse отказ заменён предупреждением.** Web обязан подниматься без
ClickHouse (§70.5: гейт владения в этом случае пропускается). До §111 вместе с гейтом пропускалась
и сверка имён, поэтому такая нода стартовала. §111 переносит сверку раньше — но новых причин не
подняться при лежащем ClickHouse не добавляет: отказ в этом состоянии наступит на первом старте с
доступным ClickHouse, как и раньше.

## 111.4 Поведение

- Сверка имён баз выполняется в стартовом гейте Web **до** проверки доступности ClickHouse.
- Запись имени — условная: строка обновляется, только если в ней всё ещё сидированное имя.
  Две реплики Web, стартующие одновременно, не мешают друг другу: вторая либо видит уже
  переименованную базу, либо обновляет ноль строк.
- Переименование пишет в лог строку уровня info `seeded team database rebased for instance`
  (команда, прежнее и новое имя); каждое решение сверки — строку уровня debug (§51.9).
- Текст отказа называет причину: «в PostgreSQL уже есть узлы или команды» либо «нода уже
  захватила базы ClickHouse под прежним именем» — и отсылает к процедуре смены идентификатора.
  Фраза `is already bound to` сохранена: по ней отказ ищут в логах и в DEPLOYMENT.
- Базу переименовывает только Web. Sender и Receiver идентификатор сверяют, но имён баз не трогают
  (§70.5: Sender может стартовать раньше Web).
- **Захват базы, начатый соседней репликой.** Нода с непустым `instance.id` считает базу «без
  данных», если в ней нет таблиц, кроме таблицы-маркера. Застав маркер без строки, реплика не
  отказывает, а ждёт запись (до 1 с) и решает по содержимому: свой идентификатор — база своя;
  чужой — отказ `ErrForeignDatabase`; строка так и не появилась (сосед умер между созданием
  маркера и записью) — маркер дописывается. Если кроме маркера в базе есть таблицы, решает
  прежний гейт первого запуска. Для ноды **без** идентификатора правило §70.5 не меняется: её
  маркер неотличим от маркера соседа, и ждать чужую запись ей нельзя.

## 111.5 Что меняется для оператора

- Порядок первого запуска сервисов новой ноды больше не важен: Web поднимется и после Receiver, и
  после Sender, и после собственного оборванного старта.
- Реплики Web новой ноды с идентификатором можно запускать одновременно: ни одна не завершится
  из-за того, что соседняя ещё не дописала маркер владения.
- Обход «пересоздать базу PostgreSQL и запустить заново» из процедуры восстановления §110 больше не
  нужен и из DEPLOYMENT убран. Остаётся требование задать `instance.id` до первого старта Web: от
  него зависят имена баз.
- Нода, застрявшая в этом состоянии на прежней версии (идентификатор заявлен, база Default —
  `nexus_default`, узлов нет), после обновления поднимается сама.

## 111.6 Границы и вне рамок

- **Смена `instance.id` на работающей ноде** — по-прежнему ручная процедура (DEPLOYMENT §5А.5):
  базы в ClickHouse переименовывает оператор.
- **Нода с узлами под сидированным именем.** Если на прежней версии Web стартовал без ClickHouse и
  на ноде успели создать узлы или команды, признак «свежий PostgreSQL» уже не выполняется — отказ
  остаётся, переезд вручную.
- **Нода, захватившая `nexus_default`, а потом получившая идентификатор** (сначала работала без
  него, затем значение переписали флагом `--instance-id-force`) — отказ остаётся: в ClickHouse уже
  есть её база под старым именем.
- **Гейт владения баз ClickHouse** меняется только в одном месте — §111.4, маркер без строки в
  базе без таблиц у ноды с идентификатором. Чужой маркер, конфликт владения, непустая база без
  маркера и весь гейт первого запуска для ноды без идентификатора — как были.
- **Две ноды с одинаковым `instance.id`** на общем ClickHouse неразличимы и до §111, и после:
  уникальность идентификатора — договорённость §70, программно она не проверяется.
- **Одновременный первый старт двух нод без идентификатора** на общей пустой базе — окно §70.5,
  §111 его не касается.

## 111.7 Проверка

- Unit: решение сверки по всем строкам матрицы §111.3, включая пустой идентификатор, уже
  правильное и «чужое» имя.
- Integration через настоящий стартовый гейт (PostgreSQL + ClickHouse): S1–S4 проходят; узел под
  сидированным именем и `ch_claimed = true` по-прежнему дают отказ; не свежая нода без ClickHouse
  стартует. Тесты S1–S4 красные на коде до §111.
- Integration гейта ClickHouse: маркер без строки — реплика дожидается записи соседа и строку не
  дублирует; сосед умер — маркер дописывается; в маркер вписалась чужая нода — отказ; в базе есть
  таблица — отказ; нода без идентификатора — отказ, как раньше; две реплики с разносом старта
  0–20 мс проходят обе. Первые три и последний — красные на коде до §111.
- Стенд: база, застрявшая в этом состоянии на прогоне §110, поднимается новым бинарём; запуск
  Receiver раньше Web на чистой базе; обычный первый старт; рестарт ноды с узлами ничего не
  переименовывает.
