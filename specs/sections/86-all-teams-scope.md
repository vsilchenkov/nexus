# 86. Сквозной просмотр узлов всех команд («Все команды»)

Раздел вводит **сквозной режим просмотра** — пункт «Все команды» в переключателе команд, который
показывает узлы всех команд пользователя одним списком, с метриками каждого узла. Попутно
устраняется молчаливое наследование команды при создании узла: команда выбирается явно. Развивает
§18 (multi-tenancy, переключатель), §44 (счётчики рабочего стола), §49 (избранные команды), §62
(кросс-командный поиск), §65 (команда на форме узла), §71 (персональные предпочтения), §76
(параметр `?team=`).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 86.1 Проблема

Скоуп команды живёт **только** в серверной сессии (`Session.CurrentTeamID` в Redis, §18.3), и
`GET /api/nodes` фильтрует `WHERE team_id = $1`. На боевой установке команд двенадцать, поэтому
«окинуть взглядом всё хозяйство» нечем: оператор перебирает команды переключателем, и состояние
инфраструктуры целиком не видит никогда.

Единственное кросс-командное чтение до §86 — глобальный поиск §62 (`GET /api/search/nodes`): он
ограничен подстрокой (≥ 2 рун), отдаёт до 50 строк и не несёт ни метрик, ни статусов. Это
навигационный инструмент («найди узел, я не помню команду»), а не обзорный экран.

## 86.2 Что такое «Все команды»

**Это режим просмотра, а не команда.** Сессионная `current_team_id` при входе в режим **не
меняется**: она остаётся у последней выбранной реальной команды и продолжает обслуживать всё
остальное приложение. Причина — цена альтернативы: `currentTeamID(c)` читают около девяноста мест,
и специальное значение в сессии потребовало бы, чтобы каждое из них умело «команда не выбрана»,
включая все мутации, которым писать было бы некуда.

Скоуп режима — **членства пользователя**, а не все команды инстанса. Роль (`viewer`/`manager`/`admin`)
видимость не расширяет: `admin` в сквозном режиме видит только свои команды — тот же принцип, что в
§62.3 и §76.5 (no-leak). Членства резолвятся **на каждый запрос** через `TeamRepo.ListUserTeams`, то
есть строже действующего поведения: сессионный скоуп §18.3 переживает исключение из команды до
самолечения `GET /api/me/teams` (§18.9), а сквозной режим — нет.

**Значение скоупа — `*`.** Не `all`: строка `all` проходит формат slug'а команды
(`^[a-z][a-z0-9_]{0,31}$`, §18.1) и однажды столкнулась бы с реальной командой; `*` slug'ом быть не
может ни при каких условиях. Заодно значение согласовано с уже существующим `?team_id=*` аудита
(«глобально»).

Режим включается на рабочем столе и в аудите. Логи запросов, вкладка «Очередь», Kafka и «Настройки»
в сквозной режим не входят — см. §86.9.

## 86.3 API

Скоуп передаётся параметром `scope=all`. Отсутствие параметра — прежнее поведение по сессии, ни один
существующий вызов не меняется.

| Endpoint | Что делает |
|---|---|
| `GET /api/nodes?scope=all` | узлы всех команд-членств; `WHERE team_id = ANY($1)` |
| `GET /api/metrics/nodes?scope=all&node_ids=…` | метрики **явно перечисленных** узлов (порционная загрузка, §86.4); потолок 200 id на запрос |
| `GET /api/metrics/totals?scope=all` | агрегат для KPI-шапки по **всем** узлам скоупа |
| `GET /api/audit?scope=all` | журнал по всем командам-членствам |
| `POST /api/nodes` | необязательное поле `team_id` (§86.6) |

- **Только session-cookie.** API-токен закреплён за одной командой (`token.team_id`, §18.3), и
  сквозная выдача ему бессмысленна — `scope=all` под токеном даёт **403**. Тот же довод, что у
  `/api/nodes/{id}/team` (§58) и `/me/switch-team` (§18).
- **`scope=all` ≠ `team_id=*` в аудите.** Существующий `?team_id=*` означает «все команды
  **инстанса**» и доступен только `admin`; `scope=all` — «все **мои** команды» и доступен всем, кто
  вправе читать аудит (manager+, §26.3). Два разных множества, путать нельзя.
- Механизм фильтрации уже существует и не требует ни SQL, ни миграций: `ListNodesFilter.TeamIDs`
  (§62) → `WHERE team_id = ANY($1)`. Фильтр аудита расширяется тем же приёмом — полем, а не новым
  методом порта, чтобы не ломать стабы в тестах (ISP).
- Имена команд в ответе **не обогащаются**: у клиента уже есть карта `id → name` из
  `GET /api/me/teams`. В §62 обогащение делал сервер, потому что глобальный поиск живёт в шапке и
  членства ему не гарантированы; на рабочем столе они загружены всегда.

## 86.4 Модель загрузки метрик

Метрики каждого узла в сквозном режиме **сохраняются полностью** — и в таблице, и в карточках:
оператору нужна жизнь каждого узла, а не список конфигураций.

**Порционность.** Метрики строк запрашиваются только для узлов, попавших в поле зрения
(`IntersectionObserver`), пачками; прокрутка догружает следующую. Список узлов приходит отдельно и
мгновенно (один запрос в PostgreSQL), поэтому время до первого экрана не зависит от общего числа
узлов.

**KPI-шапка считается отдельным запросом** и заполняется позже таблицы, со своим — более редким —
автообновлением. Дешевле полного прохода по всем узлам скоупа её не посчитать: единой таблицы для
агрегата не существует, у каждой команды своя БД ClickHouse, у каждого узла своя таблица.

> **Уточнение §44.A для сквозного режима.** Инвариант «шапка = Σ **видимых** строк таблицы»
> относится к режиму одной команды и там не меняется. В сквозном режиме строки догружаются
> порционно, поэтому шапка — это Σ по **всем узлам скоупа**, а не по загруженным строкам. Иначе
> итог менялся бы от прокрутки. Порционность и раздельный агрегат включаются **только** при
> `scope=all`; путь одной команды не затронут.

**Режим подсчёта уникальных сквозной режим НЕ меняет** — действует общая настройка §44.L
(`metrics_approx_counts`, по умолчанию точный `uniqExact`). Изначально планировалось принудительно
включать приблизительный подсчёт, но замер (§86.4.1) показал, что нужды нет: всё хозяйство за
период по умолчанию считается около секунды. А принудительный HLL дал бы неприятный побочный
эффект — число узла на рабочем столе отличалось бы от точного числа на его собственной странице.
Оператор по-прежнему может включить приблизительный режим глобально, когда данных станет больше.

**Кеш с коротким TTL и singleflight** на агрегате шапки (ключ: набор команд + окно + режим
подсчёта). Без него автообновление рабочего стола и несколько операторов, глядящих на один экран,
умножают одну и ту же работу. Границы окна в ключе **квантуются по TTL**: у скользящего окна
(«последние 24 часа») правая граница — «сейчас», и без квантования ключ был бы уникален на каждый
запрос, то есть кеш не срабатывал бы никогда.

**Prometheus-ветка получила скоуп.** Fallback без ClickHouse строил строки из ответа Prometheus, а
у его метки команды нет (`node = <path>`) — то есть рабочий стол без ClickHouse показывал пути узлов
**всех** команд инстанса, и в сквозном режиме это стало бы прямой утечкой. Теперь строки строятся по
узлам скоупа, а Prometheus только поставляет числа по пути. Два следствия: узел без трафика получает
строку с нулями (как в CH-ветке, где строка есть у каждого узла), а «сирота» — трафик по пути без
узла в конфигурации — на рабочем столе больше не виден и остаётся предметом диагностики §44.E.

### 86.4.1 Замер, на котором основаны решения (бой, v1.26.0, 11.08.2026)

Двенадцать команд; данные сняты по семи, для которых есть API-токены.

| Команда | Узлов | Различных таблиц | `external_table` | 24 ч | 30 д | Запросов за 30 д |
|---|---|---|---|---|---|---|
| vika | 12 | 11 | 0 | 0.25 с | 0.64 с | 2 200 415 |
| webhook | 8 | 8 | 0 | 0.11 с | 0.19 с | 100 262 |
| conv | 4 | 4 | 0 | 0.09 с | 0.09 с | 1 489 |
| task | 3 | 3 | 0 | 0.18 с | 0.11 с | 39 702 |
| geo | 3 | 3 | 0 | 0.14 с | 0.15 с | 117 822 |
| gate | 2 | 2 | 2 | 0.30 с | **2.23 с** | 10 693 375 |
| edo | 2 | 2 | 0 | 0.09 с | 0.16 с | 101 756 |
| **Итого** | **34** | **33** | **2** | **≈ 1.2 с** | **≈ 3.6 с** | 13 252 821 |

Два вывода, изменившие проект:

- **Батч по таблице (`GROUP BY node_id` вместо запроса на узел) отвергнут.** На боевых данных
  таблиц столько же, сколько узлов: 33 на 34, общая ровно одна (`nexus_vika.dadata` на два узла).
  Приём сэкономил бы один запрос из тридцати четырёх, а стоил бы новых методов порта, отдельной
  ветки для `external_table` (§64 разрешает им произвольную схему, а §61 оставил послабление
  `OR node_id = ''` — строки без `node_id` схлопнулись бы в чужую корзину) и тестов на
  эквивалентность агрегаций. Записано здесь, чтобы приём не изобретали заново.
- **Стоимость определяется объёмом данных, а не числом узлов.** `gate` — два узла и 2.23 с за 30
  дней (10.7 млн запросов), `vika` — двенадцать узлов и 0.64 с (2.2 млн). Поэтому рычаги — те, что
  бьют по объёму (приблизительный подсчёт, кеш), а порционность отвечает за скорость появления
  строк, а не за экономию прохода для шапки. Ориентир §44.L «171 узел / 30 д ≈ 7 с» снят на
  синтетическом стенде и боевую картину не описывает.

## 86.5 Избранное для «Всех команд»

Пункт добавляется в избранное звездой, как обычная команда, и показывается в секции «Избранное»
сайдбара (§49.2) **первым**, вне drag-and-drop-сортировки.

Хранится **не** в `user_team_favorites`: у той таблицы составной внешний ключ на
`user_teams (user_id, team_id)` (миграция 0023), дающий инвариант «избранное ⊆ членство», и
псевдо-идентификатор в неё не вставится. Вместо этого — generic-хранилище предпочтений §71
(`user_preferences`, миграция 0031): глобальная строка пользователя (`team_id IS NULL`), ключ
`teams.favorite_all`, значение `true`. §71 ровно для этого и делался («будущие префы ложатся сюда
новым key — без новой миграции и без правки бэкенда»); ключ проходит `CHECK` формата.

Позиция среди избранных команд не хранится намеренно: сливать два разных хранилища в один
упорядоченный список ради одного элемента дороже, чем закрепить его сверху.

## 86.6 Команда при создании узла

До §86 команда узла наследовалась молча: `n.TeamID = currentTeamID(c)`, а форма показывала её
текстом (§65). В сквозном режиме такой команды попросту нет, поэтому она **выбирается явно**.

- `CreateNodeRequest` получает **необязательное** поле `team_id`. Пусто → команда сессии, поэтому
  существующие клиенты и API-токены не ломаются.
- Заданная команда обязана быть среди членств пользователя, иначе `ErrUserNotTeamMember` → **403**.
  Приём переиспользуется у создания API-токена (§18.3, `ensureMembership`), где молчаливое
  наследование убрали по той же причине.
- Команда пишется в детали аудита `node.create`.
- Правка узла команду по-прежнему **не меняет** (`ErrPermissionDenied`); перенос — только
  `POST /api/nodes/{id}/move` (admin, §18.5). Поэтому селект есть на форме создания, а на форме
  правки остаётся прежняя строка-текст плюс кнопка «Перенести».
- `normalizeCHTable` (§18.1) и потолок числа узлов считаются от `n.TeamID` и работают без изменений.

**Префикс БД ClickHouse следует за выбранной командой.** Поле «Таблица логов» подставляет
`nexus_<slug>.`; в сквозном режиме брать его из текущей команды сессии нельзя. Ошибка здесь тихая и
дорогая: `normalizeCHTable` дописывает префикс только к именам **без** префикса, а явно указанный
чужой сохраняет — узел одной команды начал бы писать логи в БД другой. При смене команды в селекте
переписывается только префикс, набранное имя таблицы сохраняется.

## 86.7 Интерфейс

- **Переключатель команд** (`TeamSwitcher`, шапка): строка «Все команды» сверху, отделена
  разделителем, со звездой избранного. Кнопки «Поделиться» (§76.2) у неё нет — у режима нет slug'а,
  а ссылка `?team=*` описывала бы у получателя другое множество команд.
- **Таблица**: добавляется колонка «Команда»; метрические колонки на месте. Ячейки метрик умеют
  состояние «ещё не загружено».
- **Карточки**: состав прежний (метрики + спарклайн); имя команды — чипом в правом слоте шапки
  карточки, тем же визуальным языком, что у результата глобального поиска §62. Высота карточки
  одинакова в загруженном и незагруженном состоянии — вёрстка не прыгает при дозагрузке цифр (приём
  §44.K).
- **Ключ строки и сшивка метрик — по `id` узла, не по пути.** Путь уникален лишь внутри команды
  (`UNIQUE(team_id, path)`, §18.1), поэтому в сквозном списке одинаковые пути в разных командах —
  норма, а не аномалия.
- **Звезда «период по умолчанию»** (§71) в сквозном режиме отключена: преф хранится на команду, а
  команды здесь нет. Сброс периода при смене команды не срабатывает на вход и выход из режима.
- **Аудит**: колонка «Команда».

### 86.7.1 Параметр `?team=*` и его стыковка с §76

Режим адресуем: `?team=*` на тех же маршрутах, где §76 разрешает параметр (`/`, `/kafka`, `/audit`).

§76 объявляет параметр **строгим зеркалом команды сессии** и держит единственного писателя
(`useTeamUrlParam`) с одноразовым guard'ом, guard'ом ожидания и двухпроходной записью через state —
всё это лечит гонку двух писателей `setSearchParams` (§76.7). Значение `*` разбирается **до**
резолва slug'а и выпадает из этой машины: оно не вызывает `switch-team`, не поднимает баннер
«команда недоступна» и не перезаписывается слогом текущей команды.

Режим переживает уход на страницу узла и возврат: значение зеркалится в `sessionStorage`
(приём §62 для строки глобального поиска). Без этого клик по узлу из сквозного списка переключал бы
сессию на его команду (§58, `useEnsureNodeTeam`), а «Назад» молча высаживал бы в одну команду.

## 86.8 Исход последнего вызова при совпадении путей

Бейдж исхода (§46/§52) читается из Redis по ключу `nexus:node:last_error:<path>` — **без команды**;
fallback — гаудж Prometheus с меткой `node = <path>`, тоже без слога. Два узла с одинаковым путём в
разных командах делят одно значение.

Это **не новый дефект**, а существующий: сегодня он невидим, потому что на экране всегда одна
команда. Сквозной режим выводит его на свет, поэтому §86 обязан на него отреагировать: при
обнаружении совпадения путей внутри скоупа бейдж таких узлов показывается как «неизвестно» (у
`Outcome` уже есть `Known=false`, и §84.7 закрепил правило «не красить неизвестное в ok»), с
`Debug`-логом.

Числа и спарклайн этим **не задеты**: они приходят из ClickHouse с фильтром по `node_id` (UUID)
внутри таблицы узла. Ошибался бы только бейдж.

Правильная починка — team-квалифицированный ключ — меняет контракт между Sender и Web (ключ пишет
`internal/platform/nodestatus`, метку ставит Receiver) и требует согласованного выката, поэтому она
**вне этого раздела** и вынесена в follow-up.

## 86.9 Границы защиты (что режим НЕ даёт)

- **Не даёт доступа к чужим командам.** Множество — членства пользователя; роль его не расширяет.
- **Не отменяет серверных проверок.** Каждый запрос по-прежнему team-scoped: `scope=all` подставляет
  список команд, а не снимает фильтр. Пустой `teamID` фильтр не отключает — новых путей с пустой
  командой раздел не вводит (в usecase проверка выглядит как `if teamID != "" && …`, то есть
  пустое значение было бы fail-open).
- **Не трогает поток данных.** Receiver резолвит команду из slug'а в URL, кеш узла —
  `node:<team_slug>:<path>`. §86 — режим чтения в Web: ни миграций, ни изменений в Receiver и
  Sender.
- **Не даёт мутаций из сквозного списка.** Правка, удаление, перенос открываются на странице узла,
  как и раньше.
- **Не чинит совпадение путей** в Redis/Prometheus — только перестаёт показывать по нему неправду
  (§86.8).

## 86.x Вне scope

- Сквозные **логи запросов**: у каждой команды своя БД ClickHouse, у каждого узла своя таблица, и
  сквозной журнал означал бы UNION по десяткам таблиц с разной схемой (§64 допускает произвольную).
- Вкладка «Очередь» и Kafka в сквозном режиме (метрики кластерные, разбивка team-scoped).
- Кнопка «Поделиться» для пункта «Все команды».
- Team-квалифицированный ключ исхода последнего вызова — follow-up §86.8.
- Порционная загрузка метрик в режиме одной команды — возможное расширение после обкатки.
- Пагинация списка узлов: список остаётся одним ответом (запрос в PostgreSQL дёшев), стоимость
  ограничивает порционность метрик, а не длина списка.
