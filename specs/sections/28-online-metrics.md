## 28. Онлайн-метрики, период просмотра, публичный адрес и UX-доработки

Раздел объединяет пакет доработок «онлайн-метрики» (8 пунктов ТЗ): публичный адрес приложения в
настройках, онлайн-обновление метрик, маскирование данных авторизации, выбор периода метрик,
понятные ошибки валидации узла, фильтр `RabbitMQAsync` на главной, плюс два багфикса тестового
стенда (CH-таблица узла и резолв async-узла).

### 28.1. Публичный адрес приложения (Пункт 1)

Полный адрес узла (`<origin>/api/v1/<verb>/<path>`) собирался от `window.location.origin` — адреса
хоста в браузере. После публикации приложения адрес сайта отличается. Вводится общесистемная
настройка **«Публичный адрес приложения»** (`app_settings.general.public_base_url`): если задана,
UI собирает полный адрес узла от неё, иначе — от origin браузера.

- Модель: `domain.AppSettings.General.PublicBaseURL *string` (тот же JSONB-синглтон `app_settings`,
  новая миграция не нужна). Валидация `domain.ValidatePublicBaseURL`: пусто ИЛИ абсолютный
  http(s)-origin без пути, query и хвостового слеша.
- API: `GET /api/settings/public` (read-only, **любой авторизованный** — нужно manager/viewer для
  сборки адреса) возвращает `{public_base_url}`. Правка — через `PUT /api/settings/app` (admin-only,
  секция `general`); ошибка валидации → 400.
- UI: вкладка **Settings → Общие/General** (admin). Сборка адреса вынесена в единый хелпер
  `lib/nodeUrl.buildNodeUrl` / хук `useNodeUrlBuilder` (учитывает `public_base_url` и slug текущей
  команды; для не-default команды добавляет слог).

### 28.2. Онлайн-обновление метрик (Пункт 2)

Метрики и графики на главной (Overview) и странице узла должны обновляться онлайн без перезагрузки.
Реализовано поллингом TanStack Query с единым интервалом `METRICS_REFETCH_MS = 12s` для всех
метрик-запросов (`metrics-overview`, `metrics-nodes`, `useNodeMetrics`, recent logs). `queryKey`
включает период, поэтому смена периода и фоновое обновление работают для всех виджетов/графиков.

### 28.3. Маскирование данных авторизации (Пункт 3)

Данные авторизации (incoming/outgoing credentials, RMQ-пароль) показывались открытым текстом при
вводе. Бэкенд значения секретов наружу **не отдаёт** (только флаги `*_set`) — маскирование делается
на стороне UI:

- Компонент `ui/SecretInput`: `type=password` + кнопка-глазик, раскрывающая только то, что вводится
  в форме (сохранённые секреты не запрашиваются и не показываются).
- viewer (роль «только просмотр») не видит и не редактирует данные авторизации: CRUD узлов уже
  ограничен manager+ на бэкенде; в UI кнопки «New node»/«Edit» скрыты для viewer, прямой переход на
  форму узла редиректит. Просмотр/ввод кред доступен только manager/admin.

### 28.4. Период просмотра метрик (Пункт 4)

Метрики/график показывались только за последний час. Вводится поле **«Период»** (`PeriodPicker`)
с пресетами `1h / 3h / 24h / 7d / 14d / 30d`, опцией **«Произвольный»** (два `datetime-local` =
выбор из календаря) и значением по умолчанию `1h`. Размещён на Overview (per-node throughput) и
вкладках узла «Обзор»/«Метрики».

- API метрик принимает либо `range=<preset>`, либо произвольный `from`/`to` (RFC3339 или UnixMilli)
  во всех трёх эндпоинтах (`/api/metrics/overview|nodes|nodes/:id`).
- Prometheus-путь (`NodeThroughput`/`NodeSeries`) переведён на `(since, until time.Time)`: запрос
  вычисляется на момент `until`, что даёт произвольный календарный период. Глобальные KPI Overview
  остаются за 24ч. (KPI/ряд узла изначально считались из ClickHouse по `(sinceMs, untilMs]`; позже,
  чтобы метрики не зависели от логов CH, переведены на Prometheus — см. §6.1 и IMPLEMENTATION.md §4.11.2.)

### 28.5. Понятные ошибки валидации узла (Пункт 5)

Ошибки валидации уходили сырым текстом домена (например `domain: rmq_queue length must be 1..255
and match ^[a-zA-Z0-9._-]+$`) одним баннером без указания поля. Теперь:

- Бэкенд сопоставляет ~33 доменные ошибки `Node.Validate()`/`validateRMQ()` с парой `{i18n-code,
  field}` (карта `node_validation.go`); `node_handler` отдаёт `{error, code, field}`. Ключи
  `node.validation.*` локализованы (en/ru) и на бэкенде, и во фронтенде.
- Фронтенд переводит `code` в языке UI и показывает сообщение inline у конкретного поля (красная
  рамка + текст) для `path`/`target_url`/`clickhouse_table`/`rmq_host`/`rmq_queue`; для остальных —
  локализованный баннер.
- Добавлена проверка полноты логирования: при включённом `logging_enabled` обязателен
  `clickhouse_table`, иначе `ErrNodeLogsNotConfigured` (формализует «логирование включено, но не
  настроено»).

### 28.6. Фильтр RabbitMQAsync на Overview (Пункт 6)

В фильтре по типу узла на главной были только `request` и `requestAsync`. Добавлен третий тип
`RabbitMQAsync` (enum `RootMethodRabbitMQAsync`). Бэкенд-фильтр `root_method` уже принимал все три.

### 28.7. Багфикс: CH-таблица узла без шаблона (Пункт 7)

Узлы, созданные с `clickhouse_table`, но **без** `clickhouse_template_id`, не получали таблицу в
ClickHouse (`provisionTable` был no-op), хотя имя нормализовалось в `nexus_<team>.<table>`. Чтение
логов/метрик падало с CH `code 60` (Unknown table). Исправление: при включённом логировании и
пустом `template_id` таблица создаётся из **дефолтного шаблона** каталога
(`CHTemplateRepo.GetDefault`); при недоступности CH/каталога — мягкая деградация (узел создаётся,
лог-предупреждение). Явный `template_id` сохраняет строгую семантику (`ErrCHUnavailable`).

### 28.8. Багфикс: резолв async-узла по legacy-пути со слешем (Пункт 8)

URL `/api/v1/requestAsync/webhook/sendasynq` разбирался как `(team=webhook, path=sendasynq)` →
команды `webhook` нет → 404 `node not found`. Узлы с путём-со-слешем в default-команде не
находились по адресу без слога (а именно такой показывал UI). Исправление: общий `resolveNode` в
Receiver при `ErrNodeNotFound` и непустом угаданном слоге повторяет резолв как
`(default-team, "<slug>/<path>")`. Явная существующая команда сохраняет приоритет (fallback только
на miss). Применяется и в sync, и в async.

### 28.9. Scope и неочевидности

- `team_id` в v1 — `'default'`; включение слога в адрес узла актуально при multi-tenancy v2 (§18).
- `public_base_url` — не секрет: `GET /api/settings/public` не маскирует значение.
- Изменение интерфейса `PromMetrics` (since/until) не затрагивает Telegram-алерты (§22): метод
  `NodeErrors(window)` оставлен как был.
