# 57. Гарантированная инвалидация конфига узла в Receiver

Раздел закрывает окно рассинхрона конфигурации узла между Web (запись) и Receiver
(чтение): после изменения узла (в т.ч. авторизации) Receiver должен перечитать
свежий конфиг сразу, а не ждать истечения TTL кеша. Развивает §9.2 (трёхуровневый
кеш), §50/§51 (кеш узла по команде, наблюдаемость).

Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

## 57.1 Зачем: окно рассинхрона

При `PUT /api/nodes/{id}` `NodeUsecase.Update` делает write-through в Redis
(`cacheSet`) — в норме изменение действует на первом же запросе к Receiver
(sub-second). Но:

- **write-through молча становится no-op**, если team-slug не резолвится
  (`teams==nil` / ошибка `GetByID`) — `resolveCacheTeamSlug` возвращает `""`, и
  старое значение живёт в Redis до TTL (`redis.node_ttl_sec` = **до 300 с** в prod,
  60 с в debug).
- **L1 in-memory кеш Receiver'а** (`nodecache.L2Reader`, если включён
  `receiver.l2_cache.enabled`) Web инвалидировать не может — старое значение живёт
  до `ttl_ms` (2 с).
- Существующий pub/sub `nexus:config:reload` обслуживает только секции
  `app_settings` (sentry/clickhouse/…); **события про узлы там нет**.

Итог: в норме — sub-second, но при сбое write-through — до 5 минут. §57 закрывает
это окно явной инвалидацией.

## 57.2 Модель: выделенный pub/sub канал инвалидации

Отдельный Redis pub/sub канал **`nexus:nodes:invalidate`**
([internal/platform/nodeevents](../../internal/platform/nodeevents/nodeevents.go)).
Событие несёт `team_id`, `path` и (при переименовании) `old_path`.

- **Web публикует** событие после успешного commit в `Create`/`Update`/`Delete`/
  `Move`/`SetStatus` (best-effort: ошибка логируется, запрос не рушит; write-through
  остаётся быстрым путём, событие — гарантия/бэкстоп).
- **Receiver подписан**: на событие резолвит `team_id`→slug и **выселяет узел из
  обоих слоёв** — L1 (`L2Reader`, in-memory LRU) и Redis (`DEL` ключа
  `node:<slug>:<path>`). Следующий запрос к этому узлу читает свежий конфиг из PG
  (авторитетный источник) и делает write-back.

Это закрывает L1-окно полностью и Redis-окно во всех случаях, кроме полного
падения Redis в момент publish (тогда событие теряется, и страховкой остаётся
TTL — как раньше).

## 57.3 Почему по `team_id`, а не по slug

Ключ кеша включает `team_slug`, но событие публикуется по **`team_id`**: провал
резолва slug на стороне Web (`teams.GetByID` упал) — это ровно тот сбой, из-за
которого write-through стал no-op. Публикуй Web по slug — событие в этом случае
тоже не собралось бы. Поэтому slug резолвит **Receiver** (у него есть доступ к PG),
и инвалидация не зависит от способности Web резолвить slug.

## 57.4 Неочевидности

- **Инвалидация, а не перезапись.** Receiver делает `DEL` Redis-ключа (не Set
  свежим значением) — так следующий Get гарантированно идёт в PG (авторитет) и
  сам заполняет кеш, даже если событие принесло неполные данные. Событие несёт
  только ключ (team_id+path), не сам конфиг.
- **Best-effort с обеих сторон.** Publish не рушит запрос Web; приём в Receiver не
  блокирует обработку трафика. При потере события окно рассинхрона = TTL (как до
  §57) — деградация, а не поломка.
- **Порядок при переименовании.** При смене `path` выселяются и новый, и старый
  ключ (`old_path` в событии) — иначе старый путь остался бы в кеше Receiver'а
  указывать на переехавший узел.
- **Наблюдаемость (§51.9).** Тихий no-op резолва slug в `cacheSet` уже виден на
  `Warn`; приём события в Receiver и исход выселения (L1/Redis) — на `Debug`.

## 57.5 Инвариант

Изменение узла через Web → гарантированный refresh конфига в Receiver (L1+Redis
выселены), а не ожидание TTL. Единственное остаточное окно — полный отказ Redis в
момент публикации события.
