# 80. Пропускная способность async-очереди: медленный узел не должен задерживать остальных

Раздел разбирает боевой инцидент 2026-08-05: `consumer lag` топика `nexus.async` рос непрерывно
(578 и выше), при этом три из четырёх инстансов consumer'а простаивали, а сообщения быстрого узла
ждали доставки 25 минут.

Развивает [§3.5](03-receiver.md) (async-маршрутизация и FIFO по узлу), [§5.1](05-storage.md)
(топики и партиции), [§9](09-resilience.md) (устойчивость и масштабирование),
[§31](31-kafka-monitor.md) (экран мониторинга Kafka), [§36](36-dlq-reprocessor.md) (DLQ).
Карта реализации — [../IMPLEMENTATION.md](../IMPLEMENTATION.md).

---

## 80.1 Диагноз: узел не помещается в партицию

Замер боевого кластера 05.08.2026, 17:00 МСК (окно 1 ч):

| Узел | Команда | Запросов/ч | p95 | Требуется времени | Доля ёмкости партиции |
|---|---|---|---|---|---|
| **`acs_sigur`** | webhook | 219 | **22 366 мс** | 4906 с | **136 %** |
| `omnichannel` | webhook | 1138 | 86 мс | 98 с | 2,7 % |
| `task_vika` | task | 148 | 2 811 мс | 416 с | 11,6 % |
| `email/dashamail` | vika | 3686 | 74 мс | 273 с | 7,6 % |

Механика, из-за которой это ломает всё остальное:

1. Receiver публикует в `nexus.async` с **ключом = путь узла** — ради FIFO по узлу (§3.5). Значит
   все сообщения одного узла всегда попадают в **одну и ту же партицию**.
2. Consumer Sender'а запускает по одной горутине на инстанс, и каждая обрабатывает сообщения
   партиции **строго последовательно**: следующее начинается только после доставки предыдущего.
3. Отсюда потолок узла: `1 / латентность внешнего вызова`, **независимо** от числа партиций и
   инстансов. Для `acs_sigur` это 160 сообщений в час при входящих 219 — структурный дефицит, лаг
   растёт линейно и не рассосётся сам.

Проверка через peek подтвердила и второй эффект — **head-of-line blocking**: `acs_sigur` и
`omnichannel` захешировались на партицию 3, у обоих по 50 сообщений в очереди, у самого старого
возраст 25 минут; у узлов на других партициях очередь пуста. Быстрый узел (2,7 % ёмкости) стоял за
медленным. In-flight по кластеру при этом равнялся 1: три инстанса простаивали.

Ситуация описана в [../IMPLEMENTATION.md](../IMPLEMENTATION.md) как известный риск («партиций 4,
узлов десятки»), но средств ни диагностировать, ни разрулить её в продукте нет.

## 80.2 Диагностика: «кто держит очередь»

Причину пришлось вычислять вручную — сопоставлять `p95` из метрик узлов с peek'ом очереди по
каждому узлу поочерёдно. Экран «Мониторинг Kafka» показывает общий лаг и топ продюсеров, но не
отвечает на вопрос «кто именно не пускает остальных».

**Расчёт доли ёмкости партиции** — `запросов за период × p95 / длительность периода`. Величина
самоочевидна в интерпретации: >100 % означает, что узел физически не помещается в одну партицию.

Блок на экране мониторинга:

```
┌ Кто держит очередь ──────────────────────────────────────────────────────────┐
│ УЗЕЛ         ПАРТИЦИЯ  СООБЩ/Ч   P95      ЁМКОСТЬ  ЖДУТ  ВОЗРАСТ ГОЛОВЫ       │
│ acs_sigur       3        219    22.4 c    136% ⛔    50    25 мин             │
│ omnichannel     3       1138    0.09 c      3%       50    25 мин             │
│ task_vika       1        148     2.8 c     12%        0    —                  │
│ ⛔ Узел требует больше ёмкости, чем даёт одна партиция — лаг будет расти.     │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Метрика лага сейчас недостоверна и чинится в этом же пункте.** Все инстансы consumer'а публикуют
`nexus_kafka_lag` с одинаковым набором меток (библиотека отдаёт `partition="-1"` для group-reader),
поэтому в серии выживает значение последнего записавшего, а `sum()` показывает лаг одного инстанса
вместо группы. Источник истины — админ-протокол (`ListOffsets − OffsetFetch`), он уже используется
для таблицы топиков. Тот же дефект метки делает бесполезным алерт `NexusKafkaLagHigh`.

**Возраст головы очереди** (`сколько ждёт самое старое неподтверждённое сообщение`) добавляется
метрикой и колонкой: именно он отвечает на вопрос «доставка встала или просто много трафика»;
сегодня это видно только ручным peek'ом.

> **Узловой срез этого пункта вынесен в [§84.8](84-node-observability.md) и уже реализован.** На
> странице узла показываются доля ёмкости партиции (на вкладке «Метрики», из уже полученных метрик)
> и «ждут / партиция / возраст головы» (на вкладке «Очередь», из уже загруженного списка) — без
> единого нового запроса к ClickHouse или Kafka. За §80 остаётся всё остальное: **общий** экран
> «Кто держит очередь» со сравнением узлов между собой, исправление метки `partition="-1"` у
> `nexus_kafka_lag` и алерта на ней, а также возраст головы как **метрика Prometheus** (§84.8
> считает его на клиенте из peek'а и в метрики не пишет).

## 80.3 Параллелизм внутри партиции с сохранением FIFO по узлу

**Решение head-of-line blocking'а.** Сообщения партиции разбираются пулом воркеров с группировкой по
ключу: **разные узлы обрабатываются параллельно, сообщения одного узла — строго последовательно**.
FIFO-гарантия §3.5 не нарушается, а быстрый узел перестаёт зависеть от соседа по партиции.

Требования:

- окно in-flight ограничено (иначе пул вычерпает партицию в память);
- offset коммитится по watermark — наименьшему необработанному, а не по факту завершения отдельного
  сообщения; при падении воркера переобработка допускается (семантика at-least-once не меняется);
- ключ `sender.workers` в конфигурации **уже существует и сегодня не читается ничем** — он
  оживает под эту семантику.

## 80.4 Параллельная доставка одного узла

Пункт §80.3 спасает соседей, но не сам перегруженный узел: при FIFO его потолок остаётся
`1 / латентность`. Для узлов, которым порядок доставки не нужен (вебхуки, уведомления), вводится
per-node параметр **`async_max_inflight`** (по умолчанию `1` — текущее поведение).

Для `acs_sigur` значение 8 снимает дефицит: 136 % → 17 % ёмкости.

**Цена — потеря порядка доставки для этого узла**, поэтому параметр задаётся явно владельцем узла, а
форма сопровождает его предупреждением. Значение >1 несовместимо с ожиданием «получатель обрабатывает
сообщения строго по очереди».

## 80.5 Circuit breaker: «медленно» не должно превращаться в «не доставляем вообще»

Через два часа после разбора §80.1 тот же узел `acs_sigur` ушёл в отказ целиком. Приёмник упёрся в
таймаут (`p99 = 30 001 мс` при таймауте узла 30 000 мс), пять подряд неудач открыли circuit breaker —
и дальше **562 записи упали вообще без сетевого вызова**: `reason = circuit_breaker_open`,
`duration_ms = 0`, `attempts = 0`, сразу в DLQ. Лаг топика при этом «рассосался» — но не потому, что
сообщения доставили, а потому что их провалили.

**Проблема.** Порог (5 неудач) и cooldown (30 с) захардкожены в коде: ни глобального ключа
конфигурации, ни переопределения на узле. Для медленного, но живого приёмника это означает: пять
таймаутов подряд — и весь поток узла уходит в DLQ, где ждёт повторов по 5 минут, хотя приёмник
отвечает, просто медленно.

**Решение.**

1. Порог и cooldown выносятся в конфигурацию — глобальные значения плюс переопределение на узле
   (у узла с 20-секундным приёмником и у узла с 200-миллисекундным разная норма).
2. **Таймаут отличается от отказа соединения.** Отказ (`connection refused`, DNS, TLS) — сигнал, что
   приёмника нет, и брейкер обязан открыться быстро. Таймаут при установленном соединении означает
   «медленно», и его вклад в счётчик брейкера должен быть настраиваемым вплоть до нуля — иначе
   защита от перегрузки сама создаёт отказ в обслуживании.
3. Состояние брейкера обязано быть видно в UI узла и в причинах отказа: сегодня оператор видит
   `circuit_breaker_open` только в тексте ошибки записи и не может понять, когда он закроется.

**Граница защиты.** Раздел не отменяет брейкер: при действительно лежащем приёмнике он экономит и
партицию (§80.1), и внешний сервис. Речь только о том, чтобы «медленный» и «мёртвый» приёмники
различались, а параметры не были зашиты в код.

> **Статус.** Пункты 1 и 3 закрыты разделом [§81](81-breaker-manual-reset.md): порог и cooldown
> уехали в конфигурацию с переопределением на узле (§81.3), состояние брейкера показано на вкладке
> «Очередь» вместе с ручным сбросом (§81.4). Там же появилось то, чего этот раздел не предусматривал
> вовсе: отмена вызывающей стороны перестала засчитываться отказом приёмника (§81.2) — без этого
> брейкер открывался на исправном узле и выйти из состояния не мог. **Пункт 2 остаётся здесь**:
> настраиваемый вклад таймаута в счётчик отказов §81 не делает, он лишь вводит трёхзначный вердикт,
> в который этот вклад добавляется одной веткой.

## 80.6 Попутная гигиена consumer'а

- **Кеш узлов на стороне Sender.** Сейчас на КАЖДОЕ сообщение выполняется `SELECT` узла из
  PostgreSQL; L2-кеш есть только у Receiver. При параллельной обработке (§80.3) нагрузка на БД
  умножится, поэтому кеш обязателен вместе с ним.
- **Ограничение бесконечного повтора на месте.** При недоступности PostgreSQL или отказе публикации
  в DLQ обработчик повторяет одно и то же сообщение с паузой 1 с **бесконечно**, замораживая
  партицию. Нужен предел попыток с переходом к следующему сообщению и явной метрикой — иначе одна
  внешняя авария останавливает доставку всех узлов партиции.

## 80.7 Эксплуатационные меры, доступные без кода

Порядок применения в аварии:

1. **Ускорить приёмник.** 22 с на вебхук — свойство принимающей системы, а не шины; это самый
   прямой множитель.
2. **Увеличить число партиций и инстансов** (`kafka-topics --alter`, затем `kafka.consumer.instances`
   и рестарт Sender'а). Расселяет узлы и снимает блокировку соседей, но **не лечит** узел, которому
   не хватает одной партиции. Плата: смена числа партиций меняет распределение ключей, поэтому на
   переходный период порядок доставки узла не гарантирован (часть сообщений остаётся в старой
   партиции, новые идут в другую).
3. **Ограничить приём** узла (`receiver.rate_limit_per_node`), если продюсер обгоняет consumer.
4. **Поставить узел на паузу** — трафик уходит в delay-топик §3.6 и партиция освобождается; темп
   разбора задают параметры sweeper'а.

## 80.8 Вне рамок раздела

- **Шардирование одного узла по партициям** (смена ключа) — ломает FIFO-гарантию §3.5 для всех узлов
  сразу; вместо этого вводится явный per-node параметр §80.4.
- **Приоритеты сообщений** и отдельные топики/деплойменты Sender'а под тяжёлые узлы — возможное
  развитие, если per-node параллелизма окажется мало.
- **Автоматическое масштабирование** числа партиций/инстансов.
- **Изменение семантики доставки** (exactly-once) — не рассматривается.
